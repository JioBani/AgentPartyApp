# BUG-008 · 탭을 닫아도 탭 그룹이 있던 자리에 그대로 있게 하기

## 문제와 배경

탭 그룹이 `1 2 3` 으로 놓인 상태에서 **1번 그룹의 탭 하나를 닫으면 배치가 `2 3 1` 로
바뀐다** — 닫은 그룹이 맨 뒤로 밀린다. 그룹 자체는 남아 있으므로 "빈 그룹이 정리된"
결과가 아니라, 순서만 뒤바뀌는 현상이다.

원인의 절반은 확인됐다. 레이아웃은 두 벌의 순서를 들고 있다.

- `panels` 배열 순서
- `grid`(중첩 분할 트리)의 잎 순서

화면은 격자를 따르고, **격자가 없으면 배열을 따른다**
(`Workbench.tsx` 의 `layout.grid || rowGrid(layout.panels)`).

그리고 이 둘은 정상적인 조작만으로도 어긋난다. 탭을 끌어내 새 그룹을 만들면 새 패널은
`panels` 끝에 붙지만 격자에는 다른 자리에 꽂히기 때문이다. 실제 앱에서 드래그로 그룹을
만들어 확인한 상태:

```
panels: G1[one,extra]  G2[two,three]
grid  : row(G2 G1)          ← 화면은 G2 가 왼쪽
```

즉 **격자가 사라지는 순간 화면 순서가 배열 순서로 튄다.** `1 2 3` → `2 3 1` 은 정확히
이 모양이며, 보고된 증상과 일치한다.

## 아직 확인되지 않은 것 (다음 사람이 이어받을 지점)

**탭 닫기 자체는 격자를 지킨다.** 실제 앱을 띄워 다음을 모두 시도했지만 순서는 유지됐다.

| 시도한 배치 | 닫은 탭 | 결과 |
| --- | --- | --- |
| 평면 3열 | 1번의 두 탭 중 하나 | 순서 유지 |
| 평면 3열 / 4열 | 1번의 마지막 탭 | 1번만 제거, 순서 유지 |
| `row(col(1 2) 3)` | 1번의 탭 | 격자 유지 |
| `col(row(1 2) 3)`, `row(1 col(2 3))` | 1번의 마지막 탭 | 올바르게 붕괴 |
| 배열 `2 3 1` / 격자 `row(1 2 3)` (어긋난 상태) | 1번의 탭 | **격자 유지** |

그러므로 `closeTab` 은 방아쇠가 아니다. **격자를 날리는 다른 경로가 있고, 탭 닫기는
그 결과를 눈에 보이게 만들 뿐**일 가능성이 크다. 아직 좁히지 못한 후보:

- 저장·복원(`seedLayout`, `sanitizeLayout`)에서 격자가 빠지는 경우
- 다른 창이 보낸 레이아웃을 받아들이는(adopt) 경로가 격자를 덮어쓰는 경우
- 세션 종료(`closeSession`)가 유발하는 재시드

재현을 확정하려면 **사용자가 그 세 그룹을 만든 방법**(드래그 / 분할 버튼 / 재시작 후 복원 /
창 두 개)을 알아야 한다. 이 답이 위 후보 중 어디를 팔지 결정한다.

## 곁다리로 발견된 것

드래그로 탭을 빼낼 때 **떨어뜨린 방향과 무관하게 새 그룹이 항상 왼쪽에 생긴다.**
화면 맨 오른쪽 끝(가로 98.5%)과 맨 왼쪽 끝(1.5%)에 각각 떨어뜨렸는데 두 경우 모두
`row(NEW OLD)` 가 나왔다. 다만 이 관측은 합성 포인터 이벤트로 얻은 것이라 실제 마우스
드래그와 같다고 단정할 수 없다 — 별건으로 다시 확인해야 한다.

## 원하는 동작과 범위

탭을 닫아도 남아 있는 탭 그룹은 **화면상의 자리를 유지**한다. 빈 그룹이 사라져 생긴
공간만 이웃이 나눠 갖는다(편집기에서 분할 창을 닫는 동작과 같다).

## 완료 조건

- [ ] `1 2 3` → 1번 탭 닫기 → `2 3 1` 을 실제 앱에서 재현한다.
- [ ] 격자를 잃는 경로를 특정하고, 그 지점에서 근본 원인을 고친다.
- [ ] `panels` 순서와 격자 순서가 어긋난 상태에서 저장·복원·창 간 채택을 왕복해도
      화면 순서가 유지되는 E2E 를 추가한다(실제 앱을 띄워 API 로 조작).
- [ ] 드래그 드롭 방향이 새 그룹의 위치에 반영되는지 별도로 확인한다.

## 제외 범위와 미결 사항

`closeTab` 의 격자 처리는 이번 조사에서 정상으로 확인됐으므로 손대지 않는다.
드래그 드롭 방향 문제는 별도 항목으로 분리한다.
