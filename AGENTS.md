# Agent Instructions

- 사용자 허락 없이 시스템·개발자·파티 프롬프트나 도구 사용 지침을 임의로 추가하거나 변경하지 않는다.
- 사용자 지침 없이 기존 CLI에서 가능하던 기능을 AgentParty가 임의로 비활성화하거나 숨기거나 사용을 금지하지 않는다. AgentParty 자체 기능이 같은 작업을 지원하더라도 Computer Use 같은 CLI 기능을 제한할 근거가 되지 않는다. AgentParty는 CLI로 시작한 세션도 포함해 기존 CLI를 래핑하는 앱이지, 그 기능을 대체하는 별도의 데스크톱 앱이 아니다.
- When problems occur, prioritize fixing the root cause over temporary workarounds. Short-term bypasses can create larger costs later.
- Do not work only from unverified hypotheses. If something is uncertain, inspect the project or search reliable sources before acting.
- Do not hide failures with silent fallback behavior. Surface errors through logs, notifications, or other visible diagnostics.
- Do not manually reopen, parse, list, hash, or otherwise re-check files produced by a deterministic script when that script or its designated validator already verifies the required properties. Treat a successful validator exit and its concise result as the evidence; do not repeat the same check with ad-hoc shell commands or LLM inspection.
- If a required deterministic invariant is not covered, add it to the producer, lint, or test and run that check once instead of performing a one-off manual inspection. Manually inspect generated files only to diagnose a failed validator or when the remaining question is inherently visual, behavioral, or judgment-based; state that reason.
- For every update, assess whether it can cause compatibility problems for existing users after they upgrade, including persisted data, configuration, sessions, and integrations.
- If a migration is required, explain its scope and risks and obtain the user's explicit confirmation before implementing or running it.
- Every user-facing capability must be exposed through the local automation HTTP API so AI agents can drive and QA it. Route UI and HTTP through the same `AppController` method, register the capability once in the route table under `src/main/api/routes/` (this publishes the HTTP endpoint, the `GET /api/spec` declaration, and the mobile-link method together), and document it in `docs/API.md`.
- When an automation or QA workflow represents a party member using a capability that exists as an AgentParty MCP tool, drive it through the member-scoped real MCP transport endpoint (`/api/parties/:partyId/members/:name/mcp-tools/:tool`) by default. Do not substitute the lower-level HTTP action route or call the party controller directly: doing so bypasses MCP schema, identity, framing, and host-routing behavior and can make QA pass while the product fails. Direct HTTP is allowed only when the test is specifically about the HTTP contract, fixture setup or state inspection, a human-only action, or a capability with no MCP tool; state that reason in the test or validation notes.
- For feature testing, create or reuse a QA workspace and run end-to-end tests when the change needs behavioral verification.
- Product E2E/QA must launch the real AgentParty application process and drive the user-visible workflow through the UI or its local automation API. For party-member actions, use the real MCP transport rule above unless an explicit exception applies. Do not count an isolated module, mocked backend, or special code-path test as product E2E. When validating model behavior, make a real provider call for every requested model and runtime setting, while keeping prompts and output limits minimal to control cost.
- After feature development, prioritize manual end-to-end testing against the real running AgentParty application through its local automation API instead of writing a new test script. Use its member-scoped MCP transport for party-member actions. Create a dedicated test script only for a sufficiently complex or difficult case where scripting is materially faster than manual API-driven verification.
- When merging work whose relevant validation already passed in its owning worktree and whose interaction risk with other pending work is low, do not repeat the full typecheck, build, and E2E suite for each merge into `master`. At merge time, verify that the intended changes are included, confirm there are no conflicts, and run only the minimum necessary smoke checks. After all planned work is merged, run the full integrated validation once immediately before release. Do not skip targeted regression testing when interaction risk is high or when a change affects core runtime, data, security, or release paths.
- Order work by dependencies and the critical path rather than by a simple task-list sequence. At each stage, distinguish prerequisites, deployment or integration blockers, and independent follow-up work so unrelated tasks are not needlessly serialized.
- Treat member collaboration as parallel by default. When another member is waiting on your output, decision, or status, provide the minimum result needed to unblock them first, then perform independent validation, cleanup, or supplementary work afterward or in parallel.
- Do not block deployment on worktree or temporary-directory cleanup that is not required for the release. Track any remaining cleanup and perform it after deployment succeeds and is verified. Cleanup required for safety, integrity, or release reproducibility remains a pre-deployment gate.
- Design UI interactions to be user-friendly and task-oriented. Avoid relying on top-bar quick input for important workflows when an in-view form, modal, or richer interaction would be clearer.
- When creating, moving, or refactoring UI, verify spacing, alignment, padding, margins, overflow, and overlap in the rendered component inside the real AgentParty application. Cover representative window sizes and both light and dark themes, every affected tab, the bottom of scrollable content, relevant interactions and expanded states, and long-string and error states. Preserve DOM geometry assertions and screenshots when practical. A build or static code review alone is never sufficient to declare UI work complete.
- Treat UI accessibility as a regression gate for every new or changed UI feature: verify that it does not obscure or intercept existing controls, especially the composer and input fields, permission and Message Gate dialogs, menus, confirmations, and their close/cancel actions. In the real app, open overlapping states and test actual pointer hit targets, keyboard focus/order, and dismissal; inspect z-index and stacking contexts, portals, fixed/sticky elements, clipping, and native views such as WebContentsView. Check representative window sizes and both themes. A control that looks visible but cannot be clicked or focused fails this gate (for example, a composer painted above a permission popup that prevents changing permissions). Preserve targeted geometry, hit-test, interaction assertions, and screenshots when practical; do not accept a screenshot alone as proof of accessibility.
- After every implementation task, review the changed code for AI readability, clean architecture boundaries, low change surface, and extensibility. If the code does not meet those rules, refactor it before treating the task as complete.
- Work only in a git worktree on a feature branch (`git worktree add ../<repo>-wt-<topic> -b <topic>`); never edit or commit on the `main`/`master` branch checkout directly. Merge back only after tests and the architecture review pass.
- Never use a worktree as the cwd when creating a party member or spawning an agent. Worktrees are removed by default once their work is finished, and a session rooted there can be lost with it. Start members and agents from the main checkout (`C:\Project\AgentPartyApp`) and point them at the worktree by absolute path for editing, building, and committing.
- Worktree dependency sharing — MANDATORY handling (the shared install was wiped twice by cleanup mistakes: 2026-08-17 and 2026-08-23). Every worktree shares the ONE `node_modules` installed in the main checkout (`C:\Project\AgentPartyApp`), linked in as a junction (`cmd /c mklink /J <worktree>\node_modules C:\Project\AgentPartyApp\node_modules`):
  - `npm install` runs ONLY in the main checkout, never inside a worktree, and fails while the app is running from that checkout.
  - Before removing a worktree — `git worktree remove`, directory deletion, or ANY recursive cleanup — check what `node_modules` there is (`Get-Item <path>\node_modules | Select-Object LinkType,Target`, or `ls -la`). If it is a junction/link, remove the LINK ITSELF first (`cmd /c rmdir <worktree>\node_modules` — this removes only the link, never the target), and only then remove the worktree. A recursive delete or worktree removal that walks through a live junction deletes the shared install for every agent at once.
  - If the link targets the shared install and anything about the cleanup is unclear, STOP and report instead of proceeding.
  - Never point a worktree's `node_modules` at ANOTHER worktree's install as a temporary substitute; borrowing chains the blast radius of the next cleanup mistake.
  - If the shared `node_modules` is ever found empty or broken: stop all builds, tests, and packaging, announce it to the party immediately, and restore with `npm install` in the main checkout before anything resumes.
