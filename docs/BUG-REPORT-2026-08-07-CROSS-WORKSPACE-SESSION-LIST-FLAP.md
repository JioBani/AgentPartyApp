# 장애 보고서 — 멤버 상태가 idle ↔ not-started 로 계속 깜빡인다

- 작성일: 2026-08-07 (KST)
- 대상: WSL 워크스페이스 `wsl+Ubuntu-20.04:/home/spdlqj8876/Claude`, 파티 `CARR-935`, 멤버 `req`
- 심각도: 높음 (UI 사용 불가 수준, 데이터 유실 없음)
- 원인이 된 변경: 61e12c1 "Fix session lifecycle" 의 단일 인스턴스 잠금 + 멀티 워크스페이스
- 수정: 본 문서의 §5

## 1. 증상

사용자 보고: "CARR-935 의 `req` 멤버가 idle 과 not started 상태를 엄청 깜빡거리면서 반복해서 UI 가 계속 변화했다."

## 2. 판정

**데이터 유실은 없다. 렌더러의 세션 배열을 두 곳에서 덮어쓰고 있었다.**

`session:list` IPC 는 렌더러의 세션 배열을 **병합이 아니라 통째로 교체**한다
(`App.tsx` 의 `onSessions` → `setState({ ...current, sessions: next })`). 따라서
"창 하나당 생산자는 정확히 하나" 가 지켜야 할 불변식인데, 데스크톱에는 생산자가
둘 있었다.

| 생산자 | 위치 | WSL 창에 보내는 것 |
|---|---|---|
| 이 프로세스의 SessionManager | `main.ts` 의 `sessions` 핸들러 | **빈 배열** — WSL 세션을 하나도 들고 있지 않으므로 |
| WSL 엔진 | `forwardRemoteEvent` | 진짜 목록 |

두 메시지가 번갈아 도착하면 `deriveStatus`(`memberStatus.ts:44`)가
`!session` → `not-started`, 다음 메시지에 `idle` 을 반복한다. 이것이 깜빡임이다.

## 3. 왜 지금 터졌나

단일 인스턴스 잠금 이전에는 한 프로세스가 한 워크스페이스만 다뤘다. WSL 워크스페이스
앱의 로컬 SessionManager 는 세션이 거의 없어 `sessions` 이벤트 자체가 드물게 발생했고,
빈 목록 방송도 드물었다.

멀티 워크스페이스가 되면서 **한 프로세스가 WSL 창과 Windows 창을 동시에** 갖게 됐다.
장애 당시 `C:\Project\AgentPartyApp` 워크스페이스에서 멤버 셋(`main`, `token-audit`,
`usage-report`)이 작업 중이었고, 그 세션들이 이벤트를 낼 때마다
(`sessionManager.ts` 의 `snapshot`·`status` 마다 `emit("sessions")`) WSL 창으로 빈
목록이 날아갔다. 드물던 결함이 상시가 됐다.

## 4. 확인 방법과 근거

추측이 아니라 실제 앱에 푸시 계측을 넣고 확인했다. 두 워크스페이스를 한 프로세스에
띄우고 로컬 멤버를 기동한 뒤, 같은 WSL 창이 받은 `session:list` 를 집계:

```
  13  local  → wsl+Ubuntu-20.04:/tmp/...   count=0     ← 결함
  13  remote → wsl+Ubuntu-20.04:/tmp/...   count=2     ← 정상
  13  local  → C:\...\workspace            count=2
```

같은 창에 대해 빈 목록과 실제 목록이 **정확히 교대**했다.

앱 로그만으로는 잡히지 않았다는 점도 기록해 둔다. 장애 당시 해당 창의 로그에는
`party:start` 가 한 번뿐이고 어떤 재시작 루프도 없었다 — 백엔드는 정상이었고 문제는
전적으로 방송 경로에 있었다.

## 5. 수정

`src/main/sessionListRouting.ts` 를 신설해 "누가 어느 창의 세션 목록을 쓸 수 있는가" 를
한곳에서 결정한다. `main.ts` 의 로컬 방송은 `windowsServedLocally()` 가 돌려준 창에만
보낸다 — 원격(WSL) 워크스페이스 창은 제외된다.

워크스페이스가 원격인지 판단하는 규칙은 `EngineRegistry` 가 어떤 엔진을 만들지
결정할 때 쓰는 규칙과 **같은 함수**(`isWslLocation`)를 쓰도록 통일했다. 같은 규칙이 두
군데에 다르게 적혀 있으면 언젠가 어긋나고, 어긋나는 순간 이 버그가 이름만 바꿔 돌아온다.

`session:list` 전송은 `pushSessionList()` 한 곳으로 모으고, 어느 생산자가 어느 창에
몇 개를 보냈는지 debug 레벨로 남긴다. 이 결함의 본질은 "목록이 틀렸다" 가 아니라
"두 번째 생산자가 있다" 이므로, 사후에 그것을 확인할 수 있어야 한다.

## 6. 검증

- `npm run test:session-list-routing` — 라우팅 결정 자체(원격 창 제외, 워크스페이스별
  필터링, 경로 표기 차이)를 고정한다.
- `npm run test:e2e:cross-workspace-flap` — 실제 앱 두 창/두 워크스페이스로 재현
  조건을 만들고, **앱 자신의 로그**에서 "이 프로세스가 WSL 창의 목록을 쓴 적이 없음" 을
  검증한다.

### 6-1. 처음 만든 E2E 는 버그를 못 잡았다 (기록)

첫 버전은 렌더러의 상태 텍스트를 400ms 간격으로 30번 읽었다. **결함이 있는 빌드에서도
통과했다.** 빈 목록이 밀리초 안에 덮이기 때문에 DOM 폴링으로는 거의 잡히지 않는다 —
그런데도 React 는 그 사이 프레임을 그리므로 사용자는 깜빡임을 본다. 같은 실행의 로그에는
결함이 그대로 찍혀 있었다. **증상(스트로브)이 아니라 원인(푸시)을 측정하도록** 다시 썼다.

## 7. 함께 발견한 별개 결함 (미수정)

### 7-1. `npm run start` 는 빌드하지 않는다 — E2E 가 조용히 무의미해진다

`scripts/launch-electron.mjs` 는 `dist/` 를 그대로 실행한다. 소스를 고치고 E2E 를
돌리면 **이전 빌드가 실행되며, 결과는 PASS 로 나온다.** 이 조사 중에 실제로 수정본과
원본이 같은 `dist` 로 돌아가 두 번의 PASS 가 아무것도 증명하지 못했다.

E2E 러너가 실행 전 빌드를 강제하거나, 최소한 `dist` 가 소스보다 오래됐으면 실패시켜야
한다. 지금은 "테스트를 통과했다" 가 "지금 코드가 통과했다" 를 뜻하지 않는다.

### 7-2. 워크스페이스 동일성이 대소문자를 구분한다

`workspaceLocationKey` 는 로컬 경로에 `path.resolve` 만 적용하고 case-fold 하지 않는다.
Windows 에서 `C:\Project\App` 과 `c:\project\app` 은 같은 폴더인데 키가 갈린다. 갈리면
엔진도 창 그룹도 둘로 나뉘어, 61e12c1 이 없앤 "한 워크스페이스에 하네스 중복" 이 다시
생길 수 있다.

로컬 호스트가 Windows 일 때만 case-fold 해야 한다 — WSL 배포판 안에서 도는 엔진에게
경로는 실제로 대소문자를 구분하므로, 공유 코드에서 일괄 적용하면 그쪽이 깨진다.
