# 기획 노트 — 원격 사용 (Remote Access)

> 작성 시작: 2026-07-25
> 사용자와 대화하며 나온 기능 이야기를 정리해 담는 문서. 대화가 진행되는 대로 계속 갱신한다.
> 작업 브랜치: `feat/remote-access` (워크트리 `C:\Project\AgentPartyApp-remote`)

## 1. 개요

**A PC에서 돌아가고 있는 AgentParty를, B PC에서 그대로 이어서 쓰는 것.**

B PC에서도 AgentParty의 모든 기능을 동일하게 쓰되, 실제 작업(에이전트 실행, 파일 접근)은
A PC에서 계속 일어난다. B PC는 A PC의 **상태를 동기화받아** 자기 화면을 그리고,
조작은 A PC로 보낸다.

가장 단순한 형태를 우선한다.

## 2. 배경 · 문제

- AgentParty는 로컬 작업공간에 묶인 데스크톱 앱이라, 그 PC 앞에 있어야만 쓸 수 있다.
- A PC에서 파티를 돌려놓고 자리를 뜨면, 다른 PC(B)에서는 진행 상황을 보거나 개입할 수 없다.

## 3. 하려는 것

### 3.0 요구사항의 일반형 (확정)

> **한쪽 PC에서 AgentParty를 켜두고, 다른 곳의 AgentParty에서 거기에 원격 접속한다.**

특정 장소 조합이 아니라 **일반 요구사항**이다. 아래는 같은 요구의 다른 사례일 뿐이다.

| 시나리오 | 호스트 (앱이 켜져 있는 쪽) | 클라이언트 (접속하는 쪽) |
|---|---|---|
| 퇴근 후 작업 | 회사 PC | 집 PC |
| 외출 중 작업 | 집 PC | 노트북 (밖) |
| (일반형) | 켜둔 어느 PC든 | 접속하는 어느 PC든 |

따라서 다음이 설계 원칙이 된다.

- **역할은 고정이 아니라 모드다.** 같은 AgentParty 설치본이 상황에 따라 호스트도 되고
  클라이언트도 된다. "회사용 빌드"를 따로 만들지 않는다.
- **호스트는 여러 개일 수 있다.** 집·회사를 둘 다 켜둘 수 있으므로, 클라이언트는
  **원격 호스트 목록**에서 골라 붙는 형태여야 한다 (VS Code의 remote 대상 목록과 같은 감각).
- 사용 방식은 §8.1 그대로 — 클라이언트에서도 AgentParty를 켜고, **원격 작업공간(cwd)을 연다.**

### 3.0.1 따라오는 제약

- **두 PC가 서로 다른 네트워크에 있다.** 같은 LAN 전제는 성립하지 않는다 → §8.4.
- **인바운드 접속은 막혀 있다고 봐야 한다.** 회사 방화벽이든 집 공유기 NAT든 마찬가지고,
  포트포워딩은 현실적이지도 바람직하지도 않다. **연결은 호스트가 바깥으로 나가는(outbound)
  방향**을 기본으로 설계한다.
- **호스트는 켜져 있어야 한다.** 사용자 확인: **퇴근 후에도 회사 PC를 켜둘 수 있다.**
  다만 절전·잠금·재부팅은 여전히 일어나므로 재연결과 상태 표시가 필수(§8.5).
- **회사 PC라는 사례에는 조직 정책이 얹힌다.** 원격 통로를 여는 것과 소프트웨어 설치
  가능 여부는 기술이 아니라 정책의 영역이다. 여기서 막히면 §8.4의 경로 선택만 바뀌고
  설계 자체는 바뀌지 않는다.

- 호스트: AgentParty가 열려 있는 상태 (= 원본)
- 클라이언트: 호스트와 **같은 데이터**를 보고, **같은 기능**을 조작
- 작업의 실체는 호스트에 그대로 있음 — 클라이언트는 보고 조작하는 창구

### 3.1 동기화 방식 — 화면이 아니라 데이터 (결정)

**픽셀 미러링(화면 공유형)은 하지 않는다.** B PC는 A PC의 화면 이미지를 받지 않고,
**애플리케이션 상태(데이터)** 를 받아 자기 UI로 렌더링한다.

- 화면 크기·레이아웃은 B PC 사정에 맞게 그려진다 (A 창 크기에 묶이지 않음).
- 대역폭은 화면 스트림이 아니라 상태 변화량에 비례한다.
- B PC의 패널 배치·탭 구성 같은 **화면(뷰) 상태는 동기화 대상이 아니다** — 확인 필요(§12).

### 3.2 동기화 대상 — "다른 모든 기능들"

사용자 요구: 대화, 멤버 상태, **그 외 모든 기능**. 즉 부분 기능(읽기 전용 모니터링 등)이
아니라 앱 전 기능이 원격에서 동작하는 것이 목표다. 현재 앱이 제공하는 기능 범위는
[USER_FEATURES.md](USER_FEATURES.md) 참조. 개략적으로:

| 영역 | 동기화/조작 대상 예 |
|---|---|
| 대화 | 트랜스크립트(스트리밍 포함), 메시지 전송, 승인·사용자 질문 응답 |
| 멤버 | 멤버 목록·상태(실행중/대기), 생성·삭제, 모델·추론강도·권한 변경 |
| 파티 | 파티 목록, 생성·전환, 멤버 간 통신, Message Gate 설정 |
| 세션 | 세션 생명주기(시작/중단/재개), 컨텍스트·압축 상태 |
| 운영 | 토큰 사용량 통계, 계정 사용 한도, 전역 런타임 설정, MCP 서버 |
| 작업공간 | 작업공간 선택·전환 (실체는 A PC의 파일시스템) |

## 4. 세부 동작

### 4.1 접속 구조 — 외부 중계 서버 경유 (사용자 방향)

로컬 서버를 직접 노출(포트포워딩)하지 않고, **바깥에 둔 웹서버를 중계(relay)** 로 쓴다.
A PC와 B PC가 각각 그 서버로 **밖으로 나가는 연결**을 맺고, 서버는 둘 사이를 이어준다.

- 장점: 공유기/방화벽 설정 없이 어디서든 붙는다. 고정 IP·DDNS 불필요.
- 후보로 Firebase 같은 기성 백엔드 언급 (§7.4에서 적합성 검토).
- 범위: **개인용**. 다중 사용자·팀 공유는 목표 아님.

## 7. 난이도 평가 (2026-07-25, 코드 확인 기반)

**결론: 중간(medium).** 구조적으로는 유리한 편이다 — 이 앱은 이미 원격화에 필요한 이음매를
갖고 있다. 어려움은 아키텍처가 아니라 **볼륨·재연결·로컬 전용 기능의 긴 꼬리**에 있다.

### 7.1 유리한 점 (이미 되어 있는 것)

| 사실 | 확인 위치 | 의미 |
|---|---|---|
| 렌더러는 Electron에 **직접 의존이 0** 이다. `electron` import·`ipcRenderer` 사용 없음 | `src/renderer` 전역 검색 결과 없음 | 렌더러 코드를 고치지 않고도 브라우저에서 띄울 수 있다 |
| 렌더러 ↔ 메인 통신이 **단일 객체 `window.agentParty` 하나**로 모여 있다 (메서드 ~60 + 이벤트 구독 13, 호출부 78곳) | [preload.ts](../src/preload/preload.ts) 144줄 | **이 객체 하나를 원격 구현으로 갈아끼우면 원격 클라이언트가 된다.** 이 기능의 핵심 이음매 |
| 상태 팬아웃이 **한 함수로 수렴**한다 | `broadcastToWorkspace` in [main.ts](../src/main/main.ts) | 원격으로 밀어줄 지점이 한 곳 |
| 모든 사용자 기능이 `AppController` 단일 경로 + HTTP API로 노출돼 있다 | [appController.ts](../src/main/application/appController.ts) 899줄, [automationApi.ts](../src/main/automationApi.ts), [API.md](API.md) | **B → A 방향(조작)은 사실상 이미 존재**한다 |
| 렌더러가 Vite 번들이다 | [vite.config.ts](../vite.config.ts) | B PC를 **브라우저만으로** 붙게 하는 선택지가 열려 있다 (앱 설치 불필요) |

### 7.2 새로 만들어야 하는 것

1. **상태 푸시 채널** — 현재 HTTP API는 요청/응답뿐이고 **스트리밍이 없다**
   (`automationApi.ts`에 SSE/WebSocket 없음). 13개 이벤트 채널을 원격으로 밀어주는
   구독 전송로가 이 작업의 실제 무게중심.
2. **`window.agentParty`의 원격 구현체** — 메서드는 HTTP 호출로, 이벤트 구독은
   위 스트림으로 매핑하는 얇은 어댑터.
3. **부트스트랩 + 재연결** — 붙는 순간의 전체 스냅샷, 끊겼다 붙었을 때 놓친 구간 이어받기.
4. **인증/페어링** — 개인용이라도 중계 서버를 지나므로 필수.

### 7.3 진짜 까다로운 부분 (예상 난관)

- **트랜스크립트 볼륨.** 실제로 이 앱에서 **전체 트랜스크립트 ~30MB**가 한 파이프를 막아
  사용자 턴이 33초 대기한 사건이 있었다 —
  [HANDOFF-2026-07-20](HANDOFF-2026-07-20-transcript-rpc-backpressure.md).
  로컬 IPC에서도 터진 볼륨이므로, 인터넷 너머 중계로 **전량 전송은 불가**.
  증분(델타) 전송과 지연 로딩이 전제 조건이다.
- **로컬 전용 기능의 재정의.** 작업공간 선택(네이티브 폴더 다이얼로그), 창 최소화·최대화·
  새 창, `openExternal`, 첨부 파일 — 이들은 "B PC에서 눌렀을 때 A PC의 무엇을 하는가"를
  기능별로 다시 정해야 한다. 개수는 적지만 판단이 필요한 항목들.
- **보안.** A PC의 앱은 Claude/Codex/Cursor **구독 토큰과 작업공간 파일 접근 권한**을 쥐고
  있다. 원격 통로가 뚫리면 그게 그대로 노출된다. 개인용이라도 대충 넘길 수 없는 축.
- **동시 접속 시 상태 정합.** 이미 다중 창이 한 작업공간을 공유하는 구조라 기반은 있지만,
  원격 지연이 끼면 낙관적 UI 갱신과 충돌 처리가 필요해질 수 있다.

### 7.4 Firebase 적합성 — 부분적으로만

- **잘 맞는 것:** 인증(Firebase Auth), 페어링·접속 정보 같은 저빈도 메타데이터.
- **안 맞는 것:** **트랜스크립트 스트리밍**. Firestore는 문서당 지속 쓰기 처리량이 낮고
  (초당 1회 수준 권장) 토큰 델타처럼 초당 수십 건 쓰기에는 비용·지연 모두 불리하다.
  RTDB가 그나마 낫지만 여전히 중계용으로는 과한 우회.
- **더 단순한 대안(검토 필요):**
  1. **WebSocket 중계만 하는 최소 서버** (Cloudflare Workers/Durable Objects, 소형 VPS 등) —
     A가 밖으로 연결을 유지, B가 붙으면 이어줌. 상태 저장 없음.
  2. **터널/사설망** (Cloudflare Tunnel, Tailscale 등) — 클라우드 코드를 **한 줄도 안 쓰고**
     A PC의 기존 HTTP API를 B에서 그대로 부른다. 개인용 한정이면 가장 빠른 경로.
  - 즉 "웹서버를 둔다"는 방향은 맞지만, **Firebase보다 얇은 선택지가 있다.**

### 7.5 규모 감각

- 렌더러(전체 32k LOC)는 **거의 손대지 않아도 된다** — 어댑터가 충실하면.
- 새로 쓰는 코드는 전송 계층 + 어댑터 + 페어링 정도로, 신규 코드량 자체는 크지 않다.
- 대신 "모든 기능"의 마지막 10%(다이얼로그·파일·창 제어·엣지케이스)가 전체 일정의
  절반을 먹는 전형적인 형태가 될 가능성이 높다.

> **§7은 "A의 앱을 B가 원격 조작한다"(미러형)를 전제로 한 평가다. §8에서 사용자가 제시한
> 다른 프레임 — "B의 AgentParty가 원격 cwd를 연다" — 이 훨씬 싸다는 것이 확인되어,
> 설계 방향은 §8로 간다.**

## 8. 설계 방향 전환 — "원격 cwd 열기" (채택 후보)

### 8.1 사용자가 제시한 프레임

> 디스코드 같은 채팅으로 관리할까 하다가, **그냥 AgentParty에서 cwd를 원격으로 접속하는
> 느낌**이면 좋겠다.

즉 B PC에도 AgentParty가 그냥 돌고, **작업공간(cwd)만 A PC의 것을 연다.** VS Code의
Remote와 같은 모델이다. UI·창·설정은 B의 것이고, 작업공간에 뿌리내린 모든 것(파티, 멤버,
트랜스크립트, 하네스 실행, 파일)은 A에서 돈다.

이 프레임은 §7의 미러형보다 **구조적으로 싸다.** 미러형에서 제일 성가셨던 항목들
(창 제어, 네이티브 다이얼로그, `openExternal`, 렌더러 원격화)이 **전부 사라진다** —
그것들은 B PC 자기 앱의 로컬 기능으로 남기 때문이다.

### 8.2 결정적 사실 — 이 구조가 이미 절반 이상 만들어져 있다

WSL 원격 엔진 작업([WSL_REMOTE.md](WSL_REMOTE.md))이 남긴 자산이 그대로 쓰인다.

| 있는 것 | 위치 | 원격 PC에서의 역할 |
|---|---|---|
| **엔진 경계** — 작업공간 단위로 주소화된 서비스 인터페이스 | [engineConnection.ts](../src/main/engine/engineConnection.ts) | 로컬/원격이 갈리는 지점. 이미 존재 |
| **로컬 구현** | [localEngine.ts](../src/main/engine/localEngine.ts) | A PC가 자기 작업공간에 대해 이미 돌리는 것 |
| **원격 클라이언트** | [remoteEngineClient.ts](../src/main/engine/transport/remoteEngineClient.ts) 185줄 | B PC가 쓸 클라이언트 — **이미 있음** |
| **엔진 서버** | [engineServerEntry.ts](../src/main/engine/transport/engineServerEntry.ts) | A PC가 띄울 서버 측 — **이미 있음** |
| **RPC 프로토콜** — 요청/응답 + **서버→클라이언트 이벤트 푸시**(`RpcEvent`) + **역방향 호출**(`RpcHostCall`) | [rpc.ts](../src/main/engine/transport/rpc.ts) | §7.2에서 "새로 만들어야 한다"고 봤던 **상태 푸시 채널이 이미 프로토콜에 있다** |
| **작업공간 위치 파서** (`local` / `wsl` 구분, URI 형식) | [workspaceLocation.ts](../src/shared/workspaceLocation.ts) | 여기에 `remote` 종류를 하나 더 추가 |
| **엔진 라우팅** — 위치 종류로 로컬/원격 분기 | [engineRegistry.ts](../src/main/engine/engineRegistry.ts) `create()` | 분기 한 줄 추가 지점 |

RPC는 **newline-delimited JSON을 스트림 쌍(Readable/Writable) 위에 얹은 형태**라
전송로에 묶여 있지 않다. 지금은 `wsl.exe` 자식 프로세스의 stdio를 타고 있을 뿐,
**TCP 소켓/WebSocket으로 바꾸는 것은 스트림을 갈아끼우는 일**이다.

### 8.3 그래서 새로 할 일 (미러형 대비 대폭 축소)

1. **`remote` 작업공간 종류 추가** — URI 형식 정의(예: `ap+remote://<host>/<path>`),
   파서·표시 문자열.
2. **네트워크 전송로** — 기존 stdio 대신 소켓 위에 같은 RPC를 태운다. `net.Socket`은
   이미 스트림이라 프레이밍은 그대로 재사용 가능.
3. **A PC 측 리스너** — ⚠️ **별도 데몬으로 띄우면 안 된다.** "작업공간 하나당 인메모리
   소스 하나"가 잠긴 규칙이므로, A의 앱이 이미 들고 있는 `LocalEngine`을 **앱 안에서**
   네트워크로 노출해야 한다. 그래야 A 창과 B 창이 같은 데이터를 본다.
4. **페어링·인증·암호화** — 접속 허가 방식.
5. **자격증명 소유권 결정** — WSL 케이스는 "데스크톱이 프로바이더 자격증명을 쥐고 엔진이
   역방향 호출로 빌려 쓰는" 구조(`RpcHostCall`)다. 원격 PC 케이스에서는 **A(엔진 호스트)의
   구독을 쓸지, B(접속자)의 구독을 쓸지** 정해야 한다. 이건 기능 결정이지 기술 문제가 아님.
6. **확인 필요:** 세션 제어(send/interrupt/approve)의 세션→엔진 라우팅이 이미 끝났는지.
   `engineConnection.ts` 주석에는 "transport stage에서 도입"이라 적혀 있는데 WSL 경로는
   동작 중이므로, 현재 코드 상태를 확인해야 한다.

### 8.4 연결 경로 (무료, §3.0 일반형 반영)

호스트와 클라이언트는 서로 다른 네트워크에 있고, 호스트 쪽 인바운드는 막혀 있다고
전제한다. 따라서 **"클라이언트가 호스트의 공인 IP로 직접 접속"은 성립하지 않는다.**

| 방법 | 비용 | 호스트 PC 요구사항 | 평가 |
|---|---|---|---|
| **Tailscale 개인 무료 티어** | 0 (개인 100대) | 설치 권한 필요 | **1순위.** 양쪽에 깔면 서로 사설 IP처럼 보임(NAT 통과, 막히면 443 릴레이 폴백). **앱은 "호스트:포트"로 붙으면 되므로 코드 변경 0.** 내 집·내 노트북처럼 **내 소유 기기끼리는 사실상 무조건 이 경로** |
| 기존 VPN (회사 VPN 등) | 0 | 조직이 허용한 경우 | 클라이언트가 그 VPN에 붙을 수 있으면 위와 동일 효과 |
| **자체 중계 서버 경유** | 0~ (무료 티어) | 설치 불필요 (앱 자체가 outbound 연결) | 호스트에 Tailscale을 못 깔 때(=회사 PC 사례)의 경로. 호스트 AgentParty가 중계로 **나가는** WebSocket을 유지하고 클라이언트도 붙어서 이어짐. **앱에 중계 클라이언트 구현 필요** |
| 같은 LAN 직결 | 0 | — | 실사용 시나리오는 아니지만 **개발·테스트 1단계로는 유용** |
| Firebase | 무료 티어 | — | §7.4대로 스트리밍에 부적합. 인증 용도로만 선택적 |

**권장 순서**

1. **LAN 직결로 먼저 동작시킨다** (개발·검증용). 전송로가 소켓이라는 것만 확정.
2. **실사용은 Tailscale**로 얻는다 — 앱 코드 추가 없이 §8.3의 결과물이 그대로 동작.
3. 회사 PC에 Tailscale 설치가 불가한 경우에만 **중계 서버 경유**를 추가 구현한다.
   이때도 §8.3의 RPC는 그대로 두고 **스트림 공급자만 교체**된다 (직접 소켓 → 중계 WebSocket).

즉 **중계 서버는 3순위 폴백이지 전제가 아니다.** 그리고 어느 경로든 시작 비용은 0이다.

### 8.5 연결 끊김·호스트 부재 처리 (시나리오 확정으로 승격된 요구)

호스트는 켜둘 수 있지만(사용자 확인) 절전·잠금·재부팅·네트워크 변경은 여전히 일어난다.
따라서 다음이 기능 요구사항이 된다.

- 원격 작업공간의 **연결 상태를 UI에 명시**한다 (연결됨 / 재연결 중 / 호스트 없음).
  침묵하는 실패는 금지 — 프로젝트 규칙([AGENTS.md](../AGENTS.md))과도 일치.
- 끊긴 동안 진행된 에이전트 작업은 회사 PC에서 계속 돌아간다. 재연결 시 **놓친 구간을
  이어받아야** 한다(전량 재전송 금지 — §7.3 트랜스크립트 볼륨).
- 호스트가 아예 꺼진 경우 로컬 캐시로 **읽기만이라도** 가능하게 할지는 미결(§12).

### 8.6 보안 — 시나리오가 위험을 키운다

#### 8.6.1 위협의 크기 — 이 앱은 "코드를 실행하는" 앱이다

원격 통로가 뚫렸을 때 잃는 것을 정확히 적는다. 일반적인 웹앱 유출과 급이 다르다.

| 노출되는 것 | 의미 |
|---|---|
| **에이전트에 메시지를 보낼 수 있는 권한** | 에이전트는 호스트 PC에서 파일을 수정하고 셸을 실행한다. 권한 모드에 따라 승인 없이도 실행된다 → **사실상 호스트 PC 원격 코드 실행** |
| 작업공간 소스코드 전체 | 읽기·쓰기 모두 |
| **프로바이더 구독 토큰** (Claude/Codex/Cursor OAuth, OpenRouter 키) | 계정 도용·과금 |
| MCP 서버 설정과 그 자격증명 | 연결된 외부 서비스로 전파 |

즉 이 기능의 보안 실패는 "대화 내용이 새는 것"이 아니라 **PC를 내주는 것**이다.
설계에서 보안은 부가 항목이 아니라 1급 요구사항으로 다룬다.

#### 8.6.2 지금 코드의 사실 — 자동화 API는 인증이 없다

[automationApi.ts](../src/main/automationApi.ts)는 **`127.0.0.1`에만 바인딩**하고
(`server.listen(preferredPort, "127.0.0.1")`), **인증 수단이 하나도 없다.** 토큰도
서명도 없다. 지금까지는 "로컬 루프백에서만 닿는다"가 유일한 보호막이었고, 그 전제
아래에서는 합리적인 선택이었다.

> ⚠️ **따라서 원격화의 첫 번째 금지 사항:** 이 API를 그대로 외부 인터페이스에
> 바인딩하는 것. 한 줄(`"127.0.0.1"` → `"0.0.0.0"`)로 **인증 없는 전체 앱 제어권**이
> 네트워크에 열린다. 원격 엔진 리스너는 **이 API와 별개의, 인증이 붙은 표면**이어야 한다.

#### 8.6.3 Tailscale이 주는 것 / 안 주는 것

**주는 것**

- **종단 간 암호화(WireGuard).** 조정 서버도 릴레이(DERP)도 평문을 못 본다.
- **기기 신원.** 내 tailnet에 로그인한 기기만 그 IP에 닿는다. 인터넷 전체에서는 안 보인다.
- 선택적 강화: **ACL**(어느 기기가 어느 포트에 닿을지 제한), **키 만료**(주기적 재인증),
  IdP의 **MFA**, **Tailnet Lock**(조정 서버가 임의 기기를 끼워넣지 못하게 서명 검증).

**안 주는 것 — 여기부터는 앱이 책임진다**

- **계정이 뚫리면 끝.** tailnet은 구글/깃허브 같은 IdP 계정에 묶인다. 그 계정이 털리면
  공격자 기기가 정식으로 tailnet에 들어온다 → MFA는 선택이 아니라 필수.
- **기본 ACL은 내 기기끼리 전부 허용**이다. tailnet 안의 아무 기기(예: 감염된 폰)나
  호스트 포트에 닿을 수 있다.
- **앱 수준 인가가 없다.** "누가 접속했나", "이 접속을 끊는다"는 Tailscale이 못 해준다.
- **바인딩을 잘못하면 무의미**하다. Tailscale 인터페이스가 아니라 `0.0.0.0`에 열면
  카페 와이파이에도 열린 것이다.

#### 8.6.4 앱이 반드시 지킬 최소 요건

1. **인증 없는 표면을 절대 원격에 노출하지 않는다** (§8.6.2). 원격 리스너는 전용 표면.
2. **기기 페어링** — 호스트에서 명시적으로 승인한 기기만. 페어링 시 기기별 자격증명을
   발급하고, 개별 폐기(revoke)가 가능해야 한다.
3. **바인딩 범위 최소화** — `0.0.0.0` 금지. Tailscale 인터페이스 또는 루프백+터널로 한정.
4. **전송 구간 암호화** — Tailscale 경로는 WireGuard가 처리. 중계 서버 경로는 TLS +
   **종단 인증**(중계 서버를 신뢰하지 않는 전제로 설계).
5. **호스트 UI에 접속 상태 노출** — 현재 접속 중인 기기 표시와 **즉시 끊기**. 침묵 금지
   (프로젝트 규칙 [AGENTS.md](../AGENTS.md)).
6. **원격 기원 명령의 감사 로그** — 무엇이 원격에서 들어왔는지 남긴다.
7. 호스트가 회사 PC인 사례에서는 조직 정책과 충돌하지 않는지 사용자 확인이 필요하다
   (기술로 해결할 수 없는 항목).

미결: 원격 접속 시 **권한 모드를 강제로 낮출지**(예: 원격 세션에서는 자동 승인 금지)는
결정 필요 — 편의와 안전의 교환.

### 8.7 디스코드 경유 안 — 보류에서 **임시 방편(1단계)으로 승격**

초기 평가는 "얻는 게 알림·간단한 명령에 그친다"였다. 하지만 사용자가 제시한 형태는
전면 대체가 아니라 **범위를 좁힌 임시 방편**이므로 성격이 다르다 → §9에서 별도로 다룬다.

## 9. 임시 방편 — 멤버별 디스코드 대화 브리지

### 9.1 사용자가 원하는 형태

> 회사 PC에 AgentParty를 열어두고, **특정 멤버에게 "디스코드로 대화할 수 있게 해줘"** 라고
> 하면, 그 멤버는 그때부터 **디스코드로도 나와 대화**할 수 있다.

즉 앱 전체를 원격화하는 것이 아니라, **멤버 하나의 대화 창구를 디스코드로 하나 더 여는 것**이다.
범위가 좁아 비용이 작고, §8(원격 엔진)과 **경쟁하지 않고 병행**할 수 있다.

### 9.2 왜 이게 임시 방편으로 좋은가

- **방화벽 문제가 공짜로 풀린다.** 디스코드 봇은 호스트에서 디스코드로 **나가는**
  WebSocket(게이트웨이) 하나를 유지한다. 인바운드 개방·포트포워딩·중계 서버 개발이
  전부 불필요하고, **회사 PC에 아무것도 설치하지 않아도 된다**(Tailscale 설치 권한 문제 회피).
- **비용 0.** 디스코드 봇은 무료.
- **양방향이 이미 앱 안에 있다.** 새 전송로를 만들 필요가 없다:
  - 나가는 방향: `sessionManager.on("events")` — 멤버 출력 스트림이 이미 이벤트로 흐른다
    ([main.ts](../src/main/main.ts)).
  - 들어오는 방향: `AppController.handlePartyAction(workspace, name, action, body)` —
    멤버에게 메시지를 넣는 단일 경로가 이미 있다 ([appController.ts](../src/main/application/appController.ts)).
  - 즉 브리지는 **이 둘을 디스코드에 이어붙이는 어댑터**다. 새 프로토콜 설계가 없다.
- 현재 디스코드 관련 코드는 저장소에 **전혀 없다** (신규 추가, 기존 구조 훼손 없음).

### 9.3 "멤버에게 말해서 켠다"를 어떻게 구현할까

두 가지 해석이 가능하고, **둘 다 하는 것**이 자연스럽다.

1. **앱 기능으로서의 토글** (기본) — 멤버 런타임 설정에 "디스코드 브리지" on/off.
   프로젝트 규칙대로 UI와 HTTP API가 같은 `AppController` 메서드를 타고,
   [apiSpec.ts](../src/shared/apiSpec.ts)·[API.md](API.md)에 등록한다.
2. **멤버가 스스로 켜기** — 파티 멤버는 이미 인프로세스 MCP 툴 표면(`agentparty-app`)으로
   앱을 조작한다([PARTY_COMMUNICATION.md](PARTY_COMMUNICATION.md)). 여기에 툴을 하나
   추가하면 **말 그대로 "너 디스코드로도 대화 가능하게 해줘"가 동작**한다.

### 9.4 채널 구조 (초안 — 상세 설계는 §10.2로 대체됨)

- 나만 있는 **개인 디스코드 서버**를 하나 만들고 봇을 초대한다.
- **멤버 1명 = 채널 1개** (`#impl`, `#reviewer` …). 채널이 곧 그 멤버와의 대화창.
- 브리지가 켜진 멤버만 채널이 생기고, 끄면 채널을 보관/삭제.

### 9.5 한계 — 이건 "앱의 대체"가 아니다

| 잃는 것 | 이유 |
|---|---|
| 승인 프롬프트 응답 | 텍스트로는 어색. (디스코드 버튼 컴포넌트로 2단계에서 가능은 하다) |
| diff·도구 출력·서브에이전트 활동 | 앱 트랜스크립트의 구조를 채팅으로 옮기기 어렵다 |
| 멤버 런타임 변경(모델·effort·권한), 토큰 사용량, 워크벤치 | 채팅 밖의 기능 |
| 실시간 스트리밍 | **디스코드 레이트 리밋**(채널당 대략 5초에 5건) 때문에 토큰 단위 스트리밍은 불가. **턴 단위로 묶어서** 보내야 한다 |
| 긴 출력 | 메시지 2000자 제한 → 분할 또는 파일 첨부 |

즉 **"진행 상황 보고 + 지시 내리기"** 까지가 현실적인 사정권이다. 그 이상을 원하면 §8.

### 9.6 보안 — 디스코드는 Tailscale보다 **정책적으로 더 위험할 수 있다**

§8.6의 위협(에이전트에 말을 걸 수 있다 = 호스트에서 코드가 실행된다)은 **그대로 적용된다.**
게다가 디스코드 경로에는 §8에 없던 위험이 추가된다.

- **제3자 서버를 경유한다.** Tailscale은 종단 간 암호화라 중계가 평문을 못 보지만,
  디스코드는 **대화 내용이 디스코드 서버에 평문으로 저장**된다.
  호스트가 회사 PC라면 **회사 코드·로그가 외부 서비스에 남는다** — 조직 정책상
  Tailscale보다 문제가 될 소지가 크다. 이건 기술이 아니라 사용자가 판단할 항목.
- **발신자 검증 필수.** 채널에 들어온 아무 메시지나 멤버에게 전달하면 안 된다.
  **허용된 디스코드 사용자 ID만** 받도록 화이트리스트를 두고, 그 외에는 무시 + 로그.
- **봇 토큰 보관** — 호스트에 저장되는 자격증명이 하나 늘어난다.
- 봇을 **개인 서버에만** 초대한다. 공용 서버에 들어가면 그 서버 인원 전체가 잠재 발신자.

### 9.7 난이도 — 작다

새 전송로도 새 프로토콜도 없고(§9.2), 붙일 지점이 이미 단일 경로로 존재한다.
필요한 것은 봇 게이트웨이 연결 + 멤버↔채널 매핑 + 턴 단위 버퍼링/분할 +
발신자 화이트리스트 + 설정 UI/API. **§8보다 확실히 싸고, §8의 작업을 낭비시키지 않는다**
(브리지는 어댑터 레이어라 원격 엔진이 완성돼도 그대로 유효하다).

### 9.8 플랫폼 결정 — **디스코드로 확정** (2026-07-25)

사용자가 디스코드로 결정. 이후 재확인 요청이 있어 슬랙과 비교했고, **결정을 유지**한다.

| 항목 | 디스코드 | 슬랙 | 이 기능 기준 판정 |
|---|---|---|---|
| **무료 플랜 기록 보존** | 무제한 | **90일 후 열람 불가, 1년 후 영구 삭제** | **디스코드 승 — 결정적.** "대화 전부 전달"이 요구사항인데 무료 슬랙은 그 기록을 90일 만에 잃는다 |
| 무료 저장 용량 | 넉넉 (첨부 파일 위주) | 5GB | 긴 출력·로그를 파일로 붙이는 설계(§10.1)에 디스코드가 유리 |
| 메시지 전송 한도 | 채널당 5건/5초 (버스트 허용) | **채널당 초당 1건** (짧은 버스트 허용) | 사실상 비슷. 지속 처리량은 디스코드가 약간 유리 |
| 메시지 길이 | 2000자 (임베드 4096/합계 6000) | ~4000자 (블록당 3000) | 슬랙이 조금 길지만, 임베드를 쓰면 디스코드가 실효 우위 |
| **인터랙티브 UI** | 버튼·셀렉트·모달 (충분) | **Block Kit — 더 우수** | **슬랙 승.** 승인·질문 UI를 만들기엔 슬랙이 더 좋다 |
| 스레드 | 자동 보관(archive) 있음 | 스레드가 1급, 보관 없음 | 슬랙 소폭 우위 |
| 인바운드 없이 동작 | 게이트웨이 WebSocket + 인터랙션도 게이트웨이 수신 | Socket Mode로 가능 | **동률** — 둘 다 방화벽 문제 없음 |
| 앱 등록 난이도 | 봇 만들고 서버에 초대 | 앱 생성 + 스코프 + Socket Mode 설정 | 디스코드가 간단 |
| 무료 앱 개수 | 제한 없음 | 10개 | 무관 |

**판정 근거:** 슬랙이 이기는 항목(Block Kit, 스레드)은 *더 예쁘게 만들 수 있다*는 쪽이고,
디스코드가 이기는 항목(기록 보존)은 *요구사항이 성립하는가*의 문제다. "대화 내용을 전부
전달한다"가 확정 요구인 이상, 90일 뒤 사라지는 저장소는 이 기능의 전제와 충돌한다.
따라서 **디스코드 유지**.

이후 설계는 디스코드를 전제로 한다.

- 다만 브리지 내부는 **플랫폼 어댑터 경계**를 두어, 나중에 슬랙·텔레그램을 얹더라도
  멤버 이벤트↔메시지 변환 로직을 다시 쓰지 않게 한다. (과잉 추상화는 하지 않되,
  "디스코드 SDK 호출"이 코드 전반에 흩어지지 않게만 격리)

### 9.9 사용자 결정 (2026-07-25)

- **회사 기밀 문제**: 디스코드로는 **회사와 무관한 내용만** 다룬다 → §9.6의 정책 위험은
  사용자가 사용 범위로 회피. (기술적 강제는 하지 않음)
- **전달 범위**: **대화 내용 전부** 전달 희망.
- **승인 요청**: 디스코드에서도 처리하고 싶음. **선택지(옵션)까지** 노출.
- **사용자 인터랙션**: 가능한 범위에서 봇을 통해 지원.

## 10. 디스코드 브리지 — 표면 설계

### 10.1 "전부 전달"은 가능한가 — 조건부 가능

**내용은 전부 보낼 수 있다. 형태는 원본 그대로가 아니라 재구성해야 한다.**

디스코드의 제약(2026-07 확인):

| 제약 | 값 | 영향 |
|---|---|---|
| 채널당 메시지 생성 | **5건 / 5초** | 토큰 단위 스트리밍 **불가**. 묶어서 보내야 함 |
| 전역 요청 | **50 req/s** | 멤버 여럿이 동시에 떠들 때의 상한 |
| 메시지 길이 | 2000자 | 긴 응답은 분할 또는 파일 첨부 |
| 임베드 | 설명 4096자 / 합계 6000자 | **메시지 수를 줄이는 수단** — 레이트 리밋 회피에 유리 |
| 버튼 | 행당 5개, 최대 5행 | 승인 프리셋에 충분 |
| 셀렉트 메뉴 | 옵션 25개 | AskUserQuestion 선택지에 충분 |
| 인터랙션 응답 | 3초 내 ack, defer 시 15분 | 승인 처리 시간 확보 가능 |

→ 설계 원칙: **"턴 단위로 묶고, 길면 파일로, 밀도는 임베드로."**

### 10.2 채널 구조 (구현 결과는 §11.12로 대체됨)

사용자 초안: *멤버별로 채널이나 스레드를 만들어 거기서 대화*. 방향은 맞다.
문제는 "전부 전달"과 결합될 때 **채널 하나가 노이즈로 덮인다**는 것. 개선안:

> **채널 = 멤버 (대화의 본류) / 스레드 = 턴 하나 (상세)**

- `#impl`, `#reviewer` … 브리지를 켠 멤버마다 채널 1개.
- **채널 본류에는 읽어야 할 것만 남긴다** — 내 지시, 멤버의 최종 응답, 승인 요청, 질문,
  턴 상태 한 줄.
- **턴의 상세(추론·도구 호출·긴 출력·서브에이전트 활동)는 그 턴 헤더 메시지에 붙은
  스레드로 들어간다.** "전부 전달" 요구는 스레드가 충족하고, 노이즈는 스레드에 격리된다.
- 모바일에서 스레드를 열지 않으면 안 보이므로 **알림 부담이 줄어든다.**
- 나중에 필요 없어지면 스레드만 끄면 되고, 채널 구조는 그대로다.

부수 이점(구현 시 실측 확인 필요): 디스코드 스레드는 자체 채널 ID를 가지므로 레이트 리밋
버킷이 본류 채널과 분리될 가능성이 높다. 그렇다면 상세 폭주가 본류 대화의 지연을 만들지
않는다. **확정하지 말고 구현 시 측정한다.**

### 10.3 승인 · 질문 · 사용자 인터랙션

이건 **스레드가 아니라 채널 본류**에 올린다 — 놓치면 작업이 멈추는 항목이기 때문.

- **승인 요청**: 임베드(명령/변경 요약) + **버튼**(거부 / 이번만 / 이 세션 동안 / 항상 허용).
  앱의 기존 프리셋과 라벨을 맞춘다.
- **AskUserQuestion**: 질문 + **셀렉트 메뉴 또는 버튼**으로 선택지. 자유 입력이 필요하면
  모달(Discord Modal) 또는 그냥 채널에 답글.
- **응답 후에는 원본 메시지를 편집**해 결과를 박아둔다("✅ 이번만 허용 · 21:41").
  버튼은 비활성화. 히스토리에 무엇을 승인했는지 남는다.
- **만료 처리**: 앱에서 이미 처리됐거나 세션이 끝난 요청은 메시지를 "만료됨"으로 편집.
  디스코드에서 누른 것이 뒤늦게 반영되는 일이 없어야 한다.
- **멘션 알림**은 승인·질문에만 건다. 일반 대화는 무음.

### 10.4 진행 상태 표현 (스트리밍 대체)

토큰 스트리밍이 불가하므로 **턴 헤더 메시지 1개를 편집**해서 진행을 보여준다.
(예: `⏳ 작업 중 · 도구 3회 · 1분 12초` → 완료 시 `✅ 완료`) 편집도 레이트 리밋을
먹으므로 **몇 초 간격으로 throttle**한다. 최종 응답은 별도 메시지로 게시.

### 10.5 켜는 단위

파티 전역 on/off + **멤버별 override**. 이 상속 패턴은 앱에 이미 있다
([MESSAGE_GATE.md](MESSAGE_GATE.md)의 파티 규칙 ↔ 멤버 오버라이드) — 같은 관례를 따르면
사용자도 코드도 일관된다.

### 10.6 대안 — 파티 전체를 한 채널에 (웹훅 아이덴티티)

멤버마다 채널을 파지 않고 **파티 = 채널 1개**로 두고, 디스코드 **웹훅**으로 메시지마다
발신자 이름·아바타를 멤버 것으로 바꿔 보내는 방법도 있다. 단톡방처럼 여러 멤버가 한
화면에서 대화하는 느낌이 난다.

- 장점: 파티 전체 흐름이 한눈에 보임. 채널 수 관리 불필요.
- 단점: **채널 하나에 레이트 리밋이 집중**(5건/5초를 전 멤버가 나눠 씀) → "전부 전달"과
  상성이 나쁘다. 멤버별 알림 제어도 불가.
- 판단: **기본은 §10.2(멤버=채널), 웹훅 방식은 "파티 요약 피드" 옵션으로 나중에 검토.**

### 10.7 남은 결정 필요

- 디스코드에 **회사 작업 내용이 흘러도 되는지** (§9.6 — 가장 중요한 판단).
- 브리지가 전달할 범위: 최종 응답만 / 요약 포함 / 도구 활동까지.
- 승인 요청을 디스코드로 보낼지 (보낸다면 버튼 UI 필요, 아니면 "승인 대기 중"만 알리고
  실제 승인은 앱에서).
- 디스코드에서 온 메시지의 **발신자 표기** — 멤버 입장에서 사용자로 보이는지, 별도 출처로
  구분되는지 (파티 메시지는 이미 `<channel source=...>` 관례가 있다 →
  [PARTY_COMMUNICATION.md](PARTY_COMMUNICATION.md)).

## 11. 1차 구현 확정 — MCP 기반 보고 브리지 (2026-07-25)

> **성격: 업무를 위한 임시 프로젝트.** §8(원격 엔진)은 유효한 본선이고, 이건 먼저 쓰기
> 위한 최소 구현이다. §10의 표면 설계 중 상당 부분은 아래 결정으로 **불필요해졌다**(§11.7).

### 11.1 핵심 발상 — 브리지가 요약하지 않는다, **멤버가 요약한다**

사용자가 실제로 하려는 것:

> 앱에서 **보고용 멤버**를 하나 만들고, 그 멤버가 내 지시에 맞게 현재 상황을 적당히
> 요약해서 디스코드로 보고한다.

이 한 줄이 §10의 난제를 통째로 없앤다. 앱이 트랜스크립트를 기계적으로 전량 전달하는 것이
아니라, **에이전트가 판단해서 필요한 것만 말로 보낸다.** 그래서:

- 레이트 리밋 압박이 사라진다 (사람이 읽을 분량 = 초당 수십 건이 될 수 없다).
- 2000자 제한이 설계 난제가 아니라 **도구의 입력 검증 항목**으로 축소된다.
- "턴=스레드" 같은 노이즈 격리 구조가 필요 없다.

### 11.2 사용 흐름 (확정)

1. 사용자가 앱에서 멤버를 하나 생성한다 (보고 담당).
2. 사용자가 그 멤버에게 **"디스코드 연결해"** 라고 말한다.
3. 멤버가 **네이티브 MCP 도구**로 **미리 설정된 디스코드**에 붙어 **채널을 만든다.**
4. 이후 그 채널에서 대화한다 — 멤버가 상황을 요약해 보고하고, 사용자가 지시를 내린다.

디스코드 봇 토큰·서버(길드) 지정은 **앱 설정에 미리 세팅**되어 있고, 멤버는 채널 생성부터
한다. (토큰을 에이전트가 다루지 않는다 — 보안상 중요)

### 11.3 MCP 도구 표면 (제안)

기존 인프로세스 MCP 서버 `agentparty-app`에 도구를 추가한다.
([partyBridge.ts](../src/core/partyBridge.ts) — `PARTY_MCP_SERVER`, `PARTY_TOOL_NAMES`,
설명 맵, 핸들러 switch, 가이드 프롬프트가 한 파일에 모여 있어 추가 지점이 명확하다.)

| 도구 | 하는 일 | 반환 |
|---|---|---|
| `discord-connect` | 설정된 서버에 채널을 만들고(있으면 재사용) 이 멤버에 연결 | 채널 이름/ID, 이미 연결돼 있으면 그 사실 |
| `discord-send` | 그 채널로 텍스트 전송 | 성공 여부 / 실패 사유(§11.4) |
| `discord-disconnect` | 연결 해제 (채널은 남김) | — |

- **글자수 한계는 도구가 검증한다.** 2000자 초과 입력은 **잘라내지 않고 에러**로 돌려준다
  ("N자 초과, 나눠 보내라"). 조용한 잘림은 금지([AGENTS.md](../AGENTS.md)).
- 인터랙티브 컴포넌트(버튼·셀렉트·모달) 도구는 **만들지 않는다**(§11.5).

### 11.4 스로틀 정책 — 기계적 스로틀 없음, **에러를 에이전트에게 보여준다**

사용자 결정: 앱이 큐잉·자동 재시도를 하지 않는다. 대신 **429를 감지해 도구 에러로 반환**하고,
에이전트가 몇 초 뒤 알아서 다시 보낸다.

- 반환에 **`retry_after`(디스코드가 주는 대기 시간)** 를 포함해 에이전트가 얼마나 기다릴지
  알 수 있게 한다.
- 구현 주의: **디스코드 SDK의 자동 재시도/큐잉을 꺼야 한다.** discord.js 같은 라이브러리는
  기본적으로 레이트 리밋을 내부에서 삼키고 대기하므로, 그 상태로는 에이전트가 스로틀을
  인지하지 못한다. 얇은 REST 호출을 쓰거나 큐잉을 비활성화한다.
- 이 정책은 프로젝트의 "침묵하는 실패 금지" 규칙과 방향이 같다 — 실패를 감추지 않고
  판단 주체(여기서는 에이전트)에게 올린다.

### 11.5 인터랙션 없음 (안정성 우선)

- 버튼·셀렉트 메뉴·모달을 **쓰지 않는다.** 상호작용 응답 타임아웃, 만료 처리, 상태 동기화가
  전부 불안정 요인이므로 1차에서는 배제.
- 따라서 **승인·질문도 디스코드에서 누르지 않는다.** 필요하면 텍스트로 알리고, 실제 조작은
  앱에서 한다.
- **멤버 가이드에 명시**한다 — 그런 도구를 쓰지 않도록. 애초에 도구를 만들지 않으므로
  물리적으로 불가능하지만, 가이드 문구로도 못 박는다
  (`partyBridge.ts`의 도구 안내 프롬프트에 추가).

### 11.6 권한

- 사용자가 해당 멤버를 **auto 권한**으로 운용한다 (사용자 선택, 편의 우선).
- 유의: auto + 디스코드 통로 = 채널에 들어온 지시가 승인 없이 실행된다.
  §9.6의 **발신자 화이트리스트**(허용된 디스코드 사용자 ID만 수용)가 그래서 필수다.
  이건 편의로 생략할 수 없는 항목.

### 11.7 §10에서 **빠지는 것** (범위 축소 기록)

| §10 항목 | 1차 반영 | 이유 |
|---|---|---|
| 턴=스레드 노이즈 격리 | ✗ | 멤버가 요약하므로 노이즈 자체가 없다 |
| 전량 전달·임베드 밀도·파일 첨부 | ✗ | 요약 텍스트면 충분 |
| 버튼 승인 · 셀렉트 질문 | ✗ | §11.5 안정성 결정 |
| 진행 상태 메시지 편집 | ✗ | 멤버가 필요할 때 말로 보고 |
| 파티 전역/멤버 override 토글 | ✗ | 멤버가 MCP로 직접 연결. 설정 UI는 봇 토큰·서버 지정만 |
| 멤버=채널 | ✓ | 유지 (멤버가 `discord-connect`로 생성) |
| 발신자 화이트리스트 | ✓ | 유지 — 보안 필수 |

이 항목들은 삭제가 아니라 **보류**다. 나중에 필요해지면 §10을 다시 꺼낸다.

### 11.8 인바운드(디스코드 → 멤버) — **결정: 파티 메시지와 동일 원리로 주입**

사용자 결정: *"멤버가 유휴 상태일 때는, AgentParty 메시지 전달과 동일한 원리로 주입한다."*
→ 아래 두 안 중 **1번 확정.** 앱이 게이트웨이를 상시 유지하고, 도착한 메시지를 기존 파티
메시지 전달 경로에 얹는다.

구현상 의미:

- 전용 배달 로직을 새로 만들지 않는다. 멤버 메시지 전달은 이미
  [partyApplicationService.ts](../src/main/application/partyApplicationService.ts)가
  **유휴/작업중/세션 없음**을 구분해 처리한다 — 즉시 배달, 턴 중이면 큐잉,
  바인딩된 세션이 없으면 "queued" 응답. 디스코드 인바운드는 이 경로를 그대로 탄다.
- 따라서 **멤버가 유휴든 작업 중이든 사용자는 그냥 말을 걸 수 있다.**
- 표기는 기존 관례를 따라 `<channel source="discord" from="...">`
  ([PARTY_COMMUNICATION.md](PARTY_COMMUNICATION.md)).
- 앱 몫으로 들어오는 것: **게이트웨이 연결 유지·재연결·상태 표시**(침묵 금지).

<details>
<summary>검토했던 대안 (기각)</summary>

**멤버가 `discord-poll` 도구로 직접 읽어가기** — 구현은 작지만 멤버가 도는 동안에만 읽으므로
말을 걸어도 응답이 없을 수 있다. 사실상 보고 전용 단방향이 되어 "그 채널에서 대화한다"는
요구를 만족하지 못한다.
</details>

### 11.9 구현 단계 (제안)

| 단계 | 내용 | 검증 |
|---|---|---|
| 1 | **설정 표면** — 봇 토큰·서버(길드) ID·허용 디스코드 사용자 ID를 앱 설정에 저장. `AppController` 경유 UI+HTTP API, `apiSpec.ts`/`API.md` 등록 | 설정 저장·조회가 UI와 API 양쪽에서 동작 |
| 2 | **아웃바운드** — `discord-connect`(채널 생성/재사용) + `discord-send`(2000자 검증, 429 → `retry_after` 에러) MCP 도구 | 멤버에게 "디스코드 연결하고 한 줄 보고해" → 채널 생성 + 메시지 도착 |
| 3 | **인바운드** — 게이트웨이 상시 연결, 화이트리스트 검사 후 파티 메시지 경로로 주입 | 유휴 멤버에게 디스코드에서 말 걸기 → 멤버가 응답. 작업 중일 때는 큐잉 후 처리 |
| 4 | **연결 상태·오류 가시화** — 연결/끊김/인증 실패/레이트 리밋을 UI와 로그에 노출 | 봇 토큰을 틀리게 넣었을 때 조용히 죽지 않고 오류가 보임 |
| 5 | **멤버 가이드 문구** — 인터랙티브 컴포넌트 금지 등 `partyBridge.ts` 도구 안내에 추가 | — |
| 6 | **풀 프로세스 E2E** — 실제 앱을 띄워 위 흐름을 그대로 재현 | [E2E_TESTING.md](E2E_TESTING.md) 규칙대로 |

**1차 범위 = 1~6단계 전부.** 사용자 확인: **인바운드(3단계)까지 포함해야 완성**이다.
2단계는 중간 점검 지점일 뿐 출하 지점이 아니다 — 보고만 오고 대화가 안 되면 요구를
만족하지 못한다.

### e2e가 잡아낸 것 (설계 문서에 없던 실제 함정)

1. **파티 MCP 도구는 두 곳에 정의돼 있다.** Codex는 `buildPartyDynamicToolSpec`,
   Claude SDK는 `buildPartyToolDefs`(zod). 한쪽만 추가하면 그 하네스 멤버는 도구를
   아예 못 본다 — 처음엔 sonnet 멤버가 `discord-send`를 보지 못했다.
2. **바인딩 키의 파티 해석이 갈렸다.** HTTP는 창의 활성 파티로, 멤버 도구는 자기 실제
   파티 id로 키를 만들어 같은 멤버가 채널을 두 개 만들었다. 이제 **멤버가 속한 파티를
   조회해서** 키를 맞춘다.
3. **MESSAGE CONTENT INTENT가 꺼져 있으면 게이트웨이가 4014로 닫힌다.** 숫자만으로는
   알 수 없어 4014/4004/4013을 사람이 읽을 수 있는 안내로 변환한다.

### 아직 검증되지 않은 것 (정직하게)

- **429 실경로.** 레이트 리밋 처리는 구현했지만 실제 429를 유발한 적은 없다.
- **화이트리스트 거부 경로.** 미등록 사용자가 채널에 쓰는 상황은 미검증(봇 자기 메시지
  무시는 확인됨).
- **장시간 재연결.** 절전/네트워크 단절 후 백오프 재연결은 코드로만 존재.

## 11.12 디스코드 배치 구조 — 최종 (2026-07-26)

사용자 지적으로 드러난 문제: **PC마다 파티·멤버 이름이 같을 수 있고, 같은 PC 안에서도
cwd만 다르면 같은 이름이 나온다.** 초기 구현은 "같은 이름 채널이 있으면 재사용"이었기에
두 PC가 한 채널을 공유하고, 사용자가 한 줄 쓰면 **양쪽 멤버 모두에게 배달**되는 사고가
가능했다. 미관이 아니라 오배달 결함이다.

### 채택한 배치 (사용자 제안)

```
카테고리  "<데스크톱 이름>"        이 PC
  채널    #<파티이름>-<파티id 6자>  파티 하나   ← 고정 메시지: PC · 파티 · cwd
    스레드 <멤버 이름>             멤버 하나   ← 실제 대화는 전부 여기서
```

- **데스크톱 이름은 앱 설정 값**이다(기본값 OS 호스트명). PC 관리를 사용자가 직접 한다.
- **재사용 판정은 이름이 아니라 채널 토픽에 박은 신원**(`데스크톱|워크스페이스|파티id`)이다.
  이름이 우연히 같아도 남의 채널을 집어가지 않는다. ← 사고의 진짜 원인이 여기였다.
- 채널 이름에 **파티 id 뒤 6자**를 붙여 같은 이름 파티끼리도 구분된다.
- **스레드 메시지만 배달**한다. 파티 채널 본문에 쓴 글은 어느 멤버 앞인지 알 수 없으므로
  로그만 남기고 버린다. 사용자 결정에 따라 **봇이 본문에 답하지 않는다**(고정 메시지가
  이미 안내하므로).
- 스레드는 자동 보관(7일)되며, 보관된 스레드를 만나면 되살린 뒤 사용한다.

### 왜 스레드인가 (채널=멤버 대비)

멤버마다 채널을 파면 파티 하나에 멤버 5명이면 채널이 5개씩 늘어난다. 채널=파티,
스레드=멤버면 목록은 파티 수만큼만 늘고 멤버는 접힌다. 사용자가 사용성을 확인하고 채택.

### 마이그레이션

스레드 이전 형식(채널만 있고 스레드 없음)의 바인딩은 **로드 시 버린다**(로그 남김).
그대로 두면 `undefined` 스레드로 전송을 시도하기 때문이며, 멤버가 다시
`discord-connect`하면 새 배치로 붙는다.

## 11.13 WSL 작업공간 지원 (2026-07-26)

WSL 작업공간에서는 파티 도구가 **distro 안의 헤드리스 엔진**에서 돈다. 브리지는 데스크톱
소유(봇 토큰과 게이트웨이 소켓이 거기 있음)이므로, 도구 호출을 **역방향 호스트 채널**로
데스크톱에 위임한다 — Message Gate 리뷰어가 이미 쓰던 것과 같은 구조
([engineServerEntry.ts](../src/main/engine/transport/engineServerEntry.ts)).

**WSL e2e가 잡은 실제 결함:** distro 엔진은 작업공간을 `/tmp/...`(순수 posix 경로)로 알고,
데스크톱은 `wsl+Ubuntu-22.04:/tmp/...`로 안다. 위임된 호출이 distro의 경로를 그대로 실으면
**같은 멤버가 두 가지 키로 저장되어 채널이 두 개 생긴다**(실제로 재현됨: HTTP로 만든 채널과
에이전트가 만든 채널이 갈라져 보고가 다른 채널로 갔다). 이제 데스크톱이 **자기 URI로 강제
정규화**한다.

인바운드는 별도 처리가 필요 없다 — 배달이 `AppController.sendMemberMessage`를 타고,
그 경로가 이미 워크스페이스 종류에 따라 엔진을 고른다.

검증: `node scripts/e2e-discord-bridge.mjs --wsl --no-inbound` 통과(실모델 턴 포함).

## 12. 미결 · 확인 필요

- B PC 클라이언트의 형태 — AgentParty 앱 설치본인지, 브라우저로 접속하는 웹 UI인지.
- 화면(뷰) 상태 동기화 여부 — 패널 분할·탭 배치·현재 열린 화면까지 따라갈지,
  아니면 B는 자기 화면 구성을 독립적으로 갖는지.
- 네트워크 범위 — 같은 LAN만인지, 인터넷 너머(외부망)도 대상인지.
- 동시 사용 — A와 B에서 동시에 조작 가능한지, 충돌 시 규칙.
- 인증/보안 — 접속 허가 방식(페어링 코드/토큰 등), 전송 구간 암호화.
- 연결이 끊겼다 붙었을 때 — 놓친 변화의 복구 방식(전체 재수신 vs 증분 이어받기).

## 13. 참고 — 기존 문서와의 관계

- [WSL_REMOTE.md](WSL_REMOTE.md)는 이름은 "remote"지만 **다른 축**이다. 그쪽은
  *작업공간이 있는 OS로 엔진을 옮기는 것*(Windows UI ↔ WSL 안의 엔진)이고,
  이 기획은 *다른 PC에서 같은 앱을 쓰는 것*이다. 다만 "클라이언트(UI)와 엔진을
  분리한다"는 구조는 정확히 겹치므로, 그 경계를 재사용할 수 있는지 검토 대상.
- 앱의 모든 사용자 기능은 이미 로컬 자동화 HTTP API([API.md](API.md))로 노출돼 있다
  (`AppController` 단일 경로 원칙). **조작(명령) 측 재료는 이미 갖춰져 있다.**
  남는 과제는 반대 방향 — 상태 변화를 원격 클라이언트로 밀어주는 **구독/스트림** 축.
