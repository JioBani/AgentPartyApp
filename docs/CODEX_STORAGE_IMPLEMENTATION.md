# Codex 초기화 수명 관리와 저장소 전환 구현

2026-09-26 · `fix/codex-storage-lifecycle` · Windows Codex 0.155.1

## 변경 범위

초기화 중에는 UI의 busy/idle 상태와 별개로 실제 initialize 요청의 수명을
추적한다. 설정 변경, 멤버 닫기, 재시작, 앱 종료가 초기화 프로세스를 먼저
죽이지 않도록 처리한다. Codex Fast/service tier는 다음 turn/start에 반영해
프로세스 교체를 없앴다. 초기화 전 요청 취소는 다음 요청을 막지 않으며,
turn/start 전송 후에는 turn ID를 받은 뒤 실제 중단을 요청한다.

멤버, 사용량 조회, 모델 목록, Windows 환경 진단의 초기화는 한 프로세스
안에서 순서대로 진행한다. 초기화 완료 뒤 모델 작업은 병렬이다. 대규모
기록의 첫 색인에는 최대 300초를 허용한다. 강제 프로세스 종료/OS 종료까지
보장하는 것은 아니다. 외부 CLI와 다른 AgentParty 인스턴스는 이 큐 밖에 있다.

일시적인 SQLite 시작 오류는 같은 저장소에서 제한적으로 재시도한다.
backfill timeout은 그대로 표시하며 새 `-recovery` 저장소로 자동 이동하지
않는다. 이전 버전이 만든 recovery 디렉터리는 호환성을 위해 계속 찾는다.

새 Windows 프로필은 Codex 자체 저장소를 사용한다. 기존 프로필은 legacy를
유지하며, 최초 선택은 파일로 고정해 다른 호스트용 폴더 생성에 영향받지
않는다. 사용자 환경변수/config의 정상적인 저장소 우선순위를 바꾸지 않는다.
WSL/SSH는 별도 검증 전까지 기존 정책을 유지한다.

## 전환과 폴백

호출 형식과 전제조건은 [API 문서](API.md#codex-storage-administration-windows-desktop-local)를
따른다. 준비 → 백업 → 공식 API 검증 → 모드 기록 순서이며, 마지막 단계만
Windows 멤버의 저장소 선택을 바꾼다. 정상 실행 경로는 Python에 의존하지
않고, 일회성 백업/검증 작업만 Python 3.11+ 표준 라이브러리를 사용한다.

- 실행 중인 로컬 Codex 멤버가 있으면 거절한다. 외부 CLI/IDE도 종료해야 한다.
- SQLite backup API로 WAL을 포함한 일관된 DB 복사본을 만든다.
- 대화 파일, 설정, 앱의 멤버-ID 매핑과 이전 모드도 보관한다. 인증 파일은 복사하지 않는다.
- 모든 색인의 대화 ID, 파일, 사용자/assistant 메시지 지문과 횟수, 보호할 메타데이터와 부가 상태를 확인한다.
- paginated 대화는 다른 저장소에서 내용이 빈 값/과거 값으로 조회될 수 있다.
  비교에는 DB와 함께 보관한 페이지형 기록도 포함한다. 같은 대화를 여러
  저장소가 색인했다면 가장 많은 rollout 바이트를 반영한 복사본을 기준으로
  삼는다. 페이지형 기록은 원시 event_msg가 비었다는 이유로 빈 대화로 판정하지 않는다.
  이때 활성 goal을 확인하고 Codex의 공식 resume/unsubscribe로 기록을 갱신한다.
  모델 턴은 시작하지 않는다. 비교용 복사본도 별도로 만들어 원본 백업을 보존한다.
- resume의 인라인 응답과 전체 조회가 다른 압축 대화가 있어, 양쪽 모두
  unsubscribe 후 같은 thread/read API의 결과를 비교한다.
- 기록 갱신이 append한 설정 이벤트만 허용한다. 기존 바이트 변경이나 새로운
  대화 활동은 실패 처리한다.
- 기본 저장소에 없는 memory/queue/section 등 지원하지 못하는 상태는 버리지
  않고 중단한다. 누락된 provider를 강제로 바꾸거나 보관된 대화를 풀지 않는다.
- goal ID/누적 사용량은 병합하지 않는다. 원래 DB는 남겨두며 활성 goal은
  자동으로 다시 실행하지 않는다.
- 롤백은 최신 대화가 legacy 저장소에서 읽히는지 확인한다. 과거 백업을
  운영 파일 위에 덮어쓰지 않는다. native에서 새로 만든 멤버 대화도 포함한다.

실패하면 현재 모드를 유지하고 오류, 백업, 진행 기록을 남긴다. Codex가 이미
완료한 색인 보완/기록 갱신은 남을 수 있다. 재실행은 새 백업을 만들고 전체
검증을 다시 수행한다. 부분 진행 기록만 믿고 성공으로 이어가지 않는다.
백업 자동 삭제와 자동 폴백은 없다.

## 검증 기록

전용 userData/CODEX_HOME/작업공간에서 실제 Electron 앱과 실제 Codex를 사용했다.
모델 응답은 `gpt-6-luna`, low, standard로 확인했다. 다른 모델/호스트까지
검증했다고 간주하지 않는다. 멤버 생성·설정·메시지·중단은 실제 member-scoped
MCP transport를 통과했다. 직접 HTTP는 상태 조회, fixture, 멤버 닫기/재개,
창 종료, 저장소 관리 등 대응하는 MCP 도구가 없는 기능에 사용했다.

| 사용자 흐름 | 결과 |
| --- | --- |
| 초기화 직후 Fast/effort 변경과 첫 메시지 | 같은 PID/앱 세션, 정확한 응답 1회 |
| 초기화 중 첫 요청 중단 후 새 요청 | 취소한 요청은 실행되지 않고 다음 요청에 정상 응답 |
| 초기화 중 닫기 후 재개 | 새 프로세스로 정상 재개, backfill timeout 없음 |
| cold 초기화 중 앱 종료 | 약 3.45초 대기 후 종료, QA DB 9개의 backfill 완료 |
| 실행 중 멤버를 둔 채 저장소 전환 | 명확한 오류로 거절 |
| 내용 검증 실패 | legacy 유지, failed 상태와 백업 경로 표시 |
| legacy → native | 이전 대화 ID 유지, 이전 응답 회상 |
| native 신규 대화 → legacy | 같은 ID로 최신 응답 회상 |
| legacy에서 추가 응답 → native | 마지막 응답 회상, 대화 ID 유지 |
| 후보 앱 재실행 | native 모드 유지, 마지막 응답 회상 |
| 실제 모델의 Party 도구 호출 | `party_list` 실행 후 정확한 완료 응답 |
| turn/start 부근 중단 후 다음 요청 | 중단 완료 후 새 응답 정상 수신 |
| 새 프로필 시작 | 기본 native, 실제 응답, 멤버별 DB 디렉터리 생성 없음 |
| 새 프로필에 나중에 legacy 호스트 폴더 생성 | native 선택 유지 |

기존 조사/준비 단계의 809개 대화 분석은
[준비 검증](CODEX_STORAGE_READINESS.md)에 따로 남긴다. 후보 구현의 추가 검증
결과는 아래에 기록한다.

후보 전환 worker는 격리한 기존 색인과 페이지형 기록이 이미 있는 기본
저장소에서 809개 대화의 전체 검증을 통과했다. 이 중 페이지형 색인은
135개다. 이 결과를 빈 기본 저장소에서 모든 기록이 복원된다는 증거로
사용하지 않는다. 실제 API를 통한
최종 왕복은 최신 기록 14개와 저장된 멤버 6개를 검증했다. 부분 작업 중 앱이
재실행된 상황은 살아 있는 worker 잠금과 running 작업 기록을 fixture로
준비하고 실제 앱을 실행해 확인했다. 모드 유지, interrupted 작업 표시,
실제 MCP를 통한 새 Codex 생성 차단을 통과했다.

기본 저장소를 완전히 비운 별도 복사본 실험은 **보관된 페이지형 대화의
재개 거부로 중단됐다**. Codex의 공식 read 결과가 기존 기록과 다를 때
resume으로 복구하려 했으나, Codex가 unarchive를 먼저 요구했다. 임의로
보관 해제하지 않으므로 이 상태에서는 전환할 수 없다. 독립 재개를 거부하는
multi-agent v2 하위 대화도 같은 보수적 중단 원칙을 따른다. 현재 사용자
기본 DB에는 해당 보관 대화와 history item 6개가 이미 있음을 읽기 전용으로
확인했지만, 운영 전환 시점의 전체 검증을 생략할 근거는 아니다.

따라서 구현 완료와 모든 기존 프로필의 무조건적인 전환 가능은 구분한다.
운영 시 검증을 통과하지 못하면 legacy를 유지하고 원인을 검토해야 한다.

`npm run build`와 후속 main TypeScript 컴파일, `git diff --check`를 통과했다.
renderer를 수정하지 않아 UI 배치 검증은 대상이 아니다. 배포 패키징, macOS,
WSL/SSH의 native 전환, 외부 터미널 UI의 소유권 인계는 검증 범위에 포함하지 않는다.

격리한 QA 백업과 임시 자료는 삭제하지 않았다. 준비 단계의 QA 인증 복사본
삭제는 도구 승인 정책에서 거절되어 남아 있다. 해당 파일을 다른 명령으로
우회 삭제하지 않았으며, 운영 전환 백업에는 인증 파일을 포함하지 않는다.

검증 과정의 문제도 기록한다. 전체 복사본 검사 드라이버가 상속받은
`CODEX_SQLITE_HOME`을 제거하지 않아 현재 refactoring 세션의 운영 DB를
참조했다. 공식 read/resume 호출로 해당 운영 대화에 설정 이벤트가 추가됐다.
저장소 모드 전환이나 모델 턴 실행은 없었다. 드라이버 환경을 격리하고,
worker도 백업 대상으로 확인한 SQLite 경로를 명시적으로 사용하며, API가
선택한 Codex home 밖의 rollout을 반환하면 즉시 실패하도록 수정했다.
따라서 이 작업 전체를 “운영 데이터에 쓰기 없음”으로 표현하지 않는다.

## 운영 적용

현재 운영 프로필에는 전환을 실행하지 않았다. 이 대화를 포함한 실행 중인
Codex 세션이 있으므로 현재 세션 안에서 안전하게 실행할 수 없다. 배포 후
모든 로컬/외부 Codex를 종료한 유지보수 시점에 해당 프로필의 전환 API를
실행한다. 실패하면 모드와 원본을 유지한 채 보고서의 원인을 해결한다.

구조 검토: 초기화 조정은 core, 저장소 선택은 별도 policy, 작업 잠금/진행은
main service, 백업과 대조는 일회성 worker로 분리했다. 평소 어댑터가 Codex의
DB 스키마를 읽거나 수정하지 않는다. renderer와 사용자 데이터 포맷은
변경하지 않았다. 구현 내부 상수나 enum 존재를 확인하는 테스트는 추가하지 않았다.
