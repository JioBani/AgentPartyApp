# 기획 노트 — 대화 인계 (하네스/모델 교체 시 대화 이어가기)

> 작성: 2026-08-03 · 담당: plaaner(기획)
> 대상 요청: `docs/FEEDBACK.md` **P-6**
> 사용자와 대화하며 정해진 내용을 담는다. 진행되는 대로 갱신한다.

## 1. 한 줄

**모델이나 하네스를 바꿔도 같은 멤버와 대화를 계속한다.**
인계 문서를 만들어 넘기는 것이 아니라, **이미 남아 있는 기록을 새 모델에게 소개**하는 방식이다.

---

## 2. 배경 — 지금 사용자가 겪는 일

멤버 하나와 한참 작업하다 다른 회사 모델로 바꾸고 싶어진다. 그런데 **첫 마디를 건넨
순간부터 하네스는 잠긴다.** 대화 중인 멤버는 모델을 바꿀 수 없다.

그래서 사용자는 이렇게 한다.

1. 멤버에게 "지금까지 한 걸 문서로 정리해줘" 시킨다
2. 그 문서를 main 에게 넘긴다
3. main 이 멤버를 지우고 새 하네스로 다시 만든다
4. 문서를 새 멤버에게 넘긴다

**진짜 문제는 번거로움이 아니라, 이 방식이 "정리를 시킬 힘이 남아 있을 때만" 작동한다는
것이다.** 한도가 먼저 떨어지면 그 대화는 살릴 수 없다. 그런데 모델을 바꾸고 싶어지는
순간이 대개 한도가 떨어진 순간이다.

---

## 3. 하려는 것 — 사용자 시나리오

멤버 설정에서 하네스를 그냥 바꾼다. 경고가 한 번 뜬다.

> 새 모델은 이 대화를 그대로 물려받지 못합니다. 대신 지금까지의 기록을 **읽고**
> 이어갑니다. 같은 세션의 연속이 아니라 재구성이라, 세부는 달라질 수 있습니다.

확인하면 **같은 멤버, 같은 대화창**에서 모델만 바뀐다. 새 모델은 첫 답을 하기 전에 지난
기록을 훑고 온다 — 처음(무엇을 왜 하고 있었는지)과 끝(어디까지 왔는지)을 먼저 보고,
중간 시행착오와 도구 실행 결과는 건너뛴다.

**사용자가 준비할 것은 없다.** 인계 문서를 만드는 시점이 따로 없기 때문이다. 대화하는
내내 이미 기록되고 있었으므로, **한도가 다 떨어진 멤버도, 죽은 멤버도 넘길 수 있다.**

그리고 교체 직후만이 아니다. 스무 턴쯤 지나 "아까 우리가 정했던 거 뭐였지?" 하고 물으면
**모델이 지난 기록을 찾아보고 답한다.** 연속성은 사실 여기서 만들어진다 — 처음에 잘 읽는
것보다 나중에 물었을 때 제대로 답하는 쪽이 훨씬 크게 느껴진다.

### 사용자가 잃는 것 (숨기지 않는다)

- **대화에 붙였던 이미지는 넘어가지 않는다.** 앱이 이미지 자체를 오래 보관하지 않아
  "여기 이미지가 있었다"는 것만 남는다.
- **도구 실행 결과의 원문은 읽지 않는다.** 일부러 그렇게 한다 — 작업 결과의 진짜 모습은
  대화 기록이 아니라 지금 작업공간의 파일이다.
- **세부는 달라질 수 있다.** 읽어서 재구성하는 것이라 이전 모델의 판단이 그대로
  재현되지는 않는다. 그래서 새 모델에게 **"모르는 걸 아는 척하지 말고 물어보라"**고
  못 박는다. 조용히 지어내는 것보다 한 번 되묻는 편이 낫다.

## 4. 결정과 이유 (결정 로그)

승인을 받은 것이 아니라 **판단한 것**이다. 다음 사람이 "왜 이렇게 됐지"를 여기서 읽는다.

### D1. 요약본을 만들어 주입하지 않는다 — 기록을 읽게 한다

처음 안은 "교체 시 트랜스크립트를 요약해 새 세션에 밀어 넣기"였다. 버렸다.

- 요약은 **버린 것을 되찾을 길이 없다.** 무엇을 버렸는지 표시해도 사용자가 할 수 있는 게
  없으면 결국 조용한 손실의 정중한 버전이다.
- 요약을 만들려면 모델 호출이 필요하고, **그 호출이 실패하는 상황이 정확히 이 기능이
  필요한 상황**(한도 소진)과 겹친다.
- 반면 기록을 읽게 하면 모델 호출 0, 판단 0, 실패 경로 0이다. **항상 존재한다.**

### D2. 전용 조회 도구(MCP)를 만들지 않는다

목차/정독/검색 도구 3종을 만들려 했으나 버렸다. 사용자 지적:

> 자체 제작 도구는 하네스가 원래 갖고 있던 도구보다 성능·효율이 현저히 떨어지고
> 컨텍스트를 많이 태운다.

맞다. `wc` → `tail` → `grep` → 범위 `Read` 로 다 된다. 셋 다 네이티브에 있다.
설계 문제는 "도구를 만들 것인가"가 아니라 **"파일을 어떤 모양으로 두어야 네이티브 도구가
잘 먹는가"** 로 옮겨간다.

### D3. 넘기는 것은 **하네스 원본이 주(主), 앱 기록이 지도**

| | 앱 기록 | 하네스 기록 |
|---|---|---|
| 성격 | 정규화된 축약본 | 원본 전체 |
| 강점 | 하네스가 달라도 모양이 같고, 훑기 좋고, **멤버 간 메시지·게이트 판정이 여기에만 있음** | 안 잘림, 도구 실행 원문까지 전부 |
| 약점 | 잘림, 도구 기록이 8~9할을 먹음 | 하네스마다 형식 다름, 거대함(최대 69MB), 사용자 홈에 있음 |
| 역할 | **지도** — 흐름과 목차 | **깊이** — 특정 대목 정독 |

작은 지도로 흐름을 잡고, 필요한 대목만 원본에서 파고든다.
**둘은 서로의 보험이다** — 앱 기록은 *잘리지만 사라지지 않고*, 하네스 기록은
*안 잘리지만 사라질 수 있다*. (§6 에 양방향 실측)

### D4. 화면 렌더링 소스는 앱 기록을 유지한다

"앱 기록을 없애고 하네스 기록으로 화면을 그리자"는 안을 검토했고, **하지 않는다.**

1. **파티에서 벌어진 일이 거기 없다.** 특히 **Message Gate 가 막은 메시지는 하네스에
   도달조차 하지 않는다.** 멤버 생성·삭제, 대기열, 수신자 표시도 마찬가지다. 결국 그것들만
   따로 저장해야 하고, 그러면 기록이 두 벌인 건 그대로인데 화면이 두 출처를 시간순으로
   꿰매야 한다 — 지금보다 복잡해진다.
2. **하네스 기록은 사라진다.** 앱에 이미 그 안내가 있다 — *"저장된 세션을 찾을 수 없어…
   이전 기록은 화면에 남아 있습니다."* 지금은 하네스가 기록을 날려도 사용자는 대화를 잃지
   않는다. 렌더링을 하네스에 의존하면 **그 순간 대화창이 통째로 비워진다.**
3. **우리 화면이 남의 내부 로그에 묶인다.** 하네스 세션 파일은 문서화된 형식이 아니라
   그 제품의 구현 세부다. 형식이 바뀌면 우리 앱의 가장 중요한 화면이 깨지고, 하네스가
   셋이니 그 위험도 셋이다.

### D5. 앱 기록은 "화면용"이므로 화면에 필요한 만큼만 남긴다

앱 기록이 쓰이는 곳은 **화면 복원**뿐이다(모델에게 다시 먹이는 용도가 아니다 — 하네스는
자기 기록으로 이어간다). 그런데 지금은 도구 실행 결과 원문까지 통째로 들고 있어 멤버
하나가 9MB 까지 간다. 그게 진짜 중복이다 — 원본이 하네스에 그대로 있다.

> **대화**(사용자 발화 · 모델 답변 · 멤버 간 메시지 · 게이트 판정)는 오래 남기고,
> **도구 실행 결과 원문**은 최근 것만 남긴다.

### D6. 하네스 잠금을 푼다 (경고와 함께)

교체 자체를 막는 대신, **"연속이 아니라 재구성"**임을 알리고 진행한다.

## 5. 인계할 때 새 모델에게 주는 것

### 5.1 상시층 — 모든 멤버에게 항상 (교체와 무관)

파티 primer 와 같은 자리. 짧아서 압축에 밀려도 재주입이 싸다.

```
너의 이전 대화 기록은 <경로> 에 있다.
사용자가 이전 대화를 전제하고 말하거나("아까", "우리가 정한", "그거", "전에 얘기한"),
네가 모르는 이전 맥락이 필요하면 추측하지 말고 거기서 찾아라.
이미 파악한 내용이면 다시 읽지 마라.
```

**트리거 단어를 예시로 박는 것이 핵심이다.** "필요하면 찾아라"만 있으면 모델은 대개 그냥
답한다 — 자기가 모른다는 걸 모르기 때문이다. 지시어를 명시하면 실제로 찾으러 간다.

### 5.2 1회층 — 교체 직후 한 번

```
너는 이전 세션의 대화를 이어받은 세션이다. 하네스와 모델이 바뀌어 이전 세션의
컨텍스트를 직접 물려받지 못했다.

이전 하네스가 남긴 원본 기록:   <경로 목록, 시간순>
앱이 보관한 기록(요약본·지도):  <경로>

답하기 전에 읽어 맥락을 파악하되, 다음을 지켜라.

- 먼저 파일 크기를 확인하고, 통째로 읽지 마라.
- 앞과 끝을 먼저 읽어라. 앞에는 이 세션의 목적·역할·지켜야 할 작업 규칙이 있고,
  끝에는 현재 상태와 다음에 할 일이 있다. 둘 다 필요하다. 중간은 대개 이미 폐기된
  시행착오이니 필요할 때만 들어가라.
- 사용자 발화를 먼저 훑어라. 그것이 목차 역할을 한다. 요구·결정·번복은 사용자 발화에
  압축돼 있다.
- 도구 호출의 입력·결과, 파일 diff 는 읽지 마라. 작업 산출물의 정본은 이 기록이 아니라
  워크스페이스의 현재 파일이다. 필요하면 파일이나 git 을 직접 봐라.
- 전부 자세히 파악하려 하지 마라. 전체 흐름과 최신 목적, 미결 사항이면 된다.
  점진적으로 필요한 만큼만 더 읽어라.
- 이 기록은 완전하지 않다. 유실된 부분이 있고 이미지 첨부는 내용이 남아 있지 않다.
  모르는 것을 아는 것처럼 메우지 말고, 확실하지 않으면 사용자에게 물어라.
```

> **"앞부터 읽어라"는 사용자 지적으로 들어갔다.** 초기 안은 "끝에서부터 거슬러
> 올라가라"였는데, 이 앱의 실제 사용에서는 틀리다. 멤버 세션은 **첫 턴에 목적·역할·작업
> 규칙이 세워지고 그것이 세션 전체를 지배한다.** 버려도 되는 것은 그 사이의 시행착오다.

### 5.3 정직성 규칙

**원본이 있으면 있다고, 없으면 없다고 명시한다.** 있는 줄 알고 찾으러 갔다가 못 찾는 것이
가장 나쁘다. 세 하네스 모두 원본을 짚을 수 있지만(§6.1), 하네스가 자기 기록을 정리했거나
작업공간을 다른 PC 로 옮긴 경우는 여전히 없을 수 있다. 그때는:

> 이전 하네스의 원본 기록을 찾을 수 없습니다. 앱이 보관한 기록만 있고,
> 이건 화면용 축약본이라 세부가 빠져 있습니다.

## 6. 확인된 사실 (2026-08-03 실측)

### 6.1 멤버 ↔ 원본 파일을 이을 수 있는가 — **있다**

토큰 사용 원장에 멤버 이름과 세션 번호가 계속 기록되고 있었다. 인계용으로 만든 것이
아닌데 결과적으로 **"이 멤버가 거쳐온 세션들"의 명부**가 되어 있다.

| 하네스 | 원본 확보 | 근거 |
|---|---|---|
| **Claude Code** | ✅ | 이 작업공간 세션 19개 전부 파일 확인 |
| **Codex** | ✅ | 기록 파일 **286개 전부** 파일명과 내부 세션 번호 일치. 첫 줄에 세션 번호·작업 폴더·모델 제공자·컨텍스트 창·CLI 버전 → 원장 없이 작업 폴더로 역추적도 가능 |
| **Cursor** | ✅ (단, 추출 필요) | `~/.cursor/chats/<작업공간해시>/<세션번호>/`. **앱이 이미 Cursor 자신의 세션 번호를 그대로 저장하고 있어** 앱의 6건이 전부 폴더와 일치. 다만 내용이 **SQLite**(`store.db`)라 경로만 줘서는 못 읽는다 → §6.4 |

- **세 하네스 모두 원본을 짚어낼 수 있다.** 사용자가 실제로 하던 Claude ↔ Codex 조합은 경로만
  넘기면 되고, Cursor 만 한 단계(추출)가 더 붙는다.
- 원장에 세션 번호가 없는 턴 203건은 **전부 Message Gate 리뷰어 턴**이었다. 그건 멤버
  세션이 아니라 별도 검사 호출이라 정상이다. **멤버의 실제 턴은 전부 세션 번호를 갖는다.**

### 6.2 Cursor 만 "경로 넘기기"가 안 된다 — 앱이 뽑아줘야 한다

Claude·Codex 는 기록이 **jsonl 평문**이라 경로만 알려주면 모델이 자기 도구로 읽는다(D2).
Cursor 는 **SQLite** 라 그게 성립하지 않는다. 실측한 구조:

- `meta.json` — `cwd`, `createdAtMs`, `updatedAtMs` (어느 작업공간의 언제 대화인지)
- `store.db` — 대화 본문. `blobs(id, data)` 테이블에 내용주소(content-addressed)로 저장
  - 그중 **메시지는 평문 JSON** (`{"role":..., "content":...}`) — system / user / assistant / tool
  - 나머지는 이진 색인 블롭
  - **저장 순서가 대화 순서와 일치**한다(실측: system → user → assistant → tool → …)
  - reasoning, tool-call, tool-result, 타임스탬프까지 남아 있다

→ **교체 시 앱이 텍스트로 뽑아 임시 파일로 넘긴다.** 순수 기계적 변환이라 모델 호출 0,
판단 0 이므로 D1 의 원칙("실패 경로를 만들지 않는다")을 깨지 않는다.

> `meta.json` 에 `blobEncryptionKey` 필드가 있으나 실측한 메시지 블롭은 평문이었다.
> 암호화가 적용되는 조건이 따로 있는지는 **미확인** — 구현 시 확인할 것.

### 6.3 두 기록은 서로 다른 이유로 사라진다 — 양방향 실측

- **하네스 기록이 사라지는 쪽**: 앱에 이미 복구 안내가 있다(§4 D4-2).
- **앱 기록이 먼저 사라지는 쪽**: AgentParty 가 만든 워크스페이스 30곳 중 원장이 남은 것은
  **4곳뿐**인데(임시 폴더라 정리됨), 하네스 기록 **115개는 그대로 남아 있다.**

→ **둘 다 짚어주는 설계가 맞다.**

### 6.4 앱 기록의 현재 상태 — 스크롤백 한도에 도달

멤버 15명 중 **6명의 기록이 이미 잘려 있다.** 잘린 6명은 예외 없이 기록이 대화 도중에서
시작한다(첫 줄이 "shell 실행", "updateTodos" 같은 조각). 남아 있는 사용자 발화는 6명 중
4명이 **0~1개**다. 사용자 발화는 대화 앞쪽에 몰려 있어 **가장 먼저 지워졌다.**

원인은 보관 한도가 "대화 개수"가 아니라 **"기록 조각 개수"**로 걸려 있는 것:

| 멤버 | 실제 대화 | 도구 실행·상태 표시 |
|---|---|---|
| main | 168개 (21%) | 632개 (79%) |
| n2-transcript | 79개 (10%) | 721개 (90%) |

**도구를 많이 쓴 멤버일수록 "왜 이 일을 하고 있었는지"를 먼저 잃는다.**

## 7. 곁가지 — 기록 보관·표시

> **심각도 정정 (2026-08-03).** 이 절은 처음에 "선결 과제 — 진행 중인 데이터 손실"로
> 썼다가 낮춰 잡았다. 그 판단은 **"앱 기록을 인계에 쓴다"는 전제(D1 이전)** 에서 나온
> 것이고, 하네스 원본을 쓰기로 한 D3 이후에는 **연속성에 영향이 없다.** 결정이 바뀌면
> 거기 딸린 문제의 무게도 다시 재야 하는데 한 박자 늦었다.
>
> 정확한 성격은 "데이터 손실"이 아니라 **"스크롤백 한도 + 그 한도를 숨기는 표시"** 다.
> 앱 기록은 화면용 사본이고 원본은 하네스에 따로 있다. 아래 1번(종류별 보존)을 하면
> 같은 한도로 훨씬 오래 남아 문제 자체가 크게 준다.
>
> **좁게 남는 것 하나**: 아래 3번의 표시 결함은 원본이 있든 없든 남는다.
>
> *(2026-08-03 추가 정정: 한때 "Cursor 멤버는 원본을 못 이어 진짜 손실"이라고 적었으나,
> §6.2 에서 Cursor 원본도 확보 가능함을 확인해 그 항목은 사라졌다.)*

1. **종류별 보존** — 대화는 오래, 도구 실행 결과 원문은 최근 것만. 저장량을 늘리지 않고도
   대화를 몇 배 오래 보관한다.
2. **잘린 자리에 표식** — 몇 개를 버렸는지 기록하고, 기록 맨 앞에 남긴다. 화면에도,
   인계받는 모델에게도 **같은 사실**이 전달된다.
3. **"이전 대화 N개 더 보기"의 표시 정정** — 이 버튼은 데이터를 더 불러오는 것이 아니라
   **이미 가진 것을 더 그리는** 기능이다(처음 150개만 그리고 누를 때마다 150개씩). 그래서
   "N개 숨김"을 사용자는 "남은 전부"로 읽지만 실제로는 "아직 안 그린 개수"다. 끝까지
   누르면 대화의 시작이 아니라 **잘린 단면**이 나오는데 아무 표시가 없다. → 끝에
   *"여기부터 이전 기록은 보관 한도로 정리되었습니다"*를 띄운다.

> 표식이 생기면 자연스러운 연장선이 열린다 — 더보기의 끝에서 **하네스 원본으로
> 이어붙이기**. v1 범위는 아니지만, 표식을 지금 제대로 두면 그 자리에 붙일 수 있다.

## 8. 범위

### v1

1. 하네스 잠금 해제 + 교체 경고("연속이 아니라 재구성")
2. **상시층** 주입 — 모든 멤버, 교체 무관
3. **1회층** 주입 — 교체 직후, 원본 경로 목록 + 앱 기록 경로 + 읽기 지침
4. 원본 경로 해석 — 멤버 → 세션 번호 목록 → 파일 경로(시간순). 못 찾으면 **못 찾았다고 표시**
5. 종류별 보존 + 잘림 표식 + 더보기 끝 표시 (§7)
6. 재시작 시 버려지는 대기 메시지 — 이관/취소를 사용자 선택으로
7. UI 와 동일한 경로를 자동화 API 로도 노출 + `docs/API.md` 갱신
8. 실앱 검증 — 실제로 Claude → Codex 교체, 첫 턴 토큰을 원장에서 확인,
   그리고 **20턴 뒤 "아까 그거" 질문에 실제로 찾아보는지** 확인

### 범위 밖

- 요약 모델 (D1)
- 전용 조회 도구/MCP (D2)
- 읽기 전용 파생 파일 — **판단 유보.** v1 의 실측 토큰량을 보고 다시 판단한다.
  (앱 기록이 pretty JSON 이라 평문 대비 2~3배 비싸고, 도구 결과가 한 줄로 뭉쳐 있어
  "안 읽겠다"는 지시로 통제되지 않는 위험이 남는다)
- 더보기 끝에서 하네스 원본 이어붙이기
