# 성능 조사 보고서 — 입력 지연·스크롤 저하와 성능 API 보강 계획 (2026-09-29)

- 대상: 실행 중인 설치본 **v0.18.0** (Electron 33.4.11 / Chrome 130), 창 5개, 세션 18개(응답 중 7개)
- 증상(사용자 보고): 입력이 지연되고, 스크롤이 가끔 크게 느려짐
- 방법: 앱을 재시작하거나 조작하지 않고 로컬 자동화 API로만 측정
  - `GET /api/perf` (`deep=1`, `disk=1` 포함), `POST /api/perf/capture` (창별·메인 CPU 프로파일)
  - `POST /api/perf/record/start|stop` — 2초 간격 12분, 368샘플
  - `POST /api/measure?window=<id>` — 창별 DOM 구성
  - 프로파일의 minify된 함수명은 설치본 `app.asar`를 풀어 번들 위치로 역추적
- 코드 기준: `v0.18.0`. 아래 원인 파일들은 `v0.18.1`(현재 master)에서도 바뀌지 않았다.

> "추정"이라고 적은 값은 실측하지 않았다. 구현 시 `/api/perf/record`로 켠 전후를 비교해 확인해야 한다.

## 1. 결론

느려짐은 원인 하나가 아니라 세 가지가 겹친 결과다.

| 증상 | 원인 | 확정 수준 |

## 2. 원인 상세

### 2.1 BrowserPane의 상시 rAF 루프 — 입력 지연 주원인

- 위치: `src/renderer/workbench/BrowserPane.tsx` — `sync()`(83행)가 `requestAnimationFrame`으로 자신을 계속 예약하고, 프레임마다 `overlayCrosses()`(16행)를 호출한다.
- `overlayCrosses()`는 셀렉터 18개를 합친 `document.querySelectorAll(APP_OVERLAYS)`와 매치된 요소마다 `getBoundingClientRect()`를 실행한다. 패널이 움직이지 않아도 멈추지 않는다.
- 실측 (win-1, 8초 CPU 프로파일)

  | 항목 | 값 |
  |---|---|
  | 메인 스레드 사용률 | 90% |
  | `querySelectorAll` self time | 3,888ms (49%) |
  | `getBoundingClientRect` | 247ms |
  | React 렌더링 | 수십 ms |
  | 렌더러 프로세스 CPU | 80~103% (코어 하나를 계속 사용) |

- 번들 역추적: 프로파일의 `My`(transcriptEvents-*.js 329:692)는 `overlayCrosses`, `P`(329:1789)는 `sync`.
- 대조군: 브라우저 패널이 없는 win-2와 win-4는 평상시 메인 스레드 사용률 3~5%. 브라우저 패널은 앱 전체에서 win-1의 `tree-shop` 멤버 하나뿐이었다.
- 비용은 DOM 크기에 비례한다. win-1 요소 15,620개 중 **15,049개(96%)가 트랜스크립트 3개 안**에 있고, 4,729개가 SVG 아이콘 내부다.
- 기존 `longTasks` 지표로는 **보이지 않는다.** 프레임당 약 8ms라 50ms 기준을 넘지 않기 때문이다.

수정 방향: rAF 폴링을 ResizeObserver, 레이아웃 변경 이벤트, 오버레이가 열릴 때 스스로 알리는 방식으로 교체한다.

### 2.2 트랜스크립트 wheel 리스너 — 스크롤 저하

- 위치: `src/renderer/workbench/Transcript.tsx` — Ctrl+휠 글자 확대를 위해 스크롤러에 `addEventListener("wheel", …, { passive: false })`.
- non-passive wheel 리스너가 있으면 그 영역의 휠 스크롤은 컴포지터가 바로 처리하지 못하고, 메인 스레드의 핸들러 실행을 기다린다. 메인 스레드가 2.1 때문에 90% 차 있고 스트리밍 반영이나 세션 목록 수신이 겹치면, 휠 입력이 줄을 서서 "가끔 크게" 느려진다.
- 관련 이력: `81d0784`(perf: move transcript rendering off the main thread)에서 `zoom`을 `transform`으로 바꿔 스크롤 지연을 고쳤으나, `bbe855c`(글자 선명도)에서 `.wb-transcript-scale`에 `zoom`이 되돌아왔다. 사용자의 글자 배율이 1.1이라 zoom이 적용 중이며, "작업 중" 점 애니메이션은 일시정지 예외라 메인 스레드에서 그려진다. 이 비용은 현재 API로 측정할 수 없다.

수정 방향: Ctrl+휠 확대를 main 쪽 입력 처리(Electron `zoom-changed` 등)로 옮기고 wheel 리스너를 passive로 전환한다.

### 2.3 메인 프로세스 이벤트 루프 멈춤

12분 녹화에서 `eventLoop.maxMs` 최대 **435.7ms**, p50 최대 87.6ms. 큰 멈춤이 있던 샘플은 대용량 디스크 쓰기 시점과 겹친다(예: 07:26:00, 쓰기 14.5MB, 435.7ms).

| 원인 | 실측 | 위치 |
|---|---|---|
| 트랜스크립트 전체 동기 재기록 | 12분간 **431MB**, 누적(24.7시간) **17.3GB**, 1회 평균 약 840KB | `partyRepository.writeTranscript` — append여도 `stored.slice + incoming`으로 파일 전체를 pretty JSON(`JSON.stringify(data, null, 2)`)과 `writeFileSync`로 다시 씀. 응답 중인 세션은 10초, 쉬는 세션은 1.5초마다 |
| 세션 목록 전체를 모든 창에 전송 | `session:list` **초당 약 12회**(최대 59회). 세션 18개에 약 400KB(대부분 `snapshot.slashCommands`), 창 5개 | `sessionManager.ts` — 어댑터 스냅샷마다 `scheduleSessionsBroadcast()`(33ms 병합) → `listSessions()` 전체 전송 |

- `partyGroups:list`와 `cwd:memberLocations` IPC가 `party:update`마다 호출되어 24시간에 약 5만 건. 20ms 안에 16회씩 몰리는 묶음이 있었다.
- 모든 IPC `invoke`가 info 레벨로 로그에 남아 하루 약 5.5만 줄(7MB).

## 3. 성능 API 보강 계획

조사 중 API가 답하지 못해 코드 읽기, 수동 스크립트, asar 추출로 우회해야 했던 지점들이다. 스크롤 전용 항목(스크롤 벤치마크, 스크롤 차단 리스너 목록, 프레임·스크롤 지연)은 **범위에서 제외**했다.

### 3.1 공통 원칙

1. **상시 수집은 정수 카운터와 고정 크기 요약만** 한다. 목록이나 원본은 쌓지 않는다(현재 `longTasks`와 같은 방식).
2. **무거운 수집은 요청하거나 녹화 중일 때만** 돌리고, 시간 상한을 둔다.
3. **디스크에 쓰는 것은 캡처 파일뿐**이며, 총 바이트 상한 안에서 자동으로 지운다.
4. 새 지표를 `GET /api/perf`의 메모리 버킷 순회에 끼워 넣지 않는다. 카운터는 순회 없이 바로 읽는다.

기준으로 쓴 현재 비용(실측):
- `countEvent`: Map에 정수 누적. 비용은 사실상 0이고 디스크에 쓰지 않는다.
- `GET /api/perf` 1회 **160ms**, `deep=1` **560ms**. 대부분 창별 메모리 버킷 순회 시간이다. 2초 간격 녹화의 자체 비용은 win-1 기준 CPU 약 1.6%.
- CPU 프로파일 파일 60~90KB, 종류별 최근 2개 보존(`KEEP_PER_KIND = 2`). 힙 스냅샷은 창 JS 힙(270~330MB)에 비례해 수백 MB로 추정.
- 배포본에 소스맵 없음. 렌더러 번들 2.0MB.

### 3.3 1차 범위 — 기능 상세

#### A. 프로파일 요약 (`POST /api/perf/capture` 응답 확장)

- **무엇:** CPU 프로파일을 캡처한 뒤 파일 경로만 주는 대신, 분석 결과를 함께 반환한다.
  - `busyPct` — 샘플 중 `(idle)`이 아닌 비율
  - `topSelf` — self time 상위 N개 함수(이름, 번들 파일, 줄:열, ms, %)
  - `topStacks` — 상위 N개 호출 스택(깊이 8 정도로 자름)
- **왜 필요:** 이번 조사에서 가장 오래 걸린 단계다. 분석 스크립트를 직접 짜고 minify된 이름을 asar에서 찾아 역추적했다. 어떤 원인이든 "어느 함수가 CPU를 먹나"는 매번 묻는다. 에이전트가 API만으로 QA한다는 프로젝트 원칙과도 맞는다.
- **성능·디스크:** 90KB 안팎의 JSON 파싱 한 번이라 캡처 1회당 수 ms(추정). 파일은 기존과 동일.
- **하지 않을 것:** 앱 안에서 소스맵으로 원본 위치를 복원하는 것. 소스맵 해석에 수백 ms 메인 스레드 멈춤(추정)이 생기고 설치본 크기도 는다. 원본 위치 복원은 **앱 밖 개발 도구**가 릴리즈 버전별 소스맵으로 처리한다(소스맵은 배포본에 넣지 않고 릴리즈 산출물로 보관).

#### B. 메인 루프 멈춤 원인과 동기 fs 시간 (`GET /api/perf` → `main`)

- **무엇:**
  - 동기 fs 작업의 횟수와 **소요 ms**(합계, 최대)를 작업 이름별로 센다. 대상은 이미 단일 지점으로 모여 있는 곳부터: `partyRepository.writeJsonAtomic`(쓰기), `readJsonSurvivingWrite`(읽기), 설정 저장.
  - 이벤트 루프 멈춤 기록: 기존 `eventLoop.maxMs`에 더해, 기준(예: 100ms)을 넘는 멈춤이 있었을 때 **그 시점에 실행 중이던 작업 이름**을 최근 N건만 고정 크기 링버퍼로 보관한다. 작업 이름은 IPC 핸들러, 저장소 쓰기, 세션 브로드캐스트 같은 주요 진입점에서 "현재 작업" 변수를 설정하고 해제하는 방식으로 붙인다.
- **왜 필요:** 메인이 멈추면 모든 창이 멈춘다. 저장소는 파티와 대화가 쌓일수록 커지므로 시간이 갈수록 재발하는 종류다. 이번에도 436ms 멈춤과 디스크 쓰기의 관계는 샘플 시각을 맞춰 추정했을 뿐이다.
- **성능·디스크:** 호출마다 `performance.now()` 두 번과 정수 누적이라 무시할 수준. 메모리에만 보관.
- **하지 않을 것:** 멈춤을 잡으려고 상시 CPU 프로파일링을 켜는 것. 샘플링 프로파일러는 상시로 켜면 수 % 부하가 생긴다.

#### C. 입력 지연 (`GET /api/perf` → `windows[].input`)

- **무엇:** 렌더러에서 `PerformanceObserver({ type: "event", durationThreshold: 16 })`로 키보드, 포인터, 클릭 이벤트의 입력 지연(input delay)과 처리부터 화면 반영까지의 전체 시간을 수집한다. 보관은 `count`, `maxMs`, `p95Ms`(고정 크기 히스토그램), `lastAt`만.
- **왜 필요:** 사용자가 느끼는 증상 자체를 재는 유일한 지표다. 원인 지표가 아니라 **결과 지표**라서 수정 전후 비교와 회귀 확인에 계속 쓴다. 지금은 "입력이 늦다"를 수치로 증명할 수 없다.
- **성능·디스크:** 브라우저가 기준을 넘는 이벤트만 알려 주므로 무시할 수준. 디스크 없음.

#### D. Long Animation Frames 원인 (`GET /api/perf` → `windows[].longFrames`)

- **무엇:** `PerformanceObserver({ type: "long-animation-frame" })`(Chrome 123+, Electron 33 지원)로 50ms 넘는 프레임과 그 원인 스크립트(`scripts[].sourceURL`, `sourceFunctionName`, `invoker`, `duration`)를 수집한다. 보관은 횟수, 최댓값, 원인 스크립트별 누적 ms 상위 N개.
- **왜 필요:** 기존 `longTasks`는 "막혔다"만 알고 "누가"를 모른다. 오늘 원인 없이 넘어간 win-4의 947ms, win-2의 547ms 멈춤이 이 항목으로 설명될 수 있었다.
- **한계:** 50ms 기준이라 2.1처럼 **작은 부하가 계속되는 경우는 못 잡는다.** 그 경우는 F가 담당한다.
- **성능·디스크:** 긴 프레임에서만 발생하므로 무시할 수준. 디스크 없음.

#### E. 캡처 대상별 보존 (`perfCapture.ts` 보존 정책)

- **무엇:** 현재 `KEEP_PER_KIND = 2`는 종류(cpu/heap)별 최근 2개만 남긴다. 그래서 win-2와 win-4 프로파일을 연달아 뜨면 앞의 것이 바로 지워진다(이번 조사에서 실제로 발생).
  - CPU 프로파일: **대상(창 id, main)별** 최근 2개 보존.
  - 힙 스냅샷: 지금처럼 종류별 보존을 유지하고 **총 바이트 상한**(예: 1GB)을 추가.
- **성능·디스크:** CPU 프로파일은 대상 6개 × 2개 ≈ 1MB로 무해. 힙까지 대상별로 하면 6개 × 2개 × 수백 MB ≈ 수 GB(추정)라 하지 않는다.

### 3.4 2차 범위 — 녹화 전용

#### F. 녹화 중 창별 메인 스레드 사용률

- **무엇:** `/api/perf/record` 샘플마다 창별 CDP `Performance.getMetrics`의 누적 `TaskDuration`과 `ScriptDuration` 차이를 기록해, 구간별 메인 스레드 사용률(%)을 남긴다. 현재 `deep=1`의 400ms 순간값을 녹화 구간 전체로 확장하는 것이다.
- **왜 필요:** 50ms 미만 부하가 계속되는 경우(2.1)를 잡는 범용 지표다. 원래 안이던 "상주 루프 목록"은 이번 원인에만 맞춘 지엽적 항목이라 이것으로 대체한다.
- **성능·디스크:** 샘플마다 창에 디버거를 붙였다 떼야 한다. `deep=1` 1회가 560ms이므로 2초 간격이면 체감 부하가 생길 수 있다(추정). **간격 10초 이상**을 기본으로 하고 녹화 중에만 돈다. 디스크 없음(녹화는 기본 메모리 보관).
- **주의:** 디버거가 붙어 있는 동안에는 사용자가 DevTools를 열 수 없다. 샘플 사이에는 반드시 뗀다.

#### G. IPC 채널별 바이트

- **무엇:** `ipc.send.<channel>` 횟수 옆에 `ipc.bytes.<channel>`을 추가한다.
- **왜 필요:** main이 상태를 통째로 push하는 구조라서, 페이로드가 불어나는 문제(이번의 `slashCommands` 400KB × 초당 12회 × 창 5개)는 기능이 늘 때마다 다시 생긴다. 횟수만으로는 크기가 보이지 않는다.
- **성능·디스크:** Electron은 직렬화된 크기를 알려 주지 않으므로 한 번 더 직렬화해야 잰다. 상시로 켜면 session:list만으로 메인에서 초당 수십 ms(추정)가 든다. 따라서:
  - **녹화 중에만** 측정하거나 **표본 1/N**(예: 1/10, 수 ms/s)으로 잰다.
  - 여러 창에 같은 페이로드를 보낼 때는 한 번만 재고 창 수를 곱한다.

### 3.5 제외 항목과 이유

| 항목 | 제외 이유 |
|---|---|
| 스크롤 벤치마크, 스크롤 차단 리스너 목록, 프레임·스크롤 지연 | 요청에 따라 스크롤 관련 항목 제외 |

### 3.6 검증 방법

각 항목을 구현한 뒤 실제 앱 프로세스를 띄워 다음을 확인한다.
1. 기능 확인: 새 필드가 실제 값을 돌려주는지(0과 "측정 안 함"을 구분).
2. 비용 확인: 같은 조건에서 켠 경우와 끈 경우를 `/api/perf/record`로 각 5분 이상 비교해 창별·메인 CPU 차이가 오차 범위 안인지.
3. 디스크 확인: `GET /api/perf/captures`와 perf 폴더 크기가 상한을 넘지 않는지.
4. `docs/API.md`, `src/shared/apiSpec.ts`, 라우트 테이블을 함께 갱신.

## 4. 성능 수정 우선순위 (API 보강과 별개)

1. BrowserPane rAF 폴링 제거 — 입력 지연에 직접 효과.
2. 트랜스크립트 wheel 리스너 passive 전환 — 스크롤 저하에 직접 효과.
3. `session:list` 전체 브로드캐스트를 델타나 `session:snapshot`으로 대체하고 `slashCommands`를 목록에서 제외.
4. 트랜스크립트 저장을 실제 append 또는 비동기 쓰기로 바꾸고, `repository.read()` 결과를 캐시.
