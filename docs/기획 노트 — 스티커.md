# 기획 노트 — 스티커 (Stickers)

> 작성: 2026-08-04
> 출처: [아이디어 E-3](아이디어/아이디어.md) 에서 분리. 아이디어 문서에는 요약과 이 문서로의
> 포인터만 남긴다.
> 상태: **설계 확정, 구현 착수 전.** 아래 §12 를 제외한 모든 항목은 사용자와의 논의로 정해졌다.
> 개정 2026-08-05: 저장(풀)과 사용(팩)을 분리했다 — §4.1. 기능 on/off 설정을 추가했다 — §8.1.
> 팩 전역 활성을 없애고 **멤버별 팩 선택(다중)** 으로 바꿨다 — §4.2.

## 1. 개요

**멤버가 대화창에 스티커(디시콘 같은 이모티콘)를 붙일 수 있게 한다.**

멤버가 MCP 도구를 부르면 앱이 그 스티커를 **단독 메시지**로 대화창에 출력한다. 카카오톡에서
이모티콘을 보내는 것과 같은 모양이고, 글 사이에 끼우는 인라인 이모지는 다루지 않는다.

스티커 자산은 앱이 갖지 않는다. **사용자가 자기 팩을 설정에서 넣는다.**

## 2. 배경 · 문제

- 멤버는 지금 **글로만** 말한다.
- 워크벤치는 여러 멤버의 대화가 동시에 흐르는 **훑어보는 화면**이다. "다 됐습니다" 한 줄보다
  스티커 한 장이 빠르게 읽히고, 누가 무슨 상태인지 스캔하기 쉬워진다.
- 이미 멤버마다 고유색이 있어 시각 언어의 절반은 깔려 있다.

**핵심 난점은 "어떻게 그리느냐"가 아니라 "모델이 적절한 스티커를 어떻게 고르느냐"다.**
모델은 그림을 본 적이 없다. 이 문서의 절반은 그 문제를 다룬다.

## 3. 범위

### 3.1 하는 것

- 사용자가 스티커를 **풀**에 등록한다(앱 전역, AgentParty 전체 공유).
- 등록할 때 비전 모델이 **이름·태그·설명**을 제안하고, 사용자가 검수한다.
- 사용자가 풀에서 골라 **팩**을 짜고, **멤버마다 쓸 팩을 고른다**(다중).
- 멤버는 자기에게 할당된 팩 안에서만 고른다.
- 멤버가 도구로 **카탈로그를 조회**하고 **스티커를 전송**한다.
- 전송된 스티커는 **자기 대화창에** 단독 메시지로 표시된다.

### 3.2 1차에서 하지 않는 것

| | 왜 미루나 |
|---|---|
| **사용자가 스티커 보내기** | 입력창 피커가 새로 필요하다. 원래 동기가 "멤버 상태를 빨리 읽기"였고 사용자는 글이 더 빠르다. |
| **멤버 간 `send`·디스코드 전달** | 받는 멤버는 어차피 텍스트로만 받으므로 화면과 모델이 받는 것이 또 갈린다. |
| **움짤 해석** | 렌더는 원본 그대로 재생하되, **캡션은 첫 프레임 기준**(§5.2). 고도화되면 여러 프레임으로. |
| **zip 팩 업로드** | 압축 해제 의존성이 붙는다. 폴더·드래그앤드롭으로 충분하다. |
| **스티커 개별 비활성** | 팩에서 빼면 곧 비활성이라 별도 스위치가 필요 없다. |

## 4. 데이터 모델

### 4.1 풀과 팩 — 저장과 사용을 나눈다

**등록은 풀에 쌓는 일이고, 팩은 그 풀에서 골라 짠 사용 목록이다.** 둘은 별개의 축이다.

```
Sticker {                       Pack {
  id        <set>/<name>          id        슬러그
  set       출처 (§4.4)           name      표시 이름
  name      표시 이름             members   Sticker.id[]   ← 참조만
  tags      string[]            }
  desc      string
  file      복사 보관된 원본     Member.stickerPacks = Pack.id[]   ← §4.2
  state     ready | 미분류
}
```

- **스티커 ↔ 팩은 M:N.** 한 장이 여러 팩에 들어갈 수 있고, **아무 팩에도 없을 수 있다.**
  팩에 없는 스티커는 풀에 보관만 되고 조회에 나오지 않는다(§6.2).
- **팩에서 빼는 것은 삭제가 아니다.** 참조만 끊긴다. 풀에서 지워야 실제로 사라진다(§7.2).
- **캡션은 풀에 한 번만 붙는다.** 팩이 저장 단위였다면 같은 그림을 두 팩에 넣을 때 캡션 비용을
  두 번 치렀다. 지금은 등록 시 1회이고, 팩을 몇 개 짜든 늘지 않는다.
- **저장 위치는 앱 전역**(`userData/stickers/`). 워크스페이스나 파티로 나누지 않는다.
  스티커는 프로젝트 산출물이 아니라 사용자 취향이라, 프로젝트를 옮길 때마다 다시 넣고 캡션
  비용을 다시 치르는 것이 부자연스럽다.
- **원본 이미지는 복사해서 보관한다.** 사용자가 원본 폴더를 옮기거나 지워도 풀이 깨지지 않아야 한다.
- **팩 자체에는 활성 플래그가 없다.** 팩은 그냥 만들어 두는 것이고, 켜고 끄는 일은 멤버 쪽에서
  한다(§4.2). 전역 활성과 멤버 할당이 둘 다 있으면 "팩은 껐는데 멤버엔 붙어 있다" 같은 상태가
  생기고, 스티커가 안 나갈 때 어느 쪽이 원인인지 사용자가 두 군데를 봐야 한다.

팩이 사용 단위이므로 **"이 멤버는 이 캐릭터"** 도, **"업무용은 점잖은 것만"** 도 같은 도구로
표현된다. 캐릭터별로 나누고 싶으면 캐릭터마다 팩을 짜면 되고, 캐릭터를 섞고 싶으면 섞으면 된다 —
저장 구조가 그 선택을 미리 강요하지 않는다.

### 4.2 멤버 → 팩 (다중)

**어떤 팩을 쓸지는 파티 멤버 설정에서 멤버마다 고른다. 다중 선택이다.**

```
Member.stickerPacks = ["캐릭터A", "리액션"]     // 없으면 그 멤버는 스티커를 쓰지 않는다
```

- 여기 담긴 팩들의 **합집합**이 그 멤버의 조회 범위다(§6.2). 한 스티커가 두 팩에 겹쳐 있어도
  결과에는 한 번만 나온다.
- **빈 목록이 곧 그 멤버의 off** 다. 멤버별 on/off 스위치를 따로 두지 않는다 — §8.1 의 전역
  스위치가 기능 자체를 감추는 층이고, 여기는 "누가 무엇을 쓰나"의 층이다.
- 팩을 삭제하면 그 팩을 참조하던 멤버들에서도 **함께 걷어낸다.** 죽은 id 를 남기지 않는다.

이게 원래 §3.2 에서 "나중에"로 미뤄뒀던 항목인데, 앞당겨도 비용이 거의 없다 — 조회가 이미
"팩 목록의 합집합"이라 목록을 어디서 얻느냐만 바뀐다.

### 4.3 스티커 — 이름 1 · 태그 다수 · 설명 1

셋이 하는 일이 다르고, **검수 무게도 다르다.**

| 필드 | 역할 | 개수 | 검수 |
|---|---|---|---|
| **이름** | 호출 키의 뒷부분 | 1 | **필수** — 출처 안에서 유니크, 겹치면 등록 단계에서 수정을 요구한다 |
| **태그** | 검색 | 다수(8~12 권장) | 느슨 — 훑고 이상한 것만 지운다 |
| **설명** | 후보 중 최종 선택 | 1 | **필수** — 톤이 여기 담긴다 |

**태그는 통제하지 않는다. 일부러 다양하게 단다.**
LLM 은 파일에서 뭘 찾을 때 한 단어로 검색하지 않는다. 스티커도 같다. 동의어를 많이 달수록
적중률이 올라간다. 반대로 **어휘를 표준화하면 어휘 밖 단어에서 0건이 난다** — 통제가 recall 을
깎는다. (설계 초기에 "권장 어휘로 표준화" 안이 있었으나 이 이유로 접었다.)

**설명에는 그림 안에 적힌 글자를 그대로 넣는다.**
디시콘은 **스티커 자체가 하나의 발화**다. 모델이 "짱조타!"라고 쓰여 있다는 걸 모르면 엉뚱한
맥락에 붙인다.

> 은발 소년이 활짝 웃으며 엄지를 치켜든 그림. **"짱조타!"** 라고 적혀 있다.
> 결과가 마음에 들 때 강하게 긍정하는 용도.

⚠️ **웃는 그림인데 뜻은 비아냥**인 경우가 디시콘엔 흔하고, 비전 모델이 자주 놓친다.
반어·비꼼이 사람 검수가 실제로 값을 하는 자리다.

**캡션 언어는 사용자 언어**를 따른다. 앱에 i18n 이 없으므로 캡션 설정에 언어 필드를 두고
기본값을 OS 로케일에서 채운다(현재 한국어). 자동 판별을 숨기지 않고 눈에 보이는 값으로 둔다.

### 4.4 호출 키 — 출처 네임스페이스

한 스티커가 여러 팩에 속하므로 **키를 팩에 매달 수 없다.** 키는 풀에서 유일해야 한다.
그렇다고 풀 전체를 평평한 이름 하나로 두면 캐릭터가 늘 때마다 "짱조타"가 계속 충돌한다.

**등록 시의 폴더명을 `출처(set)`로 남겨 이름공간으로만 쓴다.**

```
id = "<set>/<name>"      예: "캐릭터A/짱조타"
```

- **출처는 이름공간일 뿐 사용 단위가 아니다.** 사용 단위는 팩이다. 같은 출처의 스티커가
  서로 다른 팩에 흩어져도 되고, 한 팩이 여러 출처를 섞어도 된다.
- 유니크 검사는 **출처 안에서만** 한다. 새 캐릭터를 넣을 때 기존 이름과의 충돌을 신경 쓸 일이 없다.
- 조회 결과에 키가 그대로 실려오므로 모델은 복사만 하면 된다.
- 사람이 읽을 수 있는 슬러그라 모델이 기억하기도 쉽다(해시를 쓰지 않는 이유).
- 출처는 등록 후에도 고칠 수 있다. 고치면 **이미 대화에 나간 키가 깨지므로**, 옛 키를 새 키로
  넘겨주는 별칭을 남긴다 — 자리표시자(§7.2)는 "삭제" 신호여야지 이름 바꿨다고 뜨면 안 된다.

## 5. 등록 흐름

### 5.1 풀에 넣기

- **폴더 선택**과 **드래그앤드롭** 둘 다 지원한다. 넣은 스티커는 **풀에 쌓인다.**
- 출처(§4.4)는 폴더명에서 자동으로 채우고 사용자가 고칠 수 있다. 파일 몇 장만 떨어뜨려
  폴더가 없으면 사용자에게 출처를 묻는다.
- 파일명이 `짱조타.png` 처럼 의미가 있으면 **이름 제안의 힌트**로 쓴다.
- 받는 포맷은 기존 `IMAGE_MEDIA_TYPES`(png/jpg/jpeg/gif/webp)를 따른다.
- **등록은 팩을 만들지 않는다.** 다만 방금 넣은 것을 바로 쓰고 싶은 것이 흔하므로,
  등록 완료 화면에서 **"이 출처로 팩 만들기"** 를 한 번의 클릭으로 제안한다(선택).

### 5.2 캡션 자동 제안

200장을 손으로 다는 것은 불가능하다. **제안이 없으면 기능 자체가 성립하지 않는다.**

- 비전 모델이 이미지를 보고 `{이름, 태그[], 설명}` 을 제안한다.
- 모델은 **설정에서 사용자가 고른다** — Message Gate 리뷰어와 같은 `{model, effort}` 모양을
  재사용한다. 목록은 **비전 가능한 모델로 필터**한다.
- **움짤은 첫 프레임만** 본다. 렌더는 원본 그대로 재생하되 해석은 정지 이미지 기준이다.

### 5.3 즉시 사용 — 검수는 선택

**넣으면 캡션 생성이 백그라운드로 돌고, 끝난 것부터 바로 쓸 수 있다.**

```
드롭
  ↓  (진행률 표시, 화면을 닫아도 계속 돈다)
 ✓ 12/200   ← 이 12장은 이미 사용 가능
  ↓
완료 → 그리드에서 훑어보며 수정(선택)
```

사용자를 기다리게 하지 않고, 200장 검수 화면에서 지치지도 않는다. 대가는 **검수 안 된 설명
때문에 엉뚱한 스티커가 가끔 나갈 수 있다**는 것이고, 그때 고치면 된다.

### 5.4 실패 처리

⚠️ 첫 프레임이 비어 있는(페이드인) 움짤 등은 캡션이 안 나온다.

- 실패한 스티커는 **"미분류"로 눈에 보이게** 남기고 **재시도 버튼**을 준다.
- 조용히 빠뜨리지 않는다 — 사용자는 넣었다고 믿는데 모델은 못 쓰는 상태가 최악이다.
- 미분류 스티커는 **팩에 들어 있어도** 조회 결과에 나오지 않는다(뜻을 모르므로 고를 수 없다).
  캡션이 채워지면 팩 편집을 다시 하지 않아도 저절로 조회에 합류한다.

## 6. 사용 흐름 — 멤버

### 6.1 도구 두 개

```js
sticker-catalog({ query?: string[], limit?: number })
// query 를 여러 단어로 받아, 태그가 겹치는 순으로 상위 N장 반환
// → [{ key, name, description, tags }]   ← 팩은 싣지 않는다(한 장이 여러 팩에 속할 수 있고,
//                                          모델이 알 필요도 없다)
// query 생략 시: 자기 팩마다 대표 몇 장 (뭐가 있는지 훑는 용도)

sticker({ key: string })
// 대화창에 단독 메시지로 출력
// → { ok: true, shown: { key, name, description } }
```

**`query` 가 배열인 것이 이 설계의 핵심이다.** 모델이 실제로 검색하는 방식 그대로라, §4.3 의
태그 다양성이 그대로 적중률로 이어진다. 모델이 태그 어휘를 미리 알 필요도 없다 — 떠오르는 말을
몇 개 던지면 된다.

기본 `limit` 은 **8**. 설명 한 줄이 ~50토큰이므로 400토큰 언저리다.

### 6.2 조회 범위와 규칙

**조회 대상은 그 멤버에게 할당된 팩들의 합집합이다**(§4.2). 같은 스티커가 두 팩에 들어 있어도
결과에는 한 번만 나온다. 자기 팩에 없는 스티커는 그 멤버에게 **없는 것과 같다.**

⚠️ **조회 범위는 부르는 멤버에 따라 다르다.** 카탈로그를 전역 캐시 하나로 만들면 A 멤버의 결과가
B 멤버에게 새는데, 스티커는 캐릭터를 나누려고 쓰는 기능이라 이 오염이 곧 기능 실패다.
캐시를 둔다면 **팩 단위로 캐시하고 멤버별로 합치는** 모양이어야 한다.

- **0건이면 빈 배열을 정직하게 반환**하고 가까운 태그를 힌트로 준다. 아무거나 하나 골라주지 않는다.
- 없는 `key` 로 `sticker` 를 부르면 `{ok:false}` + "카탈로그로 찾아라" 안내.
- 풀에는 있지만 **자기 팩에 없는** 스티커도 같은 처리. ⚠️ 이때는 **"네 팩에 없다"고 이유를 밝힌다** —
  키는 맞는데 안 나가는 상황이라, 이유를 안 주면 모델이 같은 키로 계속 재시도한다.
  다른 멤버가 쓴 스티커를 보고 따라 부르는 경우가 실제로 생긴다(대화창에 그림이 보이므로).

### 6.3 지시문 주입

멤버 지시문은 [partyBridge.ts](../src/core/partyBridge.ts) 에서 **문자열 배열을 join** 해
만든다(`:504-552`). 스티커 섹션을 **조건부**로 끼운다.

**기능이 꺼져 있거나(§8.1) 그 멤버에게 할당된 팩이 없으면 섹션 자체가 안 들어간다 — 상시 토큰이
0 이다.** 도구 등록도 같은 조건을 따른다. 지시문만 빼고 도구를 남기면 모델이 도구 목록을 보고
스스로 부르는 일이 생기고, 그러면 "안 쓴다"가 참이 아니게 된다.

조건이 **멤버마다 다르다**는 점이 중요하다. 같은 파티에서도 팩을 받은 멤버만 스티커 도구를 갖고,
나머지는 도구도 지시문도 없다. 스티커를 안 쓰는 멤버가 남의 기능 때문에 토큰을 내지 않는다.

문구 초안(지시문은 영어로 통일되어 있다):

```
## Stickers — showing state at a glance
- Your party has sticker packs. `sticker-catalog` finds one, `sticker` posts it into your
  conversation as a standalone message.
- Mainly for **turn-closing state** — done, blocked, needs a decision. In a screen the user
  skims with several members running, a sticker reads faster than a line saying the same
  thing. Reacting to something is fine too, when it fits.
- Search with SEVERAL words at once (`query: ["칭찬","좋음","최고"]`). Tags are deliberately
  redundant, so more words means better hits. Read the descriptions and pick — don't take
  the first result.
- A sticker replaces a short line, not the substance. Post it alongside what you were going
  to say, not instead of it.
```

**상태 신호가 기본, 반응도 허용**이라는 결정이 이 문구에 담긴다.

### 6.4 빈도

빈도 문구도 같은 자리에 넣는다.

⚠️ 다만 **프롬프트는 soft 다.** "한 턴에 하나만"이라고 써도 모델이 두 개 붙일 수 있다. 실제로
상한을 걸어야 할 때가 오면 **도구가 `ok:false` 로 거절**해야 진짜로 막힌다 — Message Gate 가
이미 그 형태(`partyBridge.ts:537`)라 관례도 있다. 지금 만들 것은 아니고, 프롬프트만으로 부족한
것이 드러나면 그때 그 자리로 간다.

## 7. 대화창 표시와 보존

### 7.1 트랜스크립트에는 키만 저장한다

대화 기록은 멤버마다 **파일 하나로 통째 저장**되고 턴마다 원자적으로 다시 쓰인다
([partyRepository.ts](../src/main/partyRepository.ts) `:114-167`). 여기에 base64 를 박으면
스티커 한 장당 수십~수백 KB 가 눌러앉고 **매 턴 그걸 다시 쓴다.** 같은 스티커를 100번 쓰면
100벌이 쌓인다.

```json
{ "kind": "sticker", "key": "캐릭터A/짱조타" }
```

그림은 렌더할 때 팩에서 꺼낸다. 스티커는 앱이 소유한 로컬 자산이라 URL 처럼 깨질 걱정이 없다.

### 7.2 팩에서 빼면 · 풀에서 지우면

**둘은 다르다.** 이미 대화에 나간 그림이 사라지는 것은 **풀에서 지웠을 때뿐이다.**

| 한 일 | 이미 나간 스티커 | 앞으로 |
|---|---|---|
| 팩에서 빼기 / 팩 삭제 / 멤버에서 팩 해제 | **그대로 보인다** (원본이 풀에 있다) | 조회에 안 나옴 |
| 기능 끄기(§8.1) | **그대로 보인다** | 도구·지시문 자체가 없음 |
| **풀에서 삭제** | **자리표시자**로 바뀜 | 사라짐 |

팩은 "앞으로 뭘 쓸까"의 문제라 지난 기록을 건드리면 안 된다. 반면 풀 삭제는 그 그림을 더 안 보겠다는
뜻이므로 과거까지 걷어내는 것이 맞다.

풀에서 지운 스티커는 이렇게 남는다.

```
┌──────────────┐
│ 삭제된 스티커 │
│ 짱조타        │
└──────────────┘
```

그림은 사라지지만 **이름이 남아 문맥은 읽힌다.**

⚠️ 풀에서 삭제할 때 **그 스티커가 든 팩이 있으면 목록으로 보여주고 확인을 받는다.** M:N 이라
사용자가 어디에 물려 있는지 모른 채 지우기 쉽다.

### 7.3 표시 방식

말풍선 없는 단독 메시지. **구체적인 크기·여백·클릭 동작은 디자인에서 정한다.**
다만 워크벤치는 멤버 패널이 여러 개 나란히 뜨므로 **고정 px 이 아니라 상한 + 패널 폭 비례**로
가야 좁은 패널에서 넘치지 않는다.

## 8. 설정 UI

### 8.1 기능 on/off

**스티커 기능 전체를 켜고 끄는 스위치를 설정에 둔다. 기본값은 꺼짐.**

- **끄면 스티커 설정 탭 자체가 노출되지 않는다.** 안 쓰는 사용자에게 설정이 한 칸 늘지 않는다.
  스위치는 탭 안이 아니라 **탭을 만드는 자리**(일반 설정)에 있어야 한다 — 탭 안에 두면 끈 순간
  스위치가 숨어 다시 켤 방법이 사라진다.
- 끄면 도구 등록과 지시문 주입이 함께 빠진다(§6.3). **이미 대화에 나간 스티커는 그대로 보인다.**
- 끄는 것은 **감추는 것이지 지우는 것이 아니다.** 풀과 팩은 그대로 남고, 다시 켜면 그대로 돌아온다.
- 실행 중인 멤버 세션에는 **다음 세션부터** 반영된다. 지시문은 세션 시작에 주입되므로 즉시
  적용되지 않는다 — ⚠️ 설정 화면에 이 사실을 적어야 한다. 조용히 안 먹히는 것으로 보이면 안 된다.

### 8.2 스티커 탭 (켰을 때만)

두 축을 그대로 화면으로 옮긴다 — **풀**(가진 것)과 **팩**(쓸 것).

- **풀** — 전체 스티커 그리드. 출처 필터, 태그·이름 검색, 미분류 배지.
  이름·태그·설명 인라인 수정, 개별 재캡션, 개별 삭제, **"어느 팩에 들어 있는지" 표시**.
- **스티커 추가** — 폴더 선택 / 드래그앤드롭 → 풀에 쌓임(§5.1)
- **팩 목록** — 든 스티커 수, 미분류 개수 배지, **이 팩을 쓰는 멤버 표시**.
  활성 체크박스는 없다 — 켜고 끄는 것은 멤버 설정에서 한다(§8.3).
- **팩 편집** — 풀을 보며 담기/빼기. 한 스티커가 여러 팩에 들어갈 수 있으므로
  **체크박스형 다중 소속**으로 보여야지, 옮기는 모양(드래그로 이동)이면 M:N 이 오해된다.
- **캡션 설정** — `{model, effort}` + 언어

### 8.3 파티 멤버 설정 — 쓸 팩 고르기

**멤버 설정에 "스티커 팩" 항목을 두고 팩을 다중 선택한다.** 모델·권한·게이트를 고르는 그 화면이다.

- 체크박스 목록. 고른 팩들의 합집합이 그 멤버의 조회 범위(§6.2)다.
- **아무것도 안 고르면 그 멤버는 스티커를 쓰지 않는다.** 별도의 멤버별 on/off 스위치는 없다.
- 팩이 하나도 없으면 목록 대신 **"먼저 팩을 만드세요"** 와 스티커 설정으로 가는 링크를 보여준다.
  빈 체크박스 목록만 있으면 사용자가 뭘 잘못했는지 알 수 없다.
- ⚠️ 지시문·도구는 세션 시작에 정해지므로 **실행 중인 멤버는 다음 세션부터** 반영된다(§8.1 과 같음).
  화면에 이 사실을 적는다.

⚠️ AGENTS.md 규칙대로 상단 퀵입력이 아니라 **화면 안의 제대로 된 폼/모달**로 만든다. 모달은
바깥 클릭이 아니라 **취소 버튼**으로 닫는다.

## 9. 자동화 HTTP API

AGENTS.md 규칙: UI 와 HTTP 가 **같은 `AppController` 메서드**를 통과하고,
[apiSpec.ts](../src/shared/apiSpec.ts) 와 [API.md](API.md) 에 등록한다.

경로도 **풀과 팩 두 축**으로 갈린다. 스티커는 팩 하위 자원이 아니라 **1급 자원**이고, 팩은
그 id 를 참조할 뿐이다.

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/api/stickers/settings` | 기능 on/off · 캡션 `{model, effort}` · 언어 |
| PATCH | `/api/stickers/settings` | 위 설정 변경 (§8.1 토글 포함) |
| GET | `/api/stickers/items` | **풀 전체** 목록 (출처·태그 필터, 캡션 진행 상태 포함) |
| POST | `/api/stickers/items` | 풀에 등록(경로 또는 파일들) → 출처 지정 |
| PATCH | `/api/stickers/items/:id` | 이름·태그·설명·출처 수정 |
| DELETE | `/api/stickers/items/:id` | **풀에서 삭제** (소속 팩이 있으면 응답에 알린다 §7.2) |
| POST | `/api/stickers/items/:id/recaption` | 재캡션 |
| GET | `/api/stickers/packs` | 팩 목록 |
| POST | `/api/stickers/packs` | 빈 팩 생성 (또는 초기 멤버 id 목록과 함께) |
| PATCH | `/api/stickers/packs/:id` | 이름 변경 |
| PUT | `/api/stickers/packs/:id/members` | **팩 구성 통째 교체** (스티커 id 배열) |
| DELETE | `/api/stickers/packs/:id` | 팩 삭제 (스티커는 풀에 남고, 멤버 참조는 함께 걷힌다) |
| PUT | `/api/party/members/:name/sticker-packs` | **그 멤버가 쓸 팩 통째 교체** (팩 id 배열) |
| GET | `/api/stickers/catalog?member=:name` | 멤버 도구와 같은 조회 (그 멤버 팩의 합집합) |
| POST | `/api/party/members/:name/sticker` | 멤버로서 스티커 전송 |

- 팩 구성과 멤버 할당 둘 다 담기/빼기를 각각의 엔드포인트로 두지 않고 **`PUT`으로 통째 교체**한다.
  편집 화면이 체크박스 다중 선택(§8.2·§8.3)이라 화면 모양과 그대로 맞고, 부분 갱신의 순서 경합이 없다.
- ⚠️ `catalog` 는 **`member` 가 필수다.** 범위가 멤버마다 다르므로(§6.2) 생략 시 전역으로
  넓혀주면 안 되고 오류여야 한다 — 조용히 넓힌 결과는 QA 가 실제와 다른 것을 검증하게 만든다.
- 마지막 둘은 멤버 도구와 **같은 경로**를 타야 QA 가 실제 사용자 경로를 검증할 수 있다.

## 11. 함정

- ⚠️ **도구 등록이 두 벌이다.** 한 쪽만 추가하면 특정 하네스에서 도구가 조용히 안 보인다.
  **기능 off 조건(§8.1)도 두 벌 모두에 걸어야 한다** — 한 쪽에만 걸면 껐는데 도구가 남는다.
- ⚠️ **참조가 두 단계라 어긋날 자리도 두 곳이다** — 팩→스티커, 멤버→팩. 풀에서 지운 id 가 팩에
  남거나 지운 팩 id 가 멤버에 남으면 조회에서 유령이 된다. 삭제 시 참조를 함께 걷어내고,
  그래도 남은 참조는 **조회 때 조용히 건너뛰지 말고 로그를 남긴다.**
- ⚠️ **조회 범위가 멤버마다 다르다.** 전역 카탈로그 캐시는 캐릭터 분리를 깨뜨린다(§6.2).
- ⚠️ **원격/WSL 엔진이 `party` 이벤트를 포워딩하지 않으면 UI 가 라이브 갱신되지 않는다.**
  기존에 겪은 함정이 그대로 적용된다.
- ⚠️ **트랜스크립트 cap** — 스티커도 블록 하나를 차지하므로 스크롤백을 먹는다.
  FEEDBACK #26(대화가 잘려나가는 문제)과 같은 자리.
- ⚠️ **캡션 비용은 원장에 기록하지 않기로 했다**(사용자 결정). 등록 화면에도 표시하지 않는다.
  나중에 "이달 토큰이 왜 이렇지"를 추적할 수 없다는 것을 알고 내린 결정이니, 되돌릴 때는
  이 항목을 먼저 읽을 것. **다만 생성 *실패* 는 계속 드러낸다**(§5.4) — 비용을 안 보여주는 것과
  실패를 숨기는 것은 다른 문제다.

## 12. 미결 · 확인 필요

- **비전 가능 여부 플래그** — [modelCatalog.json](../src/shared/modelCatalog.json) 에 vision
  플래그가 있는지 확인해야 한다. 없으면 추가가 선행된다(§5.2 의 모델 목록 필터가 여기 의존).
- **캡션 생성 중 앱 종료** — 재개할지, 처음부터 다시 돌릴지. 진행 상태를 풀에 저장하면 재개가 된다.
- **일괄 재캡션** — 모델을 바꾼 뒤 전량 다시 돌리는 버튼이 필요한지. 범위는 풀(출처 단위)이 자연스럽다.
- **새 멤버의 기본 팩** — 빈 목록으로 시작하면 멤버를 만들 때마다 지정해야 하고, 기본 팩을 두면
  안 원하는 멤버에도 붙는다. 파티 단위 기본값(새 멤버가 상속)이 절충안으로 보이나 미정.

## 13. 검토하고 접은 대안 — 모델에게 이미지를 직접 보여주기

"모델이 스티커 그림을 직접 보게 하자"를 검토했다. **토큰은 싸다** — 200×200 스티커 한 장이
Claude 기준 ~53토큰(면적/750), GPT `detail:low` 85토큰, Gemini 258토큰. 텍스트 캡션(~30토큰)의
2배도 안 된다. 접은 이유는 비용이 아니다.

1. **MCP 도구 설명·스키마는 문자열이라 이미지를 넣을 자리가 없다.** 현재 `McpToolResult` 도
   text 전용이다(`partyBridge.ts:555`). 도구 결과나 세션 시작 주입으로 우회할 수는 있으나
   배선이 확연히 무겁고, 스티커 하나 붙이는 데 왕복이 늘어난다.
2. **비용이 멤버 수 × 세션 수로 곱해진다.** 등록 시 1회 캡션은 팩 수명에 한 번이다.
3. **비전 없는 멤버에서 통째로 죽는다.** 파티는 하네스·모델이 제각각이다.
4. **캡션이 텍스트로 존재해야 사용자가 고칠 손잡이가 생긴다.** 모델이 그림을 오해해도 개입할
   자리가 없는 것이 이미지 방식의 실질적 약점이다.

**되돌리기 쉬운 쪽으로 먼저 간다.** 표현력이 아쉬워지면 "이 멤버는 눈으로 보기" 토글로 이미지를
얹을 수 있지만, 반대 방향(이미지 → 텍스트)은 캡션 데이터가 아예 없어 더 비싸다.

참고로 **콘택트 시트로 묶어도 토큰은 안 줄어든다** — Claude 는 면적으로 매기므로 30장 따로나
그리드 한 장이나 같다. 시트의 이점은 비용이 아니라 번호·순서가 명확해지는 것뿐이다.
