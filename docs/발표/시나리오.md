# AgentParty 사내 발표 구성안

## 발표의 핵심 메시지

- AgentParty는 여러 AI에게 일을 한꺼번에 시키기 위한 도구라기보다, **역할과 컨텍스트가 분리된 독립 세션들이 하나의 팀처럼 협업하게 만드는 데스크톱 앱**이다.
- 사람이 세션 사이에서 결과를 복사하고 전달하던 오케스트레이션을 앱과 AI가 직접 수행할 수 있게 한다.
- Claude Code, Codex, Cursor CLI 등 서로 다른 하네스와 모델을 하나의 워크벤치에서 운영하고, 세션 간 메시지·상태·권한·컨텍스트를 관리한다.
- 핵심 가치는 단순한 병렬화보다 **컨텍스트 분리, 역할 분담, 작업 흐름의 가시성**에 있다.

---

## 1. 왜 만들었는가

### 1-1. AI 개발 작업의 일반적인 흐름

- 요구사항 분석 → 설계 → 구현 → 테스트의 단계로 작업한다.
- AI를 활용하면 각 단계에서 매우 많은 코드와 도메인 정보를 읽게 된다.
- 한 세션에서 모든 단계를 처리하면 이전 단계의 정보와 현재 작업 정보가 계속 섞인다.

### 1-2. 실제로 겪은 문제

- 요구사항 분석을 끝냈다고 생각했지만, 구현 중 새로운 조건이나 누락된 흐름이 발견된다.
- 구현을 멈추고 다시 코드를 조사하고, 요구사항과 설계를 수정해야 한다.
- 하나의 세션이 코드 조사, 요구사항 판단, 구현 세부사항을 모두 떠안게 된다.
- 대화가 길어질수록 현재 결정 사항, 미결 사항, 작업 진척을 놓치기 쉬워진다.

### 1-3. 예시: 상품명 매칭 작업

- 최초 요구: 상품명 매칭 시 작업 기록 남기기.
- 구현 중 코드 매칭과 재고 매칭이라는 별도 흐름을 뒤늦게 발견.
- 추가로 확인해야 하는 내용:
  - 코드 매칭과 재고 매칭의 관계
  - 기존 매칭 결과를 덮어쓰는 조건
  - 매칭 키워드 등록 방식
  - 작업 기록을 남겨야 하는 정확한 시점
- 한 세션에서 처리하면 코드 조사와 요구사항 판단이 뒤섞이고, 구현 컨텍스트도 중간에 끊긴다.

### 1-4. 해결하고 싶었던 것

- 코드 조사, 요구사항 분석, 설계, 구현, 테스트를 역할별 세션으로 분리한다.
- 각 세션은 자기 역할에 필요한 컨텍스트만 깊게 유지한다.
- 필요한 정보는 세션끼리 직접 주고받는다.
- 사용자는 모든 메시지를 복사·붙여넣기 하지 않고 전체 흐름과 의사결정에 집중한다.

## 2. 기존 방식의 한계

### 2-1. 하나의 메인 세션 + 서브에이전트

- 장점:
  - 작업 위임과 병렬 처리가 쉽다.
  - 짧고 독립적인 조사에 유용하다.
- 한계:
  - 서브에이전트가 일시적이고, 장기적인 역할과 컨텍스트를 유지하기 어렵다.
  - 사용자가 특정 서브에이전트와 지속적으로 대화하기 어렵다.
  - 추가 질문이나 후속 조사가 생기면 메인 세션이 다시 중계하게 된다.
  - 메인 세션에 세부 정보가 계속 유입되어 오케스트레이션 컨텍스트가 오염된다.

### 2-2. 여러 터미널 세션을 직접 운영

- 코드 조사 세션에 결과를 Markdown 파일로 작성하게 한다.
- 파일 경로를 다른 세션에 전달해 요구사항 분석이나 구현을 이어간다.
- 역할 분리는 되지만 사람이 세션 생성, 결과 전달, 진행 확인을 모두 담당해야 한다.
- 여러 모델을 섞어 쓰면 창과 실행 환경이 더 분산된다.

### 2-3. AgentParty의 접근

- 서브에이전트가 아니라 **이름과 역할을 가진 지속적인 독립 멤버**를 만든다.
- 멤버들이 서로 직접 메시지를 보내고 상태를 확인한다.
- 오케스트레이터 역시 하나의 멤버로 두어 조율에 집중시킨다.
- CLI의 실행 능력은 유지하면서, 팀 운영에 필요한 부분을 데스크톱 UI로 제공한다.

## 3. AgentParty란 무엇인가

### 3-1. 기본 개념

- **작업공간**: 실제 프로젝트 폴더. 로컬 경로와 WSL 경로를 지원한다.
- **파티**: 하나의 목적을 위해 구성한 AI 에이전트 팀.
- **멤버**: 이름, 역할, 하네스, 모델, 추론 수준, 권한을 가진 독립 세션.
- **워크벤치**: 여러 멤버의 대화와 상태를 탭·분할 패널로 함께 보는 화면.

### 3-2. 앱의 본질

- 백그라운드에서는 Claude Code, Codex, Cursor CLI 같은 실제 CLI 하네스가 동작한다.
- 앱은 각 CLI의 스트리밍 출력과 도구 호출을 공통된 UI로 보여준다.
- 승인 요청, 사용자 질문, 계획, 변경 파일, diff, 이미지, MCP 상태 등을 화면에서 처리한다.
- 여기에 파티 편성, 멤버 간 통신, 메시지 제어, 컨텍스트 관리 기능을 더했다.

### 3-3. 지원 범위와 현재 제약

- 하네스: Claude Code, Codex, Cursor CLI.
- 모델은 연결된 구독과 API 제공자에 따라 선택한다.
- OpenRouter·DeepSeek 등을 통해 다양한 모델을 사용할 수 있다.
- 자체 하네스가 있는 제공자의 모델을 다른 하네스에서 구동하는 교차 하네스 기능은 구현되어 있으나, 현재 베타에서는 안정성 문제로 잠겨 있다.
- 발표에서는 실제 사용 가능한 조합과 베타 잠금 기능을 구분해서 소개한다.

## 4. 기본 사용 흐름

### 4-1. 작업공간 열기

- 프로젝트 폴더에서 AgentParty를 실행한다.
- 해당 경로를 기준으로 워크벤치가 열린다.
- 파티와 멤버 상태는 작업공간에 저장되므로 프로젝트와 함께 유지된다.

### 4-2. 파티 만들기

- 새 파티를 만들면 기본 `main` 멤버가 생성된다.
- `main`은 사용자와 대화하며 전체 작업을 조율하는 오케스트레이터 역할을 맡는다.
- 파티별로 열린 탭, 패널 구성, 멤버 배치가 저장된다.

### 4-3. 멤버 구성하기

- 직접 추가하는 경우:
  - 이름과 역할 지정
  - 하네스 선택
  - 모델과 추론 수준 선택
  - 권한 정책 선택
- 일반적인 사용 방식:
  - 사용자: “요구사항 분석 멤버와 코드 조사 멤버를 만들어서 이 작업을 나눠 진행해줘.”
  - `main`이 앱 제어 도구를 사용해 멤버를 생성하고 업무를 배정한다.

### 4-4. 협업하기

- 멤버가 다른 멤버에게 직접 메시지를 보낸다.
- 수신자가 작업 중이면 메시지는 대기열에 들어가고, 현재 턴이 끝난 뒤 전달된다.
- 긴급한 메시지는 현재 턴을 중단하고 즉시 전달할 수 있다.
- 전체 멤버에게 방송하거나 특정 멤버의 상태를 확인할 수 있다.
- 사용자는 각 멤버의 대화와 진행 상태를 동시에 확인하고, 필요한 멤버에게 직접 질문할 수 있다.

## 5. 핵심 기능

### 5-1. 독립 세션과 멤버 간 통신

- 멤버마다 별도의 대화와 컨텍스트를 유지한다.
- 이름이 있는 멤버에게 직접 질문, 후속 요청, 작업 인계가 가능하다.
- 서로 다른 모델과 하네스가 같은 파티 안에서 협업할 수 있다.
- 세션을 닫거나 다시 열어도 멤버 설정과 대화 연결 정보를 유지한다.

### 5-2. 메시지 대기열

- 바쁜 멤버에게 도착한 메시지를 안전하게 보관한다.
- 대기 메시지 확인, 취소, 편집, 순서 변경, 병합을 지원한다.
- “지금 보내기”로 우선순위를 올리고 현재 턴을 중단한 뒤 전달할 수 있다.
- 앱을 다시 시작해도 대기열이 유지된다.

### 5-3. Message Gate

- 멤버가 다른 멤버에게 보내는 메시지를 별도의 리뷰어 모델이 검사한다.
- 파티 공통 규칙 또는 멤버별 규칙을 설정할 수 있다.
- 규칙 위반 시 메시지를 전달하지 않고 위반 사유를 보여준다.
- 반드시 보내야 하는 경우 강제 전송할 수 있으며, 우회 사실이 기록된다.
- 활용 예:
  - 구현 멤버가 오케스트레이터에게 불필요한 파일·코드 세부사항을 장문으로 보고하지 않도록 제한
  - 조사 멤버가 근거 없이 설계 결정을 내리지 않도록 역할 경계 유지
  - 같은 내용을 반복 전송하거나 중복 발주하는 행동 억제

### 5-4. 컨텍스트 관리

- 멤버별 컨텍스트 사용량과 비율을 확인한다.
- 수동 압축과 임계값 기반 Auto-compact를 지원한다.
- 긴 대화에서 입력 토큰이 반복적으로 증가하는 문제를 줄인다.
- 컨텍스트 크기를 알 수 없는 모델은 임의 비율을 만들거나 자동 압축하지 않는다.

### 5-5. 권한과 사용자 개입

- 하네스에 맞는 권한 정책을 멤버별로 설정한다.
- Claude Code 권한 모드와 Codex 샌드박스·승인 정책을 UI에서 변경할 수 있다.
- 명령 실행 승인, 파일 변경 승인, 모델의 추가 질문에 대한 답변을 카드 형태로 처리한다.
- 실패나 지원 불가 상태를 조용히 우회하지 않고 대화와 진단 화면에 표시한다.

## 6. 운영과 편의 기능

### 6-1. 통합 워크벤치

- 여러 멤버를 탭과 분할 패널로 동시에 배치한다.
- 파티별 레이아웃을 저장하고 복원한다.
- 멤버 상태, 승인 대기, 읽지 않은 메시지, 실행 중 여부를 한 화면에서 확인한다.
- Markdown, 코드 블록, 표, 도구 실행 결과, diff, 이미지를 공통 형식으로 렌더링한다.

### 6-2. 세션 수명주기

- 세션 시작, 중단, 종료, 재시작, 재개를 지원한다.
- 일반 재시작은 가능한 경우 기존 대화 스레드를 이어가며 설정과 MCP 구성을 다시 적용한다.
- 문제가 생겼을 때 멤버를 삭제하고 처음부터 구성하지 않고 복구할 수 있다.

### 6-3. 모델·인증·MCP

- 연결된 구독과 API 키에 따라 사용 가능한 모델을 카탈로그로 보여준다.
- 모델의 비용, 컨텍스트, 이미지 지원, 추론 옵션을 비교해 선택한다.
- Claude·Codex 구독, Cursor CLI 로그인, OpenRouter·DeepSeek API 연결을 관리한다.
- 멤버별 MCP 서버 상태, 도구 목록, 연결 실패, 인증 필요 여부를 확인하고 재연결할 수 있다.

### 6-4. 사용량과 자원 관리

- 멤버·모델별 토큰 사용량과 추정 비용을 확인한다.
- 비용은 모델 가격표를 바탕으로 한 추정치이므로 정산 수치보다 상대적인 사용 추세를 보는 용도다.
- 유휴 멤버의 프로세스를 자동으로 닫아 메모리를 절약하고, 필요할 때 다시 깨울 수 있다.
- 특히 여러 WSL 세션을 장시간 열어둘 때 자원 사용을 줄이는 데 유용하다.

### 6-5. Discord 브리지

- 멤버별 Discord 스레드를 연결해 PC 밖에서도 진행 상황을 확인하고 메시지를 보낼 수 있다.
- 텍스트와 이미지를 주고받고, 상태 확인·중단·재시작 같은 제어 명령을 사용할 수 있다.
- 제어 명령은 LLM을 거치지 않으므로 멤버가 응답할 수 없는 상황에서도 동작한다.

## 7. AI가 앱 자체를 제어하는 구조

### 7-1. 로컬 자동화 API

- 앱의 사용자 기능은 로컬 HTTP API로도 제공된다.
- 상태, 모델, 인증, 세션, 파티, 멤버, 메시지, 권한, Message Gate, MCP, 창과 화면 이동 등을 제어할 수 있다.
- UI와 API가 같은 애플리케이션 로직을 호출하므로 별도의 테스트 전용 동작에 의존하지 않는다.
- API는 로컬 loopback 주소에만 열린다.

### 7-2. 가능한 활용

- AI가 파티와 멤버를 구성하고 작업을 배정한다.
- 앱 상태와 로그를 읽어 문제 원인을 조사한다.
- 실제 앱을 실행한 뒤 사용자 동선을 API와 UI로 수행하며 E2E QA를 진행한다.
- 화면을 캡처하고 결과를 논리적으로 판단해 다음 동작을 결정한다.

### 7-3. 의미

- AI 기능을 탑재한 앱을 넘어, **AI가 운영·진단·검증할 수 있는 소프트웨어 구조**를 실험한 사례다.
- 자동화 API는 부가 기능이 아니라 제품 기능과 테스트 가능성을 연결하는 핵심 인터페이스다.

## 8. 데모 구성

### 8-1. 권장 데모 시나리오

1. 프로젝트 작업공간 열기
2. 새 파티 생성 후 `main` 멤버 확인
3. `main`에게 역할이 다른 멤버 두 명 생성을 요청
   - `explore`: 코드 조사 전담
   - `impl`: 설계·구현 전담
4. `main`이 두 멤버에게 업무를 배정하는 과정 확인
5. 분할 패널에서 멤버들의 독립 대화와 상태를 동시에 표시
6. `explore`가 조사 결과를 `impl` 또는 `main`에게 직접 전달
7. 바쁜 멤버에게 메시지를 보내 대기열 동작 시연
8. Message Gate 규칙을 일부러 위반한 메시지 전송 → 반려 사유 확인 → 필요 시 강제 전송
9. 컨텍스트 사용량과 Auto-compact 설정 확인
10. 승인 카드, 도구 호출, 변경 파일 또는 diff 화면 확인
11. 마지막으로 통계와 자동화 API 화면 소개

### 8-2. 데모에서 강조할 것

- 여러 AI가 동시에 답하는 장면보다, **각자 다른 정보를 유지하면서 필요한 순간에 직접 협업하는 장면**을 보여준다.
- 사용자가 중간 전달자가 되지 않는다는 점을 보여준다.
- AI의 자율성뿐 아니라 대기열, Gate, 권한, 승인 등 통제 장치도 함께 보여준다.

### 8-3. 데모에서 피할 것

- 기능 목록을 메뉴 순서대로 전부 설명하지 않는다.
- 현재 베타에서 잠긴 교차 하네스 조합을 실제 지원 기능처럼 시연하지 않는다.
- 특정 모델의 일시적인 성능이나 최신 출시 여부를 발표의 중심으로 삼지 않는다.
- 긴 생성 작업을 현장에서 기다리기보다 짧은 조사·전달·검토 흐름을 사용한다.

## 9. 실제 사용 후 느낀 점

### 9-1. 장점

- 요구사항 분석과 코드 조사에서 누락과 미결 사항을 더 잘 발견한다.
- 역할별로 컨텍스트가 분리되어 각 멤버가 자기 영역을 더 깊게 다룰 수 있다.
- 현재 작업이 어느 단계에 있고 누가 무엇을 맡았는지 파악하기 쉽다.
- 다른 관점의 모델을 조합해 결과를 교차 검토할 수 있다.
- 장기간 이어지는 복잡한 작업에서 특히 유용하다.

### 9-2. 단점과 한계

- 단일 세션보다 시간과 토큰이 더 많이 들 수 있다.
- 멤버 간 메시지가 많아지면 같은 내용의 재전송, 메시지 순서 교차, 중복 작업이 생긴다.
- 역할 경계가 흐려지면 잘못된 판단을 다른 멤버가 확대할 수 있다.
- 멤버 수가 많다고 항상 좋은 것이 아니며, 쓰지 않을 역할까지 만들면 오히려 조율 비용이 커진다.
- 결국 좋은 파티 구성과 명확한 업무 분배가 필요하다.

### 9-3. 현재의 결론

- 작업 품질과 누락 방지 효과는 분명히 있었다.
- 반면 모든 작업에 멀티 에이전트가 필요한 것은 아니다.
- 짧고 명확한 작업은 하나의 세션이 더 효율적이다.
- 요구사항이 복잡하고 조사·판단·구현의 컨텍스트를 오래 분리해야 하는 작업에서 AgentParty의 가치가 커진다.
- 모델 성능이 향상되더라도 역할 분리, 관찰 가능성, 권한 통제, 재현 가능한 운영은 별도의 문제로 남는다.

## 10. 마무리

### 한 문장 요약

- **AgentParty는 여러 AI 세션을 단순히 동시에 실행하는 앱이 아니라, 역할과 컨텍스트를 분리하고 서로 직접 협업하게 만드는 AI 개발 워크벤치다.**

### 전달하고 싶은 결론

- 시작점은 개인적인 개발 과정에서 겪은 컨텍스트 오염과 수동 오케스트레이션 문제였다.
- 해결책은 더 큰 하나의 세션이 아니라, 목적이 분명한 여러 독립 세션과 이들을 연결하는 통신·통제 계층이었다.
- 실제로 사용해보니 품질 향상과 운영 비용이 함께 존재했다.
- 이 앱은 멀티 에이전트 협업 도구이면서, 동시에 AI가 직접 운영하고 검증할 수 있는 소프트웨어 구조에 대한 실험이다.
