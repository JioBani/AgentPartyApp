# 시나리오

## 앱을 만들게 된 목적

- 1P 일단 이 앱을 왜 만들게 되었는가
  - 멀티 프로바이더 모델의 세션간 통신이 필요했음
  - 근데 cli 환경이 아니고, 데스크톱 앱으로 보고 싶음
- 2P 그렇다면 왜 저런 요구사항이 필요했는가
  - 목적은 결국 하나. 컨텍스트 분리
  - 우리는 지금 요구사항 분석 -> 설계 -> 구현 -> 테스트 방식으로 작업중
  - 근데 AI 를 활용하면서, 각 단계에 컨텍스트를 분리할 필요가 생겼음.
  - 예를 들어, 우리는 요구사항 분석을 완전하게 끝내고, 설계, 구현에 들어가려고 함.
  - 그러나 설계, 구현 과정에서 요구사항 분석을 다시 해야하는 일이 빈번하게 생김
  - 요구사항이 변경되거나, 누락되거나
  - 실제 예시로 보면, 하나의 세션에서 작업한다고 가정해보자.
  - 상품명 매칭시 작업기록을 남기는 작업인데, 요구사항 분석을 다했다고 생각하고, 설계, 구현에 들어감
  - 근데 구현하다 보니까, 상품명 매칭에 코드매칭이 있었던 거임
  - 그러면 이제 여기서 구현을 멈추고, 다시 코드를 분석해야함.
  - 코드매칭이 어떻게 이루어지고, 재고매칭까지도 하는지, 매칭 키워드는 어떻게 등록하는지 등
  - 그리고 나서, 코드 분석을 다 하고 나면, 다시 요구사항을 작성해야함
  - 이 과정에서 컨텍스트 오염이 많이 발생하고, 현재 어디까지 진행됐는지를 놓치게 됨.

- 1P 이 문제를 해결하기 위해서, 보통 서브에이전트를 썼고, 나도 서브에이전트를 시도함
  - 오케스트레이터를 세션으로 하고, 분석이나 작업을 서브에이전트로 하는것
  - 근데 여기에는 치명적인 단점이 2개 있는데, 하나는 서브에이전트가 불안정 하다는것
  - 또 하나는 서브에이전트에게 말을 걸 수 없다는것
  - 먼저, 서브에이전트가 실패하거나, 세션 id 를 잃어버리는 경우가 많음
  - 그래서 추가 조사나, 세부 내용을 파악하려면 결국 메인 세션이 개입하게 됨
  - 또 서브에이전트가 분석한 코드에 대해서 궁금한점이 있으면 메인 세션과 대화를 해야함.
  - 오케스트레이터에게 컨텍스트 오염을 최소화 하기 위해서, 코드 분석 내용이나, 요구사항 분석 내용을 서브에이전트에게 바로 물어보고 싶은데, 불가능함
  - 그러다 보면 오케스트레이션을 담당해야할 메인 세션에 불필요한 지식이 늘어남
  - 결국 서브에이전트를 사용해서는 컨텍스트 분리를 효과적으로 할 수 없다.

- 1P 그래서 어떤식으로 작업을 했냐면, 사람이 오케스트레이터가 되었음
  - 세션을 여러개 열어놓고, 코드 조사 멤버에게 조사를 시키고, 결과를 md 파일로 만들라고 해서, 그 파일 경로를 붙혀넣어서 읽고 요구사항 분석해달라는 식으로
  - 근데 이건 결국 AI 가 세션간에 서로 대화할 수 있으면 해결되는 문제였음
  - 따라서 세션간 통신이 가능한 툴을 찾으려고 헀음
  - 근데 1. 세션간 통신을 지원해야 하며, 2. cli 형식이 아니여야 함
  - 을 만족하느 제품이 없었음
  - 그리고 내가 원하는 여러가지 기능을 붙혀보려면 그냥 아얘 나만의 앱을 만드는 것이 낫겟다 라고 생각해서 제작 시작




## 앱 소개 - 이건 일단 너가 알아서

- 이 앱의 기능은 사실 간단함. 세션을 만들고, 서로 통신할 수 있도록 하는것. 그게 이 앱의 기능의 70%

- 설치하고, 오른쪽 클릭 해서 Agentparty 를 열면, 해당 cwd 로 워크벤치가 열림

- 여기서 작업을 하려면 파티를 먼저 만들어야함.

- 파티는 하나의 에이전트 그룹을 말하는데, 파티원들끼리 서로 통신 할 수 있음

- 파티를 만들면 먼저 기본 멤버가 생기는데, 이 기본 멤버는 환경설정의 기본 값을 따라가게 되어있음. 

- 여기를 누르면 모델 카탈로그가 열리면서 수정 가능함

- 그리고, 오른쪽에서 + 를 눌러서 멤버를 추가 할 수 있음.

- 카탈로그에서 하네스, 모델, 추론을 선택해서 멤버를 만들면 멤버가 새로 생겼음

- 이제 이런식으로 서로 소통이 가능함.

- 근데, 일반적으로는 수동으로 멤버를 생성하지 않고, 이런 식으로 오케스트레이터한테 요청함.

- 그리고 원래는 크로스 하네스, 즉 코덱스 모델을 claude code 에서 돌릴 수 있고, 그 반대도 가능하도록 구현은 다 해놓았는데, 버그가 좀 있어서 현재는 닫아두었고,

- 이런식으로 클로드 코드로 해서 딥시크나 키미, glm 등의 모델은 생성 가능함

- 이거는 이번에 정식출시된 딥시크4 flash 인데, 이런식으로클로드 코드로 생성해서 사용할 수 있고 성능이 굉장히 좋음

- 기본적으로 이 앱은 터미널에서 도는 cli 의 출력을 이쁘게 랩핑한 것임. 즉 뒤에서 도는것은 우리가 터미널에서 도는 cli 이고 거기서 나오는 출력들, 승인 카드나 compacting 이라던가 그걸 랩핑한 것.

- 이런식으로 툴콜링이나, 승인 등에 대해서 대부분 ,UI로 다 커버가 되어있음

- 이제 메세지 게이트 

  - 이제 다음 핵심기능으로는 메세지 게이트가 있는데, 메세지게이트는 멤버끼리 통신 할 때, 통신 내용을 검열 해주는 기능임

  - 이런식으로 메세지 게이트를 설정 할 수 있는데, 중간에 모델을 선택해서, 메세지를 보낼 때 통신 규칙을 지키지 않았으면, 이런 식으로 반려해줌

  - 꼭 필요하다고 생각되면 이런식으로 강제 전송 할 수 있고,

  - 이걸 만든 이유는, 세션간 통신을 하다보면 AI 들이 서로 너무 친절하고 많은 정보를 전달하려고 함.

  - 오케스트레이터에게 코드 수정한 내용을 알린다던가. 그런걸 막기 위한 기능

  - 이것도 AI 한테 요청해서 가능합니다.

- 그리고 요건 통계인데 토큰 사용량을 보여주는 기능입니다.

  - API 비용으로 계산하고 있어서, 절대량은 정확하지 않고, 그냥 상대량을 보려고 만든 기능입니다.

- 그리고 오토 컴팩트

  - 오토 컴팩트. 이거는 특정 컨텍스트 사용량에 도달하면 자동으로 컴팩트 해주는 기능입니다.
  - 컨텍스트가 길면 기하급수적으로 사용량이 증가하는데, 그걸 막기 위한 기능입니다.

- 그리고 메세지 큐 기능

- 나머지는 당연히 지원 되어야하는 기능하고 편의기능들 입니다.

  - mcp 도구
  - 세션 재시작
    - 버그가 많아서, 뭔가 문제가 생겼다고 하면 세션 재시작 하시면 됩니다.
    - 멤버 멘션 기능

- 여기는 인증인데,

  - 사용하시는 AI 플랜을 여기서 연결하시면 됩니다.

  - 이거는 유휴 슬립인데, wsl 쓰시다 보면 세션 여러개 켜놓으면 wsl 터지던 문제 있잖아요.
  - 몇분 이상 사용 안하면 프로세스를 닫아서, 메모리를 아껴주는 기능입니다. 이거는 상당히 효과가 좋았어요





## 느낀점

- 1P 멀티 에이전트 오케스트레이팅이 과연 좋은가
  - 장점
    - 단계별로 누락을 최소화 해서 작업 가능
      - 요구사항 분석 등을 할때, 요구사항 누락이라던가, 미결 누락등이 많이 줄어듬
    - 특히 요구사항 분석에 있어서 정확도가 많이 올라간다
    - 작업자 스스로 어느 단계까지 했는지 파악하기 쉽다
  - 단점
    - 시간이 오래걸린다
    - 토큰이 많이든다
    - 서로 문제를 과정해서 증폭시키고 딴길로 샌다
  - 결론
    - 작업 퀄리티의 향상은 분명히 있으나, 토큰과 시간이 많이 든다
    - 모델이 점점 좋아지면, 하나의 세션에서 작업하는것이 나을수도 있겠다는 생각이 듦
- 1p AI 시대에서의 소프트웨어
  - 이 앱은 사실 모든 기능이 전부 API로 노출되어, 외부에서 LLM이 이 앱을 완전히 통제 가능
  - 뿐만 아니라, 앱의 상태나 로그 등에도 접근 가능
  - 이로 인해서
  - AI가 이 앱을 완전히 자동화 가능
  - 이 앱에 문제가 생겼을 때 AI 에게 이 앱의 상태를 확인시키고 어떤 부분에 문제가 있는지 빠르게 디버깅 가능
  - e2e 테스트를 스크립트가 아닌 AI 가 논리적으로 판단해서 QA 진행 가능
    - 스크립트 e2e 테스트가 작성이 굉장히 느리고, 복잡해서 시간과 토큰을 많이 잡아먹음
