대화할 수 있는 데스크톱 앱

왜 만들었고, 어떤 식으로 사용하고 있는가

이 장에서 말할 내용

  • 이 앱을 한 문장으로 설명하면, 여러 AI 세션을 만들고 세션끼리 직접 통신하게 하는 데스크톱 앱입니다.
  • 처음부터 거창한 멀티 에이전트 플랫폼을 만들려던 것은 아니었습니다.
  • 제가 실제 개발 과정에서 겪은 컨텍스트 문제를 해결하려고 만들기 시작했습니다.

다음: 왜 세션 간 통신이 필요했는지부터 설명하겠습니다.

이 장에서 말할 내용

  • 우리 작업은 보통 요구사항 분석, 설계, 구현, 테스트 순으로 진행합니다.
  • 각 단계에서는 필요한 정보의 종류가 다릅니다. 요구사항 단계에서는 사용자 의도와 미결 사항을 보고, 구현 단계에서는 함수 호출과 데이터 흐름을 봅니다.
  • 이상적으로는 요구사항을 확정한 뒤 설계와 구현으로 넘어가고 싶지만, 실제로는 구현 중에 누락된 조건을 발견합니다.
  • 그러면 구현을 진행하던 같은 대화 안에 과거 요구사항, 새로 발견한 코드 사실, 다시 열린 질문, 이미 작성한 설계와 코드가 동시에 남습니다.
  • 제가 말하는 컨텍스트 오염은 단순히 대화가 길어진다는 뜻이 아니라, 어떤 정보가 현재 유효한 기준인지 구분하기 어려워지는 상태입니다.

다음: 상품명 매칭 사례를 시간 순서대로 보겠습니다.

이 전제로 시작한 설계·구현

  • 상품명 매칭 흐름을 찾는다
  • 매칭 완료 지점에 기록 로직을 붙인다
  • 기존 매칭 결과와 함께 저장한다

이 장에서 말할 내용

  • 요구사항 분석을 다 했다고 생각하고 설계와 구현에 들어갔습니다.
  • 처음에는 상품명 매칭이 완료되는 코드 위치를 찾아 그 지점에 기록 로직을 붙이면 된다고 생각했습니다.

다음: 그런데 구현을 하다가 상품명 매칭 기능 안에 코드 매칭 기능이 같이 있다는 사실을 발견했습니다.

실제 예시

구현을 하다가 보니, 상품명 매칭 기능에 코드 매칭 기능이 같이 있었다

구현 중단

기존에 분석한 상품명 매칭 요구사항만으로는
바로 구현을 계속할 수 없었다.

코드를 다시 분석해야 했다

  • 코드 매칭은 어떻게 이루어지는가
  • 재고 매칭까지 같이 하는가
  • 매칭 키워드는 어떻게 등록하는가
  • 상품명 매칭과 코드 매칭은 어떻게 연결되는가

이 장에서 말할 내용

  • 구현을 하다가 보니 상품명 매칭 기능 안에 코드 매칭 기능이 같이 있다는 사실을 발견했습니다.
  • 그러면 여기서 구현을 계속할 수 없고, 일단 멈춰야 합니다.
  • 코드 매칭이 어떤 순서로 이루어지는지, 재고 매칭까지 같이 하는지, 매칭 키워드는 어떻게 등록하는지 다시 코드를 분석해야 합니다.
  • 처음 요구사항을 분석할 때 몰랐던 기능이기 때문에, 코드 분석 결과를 확인하기 전에는 작업 기록을 어디에 어떻게 남길지도 결정할 수 없습니다.

다음: 코드 분석이 끝나도 바로 구현으로 돌아갈 수 있는 것이 아니라, 요구사항 분석부터 다시 해야 합니다.

다시 요구사항을 정리

코드 매칭까지 포함해서 작업 기록을
언제, 어떤 조건으로 남길지 다시 작성한다.

다시 구현으로 돌아가기

앞에서 하던 구현 내용과 새 요구사항을
다시 연결하고 작업을 재개한다.

이렇게 코드 분석과 요구사항 분석을 거쳐 다시 구현으로 돌아오는 과정에서 컨텍스트 오염이 많이 발생했고, 현재 어디까지 진행했는지도 놓치게 됐다.

이 장에서 말할 내용

  • 코드 매칭 분석이 끝났다고 바로 구현으로 돌아갈 수 있는 것은 아닙니다.
  • 새로 파악한 코드 동작을 바탕으로 요구사항 분석부터 다시 해야 합니다.
  • 코드 매칭까지 작업 기록을 남길 것인지, 재고 매칭은 어떻게 다룰 것인지, 기록 시점과 조건을 다시 정리해야 합니다.
  • 요구사항을 다시 작성하고 나면, 이전에 진행하던 설계와 구현으로 돌아가 새 요구사항을 연결해야 합니다.
  • 한 세션에서 구현을 하다가 코드 분석으로 넘어가고, 다시 요구사항 분석을 한 뒤, 다시 설계와 구현으로 돌아오는 과정이 반복됩니다.
  • 이 과정에서 코드 분석 내용, 수정 전 요구사항, 새로 작성한 요구사항, 중간에 진행했던 구현 내용이 계속 쌓입니다.
  • 결국 지금 코드 분석이 끝난 것인지, 요구사항이 확정된 것인지, 설계를 다시 해야 하는지, 구현을 재개해도 되는지 놓치기 쉬워집니다.
  • 제가 말하는 컨텍스트 오염은 바로 이처럼 작업 단계를 여러 번 오가면서 이전 단계의 내용과 새 내용이 한 세션에 계속 쌓이는 문제입니다.

다음: 이 컨텍스트를 분리하기 위해 가장 먼저 서브에이전트를 시도했습니다.

이 장에서 말할 내용

  • 첫째, 서브에이전트가 실패하거나 세션 ID를 잃는 경우가 있었습니다.
  • 추가 조사나 세부 확인이 필요하면 결국 메인 세션이 다시 개입했습니다.
  • 둘째, 서브에이전트가 조사한 내용에 대해 그 에이전트에게 바로 질문하기 어려웠습니다.
  • 예를 들어 코드 조사 결과에서 이해되지 않는 부분이 있어도 사용자가 조사 에이전트에게 바로 후속 질문을 할 수 없었습니다.
  • 질문을 메인 세션에 전달하면, 메인은 질문을 다시 구성하고 서브에이전트의 결과를 읽고 답변을 중계해야 했습니다.
  • 그러려면 메인이 원래 알 필요가 없던 함수 동작, 예외 조건, 코드 위치 같은 조사 세부사항까지 이해해야 했습니다.
  • 그 결과 오케스트레이션만 담당해야 할 메인 세션에 코드 조사와 요구사항 분석 컨텍스트가 다시 쌓였습니다.
  • 즉 직접 질문할 수 없다는 제약은 단순한 불편이 아니라, 메인을 중계자로 만들고 컨텍스트 분리 목적 자체를 무너뜨리는 문제였습니다.

다음: 그래서 결국 제가 직접 오케스트레이터가 되었습니다.

  • 직접 만들 수도 있지만, 보통은 main에게 필요한 역할의 멤버를 만들어달라고 요청합니다.
  • Claude Code에서 GPT를 돌리는 식의 교차 하네스는 구현했지만 현재는 버그 때문에 베타에서 닫아두었습니다.
  • OpenRouter나 DeepSeek처럼 자체 하네스가 없는 모델은 Claude Code 또는 Codex 경로로 사용할 수 있습니다.

다음: CLI에서 보던 도구 호출과 승인도 앱 화면에서 처리합니다.

핵심 기능

Message Gate는 멤버 간 메시지를 규칙으로 검사한다

  • 중간 리뷰어 모델과 통신 규칙 설정
  • 규칙 위반 시 메시지를 전달하지 않고 반려
  • 필요하면 강제 전송 가능
  • AI에게 Gate 설정 자체를 요청할 수도 있음
AI들이 너무 친절하게 모든 세부사항을 공유하는 문제를 줄이기 위해 만들었다.

이 장에서 말할 내용

  • 멤버들이 서로 대화하게 하니 AI들이 지나치게 친절하게 많은 정보를 전달했습니다.
  • 예를 들어 구현 멤버가 오케스트레이터에게 코드 수정 세부사항을 전부 보고하면, 다시 메인의 컨텍스트가 오염됩니다.
  • 그래서 중간 리뷰어 모델이 통신 규칙을 검사하고, 위반 메시지는 반려하게 만들었습니다.
  • 꼭 필요하면 강제 전송할 수 있고, Gate 설정도 AI에게 요청할 수 있습니다.

다음: 긴 세션의 비용과 컨텍스트를 관리하기 위한 기능입니다.

느낀 점

멀티 에이전트 오케스트레이팅이 과연 좋은가?

장점

  • 단계별 누락과 미결 사항이 줄어든다
  • 특히 요구사항 분석의 정확도가 올라간다
  • 현재 어느 단계인지 파악하기 쉽다

단점

  • 시간이 오래 걸린다
  • 토큰을 많이 사용한다
  • 서로 문제를 과장하고 딴길로 샐 수 있다

이 장에서 말할 내용

  • 장점은 단계별 누락이 줄어든다는 점입니다.
  • 특히 요구사항 분석에서 놓친 조건이나 미결 사항을 더 잘 찾았습니다.
  • 각 단계가 분리되어 현재 어디까지 진행했는지도 파악하기 쉬웠습니다.
  • 반면 시간이 오래 걸리고 토큰을 많이 씁니다.
  • 여러 AI가 같은 문제를 주고받으며 문제를 과장하거나 딴길로 새는 경우도 있었습니다.

다음: 그래서 제 결론은 무조건 멀티 에이전트가 좋다는 것이 아닙니다.

결론

작업 품질 향상은 분명했다

하지만 시간과 토큰도 많이 들었다

모델이 더 좋아지면 하나의 세션이 더 나은 작업도 늘어날 수 있다.

이 장에서 말할 내용

  • 작업 품질이 좋아지는 효과는 분명히 있었습니다.
  • 하지만 모든 작업에 적용할 만큼 싸고 빠른 방식은 아니었습니다.
  • 모델이 계속 좋아지면 하나의 세션에서 작업하는 편이 더 나은 경우도 늘어날 것이라고 생각합니다.
  • 따라서 이 앱을 무조건 멀티 에이전트를 써야 한다는 주장으로 만든 것은 아닙니다.

마지막으로 이 앱을 만들며 생각하게 된 AI 시대의 소프트웨어 구조를 이야기하겠습니다.
