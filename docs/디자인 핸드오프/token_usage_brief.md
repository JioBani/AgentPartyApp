# 디자인 브리프 — 토큰 사용량 통계 (Token Usage)

> Claude Design 핸드오프용. 제품 맥락·디자인 시스템·테마 토큰은 기존 AgentParty 지식을
> 사용한다.
>
> **이 브리프의 최우선 목표: 통계적 시각화와 수치를 "어떻게 잘 표현하느냐".** 그래서 이
> 문서는 레이아웃·차트 종류를 지정하지 **않는** 대신, 그보다 앞선 것 — **데이터의 형태,
> 사용자의 눈이 해내야 할 과제, 이 데이터 고유의 인코딩 난제, 깨지면 안 되는 함정** — 을
> 정확히 규정한다. 좋은 표현은 여기서 도출된다. 구체적 시각 언어(차트 형태·배치·모션)는
> 디자인 클로드가 정한다.
>
> §5 데이터 기반은 소스코드로 검증한 사실이다. 값은 지어내지 않는다.

---

## 1. 최종 목적

**구독(Claude / Codex) 사용량을 최적화하기 위한 판단 근거를 만드는 것.**

사용자는 AgentParty로 여러 프로젝트를 동시에 작업하고, 파티마다 여러 멤버(세션)를 서로 다른
모델·effort로 돌린다. 구독 쿼터가 빠르게 소진되는데 원인이 안 보인다. 개선하려고 계속
실험한다 — 모델을 바꾸고, effort를 낮추고, 멤버를 나누고, 게이트를 도입하는 식. 그런데
**무엇이 얼마나 효과였는지 가늠이 안 된다.**

메우려는 간극(한 문장):

> **전역 계량기(구독 소진률)는 보이는데, 그것을 만든 지역 행위자 — 어떤 파티의 어떤 세션이
> 어떤 모델·effort로 얼마를 태웠는지 — 가 보이지 않는다.**

### 절대량이 아니라 상대 비교다 (전제)

구독의 "토큰→쿼터 환산식"은 비공개라 절대 소진량은 못 낸다. 그럴 필요도 없다 — 비교는
**이 앱 안에서** 이뤄진다. 그래서 1급 지표는 **비용(cost)**이다. 리스트 단가로 환산한 비용은
절대 청구액은 아니지만 **세션 간 상대 비율이 정확**하고, 그 비율이 구독 소진의 상대 비율에
대응한다. (절대 사용량은 OpenRouter 대시보드 몫 — 이 화면 밖.)

---

## 2. 이 화면이 성공하는 조건 (한 문장)

> **비용이 큰 세션이 한눈에 튀고, 동시에 "왜 컸는지" — 모델·effort·추론 — 가 그 비용 바로
> 옆에서 함께 읽혀서, 사용자가 곧장 다음 최적화 실험으로 넘어갈 수 있어야 한다.**

`이 세션이 비쌌다`만으로는 아무 조치도 못 한다. `이 세션이 비쌌는데 Opus·high로 돌아서다`
까지 읽혀야 "effort를 내려볼까"가 나온다. **비용(결과)과 환경(원인)은 절대 떨어지면 안 된다.**
이 둘을 눈이 한 번에 붙여 읽게 만드는 것이 이번 시각화의 본질이다.

## 3. 핵심 지표 — 비용과 그 환경

### 3.1 비용 (1급 지표)

```
비용 = fresh입력·in단가 + 캐시읽기·캐시읽기단가 + 캐시쓰기·캐시쓰기단가 + 출력·out단가
```
- 종류별 단가가 크게 다르다(출력 ≈ 입력 5배, 캐시읽기 ≈ 입력 0.1배) → **종류 분리 가중** 필수.
- 모델별 단가가 다르다(Opus 출력 25 vs Haiku 출력 5 → 5배) → **모델별 단가**로 계산.
- **프로바이더(Claude/Codex) 분리.** 서로 다른 계량기라 합산 무의미.
- 구독 세션은 **환산 비용**(실제 청구액 아님), OpenRouter 세션은 실비용 — 성격 구분 표식.

### 3.2 병기 필수 — "비용이 나온 환경"

비용 옆에는 **그 비용을 만든 조건**이 항상 함께:
- **모델** · **effort**(low~max, 순서형) · **추론 옵션**(모델이 지원하면 모드/버짓; 없으면 생략)

effort·추론은 출력/추론 토큰을 좌우하고 출력은 비용의 지배항이라, 이 병기만으로
`effort↓ → 비용↓` 같은 실험이 눈에 보인다.

### 3.3 보조 정량 (원인 뒷받침)

입력(fresh/캐시 분리) · 출력 · **캐시 적중률**(캐시읽기÷전체입력) · 모델 단가(in/out). 비용이라는
결과의 원인을 설명하는 원자료.

## 4. 비교의 단위와 정체성 (뼈대 — 잘못 뭉치면 서로 다른 걸 같게 본다)

- **단위 = 세션**(한 멤버의 한 실행). **파티 중심 계층에 갇히지 말 것** — 다른 파티의 세션끼리도
  매끄럽게 비교돼야 한다. 파티는 세션을 묶는 한 속성이지 유일한 상위 축이 아니다. 전역 비용순
  보기와 파티별 묶어 보기가 **둘 다** 가능해야 한다.
- **파티 = 고유 id로 구분(이름 아님).** `develop`을 지우고 같은 이름으로 다시 만들면 **다른
  파티**다(재생성=새 id). 집계·그룹·비교는 파티 id 기준. *(검증됨: 앱에 이름과 별개인 파티 id 존재.)*
- **멤버 재생성 = 다른 incarnation.** 삭제 후 같은 이름으로 재생성해도 이전과 다른 실행체다.
  원자 정체성은 **session_id**(멤버 시작마다 새로 생김) — `(파티id, 멤버이름)`이 같아도
  session_id가 다르면 다른 것. 이전 멤버와 새 멤버의 비용이 **섞이면 안 된다.**
- **세션 내부는 이질적이다.** 한 세션 안에서 모델·effort가 바뀐다. 그러므로 한 세션의 비용은
  **(모델×effort) 구간들의 합**이다. 단일 값으로 뭉개면 안 되고, 구간별로 쪼개 볼 수 있어야 한다.

## 5. 데이터 기반 (검증됨 — 신뢰해도 되는 사실)

턴마다 아래를 남긴다:
```
{ ts_start, ts_end,
  session_id,                 // 원자 정체성(incarnation 구분, 세션 내 지속)
  party_id, party_name,       // id로 구분, name은 라벨
  member_name, provider,      // provider: claude | codex | (OpenRouter=실비용)
  model, effort, reasoning?,  // 그 턴 시점 환경 (세션 중 변할 수 있음)
  tokens_in_fresh, tokens_in_cache_read, tokens_in_cache_write, tokens_out }
```
- 입력·출력·캐시가 **원천에서 분리 보고**됨(Claude·Codex 모두, 추론 토큰까지) → 종류별 가중 가능.
- **비용은 저장 안 하고 집계 때 모델 단가로 계산** → 단가 갱신 시 과거 자동 리프라이스.
- **실측/파생 구분**: 토큰·프로바이더 소진률=실측, 비용=실측토큰×공개단가의 **결정적 파생**(추정
  아님). 유일한 가정은 "비용비율 ≈ 소진비율" — 화면에 한 번 명시.

> ⚠️ 엔지니어링 TODO: 카탈로그에 입력/출력 단가는 있으나 캐시 단가가 없다. 상대 정확도를 위해
> 프로바이더 캐시 단가(읽기≈0.1×, 쓰기≈1.25×) 보강. 디자인 영향 없음.

## 6. 전역 한도 게이지 (참고선, 배분 안 함)

프로바이더 **실측 소진률**(5시간/주간 롤링, Claude·Codex 분리)은 **전역 게이지**로만 — "지금
전체가 얼마나 탔고 언제 리셋되나". 이 실측 %를 세션/멤버에 쪼개 배분하지 않는다(근사라 뺐음).
멤버 비교는 어디까지나 **비용**. 게이지=맥락, 비용=비교. 기존 사용량 인디케이터 재사용.

## 7. 사용자가 답을 원하는 질문 (시각화의 기준점)

| # | 질문 | 성격 |
| --- | --- | --- |
| Q1 | 지금 전체가 얼마나 탔나, 언제 리셋되나? | 현황(전역 게이지) |
| Q2 | 어떤 세션이 비용을 많이 썼나? (파티 무관, 전역/그룹 모두) | 범인 지목 |
| Q3 | 그 비용은 **왜** 나왔나 — 어떤 모델·effort·추론으로? | 원인 규명 |
| Q4 | 세션 안에서 모델·effort를 바꿨을 때 비용이 어떻게 달라졌나? | 실험 판정 |
| Q5 | 같은 이름으로 다시 만든 파티/멤버가 이전 것과 섞이지 않나? | 정합성 |

Q2(얼마나)와 Q3(왜)가 **한 시야에서 붙어** 읽히는 것이 이 화면의 핵심 과제다.

## 8. 시각화가 풀어야 할 문제 ★ (이 브리프의 중심)

레이아웃은 자유지만, 좋은 표현은 **데이터의 형태**와 **눈이 해야 할 일**을 정확히 알아야
나온다. 아래가 그 규정이다.

### 8.1 데이터의 형태 (표현을 좌우하는 성질)

- **넓은 동적 범위(orders of magnitude).** 세션 비용은 자릿수가 통째로 다르다 — 백그라운드
  폴러/짧은 턴 세션 vs Opus·high로 장시간 돈 impl 세션. **선형 막대로 나열하면 큰 것 몇 개가
  화면을 먹고 작은 것들은 0처럼 뭉갠다.** 큰 비용과 작은 비용을 **둘 다 읽히게** 하는 것이 첫
  난제다.
- **비용은 합성값 — 여러 축으로 동시에 분해된다.** 같은 "비용"이:
  ① 토큰 종류별(fresh입력/캐시읽기/캐시쓰기/출력, 단가 상이)
  ② 세션 내 (모델×effort) 구간별
  ③ 세션→멤버→파티 소속별
  ④ 시간축
  으로 쪼개진다. **좋은 표현은 "이 비용의 지배 동인이 무엇인지"(어느 종류·어느 모델구간)를
  즉시 드러낸다.**
- **정량값에 범주형 맥락이 붙어 있다.** 비용(연속량)에 모델(범주, 카탈로그상 다수지만 창당
  활성은 소수) · effort(5단계 순서형) · 추론(범주)이 딸려 있다. **"얼마"와 "왜"를 한 번에 읽게**
  붙이는 것이 §2의 요구.
- **두 개의 시간 프레임.** ⓐ 한도 창(벽시계, 리셋됨) ⓑ 세션 자신의 턴 시퀀스. 성격이 다르다.
- **대략적 규모감**(표현 밀도 판단용): 5시간 창에 활성 세션 대략 수 개~십수 개, 세션 하나당
  (모델×effort) 구간은 보통 1~3개, 일주일이면 파티 몇 개에 걸친 세션 incarnation 수십 개.
- **정체성 공존.** 같은 이름의 재생성 파티/멤버가 한 화면에 함께 나타날 수 있다.

### 8.2 눈이 해내야 할 지각 과제 (Jobs)

각 과제는 "몇 초 안에, 정독 없이" 달성돼야 한다.

- **J1 순위 파악** — 세션/파티를 비용순으로 즉시 (넓은 범위에서도 작은 것까지 읽히게).
- **J2 구성 파악** — 한 비용의 지배 동인(어느 토큰 종류/어느 모델·effort 구간)이 튀어 보이게.
- **J3 환경 동반 읽기** — 비용 크기와 모델·effort·추론이 **눈을 옮기지 않고** 함께 읽히게.
  (별도 표를 왕복 대조하게 만들면 실패.)
- **J4 시간 추이** — 비용이 시간에 따라 어떻게 쌓였는지(창 벽시계 / 세션 턴 순서).
- **J5 정체성 구분** — 재생성된 파티/멤버가 이전 것과 **명백히 별개로** 보이게(절대 병합 X).
- **J6 세션 내 이질성** — 한 세션이 단일 환경이 아니라 (모델×effort) 구간들의 합임이 보이게.
- **J7 공정한 크로스파티 비교** — 다른 파티 세션끼리 **공통 척도** 위에서 비교되면서도 소속은
  드러나게.

### 8.3 인코딩 예산 — 이 데이터의 결정적 제약

**색은 이미 정체성에 쓰인다.** 멤버/세션 색은 앱 전체의 길찾기 장치(사이드바·탭·포커스 테두리)
라 **시각 시리즈 색으로 그대로** 재사용해야 한다(새 팔레트 금지). 그런데 **모델·effort·추론도
범주형이라 인코딩 채널을 원한다.** 여기서 충돌이 생긴다:

> **색 채널은 "정체성(누구)"에 이미 소진됐다. 따라서 "환경(모델·effort·추론)"은 색이 아닌 다른
> 채널 — 위치·형태·질감·크기·보조 마크·라벨·그룹핑 — 로 인코딩해야 한다.** 모델까지 색으로
> 칠하면 정체성 색과 싸워 둘 다 죽는다. 이 채널 배분이 이번 디자인의 핵심 결정이다.

effort는 **순서형(low<…<max)**이므로 순서가 지각되는 채널(농도·크기·위치)이 어울린다 — 이건
디자인이 판단.

### 8.4 이 화면에서 표현이 실패하는 전형 (피할 것)

- 큰 세션 몇 개가 스케일을 독점해 작은 세션이 안 보이는 것(넓은 범위 미처리).
- 비용은 있는데 모델·effort가 **떨어진 표/툴팁에만** 있어 눈이 왕복해야 하는 것(J3 실패).
- 세션을 단일 (모델·effort)로 뭉개 세션 내 변경이 사라지는 것(J6 실패).
- 이름으로 뭉쳐 재생성 파티/멤버가 병합돼 비용이 섞이는 것(J5 실패).
- 합해서 100%가 되는 양(비용 점유율)과 안 되는 양(시간당 등)을 같은 형태로 그려 오해를
  부르는 것.
- 모든 수치가 동등한 무게로 놓인 "데이터 덤프" — 열자마자 판단이 안 서는 것.

## 9. 수치 표현 (숫자 자체를 잘 보이게)

시각화만큼 **수치의 가독**이 중요하다. 이 화면은 결국 숫자로 판단한다.

- **등폭/tabular numerals + 우측 정렬.** 본문 폰트(Maplestory)는 고정폭이 아니라 자릿수 세로
  비교가 안 된다. 표의 모든 수치는 등폭으로, 자릿수가 눈으로 정렬돼 보여야 한다.
- **단위 축약 일관.** `12.4k / 1.2M` 식 축약을 열 전체에서 동일 규칙으로. 혼재 금지.
- **자릿수 범위 미확정.** 실측 전이라 비용·토큰이 어느 자릿수일지 모른다 → 고정폭 셀 전제 금지,
  넓은 범위에서 안 깨지게.
- **숫자 하나만 놓지 말 것.** "이 비용이 큰가 작은가"는 비교 기준이 있어야 안다 — 이전 구간
  대비 증감, 다른 세션 대비 위치, 전역 대비 몫 등 **기준을 함께**.
- **비용 단위 표기.** 환산 비용(구독)과 실비용(OpenRouter)을 한 축에서 비교하되 성격 차이를
  표식으로. 통화/노셔널 여부가 오해되지 않게.
- **실측 / 파생 / 가정 구분.** 전역 소진률=실측, 비용=결정적 파생, "비용비율≈소진비율"=가정.
  가정은 화면에 한 번 명시. 빈 값은 **"아직 없음"**(0% 아님) — 앱은 값을 지어내지 않는다.

## 10. 상시 가드레일

- **열자마자 판단.** 비용 큰 세션 + 그 환경이 압도적으로 먼저 읽히고 나머지가 그다음. 명확한
  위계가 없으면 실패.
- **탐색은 좁혀 들어가고 되돌아오기 쉽게.** 전역 → 세션 → (세션 내) 구간/턴. 각 단계 back 저비용.
- **라이트/다크 양쪽 성립.** 정체성 색은 두 테마에서 유지.
- **차트 언어가 이 앱에 처음** 들어온다 — 새로 정립하되 위 색·정렬·표기 규칙 위에서.

## 11. 범위 밖 / 미확정

- **범위 밖**: 작업 종류(trigger) 분해, 오버헤드 비율, 게이트 순액, 실효 병렬도, 멤버별 추정 창%
  배분, 세션 절대 구독 소진량(OpenRouter 몫) — 모두 이전 안에서 제외/완화.
- **디자인 판단**: (모델×effort) 구간을 어떤 형태로 드러낼지, 추론 옵션을 어디까지 병기할지,
  전역 보기↔파티별 보기 전환을 어떻게 줄지, 넓은 동적 범위를 어떤 척도로 다룰지.
- **엔지니어링**: 캐시 단가 보강(§5), 서브에이전트 토큰은 현재 부모 세션 귀속(별도 축 이번 밖).
