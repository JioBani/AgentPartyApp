# Codex 저장소 전환 및 폴백 계획

작성: 2026-09-26. 이 문서는 구현 전 계획이다. 후속 구현과 후보 앱 검증 결과는 [CODEX_STORAGE_IMPLEMENTATION.md](CODEX_STORAGE_IMPLEMENTATION.md)를 따른다. 운영 프로필의 저장소 모드 전환은 아직 실행하지 않았다. 준비 단계의 증거는 [CODEX_STORAGE_READINESS.md](CODEX_STORAGE_READINESS.md)에 보존한다.

## 결정과 범위

- 정상 경로에서는 AgentParty가 멤버별 `CODEX_SQLITE_HOME`을 만들지 않는다. Codex 자체의 설정 우선순위와 호스트별 저장소를 존중한다.
- 멤버별 app-server 프로세스, 멤버 신원, 기존 thread ID, 공용 rollout 파일과 AgentParty 자체 파티·대화 저장소는 유지한다. app-server 통합은 이번 작업에 포함하지 않는다.
- 사용자 지시에 따라 목표 3개의 목표 ID·누적 사용량 보존은 필수 조건에서 제외한다. 기존 목표 DB는 백업으로 보관하되 새 저장소에 자동 재생성하거나 재활성화하지 않는다. 목표 초기화는 완료 보고에 명시한다.
- Codex DB 테이블 직접 병합, `backfill_state` 수정, DB 삭제 후 재생성, 스키마 변경은 하지 않는 방향을 우선한다. 공식 API로 복원할 수 없는 필수 상태가 발견되면 전환을 멈추고 손실 범위를 보고한다.
- Windows부터 전환한다. WSL 및 SSH는 해당 호스트의 실제 경로·버전·데이터를 조사하고 검증하기 전까지 기존 경로를 유지한다. 이는 명시된 호스트별 단계 전환이며 장애 때 자동으로 경로를 바꾸는 동작이 아니다.
- 현재 작업은 계획 요청이다. 데이터 전환 및 마이그레이션 구현은 구체적인 계획에 대한 사용자 승인 후 진행한다.

## 기존 문제가 기본 저장소에서도 발생하는가

설치된 Codex 0.155.1의 실제 Windows 실행 파일을 사용했다. 임시 `CODEX_HOME`에 기존 대화 파일 복사본을 넣고 인증·MCP 설정 없이 진단했다. 모델 턴 요청은 0회다. 원래 사용자 DB는 변경하지 않았다. 아래는 Codex 프로세스·저장소 진단이며 AgentParty 제품 E2E 통과를 뜻하지 않는다.

| 시나리오 | 실제 관찰 | 전환 조건 |
| --- | --- | --- |
| 초기화된 기본 DB에 프로세스 3개 동시 시작 및 thread 생성 | 이전 조사에서 3개 모두 성공 | 일반적인 DB 공유가 항상 실패한다는 가정은 성립하지 않음 |
| 대화 파일이 있지만 DB는 아직 없는 홈에 프로세스 3개 동시 시작 | 1개는 SQLite runtime 초기화 오류로 종료, 2개는 성공. 약 1.25초 | 최초 초기화의 순서 제어 필요. 구체적인 SQLite 내부 lock 종류는 확인되지 않음 |
| 실제 DB가 backfill `running`인 순간 해당 임시 Codex 프로세스 종료 후 같은 홈 재시작 | 약 30.47초 후 `timed out waiting for state db backfill`; DB는 `running` 유지 | 초기화 중 프로세스 교체를 막는 수명 관리 필요 |
| 새 홈에서 첫 초기화를 완료한 뒤 다른 프로세스 3개 병렬 시작 | 3개 모두 성공 | 최초 초기화 선행 방식의 적용 가능성 확인 |
| 위 공유 DB에서 한 프로세스 종료 후 다시 시작 | 성공 | 단순 재시작이 항상 DB 실패를 일으키는 것은 아님 |
| npm의 Node 실행 래퍼만 종료한 뒤 native Codex 잔존 여부 | 이번 정상 초기화 표본에서는 잔존하지 않음 | 자식 프로세스 누수를 이번 장애의 원인이라고 단정하지 않음. 모든 오류 종료 경로를 보장한 결과도 아님 |

과거 SQLite 분리 도입 커밋에는 가짜 app-server 검사뿐 아니라 실제 WSL 앱 초기화용 스크립트도 있다. 다만 해당 코드의 존재만으로 과거 공용 DB 경합의 정확한 원인과 해결 범위가 입증되지는 않는다. 이번에 별도로 재현한 것은 새 홈의 동시 초기화 실패 및 backfill 중단 후 타임아웃이다.

## 전환 전에 필요한 제품 수정

### 1. 초기화와 메시지 상태 분리

`requesting` 같은 화면 상태를 초기화 완료 여부로 사용하지 않는다. 준비 중 받은 메시지는 보존하되 실제 thread 준비 후 한 번만 보낸다. 재시도 중에는 복구 진행을 표시하고, 최종 실패 시에만 실패로 확정한다. 최종 실패나 중단을 조용히 무시하지 않는다.

### 2. 준비 중 런타임 변경

생성 직후 model/effort/fast 변경 때문에 DB를 초기화하는 프로세스를 즉시 죽이지 않는다. 요청된 최종 설정을 기록하고 안전한 초기화 경계 뒤 적용한다. 같은 제공자에서 실행 중 변경 가능한 설정은 기존 setter/turn 옵션을 활용한다. 재시작이 필요한 변경은 준비 완료 뒤 한 번 수행하고 대기 메시지와 연결한다.

명시적인 사용자 강제 중단이나 앱 강제 종료를 무한히 막지는 않는다. 그 경우 다음 시작에서 실패 원인을 드러내며, DB 상태를 임의로 `complete`로 고치지 않는다.

### 3. 저장소 단위 시작 순서

현재 `withAgentPartyCodexStartup`은 Node 프로세스 안에서만 작동한다. 코드가 환경 진단과 다른 엔진 프로세스까지 모두 조정한다고 가정하면 안 된다.

동일 호스트·동일 실제 저장소에 대해 멤버, 모델 탐색, 사용량 수집, 환경 진단의 최초 초기화를 일관되게 조정한다. 초기화가 완료된 멤버의 턴은 병렬로 유지한다. 다른 호스트의 독립 저장소까지 하나의 전역 대기열로 묶지 않는다. Codex 내부 SQLite lock을 대신 구현하는 것은 범위에서 제외한다.

다른 CLI·IDE가 독립적으로 시작하는 경우까지 AgentParty 내부 순서 제어로 막을 수는 없다. 초기화가 끝나는 동안 잠깐 발생하는 오류에는 동일 경로에서 제한적으로 재시도하되, 반복되는 backfill `running` 타임아웃은 복구 불가 상태로 보고한다. 재시도마다 새 DB를 만드는 동작은 제거한다.

### 4. 모든 시작 경로의 정책 일치

세션 실행, 모델 목록 탐색, 사용량 보조 프로세스, Windows/WSL 환경 진단의 경로 강제를 함께 점검한다. 일부만 바꾸면 진단은 성공하지만 실제 세션은 실패하거나 그 반대가 될 수 있다.

같은 thread가 외부 CLI에서 실행 중일 때 AgentParty가 중복 소유하지 않도록 기존 CLI 인계 규칙도 검증한다. 멤버별 프로세스 환경과 MCP 신원은 변경하지 않는다.

## 마이그레이션 단계

### 단계 A — 대상과 중단 조건 확정

호스트별로 실제 Codex executable/버전, CODEX_HOME, 환경변수와 설정을 적용한 최종 SQLite 경로, 기존 legacy 경로를 기록한다. AgentParty가 `~/.codex`를 새로운 강제 경로로 설정해서는 안 된다.

대상 목록에는 현재 Windows 멤버 152개의 ID뿐 아니라 전용 DB 전체에서 확인한 809개 대화 ID도 포함한다. 기존 기본 DB에 있던 대화를 덮어쓰지 않는다. 회복 디렉터리는 이름이나 존재 여부만 보고 정본으로 판단하지 않는다.

다음은 자동 진행 중단 조건이다: 대화 파일 누락, 같은 ID의 서로 다른 원본, 필수 메타데이터 충돌, 지원하지 않는 schema/CLI 조합, 미완료 backfill, 예상치 못한 메모리·대기열 내용, 동일 thread의 다른 실행 소유자, 백업 실패. 목표의 누적 사용량 차이는 사용자가 제외한 조건이므로 중단 사유로 삼지 않는다.

### 단계 B — 쓰기 중단과 백업

새 턴·멤버 시작·설정 변경·모델 탐색·진단 시작을 일시 중단하고 현재 작업은 완료 또는 사용자 중단을 기다린다. 기본 저장소를 사용하는 외부 Codex CLI·IDE·데스크톱의 쓰기도 중단한 상태를 확보한다. 사용자 프로세스를 일괄 강제 종료하지 않는다.

SQLite의 WAL까지 포함하는 일관 백업을 사용한다. `.sqlite` 본체만 복사하지 않는다. 기존 기본 DB, legacy DB, rollout 파일, AgentParty 파티/멤버/대화 매핑을 보존한다. 인증파일은 이 작업의 이전 대상이 아니다.

백업에는 실행 버전, 호스트, 설정 경로, 원본별 실제 경로, 기존 thread ID, 검증 결과를 묶는다. 대상 DB와 원본이 다른 디스크/파일인지 확인해 원본을 덮어쓰는 사고를 방지한다.

### 단계 C — 복사본 리허설

사용자 저장소와 완전히 분리한 복사본에서 진행한다. 복사본 DB 안에 원래 사용자 rollout의 절대경로가 남아 있으면 초기화/재개가 원본을 건드릴 수 있으므로, 실제 Codex의 읽기·쓰기 대상이 복사본 안에 한정됨을 보장하지 못한 상태에서는 실행하지 않는다.

먼저 공식 `thread/read(includeTurns=true)`로 ID와 대화 내용을 확인하고 색인을 보완한다. 이미 backfill이 완료된 기본 DB 복사본에서 이 방법으로 누락된 366개가 등록되고 809개 전체가 조회됨을 확인했다. 등록만을 위해 모든 기록을 `thread/resume`하지 않는다. 실제 사용자가 재개하는 멤버에 대해서만 현행 AgentParty의 모델·정책·멤버 지침을 적용해 공식 재개한다. 새 thread 생성이나 모델 턴 실행으로 이전을 대신하지 않는다.

각 ID를 순차 조회하고 원본과 대상의 실제 사용자·assistant 메시지 및 필요한 도구/첨부 항목을 비교한다. 원시 이벤트 수와 API 메시지 수를 무조건 같다고 가정하지 않는다. 이번 6개 차이는 기존 DB 복사본과 재구성 DB에서 API 메시지 내용이 동일함을 별도로 확인했다. 전체 범위를 검증하지 못한 상태에서 단지 DB 행이 생겼다는 이유로 이전 완료로 표시하지 않는다.

과거 제공자 설정이 없는 54개 기록과 보관된 1개 기록도 조회·색인 보완은 성공했다. 이를 이전하려고 제공자를 다른 것으로 바꾸거나 보관을 해제하지 않는다. 당시 현재 저장된 멤버의 ID와 이 55개는 겹치지 않았다. 실행 시에는 실제 제공자/인증/라우트 조건을 별도로 검사한다. 목록에서는 기존부터 `has_user_event=0`인 12개가 제외됐다. 따라서 전체 ID 보존과 목록에 노출될 ID 보존을 구분하며, 모든 ID를 강제로 사용자 목록에 노출시키지 않는다.

목표 3개는 원본 백업에만 남기며 이전 대상에서 제외한다. 현재 비어 있던 memory/queue가 전환 시점에도 비었는지 확인한다. 부모·자식 관계와 section/정렬/보관 상태는 API로 보존 가능한 범위를 확인하고, 필수 상태가 복원되지 않으면 그대로 손실을 숨기지 않고 중단한다. 이 확인 없이 DB 직접 병합을 추가하지 않는다.

작업 기록은 `pending → verified`를 ID별로 남긴다. 프로세스가 끊겨도 완료 항목을 중복 생성하지 않고 실패/미완료 항목부터 재개할 수 있어야 한다. 판정과 증거 수집은 이전 작업의 지정 검증기가 담당하며, 이후 임의 재검사로 대체하지 않는다.

### 단계 D — 제한된 실제 앱 확인

전용 QA 작업공간에서 실제 AgentParty 앱을 실행한다. 동일한 초기화/저장소 정책을 사용하고 별도 테스트 분기를 만들지 않는다. 멤버 생성·런타임 변경·메시지·중단은 실제 멤버 MCP transport로 수행한다. HTTP 직접 호출은 준비·상태 조회·MCP 도구가 없는 작업에 한정하고 이유를 기록한다.

필수 사용자 시나리오:

1. 실제 멤버 3개 병렬 응답, 각 응답과 도구 호출이 자기 멤버에 귀속.
2. 생성 직후 runtime 변경과 첫 메시지 전송: 오류 오표시, 유실, 중복 전송 없음.
3. 한 멤버 중단/재시작 중 나머지 멤버의 응답 계속 진행.
4. 과거 대화 재개 후 새 응답 저장, 앱 재시작 후 마지막 새 응답까지 복원.
5. 모델 목록 탐색·환경 진단을 함께 수행해도 멤버 시작/응답 정상.
6. 외부 Codex 프로세스와 서로 다른 thread를 사용한 동시 작업; 같은 thread 인계 시 중복 소유 차단.
7. 전환 후 새 턴과 새 thread를 만든 다음 legacy 모드로 되돌려도 최신 대화 복원.

짧은 실제 모델 호출로 확인하고 요청 모델/런타임별 결과를 기록한다. 이 일련의 행동을 검증하는 데 필요한 최소한만 자동화하며, enum/경로 문자열 목록/내부 호출 횟수 검사는 추가하지 않는다.

### 단계 E — 전환과 관찰

사용자 승인 후 유지보수 구간에서 실데이터에 동일 절차를 적용한다. 준비/검증이 완료되기 전에는 운영 경로를 바꾸지 않는다. 호스트별 상태를 `legacy → prepared → native`로 명확히 전환하고 실패 사유와 적용 범위를 표시한다. 전환 기록과 설정이 서로 어긋난 채 일부 프로세스가 임의 경로로 시작하지 못하게 한다.

운영 명령이 필요한 경우 `AppController`에 구현하고 UI/로컬 HTTP가 같은 메서드를 사용한다. 상태 조회·사전 검사·전환·롤백 기능은 한 route table에서 등록하고 `docs/API.md`에 문서화한다. 이 문서가 그 기능의 구현이나 실행을 의미하지는 않는다.

사용자 확인 기간은 최소 한 번의 정상 앱 재시작과 병렬 작업 완료를 포함한다. 기존 DB 정리는 이 검증과 분리하며 자동 삭제하지 않는다. 모든 지원 호스트가 검증되고 관찰이 끝나면 legacy 호환 경로를 제거할 별도 시점을 정한다.

## 폴백과 롤백

### 자동 폴백은 하지 않는다

오류를 만날 때마다 새 DB나 legacy DB로 조용히 전환하지 않는다. 같은 저장소의 실제 일시 오류에 한정한 bounded retry와, 운영자가 확인할 수 있는 명시적인 모드 롤백을 구분한다. DB 손상이나 계속 `running`인 상태를 빈 DB 성공으로 숨기지 않는다.

### 전환 전 실패

운영은 legacy 상태 그대로 유지한다. 리허설의 실패 항목과 원인을 보고하고 준비된 복사본만 보관한다. 사용자 기본 DB를 백업본으로 덮어쓰는 작업은 필요하지 않다.

### 전환 직후, 새 대화 쓰기 전 실패

AgentParty의 새로운 Codex 실행을 중지하고 실제 실행 자식까지 종료됐는지 확인한다. 기록해 둔 원래 legacy 경로와 멤버 매핑으로 되돌린다. 기본 DB는 다른 Codex 사용자의 데이터가 있으므로 일괄 복원하지 않는다. 이 구간에서도 전환 중 추가한 인덱스와 기존 사용자의 상태를 구분한다.

### 전환 후 새 턴/새 thread가 생긴 뒤 실패

목적은 과거 시점으로 되돌리는 것이 아니라 최신 사용자 대화를 유지한 채 실행 경로만 되돌리는 것이다. 관련 쓰기를 중단하고 새 상태와 현재 rollout·멤버 ID 매핑을 추가 백업한다.

기존 멤버는 동일한 thread ID와 현재 rollout을 사용해 보관한 legacy 저장소에서 공식 재개한다. 전환 뒤 새로 만든 멤버/thread도 현재 AgentParty 매핑을 유지한다. legacy 경로가 없는 신규 멤버는 첫 초기화를 순차 수행한다. 이 초기화나 복원이 실패하면 롤백 완료를 선언하지 않는다.

되돌린 저장소가 최신 턴을 읽는지 반드시 검증한다. 실제 QA 앱에서 legacy DB 생성 → native에서 새 응답 기록 → 오래된 legacy DB로 복귀 → 같은 ID에서 최신 응답 회상을 확인했다. native에서 처음 만든 대화의 legacy 재개도 통과했다. 다만 최종 전환 코드와 실제 전환 시점의 데이터로 다시 확인해야 한다. 전환 후 새로 생긴 목표·메모리·기타 DB 전용 상태는 자동 역병합을 가정하지 않고 별도로 보고·보관한다. 기존 목표 3개를 의도 없이 다시 활성화하지 않는다.

롤백 뒤에도 동일한 초기화 수명 관리 수정을 유지한다. 과거 실행 파일로 단순 다운그레이드하여 backfill 중단 버그를 다시 도입하는 것을 기본 롤백 절차로 삼지 않는다.

### 롤백 중단 조건

최신 대화 확인 실패, 새 thread 매핑 누락, legacy backfill 미완료, 다른 프로세스의 동일 thread 소유, 백업 실패가 있으면 해당 호스트의 새 실행을 중단한 상태로 보고한다. DB를 지우거나 상태 플래그를 고쳐 성공으로 처리하지 않는다.

## 진행 판단

**데이터 이전과 대화 중심 롤백의 실행 가능성은 검증됐지만, 현재 코드에서 경로 강제만 제거해 배포하면 안 된다.** 먼저 초기화 중 설정 변경으로 프로세스를 종료하는 문제와 초기화/전송 상태의 혼용을 수정한다. 이어서 모든 시작 경로에 같은 저장소 정책을 적용하고, 후보 빌드에서 초기화 경쟁·오류 표시·입력 중복 방지·CLI 인계까지 검증한 뒤 운영 전환한다.

구현 순서는 (1) 현재 legacy 모드에서도 유효한 초기화 수명 관리 수정, (2) 공식 조회 기반 이전 검증기와 명시적 호스트별 native/legacy 선택, (3) 후보 앱의 제품 E2E, (4) 승인된 Windows 유지보수 구간의 백업·검증·전환이다. WSL/SSH 전환과 기존 DB 삭제는 이 순서의 선행 조건으로 끼워 넣지 않는다. 자동 recovery 디렉터리 순환은 native 모드에서 제거하며, 롤백에도 수정된 수명 관리를 유지한다.
