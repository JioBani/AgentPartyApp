# e2e-token-usage: 원장이 6턴에 도달하지 못한다 (5/6)

- **발견**: 2026-08-17, desktop-app(모바일 연결 담당). 모바일 작업 검증 중 부수적으로 발견.
- **담당**: 미정. **모바일 연결과 무관**하므로 데스크톱 본류 쪽에서 봐야 한다(develop 확인).
- **상태**: 미해결. 원인 미확정 — 아래는 가설이고 검증되지 않았다.

## 증상

```
$ node scripts/e2e-token-usage.mjs
Error: ledger never reached 6 records (last=5).
    at waitForRecords (scripts/e2e-token-usage.mjs:136:9)
```

30초 대기 후에도 원장 레코드가 5개에서 멈춘다. 재시도해도 같은 값이라 **타이밍 흔들림이 아니다**
(2회 연속 동일).

## 기존 결함이라는 근거

`turnId` 작업(`29dc49e`) 때문이 아니다. 그 직전 커밋 **`46439c0`을 체크아웃해 재빌드한 뒤 실행해도
동일하게 5/6으로 실패**한다. 즉 이 실패는 모바일 연결 변경보다 앞선다.

`46439c0`보다 더 이전 어디서 들어왔는지는 확인하지 않았다.

## 가설 (미검증)

테스트는 6개 메시지를 **250ms 간격**으로 보내는데, 목 하네스의 자동 응답은 **약 700ms**다.

```js
["backend", …], ["backend", …], ["backend", …],   // 0ms, 250ms, 500ms
["frontend", …], ["frontend", …], ["reviewer", …]
```

`backend`는 첫 턴이 끝나기 전에 2·3번째 메시지를 받는다. 진행 중인 멤버에게 온 메시지는 큐에
쌓이고, 큐에는 **병합(merge) 설정**이 있다. 병합되면 메시지 3개가 턴 2개로 처리되고 원장 레코드도
그만큼 줄어든다 — 관측된 5/6과 맞는다.

그렇다면 **제품이 아니라 테스트의 가정이 틀린 것**이다("보낸 메시지 수 = 턴 수"는 보내는 속도가
턴보다 빠르면 성립하지 않는다).

**다만 반대일 수도 있다** — 원장이 실제로 턴 하나를 흘리고 있을 가능성을 배제하지 못했다. 둘은
사용자에게 전혀 다른 문제다:

- 테스트 가정 문제 → 제품은 정상, 테스트를 고친다.
- 원장 누락 → **사용자가 보는 비용이 실제보다 적게 나온다.** 적게 세는 것은 많이 세는 것만큼
  틀렸고, 눈에 띄지 않아 더 오래 살아남는다.

## 다음에 확인할 것

1. 실행 중 `GET /api/token-usage`의 `members` 롤업에서 `backend.turns`를 본다. **2면 병합 가설**이
   맞고(메시지 3개가 턴 2개), **3인데 총합이 5면 다른 멤버 쪽에서 하나가 빠진 것**이라 원장 누락을
   의심해야 한다.
2. 같은 구간의 `turn_complete` 이벤트 수와 원장 레코드 수를 직접 비교한다. 이제
   `turn_complete`에 `turnId`가 실리므로(`29dc49e`) 어느 턴이 기록되지 않았는지 이름으로 짚을 수
   있다 — 이 대조가 두 가설을 가른다.
3. 병합 가설이 맞으면 테스트를 고친다. 보낸 수가 아니라 **관측된 `turn_complete` 수**를 기다리거나,
   전송 간격을 턴보다 길게 둔다.
