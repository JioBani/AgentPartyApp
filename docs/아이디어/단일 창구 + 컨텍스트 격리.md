# 단일 창구 + 컨텍스트 격리

작성일: 2026-09-28
상태: 브레인스토밍 (대안 A·B 검토 중, 미결정)

## 배경: 왜 서브에이전트 대신 에이전트 파티를 만들었나

서브에이전트 기반 오케스트레이션은 서브에이전트가 사용자 입력을 받을 수 없다. 파티를 만든 목적은 두 가지였다.

1. **워커와 직접 대화한다.** 그 워커만 알아야 하는 내용이나 전문적인 내용을 해당 워커와만 이야기한다.
2. **오케스트레이터는 그 대화를 몰라도 된다.** 컨텍스트를 분리해 오케스트레이터의 컨텍스트를 오염시키지 않는다.

## 현재 문제

### 1. 정보 정합성 문제

멤버마다 알고 있는 내용이 다르다.

- 알고 있는 내용이 다른 것 자체는 문제가 아니다. 정보 분리는 의도한 결과다.
- 문제는 그 차이 때문에 생기는 행동이다.
  - **잘못된 내용을 전파한다.**
  - **확인을 요청한다.** 에이전트는 확인한 뒤에 전파하려는 성향이 있다. 자기가 받은 사용자 요청과 다른 내용이 들어오면, 모르는 내용을 확인하고 정보의 출처를 찾으려 한다.

### 2. 전파 문제 (격리 실패)

정보가 격리되지 않는다.

- A에게 질문하면 A가 확인하려고 B, C에게 모두 물어본다.
- A에게만 말한 내용을 A가 B, C에게 전파하려 한다.
- 프롬프트에 금지 규칙을 적어두었지만 잘 지켜지지 않는다.

### 3. 사용자 경험 문제

사용자 입장에서는 한 곳에서 이야기하는 편이 더 편하다.

- 여러 곳에서 대화하게 만든 것은 컨텍스트 분리를 위한 수단이었지 목적이 아니다.
- 분리만 제대로 된다면 한 곳에서 대화하는 편이 낫다.

### 4. 멤버 간 소통의 비효율

멤버끼리 주고받는 메시지 자체가 비효율적이다.

- 앞의 전파 문제, 교차 확인 문제가 대표적이다.
- 메시지 게이트로 프롬프트 규칙을 걸어 제어하려 했지만 잘 되지 않는다.
- 원인: 게이트 리뷰어는 **메시지 한 건만 보고 판단**한다. 파티 전체의 맥락 없이는 그 메시지가 불필요한 전파인지, 필요한 확인인지 구분하기 어렵다.

## 핵심 요구 (문제에서 도출)

- 사용자는 **한 창구**에서 대화한다.
- 대화 내용은 **필요한 멤버의 컨텍스트에만** 들어간다.
- 격리는 프롬프트 규칙이 아니라 **구조로** 보장한다. (프롬프트 금지는 이미 실패했다)
- 멤버가 모르는 정보를 만났을 때 다른 멤버에게 확인·전파하는 행동을 줄인다.

## 아이디어

### 큰 줄기 (모든 대안 공통)

- **입력:** 사용자는 한 곳에서 입력한다. 그 입력은 앱 내부에서 적절한 멤버로 라우팅된다.
- **출력:** 멤버들의 출력도 한 곳에서 보여준다.
  - 추론 과정(툴 호출, 중간 작업)은 각 멤버의 채팅창에 그대로 남는다.
  - 사람에게 보여줄 출력만 하나의 출력 창구로 모은다.
  - 형태는 단톡방에 가깝다. 여러 멤버의 발화가 한 대화 흐름 안에 쌓인다.

### 라우팅 방식 대안

라우팅을 어떻게 결정할지에 대해 두 가지 대안을 검토한다.

#### 대안 A: Jev 고속 라우팅

- 사용자 입력을 Jev에 넘겨 담당 멤버를 빠르게 분류한다.
- 목적: 라우팅 단계의 지연과 비용을 최소화한다.

**우려**

- **컨텍스트 한계:** Jev의 컨텍스트는 32k로 작다. 파티 전체 맥락을 담기 어려워 올바른 라우팅을 할 수 있을지 불확실하다.
- **정확도 미검증:** 라우팅 분류 정확도를 아직 측정하지 않았다.

#### 대안 B: 라우팅 전용 멤버

파티의 메시지 처리와 라우팅만 담당하는 전용 멤버를 둔다.

- **쓰기 불가.** 파일 수정이나 작업 실행은 하지 않는다. 메시지만 다룬다.
- **역할 1: 사용자 입력 라우팅.** 입력을 이해하고 적절한 멤버에게 넘긴다.
- **역할 2: 모든 소통의 중계.** 사용자↔멤버 소통뿐 아니라 멤버↔멤버 소통도 이 멤버를 거친다.
  - 멤버는 서로 직접 메시지를 보내지 않고, 라우팅 멤버가 전달 여부와 대상을 결정한다.
  - 라우팅 멤버는 파티 전체의 소통 흐름을 보고 있으므로, 메시지 게이트가 못 하던 판단(불필요한 전파 차단, 교차 확인 억제)을 **맥락을 가지고** 할 수 있다.
- 기대 효과: 문제 2(전파)와 문제 4(소통 비효율)를 프롬프트 규칙이 아니라 **구조**로 해결한다.

**착안: 오케스트레이터와 무엇이 다른가**

라우팅 멤버는 오케스트레이터와 역할이 겹쳐 보이지만, 필요한 컨텍스트의 성격이 다르다.

| | 오케스트레이터 | 라우팅 멤버 |
|---|---|---|
| 역할 | 주체자. 프로젝트 전체를 이끈다 | 소통 관리. 메시지 라우팅·정보 전파를 지시한다 |
| 필요한 컨텍스트 | 방향 판단에 필요한 수준만. 세부가 쌓이면 오히려 방해된다 | 오케스트레이터보다 자세하고 방대한 전반적 맥락. 누가 무엇을 하고 있는지 알아야 라우팅할 수 있다 |
| 메시지 | 걸러지고 압축된 것만 받는다 | 파티의 메시지를 모두 받는다 |

- 오케스트레이터는 벌어지는 일을 하나하나 알면 안 된다. 세부가 컨텍스트에 쌓이면 전체를 이끄는 판단을 방해한다.
- 메시지 라우팅은 그보다 넓고 자세한 맥락이 있어야 제대로 할 수 있다.
- 따라서 두 역할을 한 멤버에게 맡기면 서로의 컨텍스트 요구가 충돌한다. 그래서 분리한다.

**역할 3: 오케스트레이터 보호 (필터링·압축)**

- 문제: 멤버가 많으면 오케스트레이터에게 메시지가 끊임없이 들어온다. 매번 턴이 소모되고 컨텍스트가 쌓인다.
- 라우팅 멤버가 오케스트레이터로 가는 메시지를 **거르고 압축해서 한 번에** 전달한다.

**사용자 지시도 라우팅 멤버가 담당**

멤버 간 소통과 오케스트레이터 보호를 이미 라우팅 멤버가 맡는다면, 사용자 지시의 라우팅(역할 1)도 같은 멤버가 맡는 것이 자연스럽다. 모든 소통의 입구가 하나로 모인다.

**우려**

- **비용:** 모든 메시지가 LLM 멤버를 한 번 더 거치므로 호출 비용이 늘어난다.
- **속도:** 메시지마다 라우팅 멤버의 턴이 끼어들어 전달 지연이 생긴다.

**컨텍스트 분리와의 관계**

- 워커는 기존대로 컨텍스트를 분리한다.
- 라우팅 멤버만 **작업 전체의 맥락**을 안다.
  - 세부 내용까지 자세히 이해할 필요는 없다.
  - 전체적으로 어떤 일이 일어나고 있는지 파악하는 수준이면 된다.
  - 그 이해를 바탕으로 정보 전파와 메시지 라우팅을 지시한다.

**메시지 흐름 변화**

```
기존:  A ──────────────▶ B
변경:  A ──▶ 라우팅 멤버 ──▶ (적절한 멤버에게 할당)
```

A는 특정 멤버에게 보내는 대신 라우팅 멤버에게 메시지를 던지고, 라우팅 멤버가 받을 멤버를 정한다.

**열린 질문**

1. **발신 멤버가 수신자를 알아야 하는가?** A는 자기 메시지가 어느 멤버에게 전달됐는지 알아야 하는가, 몰라도 되는가.
2. **발신 멤버가 수신자를 지정할 수 있어야 하는가?** A가 받을 멤버를 지정(또는 제안)할 수 있게 할지, 결정을 전적으로 라우팅 멤버에게 맡길지.
3. **라우팅 멤버가 보는 정보의 범위.** 메시지 원문을 모두 보는가, 요약이나 메타데이터만 보는가. 원문을 모두 보면 라우팅 멤버의 컨텍스트가 커지고, 너무 적게 보면 라우팅 판단이 부정확해진다.
