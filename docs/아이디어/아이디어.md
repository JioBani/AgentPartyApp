## A. 파티 가시성 — 파티 안에서 무슨 일이 일어나는지 보이게 하기

> **세 항목이 같은 재료를 쓴다.** 파티 메시지 로그, 멤버 상태(작업중/유휴), 턴 시작·종료
> 전이, Message Gate 판정, 서브에이전트 트래커 — 전부 이미 앱 안에 있다. 따로 만들면 세 번
> 만들고, 같이 설계하면 한 번 만든다. **A-1과 A-2는 함께 착수하는 것을 권장.**

### A-1. 멤버 소통·작업 다이어그램 · `제안`

멤버끼리 **어떤 소통을 하고 있고 각자 어떤 식으로 작업 중인지** 한 장의 그림으로 보여준다.

- 원안 메모: *"가벼운 LLM을 통해서 만들어주게 하면 될듯"*
- **LLM 없이도 절반은 그려진다.** 노드(멤버)·엣지(메시지 흐름)·상태(작업중/유휴/승인대기)는
  전부 관측된 사실이다. LLM이 필요한 지점은 **"이 대화 덩어리가 무슨 작업인지" 라벨을 붙이는
  것** — 즉 요약이지 구조 생성이 아니다. 이 구분을 지키면 그림이 모델 컨디션에 좌우되지 않는다.
- 재료: 파티 메시지 저장소([partyRepository.ts](../../src/main/partyRepository.ts)),
  멤버 상태([memberStatus.ts](../../src/renderer/workbench/memberStatus.ts)),
  Gate 판정([messageGate.ts](../../src/shared/messageGate.ts)),
  서브에이전트 귀속([subagentTracker.ts](../../src/core/subagentTracker.ts))
- 결정 필요: 실시간 갱신인지 스냅샷인지 / 워크벤치 패널인지 별도 화면인지 / 렌더링 방식
  (직접 그리기 vs mermaid)

### A-2. 공유 멤버 보드 · `제안`

파티 **전원이 읽는 게시판** 하나. 두 가지 용도가 있다.

1. **모두가 알아야 할 것을 한 번만 올린다** — 지금은 오케스트레이터가 멤버마다 broadcast 해야 한다.
2. **"지금 누가 뭐 하는 중" 라이브 상태 피드** — 멤버끼리 서로의 작업을 볼 수 있다.

- 왜: 현재 멤버 간 인지는 **명시적 메시지로만** 일어난다. 주변 상태(ambient state)가 없어서
  멤버는 남이 뭘 하는지 즉시 알 수 없다.
- 재료: 인프로세스 MCP 툴 표면에 `board-post`/`board-read`/`board-status` 추가
  ([partyBridge.ts](../../src/core/partyBridge.ts) — 도구명·설명·핸들러가 한 파일에 모여 있음).
  저장은 파티별로 `.agent_party_app/` 아래. 상태 피드는 턴 시작·유휴 전이에서 자동 생성
  (`sessionManager`가 이미 `turnStartedAt`을 찍는다).
- ⚠️ 알려진 함정: **원격 엔진이 `party`/board 이벤트를 포워딩하지 않으면 UI가 라이브 갱신되지
  않는다.** WSL 경로에서 이미 겪은 문제.
- 규칙: HTTP API + [apiSpec.ts](../../src/shared/apiSpec.ts) + [API.md](../API.md) 등록,
  그리고 상단 퀵입력이 아니라 **화면 안의 제대로 된 UI**로 만든다.

### A-4. 워크트리·브랜치를 칩으로 표시 · `제안`

멤버가 **어느 워크트리·어느 브랜치에서 일하고 있는지**를 칩으로 보여준다.

- **왜 지금 필요한가**: 멤버가 여럿이면 **각자 다른 워크트리에서 작업하는 것이 정상 운용**이 됐다.
  실제로 지금 이 저장소에 워크트리가 10개 있고 멤버가 7명이다.
  그런데 **화면 어디에도 누가 어디서 일하는지 안 나온다.** 사람이 기억하거나 물어봐야 한다.
- **무엇이 잘못되는가**: 두 멤버가 **같은 워크트리에서 같은 파일을 고치는 것**을 아무도 못 막는다.
  master 에서 작업하면 안 되는 상황(미커밋 변경이 쌓여 있을 때)도 화면에 안 보인다.
- **재료**: 멤버의 작업 디렉터리는 앱이 이미 안다(세션 cwd). 거기서 `git rev-parse --abbrev-ref HEAD`
  로 브랜치를, `git rev-parse --show-toplevel` 로 워크트리 루트를 읽으면 된다.
  ⚠️ **앱이 지금 git 을 읽지 않는다** — 새로 붙이는 축이다.
- **결정 필요**:
  - **어디에 붙이나** — 탭 칩 / 사이드바 행 / 패널 헤더.
    ⚠️ **탭은 이미 자리가 없다.** [B-20](../베타%20공개%20준비/B-20%20탭이%20많으면%20스크롤이%20안%20된다.md)
    에서 탭이 넘쳐 접기(`+N ⌄`)를 넣었고, 좁아지면 **이름이 먼저 양보**하도록 만들었다.
    여기에 칩을 더하면 그 균형이 깨진다. **패널 헤더나 사이드바가 현실적이다.**
  - **무엇을 보여주나** — 브랜치명 / 워크트리 폴더명 / 둘 다. 브랜치명이 길면(`fix/b10-transcript-cap`)
    잘린다
  - **언제 갱신하나** — 사용자가 앱 밖에서 브랜치를 바꾸면 앱은 모른다. 폴링인가, 턴 경계인가
  - **master 를 경고할 것인가** — "이 멤버는 master 에서 작업 중"이 위험 신호일 때가 있다
- **연관**: [D-01](../베타%20공개%20준비/D-01%20대화창%20상태%20표시.md)(상태 표시) ·
  [D-03](../베타%20공개%20준비/D-03%20멤버%20색.md)(멤버 색) ·
  [B-22](../베타%20공개%20준비/B-22%20가로%20오버플로%20계열%20전수%20훑기.md)(가로 오버플로) —
  **전부 멤버 상단·탭 영역의 같은 자리를 두고 경쟁한다. 함께 설계해야 한다.**

### A-5. 파일을 누가 고쳤는지 기록 · `제안`

**어떤 파일을, 어떤 파티의 어떤 멤버가 수정했는지** 기록이 남는다.
사용자 원안: *"어떻게 남을지는 기술적인 문제고, **세션이 구분할 수 있으면 좋겠다.**"*

- **왜 지금 필요한가**: 멤버가 여럿이면 한 저장소를 여러 세션이 동시에 고친다. 지금은
  **"이 파일 왜 이렇게 됐지"에 답할 수단이 앱 안에 없다.** git 은 커밋된 것만 알고,
  커밋 작성자는 전부 같은 사람이라 **멤버를 구분하지 못한다.**
  파티가 여러 개면 어느 파티였는지도 안 남는다.
- **핵심 요구는 귀속(attribution)이다** — 변경 내용을 다시 보관하자는 게 아니라
  **파일 ↔ 세션**을 잇는 것. 그래서 기록 단위는 커밋이 아니라 **세션**이어야 한다.
- **재료**:
  - 하네스가 내보내는 **도구 호출에 파일 경로가 이미 들어 있다** — 트랜스크립트의 `tool` 블록이
    `name` · `input` · `cwd` 를 들고 있다([transcript.ts](../../src/shared/transcript.ts)).
    Claude 의 Edit·Write, Codex 의 apply_patch 가 여기로 지나간다.
  - 세션↔멤버↔파티 연결은 이미 있다(`sessionManager`).
  - 서브에이전트가 고친 경우의 귀속도 이미 푼 문제다([subagentTracker.ts](../../src/core/subagentTracker.ts)).
- **⚠️ 함정**:
  - **워크트리마다 경로가 다르다.** 같은 파일이 `AgentPartyApp/src/x.ts` 와
    `AgentPartyApp-f14/src/x.ts` 로 따로 잡힌다 → **저장소 상대 경로로 정규화**해야 한 줄로 모인다.
    ([A-4](#a-4-워크트리브랜치를-칩으로-표시--제안) 가 읽으려는 git 정보와 같은 재료다.)
  - **도구 호출이 곧 수정은 아니다.** 실패한 편집, 승인 거부, 계획만 세운 것까지 세면 기록이 거짓말을 한다.
  - **앱 밖 수정은 안 잡힌다.** 사용자가 에디터로 고친 것, 하네스가 셸로 고친 것
    (`sed` · 스크립트 실행)은 도구 호출로 안 보인다 → **"이 기록은 전부가 아니다"** 를 화면이 말해야 한다.
- **결정 필요**:
  - **어디서 보나** — 파일에서 세션을 찾나(`이 파일을 건드린 멤버들`), 세션에서 파일을 찾나
    (`이 멤버가 건드린 파일들`). **둘은 다른 화면이다.** 후자가 싸고, 전자가 원래 물음에 답한다
  - **보관 기간과 위치** — 파티별 `.agent_party_app/` 아래인가, 작업공간 전역인가
  - **git 을 같이 쓸 것인가** — 커밋 해시를 함께 남기면 "그 세션의 변경이 어느 커밋에 들어갔는지"까지 이어진다
- **연관**: [A-1](#a-1-멤버-소통작업-다이어그램--제안)(같은 관측 재료) ·
  [A-4](#a-4-워크트리브랜치를-칩으로-표시--제안)(워크트리·경로 정규화를 공유)

### A-3. 워크벤치 창 분리 (detach) · `제안`

한 프로세스 안에서 워크벤치 창을 떼어내 별도 창으로 본다. 멀티 모니터에서 파티를 넓게
펼치기 위한 것.

- 출처: [FEEDBACK #8](../FEEDBACK.md)의 (b). (a) 멀티 인스턴스는 이미 구현됐고 (b)만 남았다.
- 재료: 다중 창 구조([windowRegistry.ts](../../src/main/windowRegistry.ts))가 이미 있고,
  "작업공간 하나 = 인메모리 소스 하나" 규칙과도 충돌하지 않는다(한 프로세스가 스토어를 소유한 채
  창만 늘어남).

## B. 턴 제어 — 멈춰 있는 멤버를 다시 굴리기

### B-1. 기계적으로 턴 깨우기 · `제안`

멤버의 턴을 **모델의 협조 없이** 앱이 직접 깨운다. MCP 도구로 노출해 에이전트도 쓰고,
사용자도 UI에서 직접 누를 수 있게.

- 동기(사용자): **Claude Code의 해당 도구가 정상 동작하지 않아서** 앱 차원의 수단이 필요하다.
- 코드 확인(2026-07-28): 앱에 wake/nudge 계열 기능은 **없다.**
- 참고할 선례: 디스코드 브리지의 수신 핸드셰이크가 이미 **모델에게 묻지 않고 하네스 상태로
  판정**한다(`turnCount` 증가 = 실제로 집어 들었음). 같은 태도를 여기에도 적용 — "깨웠다"를
  프롬프트가 아니라 관측된 턴 전이로 확인한다.

### B-2. 한도 복구 후 자동 재개 · `제안`

사용 한도에 걸려 멈춘 멤버를, **한도가 리셋되면 자동으로 다시 턴을 굴린다.**

- 재료: 한도 데이터 파이프라인이 이미 있다([usageLimits.ts](../../src/shared/usageLimits.ts) —
  5시간·주간 창, 리셋까지 남은 시간, 제공자별). 여기에 "리셋 시각에 대기 턴 재개"를 얹는 형태.
- B-1과 같은 계열이라 함께 만드는 게 자연스럽다(깨우는 트리거만 사람 → 타이머로 바뀜).
- 결정 필요: 자동 재개를 멤버별 옵션으로 둘지 / 재개 실패 시의 표시(침묵 금지).

## C. 분석 — 쓴 만큼 잘 쓰고 있는지

### C-1. 트랜스크립트 × 사용량 기반 하네스 최적화 · `제안`

사용량 통계(**어디에** 돈·컨텍스트가 갔나)와 트랜스크립트(**왜** 그랬나 — 지시↔실제 행동)를
조인해서 최적화를 제안하거나, 나아가 적용까지 자동화한다.

- 예: Opus 멤버가 단순 편집만 반복 → 더 싼 모델/effort 제안 / 도구 왕복이 폭주해 컨텍스트를
  부풀림 → 더 이른 compact나 좁은 프롬프트 제안 / Gate 반려율이 높음 → 발신자 지시 강화.
- 재료: `turns.jsonl`이 이미 턴마다 model·effort·trigger·tokens·cost·gate.verdict를 들고 있고
  ([usageLedger.ts](../../src/main/usageLedger.ts)), 지시+도구 활동은 RawLogger/트랜스크립트에 있다.
- 1차는 **읽기 전용 "최적화 제안" 패널**(휴리스틱), 2차가 프로필 변경을 제안하는 에이전트.
- ⚠️ 2차로 갈 때 **조용한 재라우팅 금지** — 제안은 하되 몰래 바꾸지 않는다.

## D. 원격 사용

> 상세 설계는 전부 [기획 노트.md](../기획%20노트.md)에 있다. 여기엔 **상태와 남은 것만** 적는다.

### D-1. 원격 엔진 — 다른 PC의 cwd 열기 · `기획` (미착수)

기획 노트 §8. B PC의 AgentParty가 A PC의 작업공간을 연다(VS Code Remote 모델).

- **절반 이상 이미 만들어져 있다** — WSL 작업이 남긴 엔진 경계·원격 클라이언트·RPC 이벤트
  푸시·역방향 호출이 그대로 재사용된다(§8.2 표).
- 남은 것: `remote` 작업공간 종류 추가 / stdio → 소켓 전송로 교체 / 앱 안에서 `LocalEngine`을
  네트워크 노출(별도 데몬 금지) / 페어링·인증 / 자격증명 소유권 결정.
- 연결 경로: LAN 직결로 개발 → 실사용은 **Tailscale**(앱 코드 추가 0) → 설치 불가한 경우에만
  중계 서버.
- ⚠️ 보안이 1급 요구사항이다. 자동화 HTTP API는 **인증이 하나도 없고** 루프백 바인딩이 유일한
  보호막이라, 이걸 그대로 외부에 노출하는 것이 첫 번째 금지 사항(§8.6.2).

### D-2. 디스코드 브리지 — 잔여 항목 · `진행`

기획 노트 §11. 1차 구현(보고·대화·제어판·리액션 핸드셰이크·이미지 양방향)은 **완료 + 실앱
e2e 검증**. 남은 것은 검증 공백과 미결정 사항이다.

- 미검증(§11.15): 실제 429 경로 / 화이트리스트 거부 경로 / 장시간 재연결 / 같은 머신
  **다중 인스턴스 2-프로세스 e2e** / 디스코드에서 직접 친 명령 / 디스코드→멤버 이미지
- 미결(§11.14): 명령 접두사 확정 / 상태를 요청 시에만 보여줄지 주기 편집으로 항상 최신을
  유지할지 / 제어 범위를 어디까지 열지(멤버 생성·모델·권한까지?) / 자연어 지원 여부
- 보류 항목(§11.7): 턴=스레드 노이즈 격리, 전량 전달, 버튼 승인 — 필요해지면 §10을 다시 꺼낸다.

### D-3. 멤버 세션을 CLI 터미널로 이어받기 · `제안`

멤버 하나를 골라 **진짜 터미널에서 그 대화를 그대로 이어서** 진행한다. 앱 안의 패널이 아니라
사용자가 직접 조작하는 `claude` / `codex` / `cursor-agent` 프로세스로 넘긴다.

- **왜 필요한지 — 실제로 막힌 사례(2026-08-10).** 앱 안의 멤버에게 claude.ai 디자인 프로젝트를
  읽히려 했으나 `DesignSync` MCP 가 *"Re-authentication is required from an interactive Claude
  Code terminal (not available in this environment)"* 로 거부했다. `/design-login` 같은
  **대화형 재인증은 앱이 띄운 하네스 프로세스에서 원리적으로 불가능**하다. 이때 사용자에게
  남는 선택지는 "터미널에서 처음부터 다시 시작"뿐이고, 여기까지 쌓인 대화는 버려진다.
- 같은 벽에 부딪히는 것들: 하네스의 대화형 슬래시 명령(로그인·설정 마법사), 브라우저 OAuth 를
  요구하는 MCP 서버, TUI 를 띄우는 도구, 앱이 중계하지 않는 하네스 신기능.
- **재료는 이미 있다.** 멤버는 대화의 하네스 쪽 식별자를 이미 들고 있다
  ([types.ts](../../src/shared/types.ts) `PartyMember.harnessSessionId`) — 앱은 이것으로
  재시작 시 대화를 복구한다([claudeAdapter.ts](../../src/core/claudeAdapter.ts) 의
  `resumeSessionId` → `--resume`). 즉 **터미널에 넘길 재료는 새로 만들 필요가 없고, 이미
  쓰고 있는 값을 사용자에게 꺼내주기만 하면 된다.**
- **결정 필요 — 핵심은 "넘기기냐 붙기냐"다.**
  - **핸드오프(권장 시작점)**: 앱이 그 멤버를 재우고(sleep) 터미널을 띄운다. 하네스 세션의
    소유자가 한 번에 하나라 안전하다. 끝나면 다시 앱으로 돌아온다.
  - **동시 부착**: 앱과 터미널이 같은 대화를 동시에 잡는다. **하네스 프로세스가 한 대화를
    공유하도록 만들어져 있지 않다** — 크로스 하네스 락(`베타 prep` 커밋)이 존재하는 이유와
    같은 문제라, 검증 없이 열면 안 된다.
  - 어느 터미널을 띄우는가(Windows Terminal / pwsh / WSL) — 멤버가 WSL 작업공간이면
    **WSL 안에서** 떠야 한다([workspaceLocation.ts](../../src/shared/workspaceLocation.ts)).
  - 되돌아올 때 대화를 어떻게 다시 읽는가 — 터미널에서 늘어난 턴을 앱이 다시 로드해야 한다.
    트랜스크립트 원본 포인터(`/api/party/members/:name/harness-original`)가 출발점.
- **규칙**: 사용자 기능이므로 HTTP API + [apiSpec.ts](../../src/shared/apiSpec.ts) +
  [API.md](../API.md) 에 등록하고, 상단 퀵입력이 아니라 멤버 패널의 제대로 된 동작으로 만든다.

멤버가 글로만 말한다. **스티커나 이모티콘을 쓸 수 있게** 하면 상태와 태도가 한눈에 읽힌다 —
"다 됐습니다" 한 줄보다 스티커 하나가 빠르고, 여러 멤버가 동시에 말할 때 **누가 무슨 상태인지**
훑기 쉬워진다.

- **왜 이 앱에 맞나**: 이미 멤버마다 고유색이 있고 여러 대화가 동시에 흐른다. **훑어보는 화면**이라
  글자보다 그림이 먼저 읽히는 자리가 있다.
➡️ **설계 확정. 상세는 [기획 노트 — 스티커](../기획%20노트%20—%20스티커.md) 로 분리했다.**
아래는 요약이다.

- **자산은 사용자가 넣는다** — 앱이 스티커를 소유하지 않는다(앱 전역 저장, 여러 팩 동시 활성).
- **MCP 도구로 부르고 단독 메시지로 출력한다.** 글 안의 표기를 그림으로 치환하는 방식은 배제
  (모델이 의도치 않게 쓴 문자열이 그림이 되는 사고). 인라인 이모지는 다루지 않는다.
- **스티커 한 장 = 이름 1 · 태그 다수 · 설명 1.** 태그가 후보를 좁히고 설명이 최종 선택을 한다.
  등록 시 비전 모델이 셋을 제안하고 사람이 검수한다(200장을 손으로 다는 것은 불가능하다).
- **태그는 통제하지 않고 일부러 다양하게 단다.** LLM 은 한 단어로 검색하지 않으므로 조회도
  `query: [여러 단어]` 로 받는다. 어휘를 표준화하면 오히려 어휘 밖 단어에서 0건이 난다.
- **⚠️ 보이는 것과 남는 것은 이 설계에서 닫힌다.** 도구 호출과 결과가 대화 이력에 남아 모델이
  자기가 무슨 톤을 냈는지 읽는다. [P-19] 의 함정은 **표기 치환 방식에서만** 터지는 문제였다.
- **상시 컨텍스트 비용 0** — 카탈로그는 부를 때만 들어오고, 활성 팩이 없으면 지시문 섹션 자체가
  안 들어간다(팩 할당 여부가 곧 기능의 on/off).
- **연관**: [P-19](보이는 것 ↔ 모델이 받는 것) · [F-2](멤버가 대화창에 이미지 붙이기 — **문서가
  처음 적었던 "스티커는 F-2 의 특수 케이스"는 틀렸다.** 아래 착수 순서 메모 참고)

## F. 확장 — 앱 자체를 늘리는 방법

### F-1. UI 인터랙션을 데리고 오는 자체 MCP 서버 · `제안`

특정 기능을 위한 **자체 MCP 서버**를 붙여, 그 기능이 필요로 하는 **인터랙션까지 앱 UI에
표시**되게 한다. 도구 호출만 되는 게 아니라, 그 도구가 필요한 승인·입력·상태가 워크벤치
안에서 사용자에게 보이는 형태로 나타나는 것이 핵심.

- **디스코드 연결이 이미 그 모양이다.** `discord-connect`/`discord-send` 는 단순 도구가 아니라
  앱이 채널을 만들고, 들어온 메시지를 `<channel source="discord">` 로 턴에 실어주고, 연결
  상태를 UI 에 표시한다 — 즉 **도구 + 앱 측 인터랙션**이 한 벌로 묶여 있다. 이 조합을 다른
  기능에도 일반화하자는 것.
- 재료: 인프로세스 MCP 툴 표면([partyBridge.ts](../../src/core/partyBridge.ts))이 이미
  도구명·설명·핸들러를 한 파일에 모아두고, 핸들러는 자동화 HTTP API 를 통해 AppController 와
  같은 경로로 들어간다. 즉 **도구를 늘리는 축은 이미 있고, 없는 것은 "그 도구가 UI 를 띄우는"
  축**이다.
- 결정 필요:
  - **1차 대상 기능이 무엇인지** — 일반화 골격부터 만들면 쓰이지 않는 추상이 되기 쉽다.
    실제로 넣고 싶은 기능 하나를 이 방식으로 먼저 만들고, 두 번째가 생겼을 때 공통화하는 편이 안전.
  - **UI 표현 방식** — 기능마다 화면을 새로 만들 것인가, 아니면 "도구가 요구하는 인터랙션"을
    표현하는 **공통 표면**(승인 카드 / 폼 / 상태 배지)을 두고 거기에 얹을 것인가. 후자면
    Codex 승인 카드·plan 카드가 이미 비슷한 자리를 차지하고 있으니 그 관례를 재사용.
  - **범위** — 앱에 내장하는 자체 MCP 만인가, 사용자가 외부 MCP 서버를 붙이고 그 인터랙션까지
    표시하는 데까지 가는가. 후자는 신뢰·권한 설계가 따라붙는다.
- 규칙: AGENTS.md 대로 UI 와 HTTP 자동화 API 가 같은 `AppController` 메서드를 통과해야 하고,
  [apiSpec.ts](../../src/shared/apiSpec.ts) + [API.md](../API.md) 등록이 필요하다.

### F-2. 멤버가 대화창에 **이미지를 붙일 수 있게** · `제안`

지금 이미지는 **사용자 → 멤버** 한 방향뿐이다(붙여넣기·드롭으로 첨부). 반대 방향이 없어서
멤버는 무엇을 보여주고 싶어도 **경로나 URL 을 글로 말할 수밖에 없다.**

- **요청**: 도구로 **인터넷 이미지(URL)** 와 **로컬 이미지(경로)** 를 대화창에 붙일 수 있게 한다.
- **왜 자연스러운가**: 캡처를 찍는 QA 멤버, 차트를 만드는 분석 멤버, 디자인을 비교하는 멤버가
  전부 지금은 "파일을 열어보세요"라고 말하고 끝난다. 결과물이 대화 안에 남지 않는다.
- **재료는 이미 있다**: 인프로세스 MCP 툴 표면([partyBridge.ts](../../src/core/partyBridge.ts))에
  도구를 늘리는 축이 있고, 트랜스크립트는 이미 이미지 블록을 렌더한다(사용자 첨부가 그렇게 보인다).
  `mcp__agentparty-app__discord-send-image` 가 **이미 이미지를 다루는 선례**다 — 다만 목적지가
  디스코드일 뿐 대화창이 아니다.
- **결정 필요**:
  - **원본을 어디에 두는가** — URL 을 그대로 참조하면 나중에 깨지고(외부 의존), 받아서 저장하면
    보관 정책이 필요하다. 워크스페이스 `.agent_party_app/` 아래가 자연스럽다([P-13] 과 같은 저장소)
  - **로컬 경로의 신뢰 범위** — 멤버가 임의 경로를 읽어 대화에 올릴 수 있으면 워크스페이스 밖
    파일이 노출된다. cwd 안쪽으로 제한할지, 승인을 받을지
  - **원격/WSL 경로 변환** — 멤버가 보는 경로와 앱이 여는 경로가 다르다([P-13] 과 같은 문제)
  - **다른 멤버도 그 이미지를 볼 수 있는가** — 대화창에 붙는 것과 다음 턴 컨텍스트에 들어가는 것은
    별개다. 후자면 비전 미지원 모델에서의 동작도 정해야 한다
  - **크기·개수 상한** — 대화 트랜스크립트가 이미지로 비대해지는 것을 막아야 한다
- **연관**: [F-1] 의 "도구 + 앱 측 인터랙션 한 벌" 패턴의 구체 사례다. 저장소는 [P-13](붙여넣은
  이미지를 파일로 저장) · [P-18](대화창 이미지 복사·전체보기)과 공유하게 되므로 함께 설계할 것.

### F-3. 파일 내용을 **출력하지 말고 미리보기로 붙이기** · `제안`

"이 SQL 좀 보여줘"처럼 **이미 파일에 있는 내용을 사람이 보려는** 요청에서, 멤버가 그 내용을
답변으로 타이핑하는 대신 **파일 미리보기 카드**를 대화창에 붙인다. 내용은 앱이 디스크에서
읽어 렌더하므로 모델의 출력 토큰을 쓰지 않는다.

- **왜**: 파일을 그대로 받아치는 것은 모델이 하는 일 중 **가장 비싸면서 가장 가치가 없는 일**이다.
  이미 존재하는 바이트를 토큰으로 다시 만들어내는 것이라, 비용은 파일 크기에 비례하는데 새로
  생기는 정보는 0이다. 게다가 그 출력은 트랜스크립트에 남아 **이후 모든 턴의 컨텍스트를 계속
  차지한다** — 한 번 비싼 게 아니라 계속 비싸다.
- ⚠️ **핵심 구분**: 이건 *사람이 볼 때만* 절약이다. 멤버가 그 내용을 근거로 **판단해야 하면**
  어차피 읽어야 하므로 입력 토큰은 그대로다. 즉 이 기능이 대체하는 것은 "읽기"가 아니라
  **"사람에게 보여주려고 다시 쓰기"** 다. 이 선을 흐리면 "미리보기를 붙였으니 안 읽어도 된다"는
  잘못된 절약으로 이어진다.
- **재료는 이미 있다**:
  - 인프로세스 MCP 툴 표면([partyBridge.ts](../../src/core/partyBridge.ts)) — 도구 하나를 더한다
  - 파일 참조 표현은 이미 있다([fileReferences.ts](../../src/shared/fileReferences.ts) — 작성창의
    멘션 칩이 쓰는 것)
  - **큰 페이로드를 트랜스크립트 밖에 두는 선례**가 이미 있다: 도구 스크린샷을 외부에 저장하는
    [transcriptImages.ts](../../src/shared/transcriptImages.ts). 미리보기도 같은 규칙을 따라야
    트랜스크립트가 파일 내용으로 비대해지지 않는다([transcriptCap.ts](../../src/shared/transcriptCap.ts))
- **결정 필요**:
  - **어디까지 보여주는가** — 앞 N줄인지, 줄 범위 지정인지, 접었다 펴는 전체인지. SQL·CSV·로그는
    앞부분만으로 충분한 경우가 많지만 "끝을 보고 싶은" 로그도 있다
  - **누가 파일을 읽는가** — 앱이 직접 읽으면 WSL/원격 멤버의 파일에는 닿지 못한다. 그쪽은
    엔진이 읽어 넘겨야 한다([workspaceLocation.ts](../../src/shared/workspaceLocation.ts),
    [F-2] 의 경로 변환 문제와 동일)
  - **경로 신뢰 범위** — [F-2] 와 같은 문제다. cwd 밖 파일을 멤버가 임의로 대화에 올릴 수 있으면
    안 된다
  - **다음 턴 컨텍스트에 들어가는가** — 들어가면 절약이 사라진다. 기본은 "사람에게만 보이고
    컨텍스트에는 경로+요약만" 이어야 한다. 이 기본값이 이 기능의 존재 이유다
  - **바이너리·거대 파일** — 미리보기 불가 사유를 조용히 빈 카드로 두지 말고 표시할 것
- **연관**: [F-1] 의 "도구 + 앱 측 인터랙션 한 벌" 패턴, [F-2] 와 경로·신뢰 범위 설계를 공유한다.
  셋을 따로 만들면 경로 변환을 세 번 만들게 된다.

### F-4. **멤버 사이로 이미지 보내기** · `제안`

멤버가 다른 멤버에게 이미지를 보낸다. QA 멤버가 찍은 스크린샷을 수정 담당 멤버에게 그대로
넘기는 식 — 지금은 "어느 경로에 저장했다"고 **글로 말하는 것**이 유일한 방법이다.

- **지금 없는 것은 딱 하나다.** 파티 메시지가 텍스트만 나른다:
  [types.ts](../../src/shared/types.ts) 의 `PartyMessage` 는 `content: string` 뿐이고,
  `send` 도구도 `to` + `content` 두 문자열만 받는다([partyBridge.ts](../../src/core/partyBridge.ts)).
- **나머지는 이미 있다**:
  - 첨부 표현과 **큐가 첨부를 나르는 경로**가 이미 산다 — `sendUserMessage(name, text, attachments)`
    와 `enqueueForMember` 가 `ImageAttachment[]` 를 들고 다닌다
    ([partyApplicationService.ts](../../src/main/application/partyApplicationService.ts)).
    사용자 → 멤버 방향은 이미 이미지가 간다는 뜻이다.
  - `discord-send-image` 는 **멤버가 로컬 파일을 지목하면 앱이 읽어 내보내는** 선례다. 목적지가
    디스코드일 뿐 구조는 같다.
  - 수신 모델이 이미지를 못 받으면 **눈에 보이게 거절**하는 규칙도 이미 있다(텍스트 전용 모델에
    이미지를 보내면 `vision` 진단으로 거부, 조용히 버리지 않음 — [API.md](../API.md)).
- ⚠️ **[F-2]·[F-3] 과 결정적으로 다른 점**: 보내는 멤버와 받는 멤버가 **다른 기계에 있을 수 있다**
  (WSL 멤버 ↔ Windows 멤버). 그러면 경로는 건너편에서 아무 의미가 없다 — **경로가 아니라 바이트가
  움직여야 한다.** F-2/F-3 은 "앱이 읽어서 보여주면 끝"이지만 이건 엔진 경계를 넘는 전송이다.
- **결정 필요**:
  - **바이트를 어디에 두는가** — 파티 저장소(`.agent_party_app/`)에 두고 양쪽이 참조하는 방식이
    자연스럽다. 도구 스크린샷을 트랜스크립트 밖에 두는
    [transcriptImages.ts](../../src/shared/transcriptImages.ts) 와 같은 규칙을 쓸 것
  - **큐에 앉아 있는 이미지** — 메시지는 수신자의 턴이 끝날 때까지 **보이는 큐에서 기다린다**.
    그동안 이미지가 어디 살아 있어야 하고, 멤버가 지워지거나 큐를 비우면 정리돼야 한다
  - **Message Gate 가 이미지를 어떻게 심사하는가** — 게이트는 나가는 메시지를 리뷰어 모델에게
    보낸다. 리뷰어가 텍스트 전용이면 이미지를 못 본다. 캡션만 심사할지, 이미지 있는 메시지는
    통과시킬지, 비전 리뷰어를 요구할지 정해야 한다([messageGate.ts](../../src/shared/messageGate.ts))
  - **broadcast 는 어떻게 되는가** — 전원에게 이미지를 뿌리면 텍스트 전용 멤버가 섞여 있다.
    일부만 거절되는 부분 실패를 어떻게 보고할지
  - **크기·개수 상한** — 파티 저장소가 이미지로 비대해지는 것을 막을 것
- **연관**: [F-2] 와 저장·상한을 공유한다. 다만 F-2 는 자기 대화창에 붙이는 것이고 이건 **경계를
  넘는 전송**이라, F-2 를 먼저 만들어도 이 항목의 어려운 부분(엔진 경계·큐·게이트)은 그대로 남는다.

## G. 반입 — 밖에서 하던 것을 파티로 가져오기

### G-1. 기존 세션을 멤버로 import · `제안`

이미 쓰고 있던 **하네스 세션(예: 터미널에서 돌리던 Claude Code 대화)을 멤버로 가져온다.**

- **왜 자연스러운가**: 지금은 파티 안에서 시작한 대화만 멤버가 된다. 그런데 사용자는
  **앱 밖에서 이미 일하고 있던 맥락**을 갖고 있고, 그걸 파티로 데려오려면 **처음부터 다시
  설명해야 한다.** 반입이 되면 "혼자 하던 일을 파티로 확장"하는 동선이 생긴다.
- **재료가 이미 상당하다**:
  - **하네스 thread ID 저장·재사용**이 이미 있다(기능정의서 1-13-4 대화 연속성).
    즉 **"이어 붙이는 기계"는 만들어져 있고, 없는 것은 "무엇에 이어 붙일지 고르는 화면"** 이다.
  - Claude Code 원본은 `~/.claude/projects/<인코딩된 cwd>/<uuid>.jsonl` 에 있다
    ([B-11](../베타%20공개%20준비/B-11%20파티%20찾기.md) 조사에서 확인).
    Cursor 도 앱이 저장하는 세션 번호가 곧 Cursor 쪽 폴더명이라 **이미 연결돼 있다**([#26]).
  - 세션 목록 표면도 있다 — `GET /api/sessions/history`, `POST /api/sessions/resume`
- **⚠️ 함정 — 경로가 키다**: 하네스는 대화를 **절대 경로로 키잉**한다. 그래서
  **어느 작업공간에서 하던 세션인지가 곧 식별자**다. 반입 화면은 **작업공간 기준으로 묶어
  보여주는 것**이 자연스럽고, 이는 [B-11](../베타%20공개%20준비/B-11%20파티%20찾기.md) 의
  작업공간 목록과 **같은 재료**다.
- **결정 필요**:
  - **어디까지 가져오나** — 대화만? 그 세션이 쓰던 모델·권한 설정까지?
  - **원본을 공유하나 복제하나** — 같은 세션을 앱과 터미널이 동시에 이어가면 충돌한다.
    "가져오면 원본은 놓는다"가 안전하다
  - **하네스별 차이** — Claude/Codex/Cursor 가 세션을 남기는 방식이 다르다.
    셋 다 되는지, 되는 것부터 하는지
  - **목록을 어떻게 보여주나** — 세션이 많으면 [F-05](../베타%20공개%20준비/F-05%20스킬%20커맨드%20팔레트.md) 와
    같은 "많은 항목 중 고르기" 문제가 또 나온다
- **연관**: [B-11](../베타%20공개%20준비/B-11%20파티%20찾기.md)(작업공간 목록 — 같은 화면 계열) ·
  [F-08](../베타%20공개%20준비/F-08%20세션%20기록%20방침.md)(앱 기록 vs 하네스 원본) ·
  [F-04](../베타%20공개%20준비/F-04%20멤버%20생성%20빠르게.md)(멤버를 만드는 또 하나의 길)

## I. 단일 창구 — 팀을 몰라도 쓰게 하기

### I-1. 중계하지 않고 위임하는 파티 멤버 라우팅 · `기획`

사용자가 파티 구성과 각 멤버의 역할을 외우지 않아도, 하나의 대화 창구가 요청을 적절한
전문 멤버에게 **위임**한다. 답은 창구가 받아 다시 쓰지 않고, 담당 멤버가 사용자에게 직접 한다.

- **핵심 가치**: 답의 손실과 이중 비용을 줄이는 것보다, 창구에 모든 전문가의 대화가 쌓이지 않게
  하여 **멤버별 컨텍스트를 분리**하는 데 있다.
- **핵심 원칙**: 입력은 라우터를 통과할 수 있지만 출력은 라우터를 통과하지 않는 비대칭 경로.
- **현재 재료**: 멤버 `role`, `send`·`list`·`member-status`, Message Gate, 메시지 큐와 인터럽트 정책.
- **별도 검토 대상**: `@멤버`처럼 사용자가 수신자를 직접 정하는 명시적 라우팅과, 시스템이
  담당자를 고르는 자동 라우팅은 같은 전달 기반을 쓸 수 있지만 서로 다른 제품 기능이다.
- **정본**: [기획 노트 — 파티 멤버 라우팅](../기획%20노트%20—%20파티%20멤버%20라우팅.md)

## 착수 순서에 대한 메모

- **A-1 + A-2를 함께** — 재료가 같고, 따로 만들면 두 번 만든다. 새 기능이라 기존 구조를
  훼손하지 않는 것도 장점.
- **B-1 + B-2를 함께** — 트리거만 다르고 몸통이 같다. 범위가 좁아 빨리 끝난다.
- **D-1은 별건의 큰 작업** — 보안이 1급 요구사항이라 다른 것과 섞어서 하기 어렵다.
- **D-3은 D-1과 무관하게 작다** — 같은 D 묶음이지만 네트워크도 인증도 없다. 핸드오프 방식만
  잡으면 이미 있는 `harnessSessionId` 를 꺼내 터미널을 띄우는 일이라, 앱이 막히는 상황
  (대화형 재인증)을 사용자가 스스로 뚫을 수 있게 해준다.
- **E-3은 F-2 를 기다리지 않아도 된다** — 처음엔 스티커를 F-2(멤버가 이미지 붙이기)의 특수
  케이스로 적었지만 반대다. F-2 의 어려운 문제 셋(로컬 경로 신뢰 범위 · **원격/WSL 경로 변환** ·
  원본 보관 정책)은 전부 *멤버가 임의 파일을 가리키기 때문에* 생긴다. 스티커는 멤버가 **이름만
  보내고 그림은 앱이 자기 쪽에서 꺼내므로 이미지가 엔진 경계를 넘지 않는다.** WSL·원격 멤버에서
  동작이 같다. 오히려 F-1("도구 + 앱 측 인터랙션 한 벌")의 **가장 싼 첫 사례**다.
- **F-2 + F-3을 함께** — 둘 다 "멤버가 로컬 파일을 대화창에 붙인다"이고, 어려운 문제(경로 신뢰
  범위 · 원격/WSL 경로 변환 · 트랜스크립트 밖 보관)가 **같은 세 가지**다. 따로 만들면 세 번 만든다.
  F-3이 더 싸게 끝난다 — 텍스트라 이미지의 보관·비전 지원 문제가 없다.
- **버그가 먼저일 수 있다** — [FEEDBACK.md](../FEEDBACK.md) 하단에 재시작 후 멤버 대화가
  닫힌 것으로 인식되며 대화가 날아가는 문제 등 미정리 항목이 있다. 새 기능보다 우선순위가
  높은지 먼저 판단할 것.
