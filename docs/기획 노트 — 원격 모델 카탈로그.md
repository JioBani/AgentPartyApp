# 기획 노트 — 원격 모델 카탈로그

작성일: 2026-09-02
상태: 구현 완료 (feat/remote-model-catalog) — 구현 결과는 `docs/API.md`의
`GET /api/models/catalog` 절과 `src/main/remoteModelCatalog.ts` 참고

## 문제

`src/shared/modelCatalog.json`은 라우팅·가격·리더보드·reasoning 스펙의 단일 소스인데,
**앱 번들 안에 박혀 있다.** 새 모델이 나오면:

1. 개발자가 JSON을 수정하고
2. 앱을 빌드해서
3. 릴리즈를 배포해야만

사용자에게 도달한다. 사용자는 앱을 수정할 수 없으므로, 새 모델 반영 속도가
릴리즈 주기에 묶인다. 목표는 **카탈로그 배포를 앱 릴리즈에서 분리**하는 것.

## 접근 방식 비교: 원격 카탈로그 vs 라이브 디스커버리

두 방식은 대체재가 아니라 보완재다. 역할이 다르다.

| | 원격 카탈로그 | 라이브 디스커버리 |
|---|---|---|
| 해결하는 것 | 개발자 큐레이션이 사용자에게 도달하는 속도 | 큐레이션 전 공백 (개발자가 자는 동안 새 모델 출시) |
| 정보의 질 | 높음 — 가격, perf 티어, 실측 제약(xAI effort 무시, `xaiClientToolsBeta` 400 등) 포함 | 낮음 — 프로바이더가 API로 주는 것만 (id, 일부 가격/컨텍스트) |
| 커버 범위 | 전 프로바이더 동일 | 프로바이더별 편차 큼 (아래 표) |
| 인프라 | 정적 파일 호스팅 1개 | 없음 (각 프로바이더 API/CLI 이용) |
| 개발자 작업 | JSON 수정 + push | 없음 |
| 실패 모드 | fetch 실패 → 캐시/번들 폴백 | 프로바이더 API 변경 시 감지 깨짐 |

**결정: 원격 카탈로그 우선.** 근거:
- 우선 대상 4개 하네스(claude, codex, cursor, grok) 중 Claude는 디스커버리 수단이
  사실상 없다(아래). 원격 카탈로그만이 4개 전부를 커버한다.
- 큐레이션 필드(perf, 한국어 설명, 실측 제약)는 어차피 자동화 불가 — 사람이 쓴
  데이터를 빠르게 배포하는 채널이 본질적 요구다.
- "다른 것들도 쉽게 추가"하는 확장 채널로 재사용 가능(공지, 기본값 튜닝 등).

라이브 디스커버리는 후속 과제로 남긴다.

### 하네스별 디스커버리 가능성 (참고, 후속 과제용)

| 하네스 | 감지 수단 | 상태 |
|---|---|---|
| Codex | app-server `model/list` | **이미 구현됨** — 디스커버리가 정적 카탈로그보다 우선 머지 (`buildModelRoutes`) |
| Cursor | `cursor-agent --list-models` | 이미 호출 중(`cursorAgentCli.ts`)이나 grok 필터링 후 진단용으로만 사용. 라우트 빌드에 연결하면 됨 — 작업량 소 |
| Grok | ACP `session/new`가 모델 목록 보고 | 현재 `grokHarnessRoutes()`에 하드코딩. 배선 작업량 소~중 |
| Claude | Anthropic `/v1/models`는 API 키 기준 | 구독 OAuth 토큰으로 조회 가능한지 **미검증**. 단, `inferClaudeCodeProvider`가 미등록 `claude-*` id를 네이티브로 통과시키므로 실행 자체는 카탈로그 없이도 됨 — 문제는 목록 노출뿐 |

## 호스팅 방식 비교 (서버 없음 전제)

전제: 별도 서버를 운영하지 않는다. `JioBani/AgentParty-releases`가 **public repo**이고
(2026-09-02 무인증 API 200 확인), electron-updater 때문에 사용자 앱이 이미 GitHub에
접속하고 있다 — 신규 네트워크 의존성이 아니다.

### A안 — releases repo에 JSON 커밋, raw URL fetch ✅ 채택

`https://raw.githubusercontent.com/JioBani/AgentParty-releases/main/modelCatalog.json`

| 장점 | 단점 |
|---|---|
| 업데이트 = JSON 수정 + push 한 번 | raw CDN 캐시로 반영에 최대 ~5분 지연 |
| git 히스토리가 곧 카탈로그 버전 관리 (롤백 = revert) | repo가 private으로 바뀌면 즉시 깨짐 (업데이터도 같이 깨지므로 실질 리스크 아님) |
| 비용 0, 유지보수 대상 0 | GitHub 장애 시 접근 불가 (캐시/번들 폴백으로 완화) |
| 기존 배포 채널(GCM 토큰, push 권한)과 동일한 권한 모델 | |

### B안 — 고정 태그 릴리즈 에셋

`catalog` 태그 릴리즈에 `gh release upload --clobber`로 에셋 덮어쓰기.

| 장점 | 단점 |
|---|---|
| CDN 캐시 지연 없음 (에셋 URL은 즉시 최신) | 업데이트 절차가 커밋보다 번거로움 (릴리즈 에셋 조작) |
| | 히스토리가 git에 안 남음 — 덮어쓰기라 이전 버전 유실 |
| | "릴리즈 목록"에 카탈로그용 가짜 릴리즈가 섞임 |

### C안 — GitHub Pages

| 장점 | 단점 |
|---|---|
| 정식 CDN, 커스텀 도메인 가능 | Pages 빌드/배포 스텝이 추가됨 |
| | 이 용도(파일 1개)엔 과함 |

### D안 — jsDelivr (`cdn.jsdelivr.net/gh/...`)

| 장점 | 단점 |
|---|---|
| 강한 CDN | 기본 캐시 12시간 — "빨리 반영"이라는 목적 자체와 충돌 |

### E안 — Gist

| 장점 | 단점 |
|---|---|
| 간단 | repo 히스토리·권한 체계와 분리된 별도 관리 지점 생김 |

**A안 채택.** 반영 지연 ~5분은 이 용도에서 무의미한 수준이고, 나머지 안은 전부
A안 대비 추가 비용만 있고 이득이 없다.

## 클라이언트 설계

로드 우선순위와 폴백:

```
원격 최신 (fetch 성공 + 스키마 검증 통과)
  → 로컬 캐시 (userData, 직전 성공본)
    → 번들 내장본 (최후 안전망, 앱 릴리즈 시점 스냅샷)
```

- **fetch 시점**: 앱 시작 시 1회 + 주기(예: 6시간). 시작을 블로킹하지 않음 —
  번들/캐시로 먼저 뜨고 원격 도착 시 갱신.
- **스키마 버전**: 카탈로그에 `schemaVersion`을 넣는다. 구버전 앱이 새 스키마를
  만나면 그 원격본을 **버리고 캐시/번들로 폴백 + 로그** — 절반만 파싱해서 깨진
  라우팅을 만들지 않는다. 새 필드 추가(마이너)는 무시-안전하게, 파괴적 변경만
  메이저 범프.
- **실패 가시성**: fetch/검증 실패는 로그와 진단으로 노출한다. 조용한 폴백 금지
  (AGENTS.md). UI에는 현재 카탈로그의 출처(원격/캐시/번들)와 시각을 표시.
- **동기 접근 전환**: `modelCatalog.ts`의 module-load 시점 `MODELS` 상수를
  로드된 카탈로그를 참조하도록 바꿔야 함. main(레지스트리·라우터)과
  renderer(Runtime 모달) 양쪽 소비 지점의 갱신 전파가 구현의 핵심 난점.
- **자동화 API**: 카탈로그 상태 조회·강제 새로고침을 `AppController` 메서드로
  만들고 라우트 테이블 등록 + `docs/API.md` 문서화 (AGENTS.md 규칙).

## 리스크와 완화

| 리스크 | 완화 |
|---|---|
| 원격본 오타/깨진 JSON이 전 사용자에게 즉시 배포됨 | 스키마 검증 실패 시 폴백 + push 전 로컬 검증 스크립트(카탈로그 lint)를 릴리즈 절차에 추가 |
| 구버전 앱 ↔ 신버전 카탈로그 비호환 | `schemaVersion` 게이트, 파괴적 변경은 메이저 범프로만 |
| GitHub 접근 불가 환경(방화벽 등) | 캐시/번들 폴백으로 기능 유지, 출처 표시로 사용자가 구버전임을 인지 |
| 카탈로그 갱신이 세션 중 모델 목록을 바꿔 UI가 흔들림 | 갱신은 라우트 재빌드 트리거로만 반영, 진행 중인 멤버 세션의 모델은 불변 |

## 확정된 결정 (2026-09-02)

- **fetch 주기: 6시간** + 앱 시작 시 1회. 강제 새로고침은
  `POST /api/models/catalog/refresh`.
- **진실은 소스 repo의 `src/shared/modelCatalog.json` 하나.** releases repo의
  배포본은 `npm run catalog:publish`(scripts/publish-catalog.mjs)로만 갱신 —
  스키마 lint 후 GitHub Contents API로 커밋, 인증은 릴리즈와 같은 GCM 토큰.
  `release:win`에도 끼워 넣어 앱 릴리즈 때 원격이 자동으로 따라간다
  (릴리즈됐는데 원격이 구버전인 상태 방지).
- 소스 repo가 private임을 확인(2026-09-02)했으므로 "소스 repo에서 직접 raw
  fetch" 경로는 불가 — 위 publish 스크립트 방식으로 확정.
