## 1. 방법

앱 트랜스크립트가 아니라 하네스 원본(`~/.claude/projects/<proj>/<sessionId>.jsonl`)에서 두 종류를 분리 추출했다.

| 데이터 | 정의 | 규모 |
|---|---|---|
| 멤버 간 메시지 | `send`/`broadcast` 툴 호출의 본문 | SEL-6877 891건 · SEL-6874 261건 · CARR-892 207건 |
| 사용자 직접 입력 | user 턴 중 `tool_result`·`<channel>`·인터럽트 표식 제외 | 5개 파티 약 1,645건 |

판정 기준은 앱이 각 멤버에게 실제로 준 `MEMBER.md`의 `Role:` 원문이다. 추측한 역할이 아니다.

판정 축은 셋이다.

- **A. 불필요하게 과한 확인** — 확정 사항 재질의, 상대가 답한 것 재확인, 자기 권한 내 결정을 질의, 내용 없는 수신확인, 상대 응답 전 덧붙여 보내기
- **B. 불필요한 내용 전파** — 수신자 역할에 불필요한 세부, 공유 문서 내용을 본문에 재기술, 요청받지 않은 정보 투척, 같은 내용을 형식만 바꿔 재발송
- **C. 역할에 맞지 않는 보고·지식 공유** — 역할 정의가 금지한 판정·지시·처리

사용자 입력은 별도 축으로 판정했다.

- **U1 라우팅 오류** — 역할 밖 질문·지시, 담당자 건너뛰기, 같은 사안 중복 질의
- **U2 업무 배정 오류** — 역할 정의가 금지한 행위 지시, 권한 밖 업무 배정
- **U3 지시 품질** — 대명사만으로 지시, 번복, 나눠 묻기, 이미 답한 것 재질의

### 2-2. 축약 재발송 — B의 실체

B의 대부분은 하나의 행동이다: **긴 원문을 보내고 1분 안에 짧은 버전을 다시 보낸다.**

```
impl→req    728자 → 441자 → 153자                    (3연속)
impl→req    651 → 517 → 315 → 162 → 132자            (5연속)
impl→main  1018 → 405 → 130 → 112자                  (4연속, 2분)
perf→req   2330자 → 1854자   (용어만 평이하게: Extended Events→추적 도구)
req→impl    673자 → 글자 단위로 동일한 673자
explore→impl 8123자 → 7104자 ("동일 내용, 기준선만 갱신"이라 본인이 명시)
```

**파티마다 성격이 다르다.**

- SEL-6877: 64건 중 약 50건. 발신자가 `perf`·`impl`·`explore`·`req`·`main` **전원**. 구조적 행동.
- SEL-6874: 261건 중 약 20건(8%). 그중 **16건이 impl 단독**. 한 멤버의 보고 습관.
- CARR-892: 소수. main→impl dispatch 축약 2건이 대표.

### 2-3. 재발송의 원인 — 메시지 교차

멤버들이 재발송하면서 이유를 직접 적었다.

```
"교차된 것 같아 재확인: DD 재설계 정식 dispatch 를 이미 보냈어"
"교차된 듯. 리펙토링(구현) dispatch 를 이미 보냈어"
"방금 전 같은 건으로 회신을 보냈는데 엇갈린 듯합니다. 핵심만 다시 짚습니다"
"보낸 3-3 dispatch 메시지가 impl 의 변경 영역 메시지와 순서가 엇갈려 도착한 모양이다"
"회신 엇갈린 것 같습니다 — 결정 확정 전에 꼭 확인 부탁드립니다"
```

교차/엇갈림 언급 횟수는 **SEL-6877 37회 · CARR-892 5회 · SEL-6874 3회**로, 재발송이 가장 심한 파티와 일치한다.

메커니즘: A가 B에게 보냄 → B는 이전 메시지에 대한 답을 이미 발신 중 → A에게 엉뚱한 답이 도착 → A가 "엇갈렸나, 내 게 안 갔나" 판단 → 재발송.

CARR-892의 `main`이 독립적으로 같은 진단을 내리고 처방까지 기록했다(08-07T02:12).

> "기본값(queue)으로 보내면 수신자가 현재 턴을 끝낼 때까지 메시지가 처리되지 않아, 이번 이슈에서 여러 번 dispatch 와 인계가 순서 엇갈려 서로 대기하는 일이 있었다. `interrupt: true` 면 즉시 처리된다."

**다만 완전한 해결책은 아니다.** SEL-6877은 `interrupt: true`를 처음부터 파티 기본으로 켜고도 교차가 37회 났다.

### 2-4. 재발송은 정보를 잃는다

```
perf→main  181자 (워크트리 상충 1건 포함) → 축약 재송부에서 상충 1건 누락
perf→main  게이트 현황 3회 발송 → U9a 가 "조건부 해제" / "차단 유지"로 갈림
explore→req 1708→927→773→504자 → 축약될수록 근거 소실 → req "근거가 무엇인가" 되물음
```

낭비일 뿐 아니라 **모순과 추가 왕복을 만든다.**

### 2-5. 역할 이탈은 오답을 만든다

담당 역할에게 뒤집힌 사례가 7건 확인됐다.

| 이탈 | 결과 |
|---|---|
| perf 가 단위 완료 판정 회수 | req "애초 완료 판정 내린 적 없음" 정정 |
| perf 가 개발자 QA 완료 판정 | req 판정과 충돌 → main 커밋 가부 혼선 |
| main 이 마이그레이션 3단위 확정 | req 철회 → 재작업 |
| impl 이 호출경로 직접 추적 | 오판 → req 가 사용자에게 불필요한 질문 |
| req 가 코드 동작 추측 (2건) | 3분 뒤 본인 철회 |
| explore 가 정책 판정 | 6분 뒤 본인 철회 |
| impl 이 병목 진단 | perf 가 뒤집음 → 가설 폐기 |
| req 가 dataField 지정 (CARR-892) | explore 정정 — "`extra.dongNm` 은 로젠 전용" |

원인은 **남의 역할을 하면 그 역할의 방법론이 없기 때문**이다. impl 본인의 시인이 이를 보여준다.

> "같은 이름(`insert_order`)이 여러 파일에 보이길래 그 파일들이 이 경로를 부른다고 단정했다."

`explore`의 전수 추적 대신 파일명 매칭으로 때운 결과다.

### 2-6. 이탈 방향은 파티마다 다르다

| 파티 | 이탈 주체 | 방향 |
|---|---|---|
| SEL-6877 | 전 멤버 | 옆·위 한 단계씩 |
| SEL-6874 | explore · req | 위(explore) / 파일·라인까지 아래로 깊이(req) |
| SEL-6874 | impl | **아래** — 보고 규율 붕괴(금지된 커밋해시·파일 나열) |
| CARR-892 | **main** | **아래 두 칸** (impl·test 영역 침범) |

**"모두가 한 단계씩 침범한다"는 성립하지 않는다.** 파티마다 한두 멤버가 크게 벗어나고, 누구인지는 매번 다르다. 역할별 고정 처방이 듣지 않는 이유다.

### 2-7. 가장 비싼 유형 — 이중 발주

```
07-28T09:04  req→explore  4개 항목 위임
07-28T09:05  req→impl     같은 4개 항목        → 장문 회신 2건 중복 생산

08-04T07:05  req→explore  탐색 질문 3개
08-04T07:06  req→impl     같은 3개            → 동일 전수조사를 각각 수행
```

메시지 중복이 아니라 **작업 중복**이다.

### 2-8. 제대로 작동한 지점

문제만 기록하면 왜곡이 된다. 파티가 설계대로 작동한 사례도 분명하다.

```
SEL-6874  impl→req  "DD 승인을 사용자에게 받아주실 수 있을까요?"
          req 반려  "제가 DD를 대신 읽고 요약해 승인받는 건 맞지 않습니다"

CARR-892  req→impl  "배치 좌표는 네가 정하면 된다 — 그건 설계 영역이라 내가 답하지 않는다"
          req→impl  "화면의 정확한 버튼 명칭은 UR/SR 범위 밖이다. explore 에 코드 모드로
                     직접 요청해라 — 내가 답하면 추측이 섞인다"
          req→impl  공용 인터페이스 신설 건: "요구사항 개정 불필요. 구현 세부로 흡수한다"
```

CARR-892의 `req`는 가장 설계다운 질의(인터페이스 시그니처 변경)를 정확히 되돌려보냈고, `review`는 위반 0건이다. explore가 자기 오판을 명시 정정하고(SEL-6874 Q20→Q21→Q23) impl이 req 판정을 코드 근거로 반박한 것도 정상 작동이다. **모든 왕복이 낭비는 아니다.**

## 3. 사용자 작업 방식

### 3-1. 결과

| 파티 | 입력 | 문제 | 비율 | U1 | U2 | U3 |
|---|---:|---:|---:|---:|---:|---:|
| CARR-892 | 99 | 16 | **16%** | 7 | 4 | 5 |
| CARR-422 | 87 | 12 | 14% | 4 | 4 | 4 |
| SEL-6874 | 321 | 26 | 8% | 9 | 9 | 8 |
| develop | ~385 | 29 | 8% | 9 | 10 | 10 |
| SEL-6877 | 753 | 46 | 6% | 16 | 13 | 17 |

**작은 파티일수록 오류율이 높다.** 멤버가 적으면 한 명에게 몰아주게 되고, 그것이 곧 역할 위반이 된다.

### 3-2. `main`을 만들어 놓고 쓰지 않는다

| 파티 | 총 입력 | main | 전문 멤버 |
|---|---:|---:|---:|
| SEL-6874 | 321 | 22 (**6%**) | 299 (93%) |
| CARR-892 | 99 | 7 (**7%**) | 92 (92%) |
| SEL-6877 | 753 | 89 (11%) | 664 (88%) |
| CARR-422 | 87 | 20 (22%) | 67 (77%) |
| develop | 617 | 316 (51%) | 301 (48%) |

`main`의 역할 정의는 "Primary user-facing agent"인데 실제로는 6~11%만 받는다. 그런데 **main이 해야 할 일은 계속 발생하고, 그것이 옆 멤버로 샌다.**

```
SEL-6877 → perf   "main 한테 gpt sol medium 으로 다시 만들어달라고 해줘"
SEL-6877 → perf   "그럼 main 한테 너 지워다랄고 해줘"        ← 본인 삭제를 본인에게 중계
SEL-6874 → req    "gpt sol high 만들어서 핸드오프 문서 넘겨주고 다시 조사 요청해줘"
CARR-892 → req    "비전 제일 잘 파악하는 모델이 뭐지?"
CARR-422 → req    "sr 작성해주고 내 승인 없이 바로 디스패치 해줘"
develop  → harness "멤버 하나 만들어서 확인 요청해줘"          ← 최소 6회 반복
```

이것이 SEL-6877에서 main이 마이그레이션 3단위를 잘못 판정한 배경이다. **정보가 가장 적은 멤버(217k, 파티 최소)에게 조정 판단을 맡겨 놓고 상황은 알려주지 않았다.**

### 3-3. `req`가 만능 창구가 된다

CARR-892가 극단이다. **req 67건, impl·test·review 직접 입력 0건.**

```
CARR-892 → req  "docs 와 택배사모듈쪽 좀 찾아봐바"          ← req 는 코드 read 안 함
CARR-892 → req  "web 프로젝트 master 를 최신화 하고"         ← 저장소 조작
CARR-892 → req  "왜 커맨드를 사용하지? 마이그레이션을 사용 안하고"  ← 구현 수단 선택
CARR-892 → req  "impl 한테 물어봐바 많이 알고 있을거야"       ← 중계자로 사용
```

그리고 **2홉 패턴**이 반복된다.

```
사용자→req(코드 질문) → req 가 못 답함 → 사용자 "explore 한테 물어봐줘" → explore
```

SEL-6874는 req 149건인데 explore는 **3건**이다. 탐색 전용 멤버가 사용자와 사실상 단절돼 있다.

사용자 본인이 알아채고 재라우팅하는 경우도 있으나, **알아채기 전에 이미 한 턴을 쓴다.**

```
07-24T02:00  → req  "코드매칭에서 이미 상품명 매칭된 주문에 대해서 덮어 씌워버려?"
07-24T02:12  → req  "이거는 실제 코드를 봐야알겠네. explore 한테 내가 직접 물어볼게"
07-28T09:03  → req  "코드 선등록 매칭과 재고매칭이 동일한 매칭이야?"
07-28T09:04  → req  "ㄴㄴ 이거 impl 한테 물어봐바"            ← req 턴 통째로 낭비
```

### 3-4. 읽기 전용·비수정 멤버에게 쓰기를 시킨다

```
explore (읽기 전용)  ← "master 최신화 해줘" / "도메인 문서로 남겨줘" / "detach 하고 다시 attach 해줘"
perf (수정 금지)     ← "곳곳에 로그를 찍어서 확인해줘" / "측정 asp 코드 다 넣어줘"
                       "legacy, common 전부 detach 하고 qa 브랜치 attach 해줘"
impl                ← "마이그레이션 테스트는 다 지워줘"        (test 전용 영역)
harness (읽기 중심)  ← "너가 지워 걍" / "스킬 하나 만들어줘" / "동일한 시나리오를 돌려줘"
```

이는 단순 위반이 아니라 **산출물 신뢰성 문제**다. 측정자가 측정 대상 코드를 고치면 측정이 오염되고, 실제로 "너 계측 코드 지웠어?"로 뒤늦게 걱정하는 상황이 나왔다.

**사용자가 스스로 경계를 열었다는 점이 중요하다.**

```
08-03T04:57  → perf  "너가 그걸 왜 검증해 너는 코드리뷰 멤ㅂ가 아니고 성능만 측정하기 위한 멤버인데"
08-03T05:34  → perf  "건드려도 돼. 어차피 main 워크트리에서 수정할거 아니야?"    ← 40분 뒤
```

앞선 멤버 분석에서 `perf`의 역할 팽창을 "역할 이탈"로 판정했으나, **상당 부분은 사용자 지시를 따른 것**이다. 멤버 탓이 아니다.

### 3-5. 지시의 전제를 뒤에 붙인다

전 파티 공통이고 가장 비싸다.

```
SEL-6877  "작업브랜치 to qa와 to master 만들고..."  → 6턴 정정 → impl 이 병합 실행 → 롤백
CARR-422  "push 하고 to master, to qa mr 만들어줘"  → 2분 뒤 "아 front 는 develop" → MR 재작업
CARR-422  "detach 하고 다시 attach 해줘" → "ㄴㄴ 너가 해" → "그냥 니가 작업한거만"
SEL-6874  "이거 attach 해줘" → 대상 없음 → 스킬 문서 전문 두 개 추가 발송
```

`이거`로 시작해 대상·경로·브랜치를 빼고 다음 메시지로 보충한다. **되돌리기 비싼 작업(브랜치·MR·커밋·attach)에서 특히 반복된다.**

### 3-6. 즉흥 번복

```
07-16  impl/coder 구성을 하루에 sonnet → fable → opus → gpt sol xhigh  4회 교체
07-16T05:45  "gpt 5.6 sol medium 으로 열어줘" → 05:46 "아니다 high"     ← 1분, 생성 2회
07-29T07:43  "커밋해줘" → 07:44 "아 아니다 이거 잠만"
08-04T05:07  "사은품 매칭부터 성능테스트" → 05:08 "아니다 단건 매칭부터 QA 하자"
```

멤버 재생성은 컨텍스트를 0에서 다시 쌓게 한다. `docs/사용량조사.md`의 콜드 재구축 비용(SEL-6877 총비용의 20%) 위에 얹히는 항목이다.

### 3-7. develop — 전문 멤버를 만들어 놓고 두 명만 쓴다

멤버 12명 중 **main·harness에 86%**가 몰렸고, auth·test·impl2·trace·worktree는 사용자 직접 입력 **0건**이다.

`harness`의 정의는 "읽기 중심, 코드는 직접 안 고침"인데 실제 지시는 파일 삭제·스킬 생성·워크트리 attach·env 변경·QA 실행·Discord 보고·멤버 생성·impl 재트리거였다. **harness가 제2의 main이 되고, 정작 main은 단독 구현자로 밀려났다.**

그 대가가 이것이다.

```
08-03T01:39  → harness  "내가 저번에 요청했는데 어디까지 작업됐는지 모르겠네"
```

진행 상태 기억이 harness 컨텍스트에만 있어 사용자가 자기 지시의 행방을 추적하지 못한다. 인증 요구사항을 `auth`가 아닌 harness와 정리한 것도 같은 구조다.

### 3-8. 강점

역할 이탈을 **당사자보다 먼저 잡아낸다.**

```
"dd를 너가 왜확인해"                                    (req 의 DD 개입 차단)
"ur 이 많이 sr 또는 dd 쪽으로 끌려들어간거 같아"          (산출물 경계 이탈 감지)
"너가 그걸 왜 검증해 너는 성능만 측정하기 위한 멤버인데"    (perf 범위 교정)
"테스트 관련 이야기는 test2와 이야기할게"                 (자기 교정)
"찾는데 이거 explore 한테 시켜"                          (올바른 위임 제시)
"AuthorizesPermissionCode 이 패턴은 너가 이번에 추가한거 같은데, 근거가 뭐야?"
```

사람만 할 수 있는 결정(브랜치 전략·배포 단위·인덱스 승인)은 근거와 함께 선제적으로 명시한다. 재현 데이터를 직접 만들어 붙여주는 협업도 있다.

**문제는 그 기준을 본인이 어긴다는 것이다.**

## 4. 살아남은 발견

1. **메시지 교차 → 재발송.** 멤버 본인들의 진술로 확인. 교차 언급 SEL-6877 37회 · CARR-892 5회 · SEL-6874 3회.
2. **재발송은 정보를 잃는다.** 상충 항목 누락, 같은 사실이 세 가지 표현으로 분기.
3. **역할 이탈 → 오답.** 담당자에게 뒤집힌 사례 8건.
4. **이탈 방향은 파티마다 다르다.** 고정 처방이 듣지 않는다.
5. **이중 발주 = 작업 중복.** 같은 조사를 두 멤버가 각각 수행.
6. **사용자가 역할 팽창을 유발한다.** perf·harness 사례.
7. **main 우회 + main의 일은 계속 발생.** 5개 파티 공통.

## 5. 기각·철회된 가설

| # | 가설 | 판정 | 근거 |
|---|---|---|---|
| 1 | 파티가 단일 대비 2.4~2.76배 저렴 | **철회** | 반사실 모델의 결함 4가지. `docs/사용량조사.md` §7-1 |
| 2 | 파티 메시지가 불필요한 확인 작업을 유발 | **기각** | 파티 메시지 후 재독 39% vs 사용자 턴 후 46%. 방향 반대 |
| 3 | 멤버 간 내용 중복이 심하다 | **기각** | 송신 본문 6-gram 겹침 0.3~0.9%. 동일 Bash 명령 2,490개 중 1개 |
| 4 | `interrupt: true` 규칙이 재발송의 원인 | **기각** | 인과가 반대. CARR-892에서는 교차 문제의 **처방**으로 뒤늦게 도입됐고, SEL-6874는 같은 규칙에도 재발송이 impl 1명에 국한 |
| 5 | 컨텍스트 크기가 재발송의 원인 | **기각** | 재발송률 250k 미만 2.1% vs 400k 이상 0.7%. 방향 반대 |
| 6 | 금지 조항 명문화로 해결된다 | **반례 3건** | CARR-892 req 정의에 "거부하라" 있음 · SEL-6874 main 이 "구현 디테일 나열 금지" 명문화 · CARR-892 dispatch 본문에 "진행 상황 보고하지 않는다" 명시. 모두 위반됨 |

> #5의 자동 탐지기는 신뢰도가 낮다. SEL-6877에서 19건을 잡았으나 사람 판정은 약 50건, CARR-892는 탐지기 0건 vs 판정 8건이다. "같은 내용을 다른 말로 다시 쓰기"는 n-gram 겹침이 낮아 기계가 놓친다. **따라서 #5는 "기각"이라기보다 "이 방법으로는 판정 불가"가 정확하다.**

조사자가 조각 데이터로 성급히 단정한 사례도 기록한다. CARR-892의 `req`가 "자기 거부 조항을 반복 위반했다"고 판단했으나, 전량 분석 결과 **반대로 정확히 거부**했고 누수는 두 곳뿐이었다.

## 6. 권고

### 6-1. 멤버 쪽

**1위 — Message Gate를 역할별로 걸 것.** 문서화·교정·규칙 공지가 모두 실패했으므로(§5 #6), 남은 실효 수단은 발신 시점의 기계적 차단이다. `gate-set`으로 멤버마다 개별 설정한다.

```
공통      직전에 보낸 내용을 요약해 다시 보내지 말 것
          상대가 응답하기 전 추가 발신 금지
          같은 질문을 두 멤버에게 동시에 보내지 말 것
explore   "권고 / 판정 / ~하는 게 맞다 / 채택" 포함 시 반려
perf      코드 수정·커밋·attach 관련 동사 포함 시 반려
req       좌표·픽셀·필드명·파일:라인 포함 시 반려
main      구현 방식·수치 확정 표현 포함 시 반려
```

**2위 — `MEMBER.md`에 금지 조항을 넣을 것.** 단독으로는 부족하나(§5 #6) 게이트 규칙의 근거가 된다. 현재 정의는 전부 "무엇을 한다"이고 "무엇을 판정하지 않는다"가 없다.

**3위 — 메시지 교차를 줄일 것.** `interrupt: true`가 부분적 처방이나 충분하지 않다(SEL-6877 37회). 근본적으로는 **한 사안을 한 메시지로 끝내는 것**이 교차 자체를 줄인다.

### 6-2. 사용자 쪽

**1위 — 오케스트레이션 지시는 main으로 고정.** 멤버 생성·교체·삭제, 진행 추적, 단계 dispatch, 폴더 생성. 예외 없이. U1·U2의 절반이 여기서 나온다.

**2위 — req에 보내기 전에 거를 것.** "이게 사용자 관점을 바꾸는가?" 아니면 impl·explore다. CARR-892 req 정의가 이미 이 기준을 담고 있다.

**3위 — 되돌리기 비싼 지시는 첫 턴에 전제를 다 적을 것.** 기준 브랜치·대상 저장소·선행 조건. 브랜치·MR·커밋·attach 네 가지만 지켜도 U3의 큰 손실이 막힌다.

**4위 — 안 쓸 멤버는 만들지 말 것.** 만들어두면 결국 다른 멤버가 그 일을 한다(develop의 auth·harness 사례).

**5위 — 자기가 정한 역할 경계를 자기가 지킬 것.** 급할 때 가까운 멤버에게 시키는 것이 당장은 빠르지만, 그 멤버의 산출물 신뢰성과 다른 멤버의 소유권이 함께 흐려진다.

## 7. 미해결

- **재발송이 왜 SEL-6877에서만 전 멤버로 번졌는가.** 후보는 메시지 볼륨(891 vs 261, 3.4배)과 멤버 수(6 vs 4~5)이나 검증하지 않았다.
- **파티와 단일 세션 중 무엇이 효율적인가.** 이 조사도 `docs/사용량조사.md`도 답하지 못한다. §5 #1 참조. 결판을 내려면 같은 작업 범위를 단일 세션 + 적극적 컴팩션으로 수행해 `in:out`과 최대 5시간 청구량을 비교해야 한다.
- **역할 이탈을 게이트로 실제 막을 수 있는가.** 위 6-1의 규칙은 제안이며 검증되지 않았다.
