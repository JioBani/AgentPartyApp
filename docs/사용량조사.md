# AgentParty 파티 사용량 조사

## 조사 개요

- **조사일:** 2026-08-06 (KST)
- **대상:** sellmate-dockerize, Claude, qa-automation, erp 워크스페이스의 파티 12개, 멤버 40명(콜 50회 이상)
- **목적:** 파티 사용량의 실제 토큰 구성과 낭비 요인을 확인하고, 비교 가능한 관측 결과와 검증에 실패한 가설을 구분해 기록
- **분석 기준:** 아래 수치는 별도 추정 모델이 아니라 하네스 원본 트랜스크립트의 실측치다. 분석 결과를 재구성할 때는 멤버별·세션별 원본을 기준으로 해야 한다.

### 데이터 출처와 방법

앱 원장 `.agent_party_app/usage/turns.jsonl`이 아니라 하네스 원본인 `~/.claude/projects/<proj>/<sessionId>.jsonl`을 사용했다. assistant 라인은 `message.id`로 분할되어 기록되므로 **같은 id를 dedup하지 않으면 안 된다.** dedup하지 않을 경우 콜 수가 약 1.9배 부풀려진다.

앱 원장은 실제의 약 1/2.2로 과소 집계된다. 확인 사례는 SEL-6877 원장 1,868M 대 실측 4,052M, STLM-466 원장 177M 대 실측 422M이다. 두 파티의 배율이 같으므로 원장으로도 상대 비교는 가능하지만 절대 사용량 판단에는 하네스 원본을 사용해야 한다.

수치 재확인이 필요할 때 사용하는 분석 스크립트는 다음 위치에 있다.

`C:\Users\sellmate\AppData\Local\Temp\claude\C--Project-AgentPartyApp\f403f5dc-2a03-466d-b405-12d6db4ee301\scratchpad\`

(주요 파일: `an.py`, `tr5.py`, `all2.py`, `all3.py`, `decay.py`, `share.py`, `conv.py`, `chain.py`, `verify3.py`.)

### 비용 환산의 한계

`$`는 Opus 티어 정가를 적용한 환산값이다. 입력 $5/M, 출력 $25/M, cacheRead $0.5/M, cacheWrite $10/M(1시간 TTL의 2배 쓰기 요율)을 적용했다. **실제 구독 청구액이 아니며**, 계약·구독·할인·실제 과금 정책을 나타내지 않는다.

또한 본 조사는 파티와 단일 세션을 동일 작업으로 무작위 대조한 실험이 아니다. 따라서 파티가 단일 세션보다 싸거나 비싸다는 인과 결론은 내리지 않는다. 이 한계와 철회된 주장은 §7에 별도로 기록했다.

> **중요 — 결론을 인용하기 전에 §7을 먼저 확인할 것.** “파티가 단일 대비 2.4~2.76배 저렴하다”, “파티 메시지가 확인 작업을 유발한다”, “멤버 간 내용 중복이 심하다”는 주장은 각각 철회·기각·정정되었다. 이 조사에서 데이터가 지지하는 핵심 명제는 **컨텍스트가 작을수록 싸다**는 것이다.

## 1. 조사 방법 및 지표

분석 대상은 위 네 워크스페이스의 파티 12개와 멤버 40명이다. 50회 이상의 콜을 포함한 하네스 원본 트랜스크립트를 세션·멤버·파티 단위로 묶고, assistant `message.id` 기준으로 중복 제거한 뒤 산출 output, 청구 input, 컨텍스트, 캐시 및 메시지 왕복을 집계했다.

- **산출out:** 모델이 산출한 토큰
- **청구in:** 환산 비용의 기준이 되는 입력 토큰(일반 input 및 cacheRead/cacheWrite를 포함한 청구 입력 흐름)
- **콜당ctx:** 파티의 콜당 평균 입력 컨텍스트
- **in:out:** `청구input ÷ 산출output`; 낮을수록 산출량 대비 효율적
- **최대5h:** 관측된 최대 5시간 구간의 청구 토큰
- **콜드%:** 캐시가 따뜻하지 않아 재구축된 콜의 비율

## 3. 핵심 판정: 컨텍스트 크기가 지배 변수다

멤버 40명을 컨텍스트 크기로 나누면, `ctx > 380k`인 14명의 평균 in:out은 **505**, `ctx < 250k`인 17명은 **211**이었다. 관측된 차이는 2.4배다.

멤버 수로는 설명되지 않는다. 단일 멤버끼리도 STLM-465가 176, STLM-466이 649로 3.7배 차이 난다. 난이도도 설명 변수가 아니다. 최대 작업인 qa-automation/develop은 산출out 7,826k에 콜당ctx 419k였지만, 그 1/18 규모인 STLM-466/main은 산출out 438k에 콜당ctx 451k로 더 컸다.

실제로 일하는 멤버의 컨텍스트는 파티·작업·저장소와 무관하게 410~480k에 수렴했다.

이는 작업 요구량이라기보다 **컴팩션 트리거 지점**으로 해석된다. 컨텍스트가 800k까지 올라갔다가 컴팩션 후 떨어지는 톱니의 시간평균이 약 440k에 놓인 것이다.

### 세션 내부 시계열

24개 세션에서 진행도 구간별 in:out 중앙값은 초반 20% **189**에서 종반 20% **439**로 올라가 **2.32배 악화**됐다. 이는 세션 간 난이도를 가정한 반사실 모델이 아니라 같은 세션 안에서 직접 관측한 시계열이다.

STLM-466/main(컴팩션 0회)은 다음과 같이 악화됐다.

`83k/164 → 278k/393 → 432k/535 → 600k/961 → 743k/1096`

초반과 종반의 in:out이 **6.7배** 차이 난다.

SEL-6877/impl(컴팩션 4회)은 다음과 같았다.

`375k/169 → 851k/1003 → 414k/377 → 325k/313 → 290k/346`

같은 세션·같은 작업에서도 컨텍스트가 851k일 때와 414k일 때 in:out이 **2.7배** 차이 났다. 컴팩션이 비용을 되돌리는 직접 관측으로 볼 수 있다.

### 두 번째 레버: 콜당 산출량

`in:out = 컨텍스트 ÷ 콜당산출`이다. STLM-465/explore는 콜당ctx 260k에서 콜당 산출 1,476으로 in:out 176(최고 효율)을 기록했다. 반대로 STLM-466/main은 콜당ctx 452k에서 콜당 산출 698로 in:out 649였다.

따라서 비싼 패턴은 **큰 컨텍스트에서 잘게 툴 왕복하는 것**, 싼 패턴은 **한 번에 긴 산출을 내는 것**이다.

## 4. 대화 비용: SEL-6877

SEL-6877에서 송신 왕복 825회는 290M, 수신 처리 890회는 327M이었다. 합계 **617M**으로 파티 청구의 **28%**다.

실제로 주고받은 메시지 원문은 약 1.75MB, 약 584k 토큰이었다. 따라서 **청구 토큰 : 메시지 토큰 = 1,057 : 1**이다.

메시지 중앙 크기는 800자였다. 작은 메시지가 891건으로 많았고, 4,000자 초과 메시지는 1%뿐이었다. 비용의 핵심은 메시지 크기보다 횟수다. 트래픽도 perf→impl 125건, impl→perf 121건으로 두 멤버 사이에만 246건이 집중됐다.

### 언어적 부풀리기 실측 사례

실작업 0회 연쇄가 8건, 2왕복 이상 연쇄가 143건이었다.

- impl↔main: 90초 동안 6연속 왕복, 1,057자. impl이 “상충 아니다/별개 사안”을 3번 반복했다.
- explore↔req: 4분 동안 6연속 왕복, 6,546자. explore가 이미 첫 메시지에 들어 있던 같은 답을 표·추가 근거·판정 형식으로 4번 재작성했다. 🔴 이모지, “정정”, “미안하다” 등으로 톤도 상승했다.

## 5. 캐시 실측

### TTL과 갱신

캐시 TTL은 5분이 아니라 **1시간**이었다. 간격별 콜드 재구축률이 60분 경계에서 끊겼다. SEL-6877/impl 기준 45~60분 간격은 n=3에서 콜드 0%, 60~75분 간격은 n=4에서 콜드 100%였다. Claude Code는 `ttl:"1h"`를 사용하므로 cacheWrite에는 2배 요율이 적용된다.

캐시는 읽을 때마다 추가 비용 없이 수명이 갱신된다. 따라서 계속 도는 세션은 캐시를 영구적으로 따뜻하게 유지할 수 있다.

### 델타 쓰기와 누적 읽기

매 턴에는 델타만 쓴다(중앙 1k). 반면 누적 프리픽스를 읽는다(중앙 413k). 이 구조에서 캐시가 따뜻하면 큰 누적 프리픽스 읽기를 저렴하게 처리하지만, 콜드 재구축 시에는 쓰기 비용이 커진다.

SEL-6877의 cacheWrite 43.4M 중 **75%가 115회의 콜드 재구축**이었다. 환산 비용은 약 **$330**으로 파티 총비용의 **20%**다.

콜드율은 작업 밀도와 반비례했다. develop/impl2는 시간당 98.9콜에서 3.1‰, SEL-6874/main은 시간당 9.0콜에서 80.5‰였다. 따라서 디스패처 역할은 구조적으로 캐시 효율이 가장 나쁜 역할이다.

## 7. 철회한 주장 / 검정 실패한 가설

이 절은 결론만 남길 때 가장 쉽게 잘못 인용되는 내용을 보존하기 위한 것이다. 아래 항목은 원래 주장, 왜 성립하지 않았는지, 현재 판정을 함께 기록한다.

### 7-1. [철회] “파티가 단일 대비 2.4~2.76배 저렴하다”

이 수치는 `단일 추정ctx = 45k + Σ멤버고유ctx ÷ 중복률`이라는 반사실 모델에서 계산했지만 **방어 불가**로 판정했다.

1. divisor로 사용한 중복률 1.271은 파일 경로와 bash 명령 지문 기반이다. 산문 대화는 반영하지 않으며, 같은 조사에서 이미 폐기한 지표다.
2. 멤버 컨텍스트의 17.4%가 파티 때문에 생긴 메시지인데, 이를 단일 세션의 부담으로 계산한 순환논증이다.
3. impl 13일, explore 12일, main 21일이라는 서로 다른 기간의 시간평균을 더해 “동시에 들고 있다”고 가정했다.
4. 같은 작업을 파티와 단일 양쪽에서 수행한 검증 사례가 0건이다.

따라서 **파티가 싸다는 근거도, 비싸다는 근거도 없다. 모른다.** 데이터가 지지하는 명제는 “컨텍스트가 작으면 싸다”이지 “파티가 싸다”가 아니다. 컴팩션은 같은 일을 수행하면서 조정 비용이 0이며, SEL-6877/impl에서 851k→414k로 회복될 때 in:out이 2.7배 개선된 관측이 이를 뒷받침한다.

### 7-2. [기각] “파티 메시지가 불필요한 확인 작업을 유발한다”

대조군 검정 결과는 반대였다.

| 직후 조회 | 횟수 | 이미 읽은 것 재독 | 비율 |
|---|---:|---:|---:|
| 파티 메시지 후 | 629 | 246 | **39%** |
| 사용자 턴 후 | 330 | 151 | **46%** |

읽기 전용 툴 전체로 넓혀도 19% 대 22%였다. 멤버별 결과도 일관되지 않았다(develop/req +26%p, CARR-422/impl −13%p).

따라서 부풀리기는 **말로만** 일어나고 검증 작업으로 번지지 않는다. 깊은 연쇄 8건이 “실작업 0회” 조건으로 정의된 것도 이 판정을 뒷받침한다.

이 결과는 역설적으로 운영상 호재다. 파생 작업이면 로직을 고쳐야 하지만, 순수 왕복은 Message Gate 규칙으로 차단할 수 있다.

### 7-3. [정정] “멤버 간 내용 중복이 심하다”

실측은 반대였다.

- 송신 메시지 본문 6-gram 겹침: 0.3~0.9%
- 메시지가 읽은 문서를 옮긴 비율: 0.6~1.8%
- 동일 Bash 명령 중복 실행: 2,490개 중 1개

내용이 겹치는 것이 아니라 **왕복 횟수**가 문제다.

### 7-4. [정정] 조정 비용

처음에는 송신만 세어 13.7%로 집계했으나, 수신 처리까지 포함하면 **617M, 28%**다. 이 문서의 조정 비용 수치는 후자를 사용한다.

## 8. 비교 기준과 무관하게 확실한 낭비

다음은 파티와 단일의 반사실 비교가 없어도 관측 자체로 확인되는 낭비다.

1. **대화 왕복:** 617M(28%). 메시지 1토큰당 청구 토큰이 1,057개다.
2. **큰 컨텍스트 방치:** 약 435k. 같은 세션 안에서도 in:out이 2.7배 차이 난다.
3. **콜드 재구축:** SEL-6877에서 20%; main의 42회 콜드 재구축만 8.9M이다.
4. **중복 Read:** 127M(전체 Read의 41%).

## 9. 권고

1. **무거운 멤버 컨텍스트를 200~250k로 순환한다.** 세션 내부 관측에서 최대 2.7배 차이가 났다. 대화 왕복 단가와 콜드 재구축 비용도 함께 줄어들 수 있으나, 절감 폭은 별도 검증이 필요하다.
2. **메시지 크기보다 횟수를 줄인다.** 891건의 중앙 크기는 800자다. 3건을 1건으로 묶으면 왕복 2회(약 740k 토큰)가 사라지며, 해당 사례에서는 정보 손실이 0이다.
3. **Message Gate 규칙을 적용한다.** 이 앱의 `party-gate-set`으로 다음을 차단할 수 있다: 직전 내용 재전송 금지, 형식만 바꾼 재작성 금지, 확인 질문은 작업 결과와 묶기, 상대 응답 전 추가 발신 금지.
4. **디스패처를 얇게 유지하거나 제거한다.** 관측된 작업 밀도에서 콜드율이 6~8배 높았다.
5. **작은 작업에는 파티를 쓰지 않는다.** 산출 350k 이하인 CARR-935와 SEL-6925에서는 조정 오버헤드가 27~31%였고, 이득을 잠식한다.
6. **미해결 질문을 검증할 때는 단일 세션 + 적극적 컴팩션으로 다음 이슈 하나를 수행한다.** 같은 in:out과 최대 5시간 소진을 측정하면 파티 대비 인과를 검증할 수 있다. 기존 분석 스크립트를 재사용할 수 있다.

## 10. 남은 검증 과제

파티가 동일 작업의 단일 세션보다 경제적인지 여부는 이 조사만으로 답할 수 없다. 다음 검증이 필요하다.

- 동일 이슈·동일 프롬프트를 파티와 단일 세션에서 각각 수행
- 동일한 모델·출력 제한·작업 범위를 고정
- 컴팩션 정책을 명시하고 세션 내부 시계열을 기록
- `in:out`, 최대 5시간 청구량, 대화 왕복량, 캐시 콜드율을 함께 비교

그 전까지는 “파티의 가격 우위”가 아니라, **컨텍스트 크기·콜당 산출량·왕복 횟수·캐시 상태가 관측 비용을 좌우한다**고 기술하는 것이 이 조사에서 방어 가능한 결론이다.
