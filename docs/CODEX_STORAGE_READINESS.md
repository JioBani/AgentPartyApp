# Codex 저장소 전환 준비 검증

검증일: 2026-09-26. 코드: `0caade2`, 브랜치 `review/codex-storage-reversion`. Codex Windows CLI: `0.155.1`.

이하 내용은 구현 전 준비 검증 기록이다. 후속 후보 코드와 검증 범위·발견한 문제는 [구현 결과](CODEX_STORAGE_IMPLEMENTATION.md)를 따른다. 특히 페이지형 대화는 원시 event_msg 비교만으로 검증을 마치지 않는다.

## 판단

Windows 대화 저장소를 Codex의 정상 설정 경로로 돌리는 방향은 진행할 수 있다. 기존 기본 DB에 없던 366개를 공식 조회 API로 등록하고, 대상 809개의 대화를 확인했다. 실제 AgentParty에서 공유 저장소의 병렬 응답·앱 재시작·최신 대화를 유지하는 legacy 복귀도 통과했다.

그러나 **현재 제품을 그대로 전환해도 안전하다는 승인은 아니다.** 초기화 중 프로세스 종료와 새 DB의 동시 초기화 실패는 재현된 문제다. 초기화 수명 관리 및 모든 시작 경로의 저장소 정책을 수정하고 후보 빌드에서 검증해야 한다. 이 작업에서는 제품 코드, 운영 설정, 운영 DB를 변경하지 않았다.

절차와 중단 조건: [CODEX_STORAGE_TRANSITION_PLAN.md](CODEX_STORAGE_TRANSITION_PLAN.md).

## 실제 앱 검증

작업 트리의 `npm run build`가 성공했다. 격리된 userData, CODEX_HOME, QA 작업공간으로 실제 Electron 앱을 실행했다. `AGENTPARTY_E2E` 모의 경로는 사용하지 않았다. 멤버의 작업 위치는 삭제될 작업 트리가 아닌 주 체크아웃으로 지정했고 파일 편집은 요청하지 않았다.

기존 코드가 주입하는 `CODEX_SQLITE_HOME`보다 우선하는 Codex 공식 `sqlite_home` 설정으로 공유 DB를 사용했다. 이는 현재 앱을 통한 공유 저장소 호환성 검증이다. 아직 구현되지 않은 경로 강제 제거 코드의 검증으로 계산하지 않는다. 앱 멤버의 thread ID가 실제 공유 DB에 등록되는 것도 확인했다.

앱 모델 호출은 `gpt-6-luna`, low, standard로 짧게 수행했다. main의 `gpt-5.4` 프로세스에는 모델 턴을 요청하지 않았다. 외부 CLI도 실제 `gpt-6-luna` 호출을 수행했다. 다른 모델/서비스 티어의 동작까지 검증했다고 주장하지 않는다.

| 시나리오 | 결과 |
| --- | --- |
| 멤버 3개 동시 요청 | 각 멤버의 assistant 응답이 지정한 서로 다른 토큰과 정확히 일치 |
| 생성 직후 runtime 변경 및 첫 메시지 | 0.4초 안에 생성·변경·전송. 오류 없이 정확한 응답 1회 |
| 한 멤버 실행 중 중단 | 중단 이벤트 확인, 다른 멤버 응답 완료, 중단한 멤버도 다음 요청 정상 응답 |
| 모델 목록 갱신·환경 진단과 멤버 실행 병행 | 갱신 성공, Codex 진단 ok, 멤버 응답 성공 |
| 외부 `codex exec`와 앱 멤버 동시 사용 | 서로 다른 thread에서 양쪽 실제 응답 성공, CLI exit 0 |
| 공유 모드 앱 종료·재실행 | 기존 thread ID 유지. 답을 프롬프트에 재제공하지 않고 직전 응답 회상 성공 |
| native에서 만든 대화를 legacy로 복귀 | 동일 ID, 최신 대화 회상 성공. 신규 native 대화도 성공 |
| 이미 오래된 legacy 색인이 있는 상태로 롤백 | legacy → native에서 새 응답 → legacy로 돌아와 새 응답 회상 성공 |

멤버 생성·runtime 변경·메시지·중단은 실제 `/api/parties/:partyId/members/main/mcp-tools/:tool`에서 `mcp-stdio` transport를 확인했다. 직접 HTTP는 파티 fixture 준비, 읽기 전용 상태/대화 확인, MCP 도구가 없는 모델 갱신·환경 진단·앱 창 닫기에만 사용했다. 모델 출력 검사는 사용자 프롬프트의 토큰이 아닌 assistant 블록을 검사했으며, 회상 검사는 새 assistant 응답 수가 증가하는 것까지 확인했다.

## 사용자 기록 전체 복사본 검사

- 운영 SQLite 318개를 읽기 전용으로 조사했다. 중복 제거한 thread 809개의 rollout 약 11.0GiB를 복사했다. 각 파일 복사 전후 크기·수정 시각에 변화가 없었고 모든 복사본을 JSON으로 파싱했다. 이는 쓰기 중단 후 일관 백업의 대체물이 아니다.
- 문자열 경로가 다른 127개는 Windows 장경로 접두사 차이였고, 정규화하면 같은 파일이었다.
- 한 파일의 session_meta에 자식과 부모 ID가 함께 있었다. 첫 메타데이터의 ID가 대상 ID이며 `forked_from_id`가 뒤의 부모 ID와 일치했다. 모든 session_meta가 같은 ID여야 한다는 검사로 정상 분기 기록을 손상으로 오판하면 안 된다.
- 복사본의 새 기본 DB에서 공식 `thread/read(includeTurns=true)` 809개 모두 성공했다. 반환 ID와 파일 경로가 해당 복사본 안에 있는지 확인했다.
- 사용자/assistant 메시지의 내용 지문과 출현 횟수를 대조했다. 803개는 원시 메시지 이벤트와 일치했다. 6개에서 사용자 이벤트 수가 달랐지만, 기존 legacy DB의 일관 복사본과 재구성 DB에 대한 공식 API 메시지 지문은 서로 완전히 같았다. assistant 메시지 차이는 없었다. 도구 출력·첨부의 모든 바이트까지 의미 비교한 결과는 아니다.

기존 DB 비교에 사용한 일관 복사본은 복사본 안의 `rollout_path`만 격리된 파일로 바꾸어 원본 접근을 막았다. 이는 진단용 복사본의 경로 격리이며, 운영 DB 병합 또는 이전 구현이 아니다.

## 기존 기본 DB가 이미 있을 때의 이전

새 DB의 backfill 성공만으로 실제 이전을 승인하지 않았다. 운영 기본 DB를 SQLite backup API로 복사하고 모든 파일 경로를 격리한 다음 별도로 검증했다. 해당 복사본은 backfill complete였고 기존 ID 450개가 있었다. 그중 443개가 대상 809개와 겹치며, 7개는 당시 조사 범위 밖의 기존 기본 DB 기록이었다.

1. 공식 `thread/read`로 대상 809개를 순차 조회했다. 모델 턴이나 일괄 resume 없이 누락 366개가 등록됐다.
2. 결과 DB에 대상 809개 전체가 있고 기존 범위 밖 7개도 남았다.
3. 공식 `thread/list(useStateDbOnly=true)`를 제공자·소스 종류와 보관 여부까지 포함하여 페이지별 조회했다. 797개가 목록에 나왔고, 나머지 12개는 기존 legacy DB에서도 `has_user_event=0`이었다. 목록 정책과 실제 기록 보존을 구분해야 한다.
4. 부모·자식 관계 18개와 섹션 상태가 재구성 DB와 같았다. 원본들과 새 DB의 보관·메모리 모드·섹션 배치도 비교했다. 오래된 섹션 스키마의 nullable `appearance` 컬럼 부재는 null로 정규화해야 한다.

따라서 기본 이전 경로는 **공식 조회·색인 보완·검증**으로 충분한 근거가 있다. `backfill_state`를 고치거나 전체 DB를 교체하거나 과거 모든 대화를 활성 세션으로 재개할 이유가 없다.

## 재개 검사에서 발견한 기존 조건

별도 복사본에서 모델 호출 없이 809개에 공식 resume을 시도하고 성공 항목은 unsubscribe했다. 754개 성공, 54개는 과거 제공자 정의 부재, 1개는 보관 상태 때문에 거부됐다. 제공자 오류에는 openrouter, claude-subscription, deepseek, ds, openai-sse, bai가 포함된다. 현재 사용자 Codex config에도 custom provider 정의는 없었다. 다만 AgentParty가 실행 시 넣는 모델 라우트는 별개이므로, 이 결과를 운영 앱의 재개 실패 54개로 해석하면 안 된다.

당시 저장된 멤버의 harnessSessionId와 위 55개는 겹치지 않았다. 해당 기록도 공식 조회와 색인 보완은 성공했다. 이전을 통과시키기 위해 제공자를 바꾸거나 보관을 해제하지 않는다. 향후 사용자가 실제 재개할 때 필요한 제공자 설정을 명시적으로 해결한다.

목표 3개의 정확한 목표 ID·누적 사용량 이전은 사용자 결정대로 제외한다. 원본 DB를 보존하며 자동 재활성화하지 않는다. memory/queue 등의 내용은 실제 전환 시점에 다시 사전 검사한다.

## 후보 코드에서 통과해야 할 출시 조건

이번 작업이 준비 검증이므로 아래는 아직 통과 판정하지 않았다.

1. **초기화 수명 관리:** cold backfill 중 생성 직후 설정 변경·첫 전송·앱 종료가 겹치는 경우. 안전한 초기화 경계 전 불필요한 프로세스 교체 방지, 요청 보존, 정확히 한 번 전송, 최종 실패 표시를 실제 앱에서 확인한다.
2. **시작 경로 일치:** 멤버·모델 탐색·사용량·환경 진단에 같은 호스트별 정책을 적용한다. 외부 프로세스가 만든 일시적 초기화 경합은 같은 저장소에서 제한적으로 재시도하고, 계속 running인 backfill은 숨기지 않는다.
3. **멤버 도구 신원 및 CLI 인계:** 후보 코드에서 각 멤버의 실제 도구 호출 신원, 같은 thread의 앱/CLI 소유권 인계와 중복 실행 차단을 검증한다. 이번 외부 CLI 검증은 서로 다른 thread의 동시 실행이다.
4. **전환 작업 중 중단·재실행:** ID별 기록으로 이어서 진행하고, 실패한 상태를 native 완료로 표시하지 않아야 한다. 준비·검증·실행·롤백의 UI와 HTTP는 같은 AppController 경로를 사용한다.
5. **운영 직전 검사:** 관련 쓰기 중단 후 WAL을 포함한 일관 백업과 당시 전체 ID/설정/부가 상태를 검증한다. 이번 복사본과 다른 신규 데이터나 상태를 조용히 버리지 않는다.
6. **최종 후보 재검증:** 제품 코드가 바뀐 뒤 위 앱 시나리오와 대화 보존·롤백을 다시 수행한다. WSL 2개 멤버와 SSH는 별도 검증 전까지 기존 모드를 유지한다.

초기화 수명 관리 수정은 legacy에서도 먼저 적용한다. 그다음 이전 검증기/명시적 모드 선택을 구현한다. DB 교체, 스키마 병합, 자동 recovery 디렉터리 순환을 새 정상 경로에 넣지 않는다. 자세한 백업·롤백·중단 절차는 전환 계획에 정리했다.

## 증거와 남은 정리

로컬 증거: 작업 트리 `.tmp/storage-product-qa-zxrqar13/`의 실제 앱 기록, `*-result.json`, corpus 검사 요약 및 resume journal. 이들은 사용자 대화 복사본을 포함하므로 커밋·업로드하지 않는다. 복잡한 전체 기록 비교에만 임시 진단 드라이버를 사용했으며, 제품용 enum/내부 호출 횟수 테스트는 추가하지 않았다.

QA 앱은 종료했다. 인증을 사용하지 않는 corpus 프로토콜 진단에는 모델 턴을 요청하지 않았다. 임시 복사본 정리는 배포의 선행 조건으로 삼지 않는다. 단, 도구 실행 정책이 QA 인증 복사본 `codex-home/auth.json` 삭제를 차단하여 해당 파일과 데이터 복사본이 남았다. 다른 명령으로 삭제 정책을 우회하지 않았으며 사용자 원본 인증은 변경하지 않았다.
