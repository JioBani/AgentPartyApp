# Codex 기본 저장소 복귀 조사

조사일: 2026-09-26 (KST). 코드 기준: `0caade2`. 설치된 CLI: `codex-cli 0.155.1`.

후속 결정: 사용자는 목표의 정확한 이전을 필수 조건에서 제외했다. 아래는 최초 조사 기록이며, 현재 전환 범위·추가 재현 결과·마이그레이션과 폴백 절차는 [CODEX_STORAGE_TRANSITION_PLAN.md](CODEX_STORAGE_TRANSITION_PLAN.md)를 따른다. 특히 새 저장소 동시 초기화 실패와 초기화 강제 종료 후 30초 타임아웃은 후속 조사에서 실제 Codex로 재현됐다.

## 판단

AgentParty의 멤버별 SQLite 경로 강제를 제거하고 Codex가 자신의 설정에 따라 저장소를 선택하도록 되돌리는 것은 현실적인 후보다. 다만 경로 강제만 제거해서는 기존 상태를 모두 보존할 수 없다. 대화 복원은 실제 CLI로 확인했으며, 목표 상태의 별도 이전 필요성도 확인했다. 전체 마이그레이션 및 실제 모델 턴의 제품 E2E는 아직 수행하지 않았다.

기본 동작은 반드시 `~/.codex`로 강제하는 것을 뜻하지 않는다. 사용자의 `CODEX_HOME`, `CODEX_SQLITE_HOME`, `sqlite_home` 설정과 실행 호스트를 존중해야 한다. `sqlite_home` 설정은 `CODEX_SQLITE_HOME`보다 우선한다.

## 조사 방식과 한계

- 사용자 SQLite는 `mode=ro`로 조회했다. 인증정보와 대화 본문을 보고서에 포함하지 않았다.
- 기존 사용자 DB의 수정, 삭제, 스키마 변경, 데이터 병합은 하지 않았다.
- 실제 Codex 프로토콜 진단은 별도 임시 `CODEX_HOME`과 빈 작업 폴더에서 수행했다. 인증·MCP 설정은 복사하지 않았고 모델 턴도 요청하지 않았다.
- 이 진단은 Codex 저장소 호환성 조사다. 실제 AgentParty 앱을 통한 제품 E2E 또는 모델 응답 검증으로 간주하지 않는다.
- 실행 중인 환경을 읽은 시점별 집계이므로 전환 직전에는 쓰기 중단과 일관된 백업에 기반한 별도 사전 검사가 필요하다.
- Windows 전용 저장소를 조사했다. 등록된 WSL 멤버 2개의 원격 저장소는 조사하지 않았다. SSH 저장소도 검증하지 않았다.

## 실제 CLI 진단 결과

1. 빈 임시 Codex 기본 저장소를 초기화했다.
2. 초기화가 끝난 뒤, 원래 기본 DB에는 없던 대화 파일 한 개의 복사본을 임시 sessions 경로에 추가했다.
3. `thread/read(includeTurns=true)`가 기존 ID와 턴을 반환했다.
4. `thread/resume`이 같은 ID를 유지했고 새 DB에도 해당 대화가 등록됐다.
5. 같은 임시 기본 저장소에서 다른 app-server 3개를 동시에 초기화하고 각각 `thread/start`를 호출했다. 모두 성공했다.
6. 별도로 기존 `blocked` 목표가 있는 대화 파일의 복사본을 추가했다. `thread/read`, `thread/resume`은 성공했지만 `thread/goal/get`은 `goal: null`을 반환했다.
7. 설치된 CLI의 프로토콜 스키마를 기능 확인 목적으로 조사했다. `thread/goal/set`은 `threadId`, `objective`, `status`, `tokenBudget`을 받으며 기존 goal ID, 누적 토큰, 누적 시간, 생성·갱신 시각을 가져오는 필드는 없다.

위 결과는 기본 DB 공유가 항상 실패한다는 가정을 지지하지 않는다. 동시에 장시간 병렬 모델 실행, 사용자의 Codex 데스크톱/IDE와 동시 실행, 기존 809개 대화 전체의 복원 성공을 증명하지도 않는다.

## 예상 위험

### 대화 목록과 재개

기본 DB에 없는 대화는 목록에 즉시 나타나지 않을 수 있다. AgentParty의 기존 harnessSessionId를 유지하면 공식 재개 경로로 복원할 가능성이 높으며 표본에서 확인했다. 대화 파일 경로 이동이나 새 thread 생성으로 대체하면 안 된다. 원본 파일이 존재하는 것과 모든 턴을 손실 없이 재개하는 것은 별도 검증이다.

### 목표와 부가 상태

목표는 대화 파일 재개만으로 복구되지 않았다. 공개 목표 설정 API만으로는 기존 누적 사용량까지 원형 보존하기 어렵다. 무손실 이전을 원하면 승인된 일회성 호환 이전이 필요하다. 일반 실행 코드가 Codex 스키마를 계속 관리하게 해서는 안 된다.

메모리·대기열은 이번 환경에서는 비어 있었지만 다른 사용자나 실제 전환 시점에도 비어 있다고 가정하면 안 된다. 부모·자식 관계와 section 등도 무조건 버릴 수 있는 캐시로 취급하지 않는다. backfill 상태, 실행 중 작업의 lease, 스키마 이력 자체를 사용자 데이터처럼 무작정 합치면 안 된다.

### 공유 DB와 프로세스 수명

멤버별 프로세스는 유지할 수 있는 후보다. DB 공유를 위한 app-server 통합이 필수라는 근거는 없다. 다만 같은 thread를 두 프로세스가 동시에 재개하거나 초기화 중 프로세스를 강제 종료하는 문제는 DB 경로 변경만으로 해결되지 않는다.

AgentParty 이외의 Codex CLI·IDE·데스크톱도 기본 저장소를 사용할 수 있다. 멤버별 도구 신원, 승인, 응답, 목표, 중단이 서로 섞이지 않는지 실제 앱에서 검증해야 한다.

### 복구와 버전

원본 DB들의 스키마가 다르므로 파일 덮어쓰기나 테이블 전체 복사는 부적절하다. 기본 DB를 원본 중 하나로 교체하면 기존 Codex 사용자의 상태를 잃을 수 있다. `-recovery` 폴더가 존재한다는 사실만으로 그 폴더가 완전한 최신 정본이라고 판단해서도 안 된다.

WAL에 아직 기록된 데이터를 포함한 SQLite 일관 백업이 필요하다. 실행 중인 `.sqlite` 파일만 복사하는 것은 충분한 백업이 아니다. 전환 후 새 작업을 시작했다면 과거 DB로 경로만 되돌리는 것도 무손실 롤백이 아니다.

## 제안하는 전환 절차

아래는 설계 제안이며 아직 구현·실행하지 않았다. 프로젝트 지침에 따라 마이그레이션 구현과 실행 전 사용자 확인이 필요하다.

1. 호스트별 실제 Codex 홈과 최종 SQLite 경로를 확인하고, 파티 대화 ID·rollout 파일·원본/복구 DB·전용 부가 상태를 목록화한다.
2. 정상 동작하는 버전을 고정하고, 해당 호스트의 AgentParty와 다른 Codex 쓰기 프로세스를 중지한 상태에서 일관 백업을 만든다. 인증정보 이전은 이 작업에 포함하지 않는다.
3. 복사본 환경에서 공식 재개 기능으로 대화를 복원한다. 기본 DB를 덮어쓰지 않는다. 전체 범위의 기존 ID와 대화 내용을 검증하고 누락·충돌을 보고한다.
4. 공개 API로 보존할 수 없는 목표 등의 상태에는 버전을 제한한 일회성 이전을 적용한다. 대상의 기존 행과 충돌하면 중단하고 보고한다. 사용량·시간·상태를 포함한 의미 보존, 재실행 시 중복 없음, 부분 실패 후 복구를 검증한다.
5. 위 검증이 통과한 후에만 AgentParty의 DB 경로 강제를 해제한다. 코드 변경과 데이터 이전 성공 상태를 연동해 일부 멤버만 의도치 않게 다른 저장소를 쓰는 상황을 방지한다.
6. 실제 AgentParty 앱에서 병렬 응답, 생성 직후 설정 변경·전송, 한 멤버 중단, 앱 재시작 후 재개·목표 보존을 확인한다. 멤버 행동은 실제 멤버 MCP 경로를 사용한다.
7. 기존 DB는 검증 기간 동안 보관한다. 전환 후 새 작업이 발생한 경우 새 상태를 보존하는 역방향 절차 없이 이전 DB로 돌아가지 않는다. 정리는 성공 확인 후 별도 작업으로 한다.

## 결론

대화 파일이 모두 남아 있고 공식 재개 기능이 DB 누락을 복원하는 것을 확인했으므로, 대화 중심의 전환 가능성은 높다. 하지만 현재 사용자의 목표 기록까지 보존하는 마이그레이션이 이미 검증된 것은 아니다. **경로 강제 제거만으로는 불충분하며, 목표·부가 상태 이전과 실제 앱 병렬 동작 검증을 통과해야 무손실 전환이라고 말할 수 있다.**
