# F-03. 설치·배포 방식

**판정: 차단** · 출처: 사용자 · [조사-배포와 보안](조사-배포와%20보안.md)

## 무엇을

사용자가 이 프로그램을 **어떻게 받고 설치하는지** 정한다.

## 지금은

electron-builder 로 **`nsis`(설치 관리자)와 `portable`(무설치) 둘 다** 나온다.
어느 쪽을 정식 경로로 삼을지 정해지지 않았다. 배포처도 미정이다.

## 🔴 코드 서명 — 조사 완료 (2026-08-08)

서명이 없으면 **Windows SmartScreen 이 첫 실행에서 경고를 띄운다.**

> **첫 인상이 여기서 결정된다.** 사용자가 앱을 보기도 전에 *"알 수 없는 게시자"* 를 먼저 본다.

### 🔵 전제가 하나 뒤집혔다 — 서명을 사도 경고는 즉시 사라지지 않는다

조사 전 이 문서의 암묵적 전제는 *"인증서를 사면 경고가 없어진다"* 였다. **Microsoft 공식 문서 기준으로 틀렸다.**

| 사실 | 출처 |
|---|---|
| **EV 인증서는 더 이상 SmartScreen 을 우회하지 않는다.** "EV certificates no longer bypass SmartScreen… Paying a premium for EV solely to avoid SmartScreen warnings is no longer justified" | [smartscreen-reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation) (2026-05-04) |
| Azure Artifact Signing 은 **"does not provide instant SmartScreen trust"**, OV 와 기능적으로 동등 | [code-signing-options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options) |
| 평판은 **"several weeks and hundreds of clean installs"** 로 쌓인다. 신호는 ① 퍼블리셔 ② 파일 해시 두 층 | 위 동일 |
| **경고 0 을 보장하는 경로는 Microsoft Store 뿐** — Store 는 Microsoft 가 재서명하고 평판을 승계한다 | 위 동일 |
| 소비자용 SmartScreen 수동 심사 창구는 **없다**(기업 IT 전용) | 위 동일 |

**베타 규모에서의 함의**: 초대 사용자 수십 명 규모에서는 **인증서를 사도 대부분의 사용자가 경고를 본다**
(수백 건의 설치가 필요하므로). 즉 **"오늘 사야 첫 인상이 좋아진다"는 논리가 성립하지 않는다.**

서명으로 실제로 사는 것은 경고 제거가 아니라 이 셋이다:
1. 경고 문구가 *"알 수 없는 게시자"* → **실명 게시자**로 바뀐다
2. **Smart App Control**(Windows 11) 사용자에게 실행이 차단되지 않는다 — SAC 는 미서명을 하드 차단한다
3. 평판 축적이 **시작**된다. 미서명은 매 버전 해시마다 0 에서 다시 시작한다

⚠️ **자체 서명(self-signed)은 미서명과 동일 취급**된다. 우회로가 아니다.

### 🔴 사용자 조건이 선택지를 좌우한다 — 순수 개인 · 비공개 소스

사용자 확인(2026-08-08): **사업자등록 없음(순수 개인)**. 소스는 비공개. 이 두 조건으로 **두 경로가 탈락한다.**

| 경로 | 결과 | 근거 |
|---|---|---|
| **Azure Artifact Signing** (구 Trusted Signing, 월 ~$10) | ❌ **개인은 US·Canada 한정.** 조직은 한국 포함 | [quickstart 전제조건](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart) |
| **SignPath Foundation** (무료) | ❌ **OSI 승인 라이선스 + 비독점 구성요소 필수.** 비공개 소스 불가 | [signpath.org/terms.html](https://signpath.org/terms.html) |
| **EV 인증서** | ❌ 살 이유가 사라졌다(위 표) | — |

남는 것은 **① 미서명 · ② 개인사업자 등록 후 Azure · ③ Certum Open Source · ④ Microsoft Store** 넷이다.

#### ④ Store 가 이 앱과 충돌하는 지점 (추정 — 정책 확인 필요)

Store 는 서명 문제를 완전히 없애지만, **이 앱의 구조와 부딪힐 것으로 보이는 지점이 셋** 있다:
1. `build/installer.nsh` 가 하는 일 — **HKCU PATH 등록 · Explorer 우클릭 메뉴 등록**. MSIX 컨테이너는 임의 레지스트리 쓰기를 이렇게 못 한다
2. 이 앱은 **사용자가 설치한 임의의 로컬 CLI**(`claude`·`codex`·`cursor-agent`)를 프로세스로 띄운다
3. **electron-updater 는 NSIS 전용** — MSIX 는 Store 업데이트에 종속된다([F-02](F-02%20자동%20업데이트.md))

→ **Store 는 "서명이 공짜"라는 장점 하나로 택할 수 없다. 위 3개를 포기하거나 재설계해야 한다.**

#### 🔵 Zed·Obsidian 은 서명해도 SmartScreen 을 못 피했다 — 실증

서명이 경고를 없애지 못한다는 것을 레퍼런스가 직접 증언한다. Obsidian 운영진 발언:

> *"The installer is signed. The key is relatively new... Smart screen is being triggered regardless
> because Microsoft is slow to recognize the new version (exe)"*
> — [forum 95908](https://forum.obsidian.md/t/windows-installer-is-unverified-or-unsigned/95908)

> *"we've obtained a new signing certificate, which takes time to build trust with Microsoft...
> choose 'More info', then 'Run anyway'"* — [forum 91010](https://forum.obsidian.md/t/warning-when-installing-on-w11/91010)

즉 **20,644 stars 규모의 유료 상용 앱이, 법인 명의로 서명하고도 사용자에게 "More info → Run anyway" 를
안내했다.** 서명은 평판 축적의 시작점일 뿐이라는 Microsoft 문서와 일치한다.

또한 Zed 는 **서명했는데도 AV 오탐**을 겪었다 — Bitdefender 가 `auto_update_helper.exe` 를 차단([#40081](https://github.com/zed-industries/zed/issues/40081)),
Defender 가 설치 프로그램의 PowerShell 을 `Behavior:Win32/SuspLummaInj.A` 로 차단([#40920](https://github.com/zed-industries/zed/issues/40920)).
**서명은 AV 오탐도 막아주지 않는다.**

**그리고 유명 무료 앱 상당수는 그냥 미서명으로 낸다** — 이것이 ③"무료 프로그램은 어떻게 하나"의 실제 답이다.

| 앱 | 상태 | 근거 |
|---|---|---|
| **FreeTube** | 미서명, **명시적 사유 공개** | *"licenses to sign applications for Windows are expensive and we'd like to avoid putting a lot of money into the project"* — [FAQ](https://docs.freetubeapp.io/faq/) |
| **ShareX** | 미서명 | 2026-01 설치 프로그램이 Windows Security 에 *"Publisher: Unknown"* 으로 차단됨 — [#8362](https://github.com/ShareX/ShareX/issues/8362) |
| **Upscayl** | 미서명 | README 가 사용자에게 *"click 'More Info' and then 'Run Anyway'"* 를 안내 — [#1471](https://github.com/upscayl/upscayl/issues/1471) 은 "not planned" 로 종료 |
| **Fluent Reader** | 미서명 | `electron-builder.yml` 에 서명 필드 없음, CI 에 서명 시크릿 없음 |

진행 방법*을 적어 두는 것이 그 부류의 공통 관행이다(Upscayl 이 그 예).

### ✅ 툴체인은 이미 준비돼 있다 — Azure Trusted Signing 이 설정만으로 붙는다

서명을 "안 한 것"이지 "못 하는 것"이 아니다. 설치된 electron-builder 를 직접 확인했다.

- `electron` `^33.2.1` · `electron-builder` `^25.1.8` (`app-builder-lib` 25.1.8 실측)
- **`win.azureSignOptions` 를 이미 지원한다** — `node_modules/app-builder-lib/out/codeSign/windowsSignAzureManager.js` 존재,
  `scheme.json` 에 `azureSignOptions` 등록됨
- 인증은 `AZURE_TENANT_ID` · `AZURE_CLIENT_ID` + (`AZURE_CLIENT_SECRET` 또는 인증서 경로) 환경변수.
  없으면 **빌드가 `InvalidConfigurationError` 로 실패한다** — 조용히 미서명으로 넘어가지 않는다

→ Azure Trusted Signing 을 택하면 **electron-builder 업그레이드가 필요 없다.** `package.json` 설정 + 환경변수뿐.
전통적 인증서(.pfx/HSM 토큰) 경로도 같은 `win` 옵션(`certificateFile`/`certificateSubjectName`)으로 지원된다.

⚠️ 같은 파일에서 발견한, F-02 에 직결되는 기본값:
**`win.verifyUpdateCodeSignature` 의 기본값이 `true`** 이고 검증 기준은 `publisherName` 이다
(`out/options/winOptions.d.ts:86-91`). 미서명 상태에서 자동 업데이트를 켜는 것,
그리고 **나중에 인증서를 바꾸는 것**이 여기서 걸린다 → [F-02](F-02%20자동%20업데이트.md).

## 정해야 할 것

### 배포처
어디서 받게 할 것인가. **[F-02](F-02%20자동%20업데이트.md) 의 업데이트 확인처와 같은 곳이어야 한다.**
(저장소는 아직 비공개이므로 GitHub Releases 를 쓰려면 그 결정과 엮인다.)

### 설치 관리자 vs 무설치
| | 장점 | 단점 |
|---|---|---|
| **nsis** | 자동 업데이트와 궁합이 좋다, 바로가기·제거가 표준 | 설치 과정이 하나 더 |
| **portable** | 받자마자 뜬다, 지우기 쉽다 | **자동 업데이트와 궁합이 나쁘다**, `process.cwd()` 가 예측 불가([B-15](B-15%20기본%20작업공간.md)) |

⚠️ **둘 다 내면 [B-15](B-15%20기본%20작업공간.md) 의 실측을 두 번 해야 한다** — 실행 경로마다 `cwd` 가 다르다.
**하나로 좁히는 것이 베타를 단순하게 만든다.**

### WSL 쪽 준비물
이 앱은 **Windows + WSL** 을 지원한다고 확정했다. 그런데 사용자 PC 의 WSL 안에
무엇이 있어야 동작하는지 **정리된 곳이 없다.**
- 무엇이 필요한가(배포판·node·하네스 CLI)
- **없으면 어떻게 알릴 것인가** — 지금은 사전 점검이 없어서 첫 턴에서야 실패한다
  ([조사-첫 실행 경험](조사-첫%20실행%20경험.md))
→ [F-09](F-09%20도움말.md) 의 사용자 문서에 들어갈 내용이기도 하다.
