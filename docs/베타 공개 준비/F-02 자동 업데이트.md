# F-02. 자동 업데이트 감지

**판정: 차단** · 출처: 사용자 · [조사-배포와 보안](조사-배포와%20보안.md)

## 무엇을

새 버전이 나온 것을 앱이 스스로 알아채고 사용자에게 알린다.

## 왜

**베타는 고칠 것이 계속 나온다.** 갱신 경로가 없으면 사용자가 **첫 빌드에 갇히고**,
고친 것이 사용자에게 닿지 않는다. 그러면 같은 제보를 계속 받게 되고,
**베타를 도는 의미 자체가 없어진다.**

## 지금은

- `package.json` 에 `publish` 설정 **없음**, electron-updater **없음**.
- 버전은 `package.json` 의 `0.1.0` 하나뿐이고 **앱 화면 어디에도 안 나온다.**

## ⚠️ 순서 — 버전 표시가 먼저다

자동 업데이트보다 **버전 표시가 앞선다.**
- 버전이 안 보이면 사용자가 **자기가 갱신됐는지도 모른다.**
- 제보를 받아도 **어느 빌드인지 몰라** 이미 고친 것을 다시 조사하게 된다.

→ **[F-13](F-13%20진단%20접근.md) 을 먼저 하거나 같이 한다.**

## 범위를 두 단계로

### 1단계 — 감지하고 알리기만 (권장 시작점)
새 버전이 있으면 **알리고, 받는 곳으로 보낸다.** 설치는 사용자가 한다.
- 싸다. 서명·설치 관리자 문제를 안 건드린다.
- 베타 초기엔 **강제로 갱신되지 않는 편이 낫다** — 사용자가 쓰던 중에 앱이 바뀌면 곤란하다.

### 2단계 — 받아서 설치까지
electron-updater. **[F-03](F-03%20설치와%20배포%20방식.md) 의 배포처·설치 형태·코드 서명과 한 몸이다.**
Windows 에서는 **서명 없이 매끄러운 자동 설치가 어렵다.**

## ⚠️ B-15 와 부딪히는 조합

기본 작업공간이 **앱 설치 폴더**가 될 수 있다([B-15](B-15%20기본%20작업공간.md)).
그 상태에서 업데이트가 설치 폴더를 갈아엎으면 **거기 있던 파티가 날아간다.**

**두 항목을 따로 처리하면 이 조합을 놓친다.** B-15 를 먼저 막고 F-02 를 얹는다.

## 조사 완료 (2026-08-08)

### 🔵 전제가 하나 뒤집혔다 — 미서명이어도 자동 업데이트는 된다

이 문서는 *"Windows 에서는 서명 없이 매끄러운 자동 설치가 어렵다"* 고 적어 뒀다. **소스를 읽어 보니 틀렸다.**

`NsisUpdater` 는 `app-update.yml` 의 `publisherName` 을 읽고, **없으면 검증 자체를 건너뛴다**:

```ts
// electron-updater/src/NsisUpdater.ts
const publisherName = (await this.configOnDisk.value).publisherName
if (publisherName == null) { return null }   // ← 검증 스킵
```
([NsisUpdater.ts](https://raw.githubusercontent.com/electron-userland/electron-builder/master/packages/electron-updater/src/NsisUpdater.ts))

→ **미서명 앱은 서명 검증을 안 하므로 자동 업데이트가 그대로 동작한다.** 서명은 자동 업데이트의
*전제조건이 아니다.*

⚠️ **다만 서명한 뒤에는 반드시 일치해야 한다.** 서명된 앱은 내려받은 설치 프로그램의 Authenticode
publisher 가 `publisherName` 과 일치해야 하고, 아니면
`"Sign verification failed, installer signed with incorrect certificate"` 로 실패한다
([windowsExecutableCodeSignatureVerifier.ts](https://raw.githubusercontent.com/electron-userland/electron-builder/master/packages/electron-updater/src/windowsExecutableCodeSignatureVerifier.ts)).
`win.verifyUpdateCodeSignature` 기본값은 `true`.

**→ 이것이 "서명을 나중에 살 때"의 실제 대가다**: 미서명으로 배포한 사용자들에게 서명 빌드를
내려보내면 publisherName 이 `null` → 실명으로 바뀌므로, 그 시점에 **한 번은 수동 재설치**가 필요할 수 있다.
반대 방향(서명 → 인증서 교체)도 같은 문제이며, 레퍼런스에도 사례가 있다(Rambox: 개인명 → LLC 명의 변경).

⚠️ 그리고 electron-updater 는 현재 두 곳에서 **fail-open** 하는데(PowerShell 버전 미지원 등),
소스에 *"This fail-open behavior is deprecated: electron-builder v28 will treat … as a verification
failure (fail-closed)"* 경고가 이미 박혀 있다. **v28 에서 조용한 통과가 실패로 바뀐다.**

### 🔴 portable 은 자동 업데이트가 원천적으로 불가능하다

> *"Simplified auto-update is supported on Windows if you use the default NSIS target"*
> — [electron.build/docs/features/auto-update](https://www.electron.build/docs/features/auto-update)

Windows 용 업데이터 클래스는 **`NsisUpdater` 하나뿐**이다(macOS `MacUpdater`, Linux 4종).
**portable · MSI · MSIX 는 자동 업데이트 대상이 아니다.**

→ **[F-03](F-03%20설치와%20배포%20방식.md) 의 "설치 관리자 vs 무설치" 결정에 이게 두 번째 근거다.**
portable 은 이미 [B-15](B-15%20기본%20작업공간.md) 의 파티 전멸 결함이 있고, 여기에 **자동 업데이트 불가**가 더해진다.
레퍼런스 대조: **Zed 는 portable 요청을 받고도 안 냈고**([discussion 40569](https://github.com/zed-industries/zed/discussions/40569)),
**Obsidian 도 공식 portable 이 없다**(커뮤니티가 7-Zip 압축 해제로 우회).

### 배포처 — 비공개 소스인데 GitHub Releases 를 쓸 수 있나: **된다. 레퍼런스가 그렇게 한다**

**Obsidian 이 정확히 우리 구조다.** `obsidianmd/obsidian-releases` 저장소(20,644 stars)는
**소스가 없고 바이너리 릴리스만 있다.** README 원문:

> *"Obsidian is not open source software and this repo DOES NOT contain the source code of Obsidian."*

`obsidian.md/download` 의 Windows 버튼이 곧바로
`github.com/obsidianmd/obsidian-releases/releases/download/v1.13.4/Obsidian-1.13.4.exe` 로 간다 — 자체 CDN 경유가 아니다.
**Zed 도 stable·preview 를 GitHub Releases 에 둔다**(`cloud.zed.dev` 는 302 리다이렉터일 뿐, nightly 만 DigitalOcean Spaces).

GitHub 약관에 컴파일된 비공개 소스 바이너리 호스팅을 금지하는 조항은 **없다**. 단 §9 에 대역폭 과다 시
*"throttle your file hosting"* 유보 조항이 있다([AUP](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)).

→ **비공개 개발 저장소와 별도로, 바이너리만 담는 공개 저장소를 하나 만드는 것**이 검증된 경로다.
현재 `app-update.yml` 이 비공개 저장소(`JioBani/AgentPartyApp`)를 가리키므로 **`build.publish` 로 덮어써야 한다**([F-03](F-03%20설치와%20배포%20방식.md) 실측).

electron-updater 가 지원하는 배포처: GitHub Releases · S3 · DigitalOcean Spaces · **Cloudflare R2** ·
Keygen · **generic HTTP(s)**. generic 은 `latest.yml` + exe 를 정적 호스팅하면 되고,
**`latest.yml` 은 이미 빌드가 생성한다**([F-03](F-03%20설치와%20배포%20방식.md) 실측).

### 🔵 Obsidian 의 업데이터 설계 — 우리가 베낄 값이 있는 부분

Obsidian 은 electron-updater 도 Squirrel 도 안 쓴다. `app.asar` 를 추출해 `main.js` 를 읽은 결과:

1. **1시간 주기**로 공개 저장소의 `desktop-releases.json` 을 확인(실패 시 자체 도메인으로 폴백)
2. 무결성을 **두 겹**으로 검증 — SHA256 해시 + **`main.js` 에 하드코딩된 X.509 인증서로 RSA-SHA256 서명 검증**
3. `minimumVersion` 게이트 — Electron 자체가 올라가야 할 때만 **전체 설치 프로그램 재실행**을 요구
4. 그 외 일상 업데이트는 **`obsidian-<ver>.asar` 8.8MB 만 내려받아** `%APPDATA%` 에 두고 부팅 시 그걸 로드

> 🔵 **핵심 교훈: Obsidian 은 업데이트 무결성을 Authenticode 에 의존하지 않는다.** 자체 RSA 인증서를
> 앱에 핀으로 박아 두었다. **코드 서명과 자동 업데이트 신뢰를 분리한 것이다.**
> 우리도 미서명 상태에서 `latest.yml` 의 `sha512` 로 같은 보장을 얻는다(이미 생성됨).

또 하나: **327MB 설치본 vs 8.8MB 업데이트**로 쪼갠 것은 대역폭 설계다. 우리 설치본은 142.5 MiB 다.
다만 이 2층 구조는 자체 업데이터를 만드는 비용이 든다 — **베타 범위에서는 과하다**(아래 권고).

⚠️ **exe 는 실행 중 자기 자신을 덮어쓸 수 없다.** Zed 는 이 때문에 별도
`auto_update_helper.exe` 를 두고 종료 시 교체를 마친다. electron-updater 의 NSIS 경로는 이걸
내부적으로 처리하므로, **직접 만들면 이 문제를 우리가 떠안는다.**

## 정해야 할 것

- 업데이트 확인처 — **[F-03](F-03%20설치와%20배포%20방식.md) 의 배포처와 같은 곳**이어야 한다. 같이 정한다.
- 확인 주기 — 시작 시 1회로 충분한가.
- 알림 형태 — 방해하지 않으면서 놓치지 않을 자리.
- **변경 내용(무엇이 고쳐졌는지)을 보여줄 것인가.** 베타에서는 이게 신뢰를 만든다 —
  제보한 사람이 자기 제보가 반영된 걸 본다.
