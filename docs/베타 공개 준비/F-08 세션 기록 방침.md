# F-08. 세션 기록을 어떻게 다룰지 정하기 (= 보관/archive)

**판정: 미정** · 갈래: *있는데 못 쓴다* · 출처: 사용자

## 무엇을

세션 기록 기능이 **있기는 한데 사실상 쓸 수 없다.**
무엇을 어떻게 남기고 어떻게 다시 꺼낼지를 **먼저 정한다.**

## ⚠️ 이건 구현 항목이 아니라 결정 항목이다

지금 없는 것은 기능이 아니라 **방침**이다.
**방침 없이 화면부터 만들면 또 못 쓰는 기능이 하나 더 는다.**

## 지금은

- 표면은 있다 — `GET /api/sessions/history`, `POST /api/sessions/resume`
  ([apiSpec.ts](../../src/shared/apiSpec.ts):36-37)
- **[P-4] 보관(archive)** 이 OPEN 개선 제안으로 남아 있다.
  사용자가 말한 *"이전에 적어놨던 세션 보관"* 이 이것이다. **같은 항목으로 합친다.**

## 설계의 바닥 — 이미 확정된 사실

1. **앱 기록은 화면용 사본이고, 하네스가 자기 원본을 따로 남긴다.**
   대화 인계도 **하네스 원본**을 쓰기로 이미 결정됐다([#26] 조사에서 확정).
2. **멤버당 800조각 상한**이 있고, 그 조각의 **79~90% 가 도구 실행·상태 표시**다.
   → 도구를 많이 쓰는 멤버는 **15턴 만에** 상한에 닿는다(다른 멤버는 57턴).
3. **[#26]**(OPEN): `이전 대화 N개 더 보기` 를 끝까지 눌러도 **잘렸다는 표시가 없다.**
   원본이 살아 있어도 **사용자는 자기가 전부 봤다고 믿는다.**

## 정해야 할 것

### ① 앱 기록의 역할을 무엇으로 좁힐 것인가
원본이 하네스에 있다면, 앱 기록은 "전부"가 아니라 **"보기 좋은 최근"** 이면 충분한가?
**이 질문에 답하면 나머지가 따라온다.**

### ② 무엇을 줄일 것인가 ← **실측으로 답이 갈렸다 (2026-08-08)**

⚠️ **이 문서가 원래 적은 "도구 조각을 줄이면 상한도 디스크도 같이 해결된다"는 틀렸다.**
[B-10](B-10%20트랜스크립트%20용량.md) 실측 결과 **레버가 둘이고 서로 다르다:**

| 문제 | 지배 요인 | 레버 | 상태 |
|---|---|---|---|
| **800 상한이 대화를 밀어냄** | **`status`** (개수 48.7%, 바이트 5.5%) | status 를 상한 예산에서 제외 | ✅ **완료** (`5fda851`) |
| 디스크 | **`tool.result`** 중 **base64 스크린샷** | 이미지를 파일로 분리 | ✅ **완료** (`d57710f`) |

⚠️ **아래 두 가지는 이 문서가 원래 적었던 것과 다르다. 실측으로 갈렸다:**
- **"디스크를 줄이려면 `tool.result` 전문을 잘라야 한다" → 아니다.** 텍스트 도구 결과는
  최대 46 KB 로 이미 하네스 임계값(Codex 40 KB) 대역이라 자를 여지가 없다. 실제로 큰 것은
  **base64 스크린샷**(최대 564 KB)이고, 그건 **압축도 truncation 도 안 듣는다**(PNG gzip 94.4%).
  → **파일로 분리**가 유일하게 듣는 수단이었다.
- **"status 개수 57.7% / 남은 대화 4~76턴" 수치는 옛 표본이다.** 재측정값은 status **48.7%**,
  상한 도달 파일에서 남은 대화 **352~451 블록**(세 파일은 **user 턴 0개**).
  수정 후 대화 보존은 **1.8~2.3배**로 늘었고, 대신 **파일 크기도 약 2배**가 된다(실측 2.08× ↔ 2.01×).

두 결정이 따로 내릴 수 있고 상충하지 않는다는 판단은 그대로 유효했다.
근거·검증표 전체는 [B-10](B-10%20트랜스크립트%20용량.md).

### ③ 보관(archive)의 뜻
지운다 / 숨긴다 / 내보낸다 중 무엇인가. **되살릴 수 있는가.**
(참고: Conductor 는 보관 시 **커밋·미커밋 변경까지 ref 로 저장**해 나중에 복원한다.
Vibe Kanban 은 **보관 = 전부 보존 / 삭제 = 워크스페이스만 제거**로 둘을 갈랐다.)

### ④ 원본으로 가는 길
앱에서 잘린 지점에서 **"나머지는 여기서 볼 수 있다"** 를 알려줄 것인가.

## ✅ ④ 원본으로 가는 길 — 구현됨 (2026-08-08, 소유자 `harness-storage`)

보관 한도에 걸린 트랜스크립트 맨 위에 **하네스 원본 경로**를 띄운다. 잘린 트랜스크립트의
맨 위 도달은 대화의 처음에 도달한 것과 화면상 구분이 안 되므로, 그 지점에서만 알린다.
새로 모을 데이터는 없었다 — `harnessSessionId` 가 이미 저장돼 있다.

엔드포인트 `GET /api/party/members/:name/harness-original`.
상세·검증표는 [B-10](B-10%20트랜스크립트%20용량.md) 참조. 브랜치 `fix/b10-transcript-cap` (`e586e48`).

## ✅ 확인 완료 — 폴더를 옮기면 하네스 원본이 따라오지 않는다 **(사실이었다)**

**2026-08-08 실측으로 확증했다.** 아래 위험은 가정이 아니라 사실이다.

Claude Code 의 디렉터리 이름은 **절대 cwd 의 순수 함수**다 —
`[a-zA-Z0-9]` 이외의 모든 문자를 `-` 로 치환(이 PC 의 project 디렉터리 74/74 로 검증).
경로가 바뀌면 **다른, 그리고 비어 있는 디렉터리**로 매핑된다.
확인: `D:\Moved\Elsewhere` → `D--Moved-Elsewhere`, `exists:false`.
이 PC 에 흔적도 있다 — 같은 프로젝트가 두 경로에 있고 한쪽은 17개 65 MB, 다른 쪽은 **0개**다.

→ **"인계는 하네스 원본을 쓴다"는 결정의 전제는 폴더를 옮기는 순간 깨진다.**
지금 구현은 이걸 숨기지 않는다: 결과에 `exists` 를 실어, 못 찾으면 죽은 경로 대신
*"작업 폴더를 옮겼다면 하네스 기록은 이전 경로에 남아 있습니다"* 라고 말한다.
**남은 결정**: 폴더 이동을 감지해 이전 경로를 기억해 둘 것인가(그러면 이동 후에도 원본을
가리킬 수 있다). 이건 아직 안 했다.

### 원래 적혀 있던 위험 (출처)

[B-11](B-11%20파티%20찾기.md) 조사에서 나온 위험이다.

**하네스는 자기 대화 기록을 절대 경로로 키잉한다.**
Vibe Kanban 이 정확히 이걸로 깨졌다 — 경로가 바뀌자 `~/.claude/projects/` 의 키가 무효가 되고
**Claude Code 세션 resume 이 끊겼다**(#2993). 후속 결함(#3255)도 열려 있다.

**이 앱에 그대로 걸린다.** 사용자가 프로젝트 폴더를 옮기면:
- 앱 상태(`.agent_party_app/`)는 **따라간다** — 설계대로 무사하다
- **하네스 원본은 옛 경로에 묶여 따라오지 않는다**

> **"폴더를 옮겨도 파티가 따라온다"는 이 앱의 장점이, 대화 연속성에서는 성립하지 않을 수 있다.**

**"인계는 하네스 원본을 쓴다"는 결정의 전제가 여기서 흔들린다.**
방침을 정하기 전에 **실제로 확인할 것.** 지금은 검증되지 않은 가정이다.

## 방침이 늦어지면

**[#26] 의 "잘렸다는 표시"만 먼저** 떼어낼 수 있다.
사용자가 **데이터 손실로 오해하는** 자리라 그것만으로도 값이 크다.
