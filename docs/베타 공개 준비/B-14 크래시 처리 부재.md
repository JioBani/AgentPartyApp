# B-14. 앱이 죽어도 아무 흔적이 없다

**판정: 차단** · 갈래: *조용히 실패한다* · 출처: [조사-베타 운영과 진단](조사-베타%20운영과%20진단.md)

---

## ✅ 1단계 완료 (2026-08-08, `beta-impl`)

**데스크톱 + 헤드리스 엔진 양쪽에 크래시 핸들러를 붙였다.** 수동 e2e 로 실제 크래시를 일으켜 확인.

### 만든 것
- `src/main/crashHandler.ts` (신규) — `installCrashHandlers({exit, describeContext})`.
  **electron 비의존**으로 만들어 두 프로세스가 같은 것을 쓴다.
- `src/main/logger.ts` — `logCritical()` 추가. 기존 `log()` 은 쓰기 실패를 삼키는데(앱을 깨면 안 되므로),
  **크래시 기록만은 실패를 stderr 로 드러낸다.** 파일을 못 써도 기록이 남는다.
- `src/main/main.ts` — import 직후 설치(무엇이든 실패하기 전에)
- `src/main/engine/transport/engineServerEntry.ts` — 헤드리스 엔진에도 설치

### 치명/비치명 판정 — 실측 근거
조치 전 동작을 **먼저 재고** 나서 정했다.

| | 조치 전 실측 | 로그 흔적 | 판정 |
|---|---|---|---|
| `uncaughtException` | 앱 죽음 | **0건** | **치명** → 기록 후 `app.exit(1)` |
| `unhandledRejection` | **앱 계속 살아있음** | **0건** | **비치명** → 기록만, 계속 실행 |

근거: Electron 33 은 메인 프로세스를 `--unhandled-rejections=warn` 으로 돌린다.
→ **rejection 을 죽이면 지금 멀쩡히 도는 앱을 새로 죽이는 것**이라 안 죽인다.
대신 패키징 빌드에선 보여줄 데도 없는 콘솔 경고를 **영구 기록**으로 바꿨다.

### 덤으로 잡은 것 — 좀비
조치 전에는 `uncaughtException` 이 나면 프로세스가 **자동화 포트와 단일 인스턴스 락을 쥔 채
남았고**, 그래서 **다음 실행이 아무 설명 없이 즉시 종료**됐다.
→ `app.quit()` 이 아니라 **`app.exit(1)`** 로 끝내 해결. 포트 반납 확인.

### 엔진 쪽 설계 포인트
엔진은 **stdout 이 RPC 채널**이라 콘솔 로깅이 꺼져 있다. `logCritical()` 은 **stderr** 로 쓰고,
`wslEngine.ts` 가 자식 stderr 를 캡처해 데스크톱 로그에 남긴다
→ **기록 하나가 경계 양쪽(엔진 로그 + 데스크톱 로그)에 남는다.** 실측 확인.

### 기록에 담는 것
`version` · `packaged` · `uptimeSec` · `windows` · `sessions` (엔진은 `runtime`·`uptimeSec`).
**경로·멤버명·프롬프트는 안 담는다** — 워크스페이스 경로도 멤버 이름도 식별 정보다.

### 남은 것
- **2단계(사용자에게 알리기)·3단계(error boundary)는 미착수** — 설계 결정이 필요해 범위에서 뺐다.
  2단계는 [F-13](F-13%20진단%20접근.md) 의 `로그 폴더 열기` 자리와 한 몸이다.
- ⚠️ **크래시 시 discovery 파일이 stale 로 남는다** (`app.exit` 은 `before-quit` 를 안 탄다).
  조치 전에도 동일했고, **깨진 상태에서 정리 로직을 더 도는 것이 위험**해 손대지 않기로 했다.
  → 별건으로 판단 필요.

---

## 무엇이 문제인가

프로세스 수준 예외 처리기가 **하나도 없다.**

| 있어야 할 것 | 현재 |
|---|---|
| `process.on("uncaughtException")` | **없음** |
| `process.on("unhandledRejection")` | **없음** |
| 렌더러 React error boundary | **없음** (`src/renderer/App.tsx`) |
| 있는 것 | 시작 시 오류만 잡는 `app.whenReady().then(bootstrap).catch()` (`src/main/main.ts:933-936`) |

**실행 중 치명적 오류가 나면 앱이 그냥 사라진다.** 사용자에게 아무 말도 없고,
**죽기 전에 로그가 남는다는 보장도 없다.**

## 왜 베타에서 특히 심각한가

이건 안정성 문제이기 전에 **정보 손실**이다.

> **가장 심각한 결함이 가장 적은 단서를 남긴다.**

베타의 목적은 "고칠 것을 찾는 것"인데, **제일 크게 터진 것만 흔적 없이 사라진다.**
사용자는 *"쓰다가 갑자기 꺼졌어요"* 라고밖에 말할 수 없고, 그걸로는 아무것도 못 고친다.

프로젝트 규칙(AGENTS.md, *"실패를 조용히 넘기지 말 것"*)의 **최상위 위반**이기도 하다.
다른 항목들은 특정 기능이 조용히 실패하는 것이고, 이건 **앱 전체가 조용히 실패**한다.

## 무엇을 만들 것인가

**세 겹으로 나눈다. 뒤로 갈수록 비싸다.**

### 1단계 — 죽기 전에 기록한다 (가장 싸고 가장 중요)
`uncaughtException` / `unhandledRejection` 을 잡아 **로그에 남기고 나서** 종료한다.
이것만으로 *"흔적 없음"* 이 *"흔적 있음"* 으로 바뀐다.

⚠️ **주의**: 예외를 잡아서 **계속 실행하려 들지 말 것.** 상태가 이미 깨진 뒤라 더 이상한 실패를
낳는다. **기록하고 정직하게 죽는 것**이 목적이다.

### 2단계 — 사용자에게 말한다
종료 전(또는 다음 실행 시) **"앱이 예기치 않게 종료됐고 기록은 여기 있다"** 를 보여준다.
→ [F-13](F-13%20진단%20접근.md) 의 `로그 폴더 열기` 와 같은 자리다. **함께 만든다.**

### 3단계 — 렌더러는 통째로 죽지 않게 한다
React error boundary. 화면 한 조각이 깨져도 **앱 전체가 흰 화면이 되지 않게** 한다.
경계를 어디에 둘지 정해야 한다(패널 단위 / 탭 단위 / 앱 루트).

⚠️ **여기서도 침묵 금지** — 경계가 오류를 잡아 예쁘게 가리기만 하면 그게 더 나쁘다.
**"이 패널이 오류로 멈췄다"를 그 자리에 표시**하고 기록에 남긴다.

## 정해야 할 것

- 1단계에서 **어디까지 기록할 것인가** — 스택만? 마지막 상태(활성 파티·멤버·턴)까지?
  후자가 훨씬 유용하지만 개인 정보가 섞일 수 있다.
- 2단계 알림을 **종료 직전에 띄울지, 다음 실행에서 띄울지.** 종료 직전은 실패하기 쉽다.
- 3단계 경계의 **입자도**.
