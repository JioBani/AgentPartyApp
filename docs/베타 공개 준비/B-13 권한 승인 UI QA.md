# B-13. 권한 승인 UI 가 검증되지 않았다

**판정: 차단 · ⚠️ 절반만 완료 (2026-08-08)** · 갈래: *작성자가 안 쓰는 경로가 비어 있다* · 출처: 사용자

---

## 1차 QA 결과 (2026-08-08, `beta-impl`)

### ① [#20] 최악 조합 — **"0" 이 아니라 "1" 이다. 다만 지적은 유효.**

⚠️ **중간에 한 번 틀렸다가 잡았다.** 처음엔 선택자를 `[class*="approval"]` 로 잡아 **0** 이 나왔는데,
실제로는 배지가 `.wb-tab-badge`(텍스트 "승인")라 안 잡힌 것이었다.
→ **[B-16](B-16%20Codex%20트랜스크립트%20미표시.md) 교훈("이름 못 찾음 ≠ 없음")에 그대로 걸릴 뻔했다.**

승인 대기를 알릴 수 있는 경로 **4개**(전부 실측):

| 경로 | 사라지는 조건 |
|---|---|
| 사이드바 멤버 배지 "승인" (`PartySidebar.tsx:298`) | **사이드바 접으면** |
| **탭 배지 "승인"** (`TabStrip.tsx:57`) | **배경 탭에도 남음** ← 최후의 보루 |
| 패널 헤더 상태 필 (`Panel.tsx:135` `{wide && …}`) | **폭 600px 미만** |
| 승인 카드 본문 | 그 멤버가 **활성 탭일 때만** |

최악 조합 실측(사이드바 접음 + 창 최소폭 + 승인 멤버가 배경 탭):
```
panelWidths: [487,487]  density: ["mid","mid"]  sidebarShown: false
channels: { sidebarBadge:0, tabBadge:1, panelStatusPill:0, approvalCard:0 }   TOTAL = 1
```
패널 5개 × 190px 까지 밀어도 탭 배지는 **visible + inViewport 유지**(26px).

**🔴 그래도 [#20] 은 유효하고, 문턱이 생각보다 훨씬 낮다:**
> `wide` 기준이 **600px** 인데, **1480px 창을 2분할만 해도 579px = mid** 다.
> 즉 상태 필은 *"좁은 창"* 이 아니라 **기본 사용 형태에서 이미 사라진다.**

남는 유일한 경로가 **26px 짜리 칩 하나**다. → [D-01](D-01%20대화창%20상태%20표시.md) 에서 다룰 것.

### ② 승인 전달 실패 — ⚠️ **실측 못 함 (정직하게 기록)**
[B-17](B-17%20파티%20생성%20실패가%20UI에서%20조용하다.md) 에서 `approve` 를 토스트에 이었으나
**IPC 를 인위적으로 실패시킬 방법이 없어 화면에 뜨는 것까지는 확인 못 했다.**
같은 헬퍼가 파티 생성 실패에서는 실제로 토스트를 띄우는 것을 확인했으므로 배선은 같은 경로지만,
**"실측했다"고 말하지 않는다.**

### ③ 멤버 설정 저장·복원 (1-11-2) — ✅ 통과
실제 Codex 멤버에 특징적 값을 주고 **앱 완전 재시작** 후 동일 확인:
`{"sandbox":"read-only","approval":"untrusted","guardian":true}` → 그대로.

### ④ 🔴 **카드 내용 검증은 못 했다** — 수단이 없다
→ **[B-18](B-18%20QA%20승인%20주입이%20실제%20승인을%20못%20만든다.md) 로 분리.**

기능정의서 1-10-1 이 정의한 항목 대부분(**명령 원문 · 작업 디렉터리 · 파일 diff ·
Codex 결정 범위 · 항상 허용될 규칙**)을 **지금 QA 수단으로는 만들 수 없다.**

**즉 B-13 의 절반은 아직 안 끝났다.** B-18 이 풀려야 나머지를 할 수 있다.

## 무엇을

권한 승인(approval) 화면에 문제가 없는지, **정보가 제대로 나오는지** QA 한다.

## ⚠️ 이 항목이 이 문서 전체의 주제를 압축한다

사용자 말 그대로 — **"내가 승인 모드를 잘 안 써서"** 이 경로가 거의 안 밟혔다.

**그런데 베타 사용자는 정확히 반대다.** 처음 온 사람은 AI 에게 권한을 다 주지 않는다.
**승인 모드가 신규 사용자의 기본 동선**이다.

> **작성자가 가장 안 쓴 화면이 신규 사용자가 가장 많이 볼 화면이다.**
> 검증 공백이 가장 큰 곳과 사용자가 가장 먼저 닿는 곳이 일치한다.

이건 우연이 아니라 **구조적**이다. 저자의 사용 습관이 곧 검증 범위이기 때문이다.
그래서 이 항목은 "버그 하나"가 아니라 **베타 전에 반드시 통과해야 할 관문**이다.

## 볼 것 — 기능정의서 1-10-1 이 정의한 것이 실제로 다 나오는가

- 승인 카드: **도구명 · 설명 · 실행 명령**
- **거부** / **이번 한 번 허용**
- **Codex 결정 범위** — 이번 한 번 · 현재 세션 · 동일 command prefix 항상 · 거부
- **명령 원문**
- **작업 디렉터리**
- **파일 diff**
- **요청 사유**
- **항상 허용될 규칙** (사용자가 무엇에 동의하는지 알 수 있어야 한다)
- 처리 후 **상태 유지** (누른 뒤 카드가 어떻게 남는가)
- **사이드바 승인 배지**

## 조사에서 나온 관련 결함

- **Guardian 토글·결과 표시가 없다** — 기능정의서 1-4-3·1-11-1 은 Guardian 을 적어 뒀는데,
  **UI 토글도, Guardian 이 막았는지 통과시켰는지 표시도 없다.**
  → **문서와 코드가 어긋난 자리다**([B-08](B-08%20통계%20산출.md) 과 같은 종류의 어긋남).
  QA 에서 실제 상태를 먼저 확인할 것.
- **prefix 규칙 안내가 부족** — "동일 command prefix 항상 허용"을 고를 때
  **무엇에 동의하는 것인지** 충분히 보이는지.

## ⚠️ [#20] 을 반드시 같은 조건에서 볼 것

[#20](OPEN): 패널 헤더 상태 필이 **`wide` 폭에서만** 렌더된다.
좁은 폭에서는 `working` 뿐 아니라 **`approval`(승인 대기)·`stalled` 까지 표시가 사라진다.

**최악 조합 — 알 경로가 정말로 0이 된다:**
> **사이드바를 접은 상태 + 좁은 패널** → 승인 대기를 알릴 경로가 **하나도 없다.**

재현: 패널을 3분할하고 각 패널을 좁힌 뒤, 사이드바를 접고, 한 멤버를 승인 대기로 만든다.

## QA 방법

프로젝트 방침대로 **실제 앱을 띄워 사람이 확인 + 캡처**가 완료 조건이다.
QA 모드(`AGENTPARTY_QA=1`)에 **승인 요청 주입**이 이미 있으므로(기능정의서 5-4-1)
세 하네스 각각에 대해 승인 상태를 만들어 화면을 확인할 수 있다.

⚠️ 단 **주입된 상태가 실제 승인 요청과 같은지** 먼저 확인할 것 —
[#21] 에서 QA 수단이 실제 상황을 못 만들어 결함이 안 잡힌 전례가 있다.
