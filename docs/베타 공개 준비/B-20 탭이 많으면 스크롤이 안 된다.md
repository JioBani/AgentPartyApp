# B-20. 탭이 여러 개일 때 스크롤이 안 된다

**판정: 차단** · 갈래: *있는데 못 쓴다* · 출처: 사용자 (2026-08-08)
**소유자: beta-impl** · **구현 완료 (2026-08-09, master `bcb0649`)** — [구현](#구현-2026-08-09) 절 참조

## 증상 (사용자 보고)

한 패널에 탭이 여러 개일 때:
- **스크롤이 되어야 하는데 안 된다**
- 그래서 **탭이 몇 개인지도 안 보인다**

## 왜 차단인가

넘친 탭에 **접근할 방법이 없다.** 항목이 화면 밖으로 밀리면 클릭할 수 없다 —
`[#11]` 과 같은 종류의 **기능 차단**이다.

그리고 개수가 안 보이는 것이 별도로 나쁘다. 이 앱은 **여러 멤버를 동시에 띄우는 것**이 전제라
탭이 쉽게 늘어나는데, **몇 개를 열어 뒀는지 모르면 관리 자체가 안 된다.**

고칠 때 **탭 스트립만 고치지 말고 같은 축의 다른 자리도 함께 훑을 것.**

이 항목은 **한 패널에 탭이 많을 때**다. 축이 다르므로 모순이 아니다.

## 구현 (2026-08-09)

시안 `Workbench Multi.dc.html` 이 나와서 착수했다. 브랜치 `feat/workbench-multi`,
커밋 `29abbea` + `bcb0649`, master 에 fast-forward 병합됨.

### 스크롤이 아니라 접기로 갔다

시안이 **가로 스크롤이 아니라 `+N ⌄` 오버플로 칩**을 쓴다. 스크롤은 개수를 안 알려주고
(이 항목의 두 번째 증상이 정확히 그것이다) 숨은 탭의 승인 대기도 못 알린다.
접기는 **개수·상태를 칩 하나가 다 말한다.** 레퍼런스(브라우저·에디터)도 접기 쪽이 다수다.

### 무엇이 생겼나

| 파일 | 역할 |
|---|---|
| `src/renderer/workbench/tabOverflow.ts` | `splitTabs(tabs, active, panelWidth)` — 보이는 탭 / 접히는 탭 분리. 유일한 판단 지점 |
| `src/renderer/workbench/TabStrip.tsx` | 보이는 탭만 렌더 · `+N ⌄` 칩 · 팝오버 · `TabMarkers` 공용화 |
| `src/renderer/workbench/layout.ts` | `promoteTab()` — 접힌 탭을 맨 앞으로 올리고 활성화 |
| `src/renderer/workbench/useDensity.ts` | 측정한 폭을 그대로 반환(기존엔 밀도 등급만 줬다) |
| `src/renderer/styles.css` | `.wb-tab-overflow*` 계열 + `.has-overflow` 패킹 규칙 |

불변 규칙 두 가지가 `splitTabs` 에 박혀 있다 — **활성 탭은 절대 안 접힌다**(밀려나면 마지막
보이는 탭과 자리를 맞바꾼다), **최소 한 개는 항상 보인다.**

### ⚠️ 폭 추정을 하지 마라 (한 번 했다가 되돌렸다)

처음엔 탭마다 폭을 추정해서 합산했다. 사용자가 바로 잡아냈다 —
*"멤버가 탭에 가득차서 추가된게 아니고, 그냥 비어있는데 +6으로 되어있잖아."*

실제 앱에서 CDP 로 재보니:

```
탭        실측폭   추정치   오차
india    107.53     118    +10.5
alpha     112.5     118     +5.5
charlie  120.05     132      +12
칩: 실측 45.1px, 예약 52px
→ 탭 상자 안에 남은 빈칸 102.1px
```

**그런데 추정을 정확하게 고쳐도 해결되지 않는다.** 정확해도 "다음 탭이 안 들어가는 만큼"의
빈칸은 원리상 남고, 사람 눈에는 *자리가 남는데 왜 숨기지* 로 읽힌다.

그래서 **추정기를 통째로 지웠다.** 지금 `splitTabs` 가 하는 계산은
`MIN_TAB(116px)` 기준으로 **몇 개가 들어가는가** 하나뿐이고, 넘칠 때는 CSS
(`.wb-tabstrip.has-overflow .wb-tab { flex: 1 1 0; min-width: 0 }`) 가 보이는 탭들에게
줄을 나눠 갖게 한다. **칩이 뜨는 순간 줄은 항상 꽉 차 있다** — 이게 "자리가 없어서 접혔다"를
설명 없이 보이게 만드는 부분이다. 코드도 68줄 줄었다.

좁아지면 **이름이 먼저 양보하고 멤버 색 점·승인/미읽음 배지는 자리를 지킨다.** 접힌 이유를
알려주는 정보가 먼저 사라지면 안 된다.

### 곁다리로 정리한 것

`+`(탭 추가) 버튼을 지웠다. 멤버는 어떤 멤버가 있는지 아는 목록인 **사이드바에서** 여는 것이라
탭 스트립의 `+` 는 갈 곳이 없었다. 넓은 패널에서는 모델 옆에 effort 를 함께 표시한다(`7b9f4db`).

### 검증 — 수동 e2e (실제 앱 + CDP 실측)

격리 `AGENTPARTY_USER_DATA` + 임시 워크스페이스로 실제 앱을 띄우고, 한 패널에 멤버 11개를
붙여 CDP `Runtime.evaluate` 로 실제 렌더 박스를 쟀다. **22/22 통과.** 핵심 두 개:

```
OK  칩이 떠 있을 때 탭 줄이 꽉 차 있다 (+N 옆에 빈칸 없음)
    — gap 0px · widths [125,125,125,125,125,125,125]
OK  활성 탭은 자리가 없어도 접히지 않는다
    — ["real","alpha","bravo","charlie","delta","foxtrot"]
```

사용자 육안 확인도 QA 인스턴스에서 마쳤다. 패널 핸들을 좌우로 끌면 탭 개수와 `+N` 숫자가
따라 바뀌면서 줄은 계속 꽉 차 있다.

### 이어받을 사람에게 남은 것

- **같은 축 전수 훑기를 안 했다.** 위 *"이 계열의 네 번째"* 표가 시킨
  *"탭 스트립만 고치지 말고 같은 축의 다른 자리도 함께 훑을 것"* 은 미이행이다.
  가로 오버플로가 있을 만한 다른 자리(툴바, 상태 줄, 칩 나열)를 훑는 작업이 남아 있다.
- `MIN_TAB = 116` 은 이름이 읽히는 최소치로 잡은 값이고 측정 근거가 아니라 판단이다.
  더 좁혀도 되는지는 실제 멤버 이름 길이 분포를 보고 정할 일이다.
