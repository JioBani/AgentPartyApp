# B-04. 사용량이 제대로 적용되지 않는다

**판정: 실측 완료 (2026-08-08) — 증상은 "멈춘 값"** · 갈래: *숫자가 안 맞는다* · 출처: 사용자

---

## ✅ 답 — **지어내지는 않는다. 낡은 값을 새 값인 척 보여준다.**

`usageLimits.ts:204` 병합 경로:
```ts
const windows = mergeWindows(prev?.windows, incoming.windows);  // 빈 incoming → prev 유지
return { …, windows, updatedAt: incoming.updatedAt };           // ← 시각은 갱신
```
`mergeWindows`(`:184-193`)는 **incoming 이 비어 있으면 이전 window 를 그대로 남긴다.**

**설계 의도 자체는 정당하다** — Claude 는 이벤트마다 window 를 하나씩만 보내므로,
안 온 window 를 지우면 안 된다.
**문제는 그 규칙이 "부분 보고"와 "읽기 실패"를 구분하지 못한다는 것이다.**

세 가지가 겹친다:
1. 읽기가 실패해도 **pill 은 마지막 성공값을 계속 보여준다**
2. **`updatedAt` 이 실패한 읽기 시각으로 갱신된다** → 스냅샷이 **없는 신선도를 주장한다**
3. **`updatedAt` 은 어디에도 렌더되지 않는다**(pill·팝오버 전부) →
   사용자에게 **오래됐음을 알 단서가 0**

> 방침(*"근거 없으면 알 수 없음"*) 위반은 **pill 이 아니라 병합 계층**에 있다.

**증상은 "안 뜬다/0이다/틀린 값"이 아니라 「멈춘 값」이다.**
사용자가 *"사용량이 안 맞는다"* 고 느낀 것이 이것일 가능성이 높다 — **값이 바뀌지 않아서 틀려 보이는 것.**

## pill 자체는 정직하다 (문제 없음)
- `available === false` → **`N/A`**
- 데이터 없음 → **`—`** + 회색 링
- 아무 provider 도 데이터가 없으면 **pill 을 아예 안 그린다**
→ **숫자를 만들어내는 곳은 없었다.**

## 1,287건 단서의 정체 — 이미 고쳐진 증상의 잔해
그 status 조각은 두 멤버 것이고 **1분 간격(60초 폴링)** 이었다.
`emitUsageStatus` 가 예전엔 `type:"status"` 를 냈고, **`3200b73`(2026-07-10)** 에서
`type:"diagnostic"` + 중복 억제로 바뀌었다.
> **대화창 도배는 2026-07-10 에 해결됐고, 1,287건은 그 이전 잔해다.**

**다만 실패 자체는 안 고쳐졌다** — 현재 형태로 앱 로그에 **1,742건**, 마지막 **2026-07-24**.
(그 뒤 로그엔 어댑터 폴링 흔적이 없어 **최근에 안 났는지 안 돌았는지는 구분 못 했다.**)

## 어디가 틀리는지 — 좁힌 결과

## 구독 vs API 키
API 키/Bedrock/Vertex 는 `rate_limits_available:false` 라 정직하게 `N/A`.
관측된 실패는 전부 **구독 경로**. 이미 한 번 회귀가 있었다 —
주석: *"read stamp available:false hid a real 30%/14% reading behind 'N/A'"*.
그래서 지금은 `windows.length > 0` 이면 available 을 못 내리게 막아 뒀다.

## 고칠 것

### ✅ 완료 (2026-08-08) — `updatedAt` 을 실패 시 갱신하지 않는다

**"부분 보고 vs 읽기 실패" 구분이 실제로 섰다.** 판별자를 전수 확인했다:
> **데이터가 있는 경로는 반드시 window 를 1개 이상 보낸다**
> (claudeAdapter 941·1111 / codexAdapter 811·1272 / cursorAdapter 162).
> **`windows: []` 는 오직 실패 분기에서만** 나온다
> (claudeAdapter 953 / codexAdapter 818·822 / cursorAdapter 153·166).

어댑터 3개 전부 이 규칙을 지켜서 `incoming.windows.length === 0` 이 **신뢰할 수 있는 판별자**다.
추정이 아니라 전수 확인이다.

**바꾼 것 한 줄** (`src/shared/usageLimits.ts`):
```ts
updatedAt: incoming.windows.length > 0 ? incoming.updatedAt : prev?.updatedAt ?? incoming.updatedAt,
```
`mergeWindows` 의 이전 window 유지는 **안 건드렸고**, pill 표시도 **안 건드렸다.**

**검증** — 5개 분기 전부:
```
1) 첫 성공            → updatedAt = T1 ✅
2) 다음 읽기 실패      → window 유지 · updatedAt 안 밀림 ✅
3) 다시 성공          → 반영 · updatedAt = T2 ✅
4) 부분 보고(weekly만) → window 유지 · updatedAt 밀림 ✅ ← 실패로 오분류 안 됨
5) 첫 읽기부터 실패    → 속일 데이터 자체가 없음 ✅
```
⚠️ **한계**: `/api/qa/usage` 가 window 최소 1개를 요구해 **실패 읽기를 실앱으로 주입할 수 없었다.**
실패 분기는 빌드된 함수로만 검증했다.

### ⚠️ 결정 필요 — 읽기 실패를 화면에 어떻게 표현할까
1. 옛값을 **지운다**(공백)
2. 옛값을 **흐리게 + "n분 전"** 으로 표시
3. 그대로 두되 **경고만** 붙인다

셋 다 UX 가 다르다. (참고: [F-08](F-08%20세션%20기록%20방침.md)·1-14-1 에
*"닫힌 멤버의 마지막 값은 흐림 처리 + `~` 표기"* 라는 **기존 관례**가 있다 — 2번과 결이 같다.)

두 가지를 혼동하면 숫자가 틀린다:

1. **게이트 리뷰 턴은 리뷰어 모델로 기록된다** → 멤버 모델 집계에서 **빼야 한다**
   (`isMemberModelTurn`). 안 빼면 **쓰지도 않은 모델이 사용량에 뜬다.**
2. **`tokens.context` 는 누적 합이 아니라 점유량이다** — 더하면 안 된다.
