# D-02. 내부 용어가 그대로 노출된다 (`spawn` 등)

**판정: 전수 조사 완료 (2026-08-08) — 적용은 결정 대기** · 출처: 사용자

---

## ✅ 노출 경로는 **하나**다 — 고치기 유리하다

`src/shared/transcriptEvents.ts:38`
```ts
text: [event.status, event.detail].join(": ")
```
**하네스가 내는 상태값과 detail 이 가공 없이 그대로 대화창에 찍힌다.**
자리마다 흩어진 게 아니라 **한 곳에서 샌다.**

## 실측 — 실제 저장된 status 조각 5,776개

> **`responding` + `requesting` 만으로 status 조각의 60%.**
> D-02 는 *"가끔 보이는 단어"* 가 아니라 **대화창에서 가장 자주 읽히는 텍스트**다.

**stderr 노출도 실재한다** — 저장본에는 ANSI 코드가 0건이지만,
[B-16](B-16%20Codex%20트랜스크립트%20미표시.md) 라이브 세션에서 Codex stderr 가
`stderr: [2m…[31mERROR[0m rmcp::transport::worker: …` 형태로 **대화창에 그대로** 찍히는 것을 확인했다.

## 그 외
- **`statusLabel()`**(`memberStatus.ts:203-223`) — 패널·사이드바 상태 필이
  `working`·`stalled`·`approval`·`not started`·`disconnected`·`sleeping` **원문 그대로**
- 코드 스캔 105줄에 구현 용어(`sessionId` 26 · `partyId` 23 · `snapshot` 7 …).
  다만 **변수명 오탐이 많아 위 실측 표가 더 신뢰할 만하다.**

## 용어표 초안

| 구현 용어 | 제안 | 근거 |
|---|---|---|
| `requesting` | **요청 중** | |
| `responding` | **응답 중** | |
| `working` | **작업 중** | `WorkingDots` 가 이미 "작업 중" 사용 → 통일 |
| `approval` | **승인 대기** | 배지가 이미 "승인" → 통일 |
| `stalled` | **응답 없음** | |
| `not started` | **시작 안 함** | |
| `disconnected` | **세션 없음** | 코드 주석이 *"왜인지 모른다"* → **원인 단정 회피** |
| `sleeping` | **절전** | 경고가 아니라 첫 지연 설명용 |
| `spawned` | **시작됨** (+ 명령 전문은 **접기**) | |
| `queued`/`dequeued` | **대기열에 넣음 / 꺼냄** | |
| `interrupt` | **중단** | |
| `idle` | **대기** | |

## ⚠️ 남길 것과 바꿀 것의 경계

**바꾼다 — 앱 내부 구현 용어**
`spawned` · `requesting` · `responding` · `stalled` · `disconnected` · `dequeued` ·
`payload`/`snapshot`/`sessionId` 류 · **원본 JSON 덤프** · **stderr 원문** · **실행 명령 전문**

**남긴다 — 하네스가 실제로 쓰는 용어 (원문 유지)**
`compact` · `plan mode` · 권한 모드 이름(`Default`/`Accept edits`/`Bypass`/`Untrusted`/…) ·
Codex 샌드박스 이름 · `Guardian` · 도구명(`Read`/`Bash`/`Grep`) · 모델명

→ **이유**: 사용자가 하네스 문서·CLI 에서 만나는 이름과 달라지면 **검색이 안 된다.**
[B-06](B-06%20하네스별%20권한%20렌더링.md) 에서 확인했듯 권한 이름은 기능정의서 정본과도 1:1이다.

**경계선상 (판단 필요)** — `idle` · `working`
하네스 용어이기도 하고 앱 상태이기도 하다. 제안은 **번역**(가장 자주 읽히므로)이지만
원문 유지도 방어 가능하다.

## 언어 통일
위 표를 한국어로 잡으면 **status 조각 60% 이상이 한국어**가 되어 현재 혼재가 크게 준다.
다만 **어느 언어를 정본으로 할지는 결정 사항**이다
([조사-개인화 하드코딩](조사-개인화%20하드코딩.md) 참고 — i18n 계층은 없다).

## 무엇을

`spawn` 처럼 **구현 용어가 사용자 화면에 그대로** 나오는 자리를 전부 찾아,
사용자가 확실히 알아볼 수 있는 표현·디자인으로 바꾼다.

## 왜

이 앱이 **작성자 한 사람에게 맞춰져 있다**는 증상이 가장 직접적으로 드러나는 자리다.

> **만든 사람은 `spawn` 을 읽지만, 처음 온 사용자는 못 읽는다.**

그리고 이건 단순한 표현 문제가 아니다 — **사용자가 무슨 일이 일어났는지 모르면
다음에 뭘 해야 할지도 모른다.** 특히 오류·진단 문구에서 그렇다.

## 방법 — 전수 조사 먼저, 용어표 하나, 일괄 적용

### ① 노출 지점 전수 조사
흩어져 있을 가능성이 높은 곳:
- **상태값** (`responding`·`requesting`·`spawn`·`idle`·`stalled`…)
- **진단 메시지** (기능정의서 1-9-4)
- **오류 문구**
- **도구 실행 카드** (도구명·출처)

### ② 용어표를 한 번 정한다
⚠️ **자리마다 다르게 번역하면 같은 것이 다른 것처럼 보인다.**
`spawn` 을 어디서는 "생성", 어디서는 "시작"으로 쓰면 사용자는 두 가지 일이라고 읽는다.

### ③ 일괄 적용

## ⚠️ 언어 통일도 여기서 같이 정한다

조사 결과 UI 문자열의 **20~30% 가 한국어**, 나머지는 영어다. **i18n 계층은 없다**
([조사-개인화 하드코딩](조사-개인화%20하드코딩.md)).

> **지금은 어느 쪽 사용자에게도 일관되지 않다.**

i18n 도입은 **베타 범위 밖**(전 문자열 리팩터링이라 비용이 이 문서의 어떤 항목보다 크다).
하지만 **한쪽으로 통일하는 것**은 훨씬 싸고 효과가 있다.
**용어표를 만드는 김에 언어도 같이 정한다** — 두 번 훑지 않는다.

## ⚠️ 남길 것과 바꿀 것을 가를 것

**전부 바꾸면 안 된다.** 이 앱의 사용자는 개발자이고, 일부 용어는 **원문이 더 정확하다.**

- 하네스가 실제로 쓰는 용어(`compact`, `plan mode`, 권한 모드 이름)는 **원문 유지**가 맞다 —
  바꾸면 하네스 문서와 대조가 안 된다.
- **앱 내부 구현 용어**(`spawn`, `prewarm`, `dispatch` 같은 것)가 바꿀 대상이다.

**이 경계를 먼저 긋고 시작한다.**
