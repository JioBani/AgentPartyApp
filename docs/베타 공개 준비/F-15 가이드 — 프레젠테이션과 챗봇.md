## 1. 화면

**nav-rail 에서 누르면 지금 창이 가이드로 넘어간다.** 새 창이 아니다.

> ⚠️ **2026-08-17 방침 변경.** 원래는 별도 창이었다(프레젠테이션을 크게 보고 작업 화면을
> 가리지 않으려고). 실제로 띄워 보니 **가이드를 열면 사용자가 앱 밖으로 튕겨 나갔다** —
> 배우려던 그 앱이 뒤에 가려지고, 관리할 창이 하나 늘고, 돌아오려면 창을 닫아야 했다.
> 가이드는 앱의 한 화면이지 별개의 프로그램이 아니다. 그래서 **세션·Token Usage·인증과
> 똑같이 `ViewId` 하나**가 됐다. 넓이는 잃지 않았다 — nav-rail(52px)과 타이틀바(38px)만
> 빼고 창 전체를 쓴다.

**화면의 기본 상태는 아무것도 없는 채팅 화면**이다.

**창의 기본 상태는 아무것도 없는 채팅 화면**이다.

| 사용자가 하는 것 | 무엇이 뜨나 |
|---|---|
| 그냥 묻는다 | **챗봇** — 이 앱에 대해 질문하고 답을 받는다 |
| **"가이드 보기"** 를 누른다 | **프레젠테이션** — 앱을 움직여 보여준다 |

두 대화는 **완전히 별개**다(기록도 따로). 다만 **모델 설정은 하나를 공유**한다 —
모델 고르는 자리를 둘로 나눌 이유가 없다.

## 2. 프레젠테이션

### 2-1. 슬라이드 = 동작 하나

⚠️ **이 모델이 이 기획의 핵심이다.**

"페이지 안에 여러 동작" 같은 2계층이 **아니다.** **1차원 슬라이드 목록**이다.

- 여러 슬라이드가 **같은 HTML 장면을 공유**하고, 슬라이드마다 그 장면의 **상태만 다르다**
- PPT에서 방향키로 애니메이션을 한 단계씩 넘기는 것과 같다
- **N번으로 가면 그 장면이 N번 상태로 재현된다** — 앞뒤 어디로 뛰어도 똑같이

**왜 이 모델인가**: 되감기·건너뛰기·특정 지점으로 점프가 전부 공짜로 따라온다. 그리고
AI에게 넘길 상태가 **"지금 몇 번" 하나**로 끝난다. 2계층이면 (페이지, 스텝) 쌍을 계속
관리해야 한다.

### 2-2. 무대는 **진짜 워크벤치**다

그림도 스크린샷도 아니다. **실제 컴포넌트를 가짜 데이터로 렌더**한다.

**재료가 이미 있다.**

| 필요한 것 | 있는 것 | |
|---|---|---|
| 앱 UI를 단독으로 띄우기 | [`src/renderer/qa/appEntry.tsx`](../../src/renderer/qa/appEntry.tsx) — Electron 껍데기 없이 App 트리를 마운트 | ✅ 쓴다 |
| 디자인 토큰 일치 | `theme/` — 같은 토큰을 쓰므로 테마가 저절로 맞는다 | ✅ 쓴다 |
| 원하는 상태를 만들어내기 | ~~QA 주입 표면 `POST /api/qa/*`~~ | ❌ **못 쓴다 — §2-2-1** |

**이게 스크린샷 노후화 문제의 해답이다.** UI를 고치면 튜토리얼이 **저절로 따라온다.**
스크린샷이라면 UI가 바뀐 순간 조용히 거짓말이 되지만, 실제 컴포넌트는 그럴 수 없다.

⚠️ **상태를 넣는 방법은 처음 생각과 달라졌다.** QA 주입은 못 쓴다(§2-2-1·§2-2-2).
**결정된 방식은 §2-2-3 "가짜 preload"** 다. 아래 순서대로 읽을 것.

### 2-2-1. ⚠️ 조사 결과 — **QA 주입으로는 안 된다** (`scout`, 2026-08-17)

**위 표의 "QA 주입으로 상태를 만든다"는 방법은 성립하지 않는다.** 조사로 확인된 사실:

| 확인된 것 | 그래서 |
|---|---|
| `POST /api/qa/*` 는 LocalEngine → 파티 저장소를 **그 워크스페이스에 직접** 변경한다 | 슬라이드를 보여주려고 주입하면 **사용자의 진짜 파티가 바뀐다.** 사고다 |
| `App` 은 `window.agentParty` **IPC 에 묶여 있다**. `appEntry.tsx` 는 마운트만 하고, `qa-render.mjs` 는 preload 를 전부 mock 으로 갈아끼운다 | 단독 마운트가 곧 격리가 아니다 |
| 같은 프로세스에서 이중 마운트해도 **IPC · `party:update` · localStorage 를 공유**한다 | 무대와 실제 앱이 서로 간섭한다 |
| E2E 의 격리는 별도 Electron + `AGENTPARTY_USER_DATA` — **프로세스 단위**다 | 창 안에 끼워 넣는 것과 다른 이야기다 |

> **무너진 것은 *방법*이지 *발상*이 아니다.** "진짜 컴포넌트를 무대로 쓴다 → UI가 바뀌면
> 가이드가 저절로 따라온다" 는 그대로 살아 있다. 죽은 것은 **상태를 QA 주입으로 넣는 방식**이다.

### 2-2-2. 왜 QA 주입이 저 모양인가 — 재사용하면 안 되는 이유

`/api/qa/*` 는 **목업 시스템이 아니다.** `handleQaRoute` 는 `isQaEnabled()` 가 아니면
**403 을 돌려준다** — `AGENTPARTY_QA=1` 또는 E2E 모드에서만 열린다.
([qaRoutes.ts](../../src/main/automation/qaRoutes.ts))

> 즉 **배포본에서는 애초에 안 열린다.** 가이드가 쓸 수 있는 물건이 아니었다.

그리고 저장소를 직접 바꾸는 것은 **사고가 아니라 그 도구의 설계 의도**다. E2E 테스트는
**진짜 파이프라인을 통과시키는 것이 목적**이라, 화면만 가짜로 그리면 아무것도 증명하지 못한다.

| | 테스트 하네스 | 프레젠테이션 무대 |
|---|---|---|
| 요구 | 진짜 경로를 **반드시 통과**해야 한다 | 진짜를 **절대 건드리면 안 된다** |

**목적이 정반대다.** 우리가 테스트 도구를 프레젠테이션 도구로 재사용하려 한 것이 잘못이었다.

### 2-2-3. 결정 — 가짜 `window.agentParty` 위에 진짜 App 을 띄운다

**앱의 상태를 바꾸지 않는다. 애초에 IPC 를 타지 않는다.**

`App` 이 바깥과 이야기하는 통로는 `window.agentParty` **하나**다. 그러니 **문서를 하나 더
주고 그 안에서만 가짜를 노출**하면 된다.

```
메인 창 (진짜 window.agentParty)
  └ 가이드 화면 (ViewId "guide")
      └ 무대 = <iframe src="guide/stage/index.html">   ← 자기만의 document
            ├ window.agentParty   ← 가짜 (IPC 로 나가지 않는다)
            ├ window.localStorage ← 인메모리 (사용자의 UI 상태를 안 건드린다)
            └ 그 위에 진짜 App 트리를 마운트
```

> **처음에는 별도 `BrowserWindow` + 전용 preload 였다.** 격리 수단으로는 맞았지만
> §1 의 이유로 창을 없앴다. `window.agentParty` 는 **document 당 하나**라서 React 서브트리
> 하나에만 가짜를 씌울 방법이 없다 — 그래서 격리의 단위를 **창에서 문서(iframe)로** 옮겼다.
> 얻는 것은 그대로다. preload 가 사라졌으므로 가짜는 이제 `ipcRenderer` 를 안 쓰고,
> 데모의 링크·타이틀바 버튼은 **에러가 아니라 아무 일도 안 하는 것**으로 처리한다.
>
> 창을 없애면서 **새로 생긴** 격리 문제가 하나 있다: iframe 은 메인 창과 **origin 을
> 공유**하므로 localStorage 도 공유한다. 무대의 `App` 이 사이드바 폭·패널 상태·테마를
> 사용자 것 위에 덮어쓸 수 있다. 그래서 무대 문서는 번들이 로드되기 **전에** 인라인
> 스크립트로 자기만의 인메모리 localStorage 를 깔고 시작한다.

**`App` 은 자기가 가짜를 보고 있다는 것을 모른다.** 그래서 **운영 코드를 고치지 않는다.**

| 얻는 것 | 왜 |
|---|---|
| **저장소를 안 건드린다** | 메인 프로세스로 나가는 IPC 자체가 없다 |
| **운영 코드에 이음매를 안 낸다** | preload 경계는 **앱이 이미 매일 쓰는 경계**다. 새로 뚫는 구멍이 아니라 썩을 데가 없다 |
| **UI 가 바뀌면 따라온다** | 진짜 컴포넌트·진짜 테마 토큰 |
| **배포본에서 돈다** | `/api/qa/*` 와 달리 QA 플래그가 필요 없다 |
| **§2-1 의 점프가 공짜** | 가짜가 슬라이드 번호로 **절대 상태**를 돌려준다. `seed` 처럼 누적되지 않는다 |

**슬라이드 = 상태 스냅샷 하나.** 몇 번으로 뛰든 그 스냅샷을 그대로 물려주면 그 화면이 나온다.

#### ⚠️ 이 설계의 유일한 실제 비용

**`window.agentParty` 표면을 가짜로 다 채워야 한다.** 그 표면이 얼마나 넓은지가 곧 비용이다.
그리고 **표면이 나중에 바뀌면 가짜도 따라가야 한다.**

> 가짜를 **진짜와 같은 타입으로 묶어서**, 표면이 바뀌면 **컴파일이 깨지게** 한다.
> 조용히 낡는 경로를 만들지 않는다.

#### 검토했으나 택하지 않은 길

| | 왜 안 하나 |
|---|---|
| 워크벤치 컴포넌트에 props/가짜 상태 이음매를 낸다 | **운영 코드를 고쳐야** 하고, 그 이음매를 가이드만 쓰면 썩는다 |
| 가이드 전용 엔진·userData 를 따로 띄운다 | 프로세스가 하나 더 뜬다. 위 방식으로 같은 격리를 훨씬 싸게 얻는다 |
| 무대를 `WebContentsView` 로 창에 얹는다 | 픽셀 좌표로 창 위에 올리는 물건이라 **DOM 흐름을 안 탄다.** 리사이즈마다 위치를 메인에 보고해야 하고, 그러고도 창 안의 다른 것과 겹칠 수 없다 |
| 무대를 따로 그린다 (목업·스크린샷) | **낡는다.** §2 를 포기하는 것 |

### 2-2-4. 장면별 판정 (`scout`) — ⚠️ **이제 제약이 아니다**

> **아래 표는 QA 주입을 기준으로 잰 것이다.** §2-2-3 으로 방식이 바뀐 뒤에는
> **제약으로 읽지 마라.** 가짜 preload 는 **스냅샷을 우리가 직접 쓴다** — "빈 파티",
> "Token Usage 대시보드", "Gate 거절" 처럼 주입으로 못 만들던 상태도 그냥 쓰면 된다.
>
> 남는 것은 **"그 화면이 요구하는 데이터 모양을 채워야 한다"** 뿐이고, 표는 그 **모양을
> 찾는 단서**로만 쓴다(어느 이벤트·어느 필드가 그 화면을 만드는지).


| 장면 | 판정 | 단서 |
|---|---|---|
| 멤버 여럿 + 상태가 다른 사이드바 | **됨** | `status:approval` 만으로는 안 되고 approval_request 가 필요. working/idle 은 OK |
| 멤버 → 멤버 메시지 | **됨** | `POST /api/party/messages` + mock (`qa/*` 아님) |
| Gate 심사·거절 | **부분** | `gate/open` 은 모달만. 거절 배지는 `emit type:gate` 로 될 것으로 **추정**(전용 테스트 없음). 실시간 리뷰는 실제 모델이 필요 |
| 권한 승인 카드 | **됨** | `interaction type:approval` / design-gallery |
| 서브에이전트 | **됨** | `subagents` + `open` |
| 사용량 / 토큰 | **부분** | `qa/usage` 는 타이틀바 한도 링만. **Token Usage 대시보드 fixture 없음** |
| 멤버 생성 · 설정 | **부분** | 설정은 `/api/navigation`. **멤버 생성 화면을 여는 QA 경로 없음** |
| 파티가 하나도 없는 빈 상태 | **안 됨** | `reset` 은 mock 멤버만 지우고 파티·main 은 남는다 |

**상태 재현**: `reset` → `seed` 로 mock 대화는 거의 재현된다. **통째 스냅샷 API 는 없다.**
`reset` 없이 `seed` 하면 **누적**된다 — §2-1 이 요구하는 "N번으로 점프하면 N번 상태" 를
지금 그대로는 만족하지 못한다.

**먼저 만들 것 (권장 순서)**: ① 무대 격리 → ② 절대 상태/장면 props → ③ Gate 거절 ·
멤버 생성 · 빈 파티 · Token Usage fixture

### 2-2-5. 구현 1차 결과 — **설계대로 된다** (`builder`, 2026-08-17)

**첫 관문(창별 preload) 통과.** Electron 은 `BrowserWindow` 마다 preload 를 따로 주고,
이 앱이 창을 여러 개 띄우면서 경로를 하나만 쓰고 있었을 뿐 막는 제약은 없었다.

| | |
|---|---|
| 가이드 preload | `src/preload/guidePreload.ts` → `dist/preload/guidePreload.js` |
| **`window.agentParty` 표면** | **108개** (invoke ~90 + 구독 18). 크지만 기계적 |
| 낡음 방지 | 가짜를 `const api: AgentPartyApi` 로 **진짜와 같은 타입에 묶었다** — 표면이 늘면 **컴파일이 깨진다** |
| 파티 변경 호출 | IPC 로 나가지 않고 **거절 메시지를 돌려준다** |

**격리를 세 겹으로 걸었다.**
- `WindowRegistry` 에 **넣지 않는다** — `GET /api/windows` 에 안 나오고 `party:update` 방송도 안 간다
- `partition: "guide"` (메모리 세션) — localStorage·테마 분리
- 가이드가 포커스일 때 메뉴의 "새 파티" 등이 **본 창으로 떨어지지 않게** 막았다

### 2-3. 이동과 목차

- **목차는 장면(챕터) 단위** — 슬라이드가 동작 단위라 20개 장면이 슬라이드 80개가 될 수 있다.
  목차를 슬라이드로 펴면 잘게 쪼개져 오히려 길어 보인다
- **진행바는 슬라이드 단위** — 어디쯤인지는 정확히 보인다
- 좌우로 넘긴다. 스텝 단위 되감기 가능
- **이어보기는 두지 않는다** — 다시 열면 처음부터

✅ **구현됨** (`builder`, 2차) — 좌우·`Home`/`End`·HTTP 점프, 진행바(슬라이드 단위),
목차(장면 단위), 랜딩의 「가이드 보기」, 마지막 「작업공간으로」.
현재 **30장 / 장면 6개**. 검증: `scripts/verify-guide-stage.mjs` 통과
(점프 · 범위 밖 500 · 카나리아 파티 미변경) + `scripts/qa-guide-slides.mjs`

**슬라이드 내용의 규칙** (2026-08-18, 사용자 지시로 재기획):

- 한 장 = **사용자 동작 하나의 결과**. "여기를 누르세요" 로 끝내지 않고, 누른 뒤의 화면을 보여준다
- **시계열 하나의 세션** — `todo-api` 폴더에서 로그인 API 에 5회 실패 제한을 넣는 일감 하나로
  전부 이어진다. 멤버끼리 대화·멤버 생성처럼 원인이 중요한 화면은 **그걸 시킨 사용자 발화가
  같은 화면에** 남는다
- **모달·메뉴는 진짜 컴포넌트를 연다** — `GuideSnapshot.steps` 가 무대 안에서 실제로 클릭한다

  셀렉터가 사라지면 조용히 넘어가지 않고 무대 위에 빨간 실패 배너가 뜬다
- **Token Usage · 세션 기록 화면은 다루지 않는다** (사용자 지시, 2026-08-18)

### 2-4. 성격

- **여정형**이다 — 기능 카탈로그가 아니라 첫 사용자의 성공 경로
- 다만 **목차는 명확히 보여준다** — 길다고 느끼지 않게
- 슬라이드 안에서 **사용자가 실제 앱을 조작하게 하지 않는다.** 마지막에 **작업공간으로 가는

- 대상은 **AgentParty 사용법만**이다. "AI 코딩 에이전트란 무엇인가" 는 다루지 않는다

### 3-0-1. 남았던 다섯 — 전부 해소 (`builder`)

| | 결과 |
|---|---|

*"설명하지 마라"* 라고 써 둬서 모델이 거절했다(**검증 문장 설계 실수**, 이후
*"물으면 그대로 답하라"* 로 고쳤으나 **재호출하지 않았다**).
읽기 자체는 `Read` 호출과 고유 문장 인용으로 증명됐으므로 **결론은 바뀌지 않는다.**

> **캡처를 눈으로 보는 것과 DOM 을 재는 것은 다르다.** 빈 랜딩은 실재하지 않는 결함이었고,
> 캡처만 믿었으면 없는 버그를 고치느라 시간을 썼을 것이다.

### 3-1. 두 개는 별개다

| | 누가 | 언제 |
|---|---|---|
| **슬라이드 채팅** | 처음 온 사용자 | 프레젠테이션 보다가 "여기서 이렇게 하면 어떻게 돼?" |
| **챗봇** | 쓰던 사용자 | 웹사이트 챗봇처럼, 궁금할 때 |

프레젠테이션 중에는 **아래에 "질문하기" 플로팅 버튼**이 있고, 누르면 커진다.
평소엔 슬라이드를 가리지 않는다.

### 3-2. AI에게 현재 위치를 알려준다

**상시 컨텍스트에 넣지 않는다.** 사용자가 채팅을 열지 않으면 대화 자체가 없으므로,
**사용자가 보낸 프롬프트에 "지금 무엇을 보고 있다" 를 붙여서** 넘긴다.

> 이게 없으면 슬라이드를 넘긴 뒤 *"여기서 이렇게 하면?"* 이 무엇을 가리키는지 AI가 모른다.

### 3-3. 챗봇은 프레젠테이션을 열 수 있다

*"그건 이 부분에 있어요"* 하고 **그 슬라이드부터 프레젠테이션을 띄운다.**

- 대화를 섞는 게 아니라 **화면만 여는 것**이라 "완전 별개" 는 깨지지 않는다
- 그리고 이게 **"이미지와 함께 대답한다"의 실질**이다 — 말로 설명하는 대신 움직이는 걸
  보여준다. 정지 이미지를 md에 따로 붙일 필요가 없어진다

**어떻게 여는가** (설계: `main`): AI 가 창을 직접 조작하지 않는다.
답변 안에 **마커**를 넣고, 가이드 창이 그걸 해석해 버튼으로 렌더한다.

```
… 그건 멤버끼리 메시지를 주고받는 부분입니다. [[slide:7]]
```

| 왜 이렇게 | |
|---|---|
| **AI 에게 조작 권한을 안 준다** | 텍스트만 뱉는다. §6-2 의 "파티 도구 없음"과 같은 원칙 |
| **없는 슬라이드를 가리키면 드러난다** | 범위 밖 번호는 **버튼을 만들지 않고 그 사실을 표시**한다. 조용히 무시하지 않는다 |
| **누르기 전엔 안 움직인다** | 읽는 중에 화면이 튀지 않는다 |

⚠️ 슬라이드 번호는 **내용이 확정된 뒤**라야 안정된다(§10). 그전까지 마커는
**기능만 배선**해 두고 실제 번호는 넣지 않는다.

### 3-4. 보존

| | 남나 |
|---|---|
| 챗봇 | **남는다** (앱을 껐다 켜도) |
| 슬라이드 채팅 | 안 남아도 된다 |

**"새로 시작하기" 버튼**과 **컨텍스트 사용량 표시**를 둔다.
컨텍스트가 차면 **각 하네스의 기본 압축 방식**을 그대로 쓴다 — CLI 래퍼를 그대로 가므로
따로 만들지 않는다.

## 4. 지식 원본

챗봇과 슬라이드 채팅이 답할 때 **매번 코드를 파지 않는다.** 정리된 md 정본을 읽는다.

- **index 를 포함한** md 묶음. 시스템 프롬프트에는 **필수 내용 + md 위치**만 넣고, 나머지는
  AI가 필요할 때 읽는다
- **관리는 사용자가 직접 한다**

### ⚠️ 이 지식은 선택이 아니다 — 코드로 확인됨

`buildPartyPrimer()`(멤버에게 자동 주입되는 안내)에는 **파티 도구 16종·통신 프로토콜·
게이트·Discord 만 들어 있다.** **앱의 화면 지도도, 자동화 HTTP API 의 존재 자체도 없다.**
(`doctor` 조사, 2026-08-17)

> [F-09](F-09%20도움말.md) 가 *"멤버는 앱을 모른다 — 지금 물으면 지어낼 것이다"* 라고 쓴 것이
> **코드로 확인된 셈이다.** 이 md 묶음을 안 만들면 가이드 챗봇도 똑같이 지어낸다.

### ⚠️ md 를 요약해 프롬프트에 굳히지 않는다

시스템 프롬프트에는 **필수 내용 + md 위치**만 넣는다(위). 편의를 위해 **md 를 요약해서
프롬프트에 박아 넣고 싶어지는데, 그 순간 정본이 또 하나 늘어난다.**

> 문서를 고쳐도 **프롬프트는 안 따라간다.** 그리고 그 어긋남은 **아무 오류도 내지 않는다** —
> 챗봇이 옛날 사실을 자신 있게 말할 뿐이다. 이 저장소가 제일 싫어하는 실패 방식이다.

프롬프트는 **어디를 읽으라고만 말하고, 내용은 읽어서 답한다.**

### ⚠️ 알고 받아들인 리스크 — 정본이 둘이다

[F-09](F-09%20도움말.md)는 *"같은 사실을 두 곳에 적으면 반드시 어긋난다"* 를 이유로 원본을
하나로 두라고 했다. 이 기획은 **그 권고를 따르지 않는다** — md는 AI가 읽는 것이고 슬라이드는
사람이 보는 것이라 성격이 다르다는 사용자 판단이다.

> **어긋남이 실제로 문제가 되면 그때 손본다.** 몰라서 이렇게 된 것이 아니라는 기록.

## 5. 자산 위치

`docs/` 아래에 두지 **않는다.** `docs/` 는 사람이 쓰는 기획 문서이고, 가이드 자산은
**코딩 자산에 가깝다.**

| 무엇 | 어디 | 왜 |
|---|---|---|
| 슬라이드 정의 · 무대 | `src/renderer/guide/` | 번들되는 **코드**다 |
| 지식 정본 md + index | 저장소 루트 `guide/knowledge/` | 런타임에 **파일로 읽히는 데이터**다 |

### ⚠️ 이 분리는 기술적으로 강제된다

**하네스는 별도 프로세스다.** 설치본에서 md가 `app.asar` 안에 있으면 **CLI가 그 경로를 못
읽는다.** 따라서 지식 정본은 **asar 밖**으로 나가야 한다 — electron-builder `extraResources`.

그리고 **가이드 세션의 작업 디렉토리를 그 폴더로 고정**한다. 그러면
- 사용자 프로젝트 코드에 **손이 닿지 않고**
- md 를 **경로로 그냥 읽을 수 있다**

개발 중 경로와 설치본 경로가 다르므로 **해석은 한 곳에서** 한다(`src/main/` 아래 모듈 하나).

### 6-2-1. 앱 도우미로의 인계

| | |
|---|---|
| 이름 | **`문제 해결`** (확정) |
| 사는 곳 | **왼쪽 nav-rail 의 항목 하나.** 누르면 화면 전환이 아니라 **워크벤치에 탭을 열고 포커스**한다 (여러 번 눌러도 하나만 유지) |
| 가이드 프롬프트에 들어갈 문장 | *"앱의 살아 있는 상태에 대한 질문(멤버가 왜 멈췄나, 로그인이 왜 안 되나)은 왼쪽 메뉴의 `문제 해결` 을 열어 물어보라고 안내한다."* |

**언제 넘길지는 이름 자체가 알려준다.**

> **가이드 = 배우는 곳** · **문제 해결 = 막혔을 때 가는 곳**

이 대비가 인계 판단의 기준이다. *"이거 어떻게 쓰나요"* 는 가이드가 답하고,
*"제 건 왜 안 되나요"* 는 넘긴다.

(`도우미` 는 가이드도 도와주는 것이라 어느 쪽을 열지 헷갈리고, `진단` 은 설정 → 런타임에
이미 같은 이름의 탭이 있어서 탈락했다. `문제 해결` 은 전문용어가 0 이라
[D-02](D-02%20내부%20용어%20노출.md) 에도 안 걸린다.)

### 6-3. 답할 수 없을 때

- **정본에 없으면 지어내지 않는다.** 모른다고 말하고 어디를 보라고 알려준다
- **범위 밖 요청**(*"내 코드 고쳐줘"*)은 거절하고 일반 멤버 쪽으로 안내한다

## 7. 비용 — 오해를 만들지 않는다

**프레젠테이션은 AI를 쓰지 않는다.** 같은 내용을 매번 모델로 생성할 이유가 없다.
그래서 **토큰이 0이다.**

문제는 **그래서 사용자가 채팅도 공짜인 줄 안다는 것**이다.

> 표시는 **"쓴다 / 안 쓴다" 두 가지만.** 토큰 수나 금액은 보여주지 않는다.

- 프레젠테이션 영역: **AI를 쓰지 않는다**는 표시
- 채팅 입력 근처: **여기서부터는 선택한 모델의 비용이 발생한다**는 표시

## 8. 진입

- 워크벤치에 진입점을 두고, 누르면 **그 창이 가이드 화면으로 넘어간다**(§1)

  **자리 확정: 왼쪽 nav-rail.**
  [앱 도우미(`문제 해결`)](../기획%20노트%20—%20앱%20도우미(doctor).md) 가 같은 nav-rail 에 들어가므로,
  나란히 두면 **가이드 = 배우는 곳 / 문제 해결 = 막혔을 때** 대비가 화면에서도 보인다(§6-2-1).

  ✅ **구현됨** — nav-rail 「가이드」(BookOpen), Workbench 바로 다음.
  클릭 → `openGuide()` → IPC `guide:open` → `AppController.openGuideScreen()`
  (`POST /api/guide/open` 과 **같은 경로**) → 메인이 그 창에 `nav:set {view:"guide"}`.
  **nav-rail 이 스스로 화면을 바꾸지 않는다** — 계정 연결 게이트를 한 곳에서만 통과시키기
  위해서다. 가이드는 이제 `ViewId "guide"` 라서 다른 화면처럼 active 표시가 붙는다.
  실패는 `setPartyNotice` 로 드러난다. 메뉴 **View → 가이드(F1)** 도 그대로 있다.

  화면에서 사용자가 가이드를 떠나면 **화면이 메인에 그 사실을 알린다**(`guide:state`).
  그래서 `GET /api/guide` 가 `open: true` 로 낡아 있지 않고, 떠난 뒤의
  `POST /api/guide/slide` 는 **조용히 성공하지 않고 에러**가 된다.

  ⚠️ **두 워크트리가 같은 nav-rail 을 만진다** (`feat/guide` · `feat/doctor`).
  둘 다 구조는 안 바꾸고 `navItems` 배열에 항목 하나씩만 넣었으므로
  **병합 시 그 배열에서 작은 충돌 하나**가 난다. 그 이상은 아니다
- **최초 설치 때 한 번만** "가이드를 먼저 보시겠습니까?" 팝업

  ✅ **구현됨** (`builder`) — **최초 설치 판정은 `settings.json` 이 없는 것**으로 한다.
  있으면 업데이트로 보고 안 띄운다. 연결이 없으면 **인증이 먼저**다.
  **띄운 순간만** `guide-offer.json` 에 기록한다.
  e2e: 업그레이드=안 뜸 / 최초 설치=뜸.
- **완료 표시는 두지 않는다** — 끝까지 본 사용자를 따로 처리하지 않는다
  (그래서 기록도 "봤는지" 가 아니라 **"띄웠는지"** 하나뿐이다)

### ⚠️ 연결이 없으면 — 닭과 달걀

**어떤 계정도 연결돼 있지 않으면 가이드를 열지 않고 설정창으로 보낸다.**

✅ **구현됨** (`builder`) — 연결이 없으면 창을 열지 않고 본 창을 인증으로 보낸다.
`available` 로 판정하지 않는다.

⚠️ **다만 실제 앱에서 그 경로를 밟아보지는 못했다.** 이 호스트에는 이미 계정이 있고,
**하네스 CLI 의 로그인은 `userData` 밖**이라 격리 환경으로도 "연결 없음"을 만들 수 없었다.
게이트 로직은 `scripts/qa-guide-auth.mjs` 로 잠갔다.

> **이게 첫 사용자가 정확히 밟는 경로**이므로, 계정이 없는 환경이 생기면 **가장 먼저 확인할 것.**

⚠️ 판정을 **하네스의 `available` 로 하면 틀린다.** [B-03](B-03%20인증%20버그.md)에 기록된
대로 `available` 은 **로그인됐다는 뜻이 아니다.** 실제 인증 상태로 판정해야 한다.
그러지 않으면 연결 안 된 사용자를 가이드 안으로 들여보내고 **첫 질문에서야 실패**한다.

## 10-1. 디자인 — 정본과 그 이행

**정본**: `claude.ai/design` 프로젝트 **AgentParty Desktop** 의 `guide.html`
(+ `guide-handoff.md`). ⚠️ **정본과 이 문서가 어긋나면 정본이 이긴다.**

기획서가 처음부터 **UI 를 한 줄도 정하지 않았고**(§1~§9 는 전부 동작·구조),
그래서 1~3차 구현은 브라우저 기본 컨트롤 그대로였다. 이 절은 그 빈자리를 메운다.

### 지킨 규칙 (handoff §1)

| | |
|---|---|
| 새 색·글꼴·반경·그림자 **금지** | 값은 전부 `var(--*)`. `guide.css` 는 정본 블록을 **그대로** 옮긴 것 |
| DS 컴포넌트 **다시 그리지 않기** | 말풍선·컴포저·모달·pill·세그먼트는 기존 `wb-*` 를 그대로 씀 |
| `guide-*` 만 이 화면의 것 | 무대·캡션·진행바·목차·질문하기 시트 |
| 무대는 **실물** | 사본·이미지가 아니라 진짜 App 트리 (§2-2-3 과 같은 결론) |

### ⚠️ 이행 중 드러난 결함 — 앱에 **타이포 토큰이 없었다**

정본 CSS 를 그대로 옮겼는데 글자 크기가 전부 어긋났다. 원인은
**앱이 `--font-*` · `--weight-*` · `--motion-*` · `--bar-height` 를 정의한 적이 없다**는 것.
`themes.ts` 는 색과 반경만 내보내고 있었다.

> 그런데 디자인 프로젝트의 `foundations/tokens.css` 는 **"themes.ts 에서 생성됨"** 이라고
> 적힌 채 그 스케일을 갖고 있었다. **어긋난 쪽은 앱이었다.**
> `var(--font-ui)` 는 오류를 내지 않고 **조용히 무효**가 되므로 눈으로만 봐서는 못 찾는다.

→ `themes.ts` 가 그 스케일을 함께 내보내도록 고쳤다. 순수 추가라 기존 화면에 영향은 없다.

### 무대의 기하 — 눈대중 금지

무대는 워크벤치를 **1440 × 942 고정 크기로 렌더한 뒤 통째로 축소**한다. 스포트라이트가
**퍼센트 좌표**이기 때문에 이 크기가 달라지면 좌표가 전부 어긋난다.

**실측 확인**(`GET /api/guide/inspect`): 슬라이드 2 의 스포트라이트가
`3.3% / 31.7% / 17.2% / 21.9%` — 정본 `3.2% / 31.6% / 17.2% / 22%`. 캡션 여백 19px(정본 18px+테두리).
무대 비율 1191.97 × 779.75 = 1.528 (정본 1440/942 = 1.529).

⚠️ **워크벤치 레이아웃이 바뀌면 좌표를 다시 재야 한다.** 옮겨 찍지 말 것.

### 모델 설정 — 워크벤치 카탈로그 그대로

- **하네스 줄만 덜어냈다.** 목록·검색·성능/비용 미터·즐겨찾기·effort·Cancel/Apply 는 워크벤치와 동일
- 가이드용 간소화 버전을 **만들지 않았다** — 사용자가 두 곳에서 다른 물건을 배우게 된다
- **모델을 고르면 그 모델의 *집* 하네스가 연결된다** — 제공자 → 하네스(anthropic→Claude Code,
  openai→Codex, cursor→Cursor, xai→Grok Build). 고정 우선순위였다면 GPT 모델이
  Claude Code 에 붙었을 것이다. 집이 없는 모델(OpenRouter·DeepSeek)만 순서로 정한다
- 노출은 **가이드가 실제로 돌 수 있는 하네스**의 모델로 한정한다

### 눈으로 확인한 것

랜딩(챗봇) · 프레젠테이션 · 목차 · 질문하기 시트 · 모델 카탈로그.
⚠️ **캡처만 믿지 않았다** — 무대 기하·스크림·좌표는 DOM 실측으로 단언했다(§3-0-1 의 교훈).

**새 자동화**: `POST /api/guide/click` — 가이드 창의 UI 를 눌러볼 수 있다. 목차와 모델
카탈로그는 이게 없으면 사람 손으로만 확인된다. `apiSpec` 등록 완료.

| 모델 검증은 **최소 비용으로 하되, 한다** | 안 하면 "답한 적 없는 채팅"을 완성으로 착각한다. `AGENTS.md` 방침 | §3-0 |
| 디자인 정본은 `guide.html`, **어긋나면 정본이 이긴다** | 기획서가 UI 를 한 줄도 안 정해서 3차까지 브라우저 기본 컨트롤이었다 | §10-1 |
| 타이포 스케일을 **`themes.ts` 에 넣는다** (하드코딩 아님) | 정본 규칙이 "값은 전부 토큰". 그리고 `var(--font-*)` 는 없으면 **조용히 무효**가 되어 눈으로 못 찾는다 | §10-1 |
| 모델 → **집 하네스**(제공자 기준) | 고정 우선순위면 GPT 모델이 Claude Code 에 붙는다. 모델이 속한 곳에 붙어야 한다 | §10-1 |
| 가이드 창에도 **클릭 API** | 목차·모델 카탈로그가 사람 손으로만 확인되면 다음에 깨져도 아무도 모른다 | §10-1 |
| **별도 창 폐기 → 메인 창의 한 화면** | 가이드를 열면 **배우려던 앱 밖으로 튕겨 나갔다.** 관리할 창이 늘고 돌아오려면 창을 닫아야 했다 | §1 |
| 무대 격리 단위를 **창 → iframe** 으로 | `window.agentParty` 는 **document 당 하나**다. React 서브트리에만 가짜를 씌울 방법이 없다 | §2-2-3 |
| 무대에 **인메모리 localStorage** | iframe 은 origin 을 공유한다. 데모가 사용자의 사이드바 폭·패널 상태를 덮어쓰면 안 된다 | §2-2-3 |
| 화면이 메인에 **상태를 보고**한다 | 사용자가 nav-rail 로 그냥 떠날 수 있다. 안 그러면 `GET /api/guide` 가 낡은 `open: true` 로 남는다 | §8 |
| `guide.css` 의 모든 규칙을 **`.guide-window` 안으로** | 이제 앱 전체 번들에 실린다. 범위 밖 세 줄이 앱 전체의 줄바꿈을 바꾸고 있었다 | §10-1 |
| `POST /api/guide/open` 에 **창 지정** | 가이드가 창마다 열리게 됐다. "어느 창" 이 실제 질문이 됐고, 없는 id 는 포커스된 창으로 **넘어가지 않고 에러**여야 한다 | §8 |
| 채팅 갱신은 가이드를 띄운 **모든 창**에 | 마지막 창에만 보내면 다른 창의 대화가 **턴 중간에 얼어붙는다.** 가이드는 하나고 창이 여럿일 뿐이다 | §8 |
