# F-05. 스킬·커맨드 팔레트 — Claude/Codex 수준의 사용성

**판정: 차단** ⭐ **사용자가 "제일 크다"고 지목** · 갈래: *있는데 못 쓴다*

## 무엇을

스킬 팔레트와 커맨드 팔레트가 **너무 쓰기 불편하다.**
Claude·Codex 앱과 **거의 동일한 사용성**을 목표로 다시 만든다.

## 왜 제일 큰가

팔레트는 **하네스 기능 전체로 들어가는 입구**다. 여기가 불편하면 사용자는 하네스가 제공하는
것의 대부분에 도달하지 못한다.

> **기능이 없는 게 아니라 닿을 수 없는 상태**라서 손해가 크다.
> 만든 것을 못 쓰는 것이므로, 새로 만드는 어떤 기능보다 회수율이 높다.

그리고 이 앱은 CLI 를 감싼 물건이라, 입구가 불편하면 사용자가 곧바로
**"이 앱은 CLI 보다 불편하다"** 는 결론에 닿는다. 그건 제품의 존재 이유를 흔든다.

## 지금은

- 커맨드 팔레트는 있다 — `/` 로 열기 · 이름·설명 검색 · 범주 구분(Commands·Skills·Agents·
  MCP prompts·Plugins·AgentParty) · 속성 배지 (기능정의서 1-8).
- **스킬 자동완성은 미착수** — [P-11] OPEN. 스킬 카탈로그도 [P-10] OPEN.

### ❌ ~~Codex 명령이 9개로 박혀 있다~~ — **오탐이었다. 정정** (2026-08-08 실측)

이 문서는 [F-11](F-11%20Claude%20Codex%20격차.md) 조사를 받아 *"하드코딩 9개뿐, 실제 조회 안 함"*
이라고 적었다. **사실이 아니다.**

`codexAdapter.ts:858-866` 의 **`refreshInventory()` 가 `skills/list` 와 `plugin/installed` 를
동시에 조회해서 `CODEX_COMMANDS` 와 병합한다.** 하드코딩 9개는 **전부가 아니라 built-in 부분**이었다.

실앱 실측(실제 Codex 세션, JSON-RPC 원문 녹화 + 팔레트 DOM):
```
보낸 요청: skills/list {"cwds":[...]}  ·  plugin/installed {}
세션 집계: 58 commands { built-in:9, skill:41, plugin:8 }
팔레트 DOM: rowCount 60 — built-in 9 · skill 41 · plugin 8 · AgentParty 2 (출처 배지까지 렌더)
```

### 🔴 그런데 실측이 문제를 **없앤 게 아니라 바꿨다**

> **Codex 멤버 60개, Claude 멤버 86개가 한 목록에 쏟아진다.**
> **없어서 문제가 아니라 너무 많아서 문제다.**

이건 F-05 를 기각하지 않는다 — 오히려 **"많은 항목 중 고르기"를 한 컴포넌트로 묶는다**는
이 항목의 원래 결론([P-2]·[P-10]·[P-11]·[P-20])과 **정확히 맞는다.**

**⚠️ 근거를 바꿔 읽을 것**: ~~"Codex 는 9개뿐이라 기능에 도달 못 한다"~~ →
**"60~86개를 거를 수단이 없어 원하는 것에 도달 못 한다."**
같은 결론이지만 **설계가 달라진다** — 늘리는 일이 아니라 **거르는 일**이다.

## 결론 먼저 — 레퍼런스는 "60~86개"를 이렇게 푼다

**셋 다 다르게 푼다. 그리고 셋 다 우리보다 적게 보여준다.**

| 수단 | Codex | Claude CLI | Claude VSCode |

| ① 트리거를 쪼갠다 | **○** `/`=명령 · `@`=스킬·플러그인·파일 | ✗ | ✗ |
| ② 섹션으로 묶는다 | ✗ | ✗ | **○** 6섹션 |

> 확장은 아예 안 보여준다. **"Claude 처럼"에는 하나의 정답이 없다** — 우리가 골라야 한다.

## 매칭 규칙 — 표로

| 입력 | Codex `/` | Codex `@` | Claude CLI `/` | Claude VSCode `/` |
|---|---|---|---|---|
| 이름 부분일치 | ✗ (접두만) | ○ | **○** | **○** |
| 퍼지 부분수열 | ✗ | **○** | ✗ | ✗ |
| 설명까지 검색 | ✗ | — | ✗ | **○** |
| 결과 개수 상한 | 없음 | 없음 | 없음 | 없음 |

근거가 된 실측:

| 입력 | Claude VSCode 결과 |
|---|---|
| `/review` | `/review` → `/code-review` → `/ultrareview` → `/codex:review` → `/security-review` → `/codex:adversarial-review` → **`/simplify`** |
| `/set` | `/config` `/codex:setup` `/clear` `/effort` `/model` `/color` `/goal` `Hooks` `Permissions` `Effort(High)` |
| `/cdrv` | 0행 |

`/simplify` 는 이름에 `review` 가 없고 설명이 `Review the changed code…` 다 → **설명 검색 확인**.
`/set` 결과 대부분이 이름에 `set` 이 없고 설명이 `Set …` 이다 → 설명 매칭은 **부분 문자열**.
`/cdrv` 0행 → **퍼지 아님**.

**공통점 (4개 표면 전부)**: ↑↓ 이동 · Enter 선택 · Esc 닫기 · 결과 개수 상한 없음 ·
퍼지 매칭은 Codex `@` 하나뿐.

## 실측 vs 선행 조사 — 뒤집힌 것 → [06-선행 조사 대조](F-05%20자료/06-선행%20조사%20대조.md)

[02-command-skill-palette.md](../claude-code-ux-research/02-command-skill-palette.md) 는 웹 문서와
`--help` 로 쓴 것이라 **실제 UI 와 어긋난 곳이 있다.** 요약:

- 제안했던 **미리보기 창(preview pane)** — 네 표면 어디에도 **없다**
- 제안했던 **배지 8종 · 아이콘 · 인자 시그니처 열** — 이만큼 넣는 레퍼런스가 **하나도 없다**
- 제안했던 **카테고리 탭** — Codex `@` 의 범위 탭이 유일. Claude 는 섹션 헤더만 쓰고,
  섹션 이름도 기능 분류가 아니라 **하려는 일** 기준이다(Context·Model·Customize·…)
- `disabled` 표현 — 실측 범위에서 **관측 못 함**

→ **선행 조사의 UI 설계 부분은 근거가 약하다. 실측을 정본으로 쓴다.**
분류 체계와 명령별 요구는 여전히 쓸모 있다.

> **교훈**: "어떤 정보를 담아야 하는가"를 문서에서 추론하면 **실제보다 훨씬 무거운 UI** 가 나온다.
> 레퍼런스의 실제 선택은 일관되게 **"덜 넣는 쪽"**이었다.

# 2단계 — 정해야 할 것 (사용자 결정 대기)

실측이 끝났으니 **"거의 동일한 사용성"을 동작으로 못 박는다.** 아래는 레퍼런스가 서로
달라서 **우리가 골라야만 하는** 지점이다. 각각 대가를 함께 적었다.

### 결정 1. 설명을 행에 그리나

- **ⓐ 안 그린다** (VSCode 확장 방식) — 행 27px, 한 번에 11행. 밀도 최고.
  대가: **처음 보는 스킬이 뭔지 알 수 없다.** 우리 사용자는 스킬 41개를 직접 만든 사람이 아니다
- **ⓑ 그린다** (CLI 방식) — 이름 + 설명 한 줄. 대가: 행이 2배, 한 번에 5~6행
- **ⓒ 선택 행만 그린다** — 목록은 이름만, 선택된 행 아래에만 설명. 대가: 레퍼런스에 선례 없음

### 결정 2. 스킬을 `/` 에 두나 `@` 로 빼나

- **ⓐ 한 목록 + 섹션** (Claude 방식) — 구현 단순. 대가: 여전히 86행
- **ⓑ 트리거 분리** (Codex 방식) — `/`=명령, `@`=스킬. 각 목록이 짧아진다.
  대가: **하네스마다 `@` 의 뜻이 다르다**(Claude 는 파일 멘션). 사용자가 두 개를 외워야 한다

### 결정 3. 설명까지 검색하나

- **ⓐ 이름만** (CLI 둘 다) — 예측 가능. 대가: 이름을 모르면 못 찾는다
- **ⓑ 이름 + 설명** (VSCode 확장) — 발견성 높음. 대가: 결과가 늘어난다(`/c` → 126행)

### 결정 4. 퍼지 매칭을 넣나

- **ⓐ 부분 문자열만** — 레퍼런스 4개 중 3개. 예측 가능
- **ⓑ 퍼지 부분수열** — Codex `@` 만. 대가: `xlsx` 가 `CodexPermissionControl.tsx` 를 부른다

### 결정 5. 모델·설정까지 이 팔레트에 넣나 ([P-2]·[P-20] 통합 여부)

- **ⓐ 넣는다** (VSCode 확장 방식) — F-05 의 원래 목표. `Model` 섹션에 하네스·모델·effort
- **ⓑ 명령만** — 팔레트는 명령 전용, 모델은 RuntimeModal 유지. 대가: **네 번 만들게 된다**

### 결정 6. 하네스 차이를 어떻게 드러내나

Codex 멤버엔 `/compact` 가 없고 Cursor 는 `/compress` 다. 미확정.
- ⓐ 없는 건 안 보여준다 · ⓑ 보여주되 비활성 + 사유 · ⓒ 하네스 배지로 구분

**⚠️ 미확정 (실측 못 함)**: 인자를 받는 명령을 어떻게 채우는가.
네 표면 모두에서 인자 입력 UI 를 관측하지 못했다. 2단계 설계 전에 추가 실측이 필요하다.

## 정해야 할 것 — "거의 동일한 사용성"을 동작으로 못 박기

**느낌으로 두면 끝이 없다.** 따라 할 동작을 구체적으로 적는다:

- 여는 키와 여는 위치
- 검색 방식 (접두 일치? 부분 일치? 설명까지 훑는가? 정렬 기준은?)
- **인자 입력** — 인자를 받는 명령을 어떻게 채우는가
- 미리보기 — 고르기 전에 무엇을 보여주는가
- 실행 직후 표시 — 무엇이 일어났는지 어떻게 아는가
- **하네스별 차이를 어떻게 드러내는가** (Cursor 압축은 `/compress` 등)
