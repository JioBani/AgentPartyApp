# B-23. 앱을 열면 멤버들이 일제히 턴을 시작하고, 멤버를 열면 그 자리에서 턴이 시작된다

**판정: 차단 — 최우선** · 갈래: *사용자가 시키지 않은 일을 한다* · 출처: 사용자 직접 보고 (2026-08-12)

---

## 증상 (사용자 보고 · 아직 재현 미실시)

두 가지가 보고됐다. 같은 원인인지 별개인지 **모른다.**

| # | 동작 | 일어나는 일 |
|---|---|---|
| ① | 앱을 연다 | **열려 있던 파티 멤버들이 일제히 턴을 시작한다** |
| ② | 멤버를 연다 | **여는 즉시 턴이 시작된다** |

사용자는 어느 쪽도 지시하지 않았다.

## 왜 최우선인가

**사용자가 시키지 않았는데 모델이 돈다.** 결과가 세 겹이다.

1. **비용** — 앱을 켤 때마다 멤버 수만큼 턴이 과금된다. 사용자가 통제할 수 없는 지출이다.
2. **속도 제한** — 5시간/주간 한도([usage-limit](../../src/main/usageLimits.ts) 계열)를 사용자가 아무 일도 안 하고 소모한다.
3. **부작용** — 턴이 돌면 파일을 고치고 명령을 실행한다. 앱을 켠 것 뿐인데 작업 트리가 바뀔 수 있다.

앱을 여는 것은 **사용자가 가장 먼저, 가장 자주 하는 동작**이다. 여기서 통제를 잃으면
베타 사용자는 앱을 신뢰할 근거가 없다.

## 조사 실마리 — ⚠️ 전부 미검증 가설이다

**아무것도 확인하지 않았다.** 아래는 담당자가 먼저 배제할 후보이지 원인이 아니다.

- **세션 복구 경로.** 재시작 시 세션을 복원하는 동작이 `master` 에 있다
  (`fix/session-lifecycle` 병합, `6d67a53`). 복원이 "이어서 돌린다"까지 하는지 확인할 것.
  → 이 증상이 그 병합 **이전에도 있었는지**를 먼저 가르면 후보가 절반으로 준다.
- **큐된 메시지 재전송.** 종료 시점에 큐에 남아 있던 메시지가 시작할 때 흘러나가는가.
  [B-01](B-01%20메시지%20큐%20버그.md) 과 같은 갈래일 수 있다.
- **프라이머·시스템 프롬프트 주입.** 파티 프라이머 설치가 턴 시작으로 오인되는가.
  Codex 는 `thread/start.developerInstructions` 로 한 번만 심는다(`docs/CODEMAP.md`).
  **화면에만 "도는 것처럼" 보이는 것**과 **실제로 과금되는 턴**은 다른 결함이다 —
  둘 중 어느 쪽인지부터 가를 것.
- ② 가 ① 의 특수 사례일 수 있다(앱 열기 = 멤버 여러 개를 여는 것).

## 조사 1차 (2026-08-12, beta-impl) — 재현 실패 · 후보 2개 배제

### ⚠️ 세션 복구 병합(`6d67a53`)은 원인이 될 수 없다

```
설치본 app.asar     2026-08-07 22:46
6d67a53 병합         2026-08-07 23:02   ← 16분 뒤
```

**사용자가 쓰는 앱에 그 코드가 없다.** 이 실마리는 닫는다. 반대로 이 말은, 원인이
**Aug 7 빌드 안에 있다**는 뜻이고 **재현도 설치본으로 해야 한다**는 뜻이다(master 로 재현하면
다른 코드를 재현하게 된다).

### 재현 시도 6건 — 전부 0건

전부 실제 앱을 띄우고, 격리 워크스페이스에서, 재시작 후 **아무 것도 하지 않고** 2분간
원장(`turns.jsonl`)을 감시했다.

| # | 조건 | 결과 |
|---|---|---|
| 1 | master 빌드, 평범한 재시작 | 0건 |
| 2 | **설치본**, 평범한 재시작 | 0건 |
| 3 | 설치본, 멤버가 턴 도는 중 + 큐 1건 확인 후 강제 종료 | 0건 |
| 4 | 설치본, **Codex** 멤버(gpt-5.4-mini) | 0건 |
| 5 | 설치본, 창을 정상적으로 닫고 재시작 | 0건 |
| 6 | 설치본, 앱은 켠 채 **멤버를 하나씩 열기**(증상 ②) | 0건 |

재시작 후 세션은 전부 `initialized` / `turnCount: 0` 이었다 — **사전 기동(1-5-1)은
설계대로 동작하고, 그 자체는 턴을 만들지 않는다.**

⚠️ 3번은 처음에 **전제가 성립하지 않은 채 통과**했다(큐가 비어 있었다). 큐에 실제로 1건이
들어간 것을 API 로 확인한 뒤에야 유효한 시험이 됐다. 이 항목을 이어받는 사람은
**"큐를 남겼다"를 관측으로 확인**하고 재실행할 것.

### 원장에서 하나 걸린다

사용자 워크스페이스 원장에서 **353분(약 6시간) 침묵 뒤 혼자 시작된 턴**이 하나 있다.

```
2026-08-10T00:47:57  main  trigger=unknown  output=1675 tokens
```

그 시각 부근에 **앱 시작 기록이 없다** — 이미 떠 있던 앱에서 저절로 돈 것이다. 보고된
증상(앱을 열 때)과는 다른 상황이지만, *사용자가 시키지 않은 턴* 이라는 점은 같다.

`trigger=unknown` 은 25건 있는데 나머지 24건은 전부 Codex 멤버가 대화 중일 때라
**귀속 누락**으로 보인다(별개 문제). 위 1건만 긴 공백 뒤에 있다.

### 사용자 관측 (2026-08-12)

| 질문 | 답 |
|---|---|
| 실제로 답변이 나왔나 | **나왔다** → 표시 문제가 아니라 **진짜 과금된 턴** |
| 직전에 앱을 어떻게 끝냈나 | **"정지"** (⚠️ 턴 정지인지 앱 정지인지 미확정) |
| 종료 시 멤버 상태 | 기억나지 않음 |
| 어느 멤버가 돌았나 | **열려 있던 멤버 전부** |

"정지" 를 **턴 정지**로 읽고 시험한 것이 위 표의 7번이다 — 재현되지 않았다.

| 7 | 설치본, 멤버 3개를 턴 도중 **정지**시키고(정지 완료 확인) 종료 후 재시작 | 0건 |

⚠️ 7번도 첫 실행은 무효였다. 정지를 누르고 4초 뒤 셋 다 여전히 `responding` 이었는데
그대로 종료해 버렸다. **정지가 실제로 걸린 것을 확인한 뒤** 다시 돌려야 유효하다.
(정지가 4초 안에 안 걸리는 것 자체는 `[#23]` 계열의 별개 관측이다.)

### ⚠️ 로그로 원인을 가를 때의 함정 두 개

이 항목을 이어받는 사람이 반드시 알아야 한다. 둘 다 **없는 것을 증거로 착각하게 만든다.**

1. **에이전트끼리 보낸 메시지는 IPC 로그에 안 남는다.** `party:message`·`user turn sent`
   는 렌더러 IPC 로그라 사용자가 입력한 것만 찍힌다. 멤버가 도구로 보낸 메시지는 인프로세스
   bridge 로 가서 로그가 없다. 그래서 `trigger=party-message` 턴은 **원래** 앞선 로그
   이벤트가 없다 — 이걸 "저절로 시작됐다"로 읽으면 오진이다.
2. **로그 파일은 앱 세션마다 새로 생기고 파일명은 UTC 다.** 파일 mtime(로컬)과 마지막
   레코드 시각(UTC, +9h 차)이 어긋나 보여서 "로그가 죽었다"고 오해하기 쉽다.

이 두 함정을 걷어내고 사용자 워크스페이스의 최근 두 앱 세션을 훑은 결과,
**저절로 시작된 턴은 발견되지 않았다.** 남은 단서는 여전히 위의 2026-08-10T00:47 한 건뿐이다.

### 다음 사람에게

재현 조건이 아직 없다. **추측으로 코드를 고치지 말 것** — 사전 기동은 설계된 동작이라
잘못 끄면 기능이 죽는다.

다음에 증상이 나면 **원장이 스스로 범인을 지목하도록** 만드는 것이 지금 가장 값싼 길이다.
현재 `trigger` 값은 `user` / `party-message` / `gate-review` / `unknown` 뿐이라
**사전 기동·세션 복구가 시작한 턴을 가리키는 값이 없다.** 그 값을 추가하면 다음 발생이
곧바로 증거가 된다.
