## 🔴 본론 — 상한의 단위가 틀렸다

`TRANSCRIPT_CAP = 800` (`src/main/partyRepository.ts:366`) 은 **블록 개수** 상한인데,
비용은 **바이트**에 있다. 두 축이 어긋나서 상한이 엉뚱한 것을 지운다.

`status` 블록은 **바이트로 5.5%, 개수로 48.7%** (3,339 / 6,854, Tatica 표본).
즉 status 가 블록 예산의 절반을 먹고 **대화를 밀어낸다.**

**800 상한에 도달한 파일 8개에 실제로 남아 있는 것** [확인, 실측 2026-08-08]

| 워크스페이스 | 멤버 | blocks | user | channel | assistant | tool | **status** | 파일 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| Tatica | qa | 800 | **0** | 58 | 130 | 144 | **410** | 2.08 MB |
| Tatica | impl | 800 | **0** | 67 | 143 | 151 | **349** | 0.56 MB |
| AgentParty | beta-impl | 800 | **0** | 11 | 102 | 206 | **374** | 0.55 MB |
| Tatica | main | 800 | 12 | 73 | 126 | 154 | **398** | 0.35 MB |
| AgentParty | planning | 800 | 25 | 38 | 101 | 119 | **439** | 0.83 MB |
| Tatica | codemap | 790 | 1 | 45 | 110 | 173 | **406** | 0.70 MB |
| Tatica | skill-keeper | 800 | 19 | 0 | 101 | 166 | **437** | 0.67 MB |
| (QA 임시 ws) | main | 795 | 4 | 1 | 4 | 0 | **761** | 0.39 MB |

- **세 파일에서 `user` 턴이 0개다.** 사용자가 무엇을 시켰는지가 통째로 사라졌다.
- 마지막 줄은 795 중 **761(96%)이 status** 다. 디스크는 0.39 MB 밖에 안 먹으면서 상한만 태운다.

> **용량을 줄이려고 둔 상한이, 정작 사용자가 보고 싶은 대화를 먼저 지운다.**

`src/renderer/App.tsx:395` 주석이 이미 같은 문제를 적어 뒀다 —
*"A transcript is capped at 800 blocks but a block can be a whole tool output, so one member's
file reaches ~15MB on disk and several times that once parsed."*
**블록 하나의 크기가 무제한이라 개수 상한이 용량을 못 잡는다**는 것을 코드가 인정하고 있다.

### 40 KB 초과 블록 (n=8) [확인]

```
564 KB  mcp__UnityMCP__manage_camera   이미지   ← 최대 유형
553 KB  mcp__UnityMCP__manage_camera   이미지
152 KB  Read                            이미지
147 KB  Read                            이미지
123 KB  Read                            이미지
 46 KB  Read                            텍스트
 40 KB  Read                            텍스트
 40 KB  Read                            텍스트
```

### 🔴 앞선 문서의 주장 두 개를 정정한다

**정정 ①: "40 KB 초과 블록은 전부 이미지" → 틀렸다.**
`AgentPartyApp` 표본에서만 성립했다(3개 전부 이미지). Tatica 에서는 8개 중 5개만 이미지다.
**유지되는 부분**: 상위 5개는 여전히 전부 이미지고, 텍스트는 40~46 KB 에서 멈춘다.

**정정 ②: "이미지가 바이트의 대부분" → 틀렸다.**
Tatica 는 tool.result 텍스트 2.55 MB > 이미지 1.57 MB 로 반대다.
**이미지는 가장 큰 개별 조각이지, 바이트 과반이 아니다.**
따라서 "압축·truncation 을 안 한다"의 근거를 **"이미지가 대부분이라서"에서 "총량이 하네스의
1/9~1/25 라서"로 바꾼다.** 후자는 표본과 무관하게 성립한다.

**새 사실**: 최대 유형은 `Read` 스크린샷이 아니라 **`mcp__UnityMCP__manage_camera` 564 KB** 다.
**MCP 도구의 이미지 반환 경로**가 가장 크다. Read 만 보면 놓친다.

## 레퍼런스는 이 문제를 어떻게 푸는가

### 모델에 넣을 때는 전부 자른다 [확인]

| 하네스 | 임계값 | 마커 |
|---|---|---|
| **Codex** | **정확히 10,000 토큰**(≈40 KB) | `Warning: truncated output (original token count: N)` + `…N tokens truncated…` (앞뒤 남기고 중간 삭제) |
| **Claude Code** Bash | 30,000자 (`BASH_MAX_OUTPUT_LENGTH`, 최대 150,000) | 중간 삭제 |
| **Claude Code** MCP | 25,000 토큰 (`MAX_MCP_OUTPUT_TOKENS`, 10,000 에서 경고) | — |
| **Claude Code** Read | 2000줄 / ~25,000 토큰 | `... [N lines truncated] ...` |
| **Zed** terminal | **16 KB** (`COMMAND_OUTPUT_LIMIT`) | `Command output too long. The first N bytes:` |
| **Zed** read_file | 16 KB 초과 → 본문 대신 **심볼 아웃라인**(`AUTO_OUTLINE_SIZE`) | — |

Codex 는 n=147 전건에서 `original − truncated = 10000` 이 정확히 일치했다.
Claude Code 텍스트 `tool_result` 실측 최대 **63,825 B**(298 MB / 17,658건 전수).

→ **우리 텍스트가 이미 이 대역 아래(최대 46 KB)라 저장용 텍스트 상한은 효과가 거의 없다.**

### 저장 시점 truncation 은 아무도 안 한다 [확인]
전부 **모델에 보낼 때 자른 그 값을 그대로 저장**한다. 저장 전용 상한은 어디에도 없다.
Codex 는 잘린 것이 롤아웃 파일에도 잘린 채 저장돼 **원본이 소실**된다.

### 압축은 Zed 하나만 한다 [확인]
`crates/agent/src/db.rs` — SQLite BLOB 에 **zstd level 3**(`COMPRESSION_LEVEL: i32 = 3`).
Claude Code 는 **append-only 라인 플러시(크래시 안전)** 때문에 평문 유지(압축 요청 이슈 #55934 미해결).
Codex·Cursor·Vibe Kanban 도 무압축.

**실측 gzip 비율**: 우리 transcript **28~36%** · Claude jsonl 39.6% · Codex 26.3% · Cursor 26.0%
⚠️ **이미지에는 안 듣는다** — base64 텍스트 **73%**, 디코딩된 PNG **94.4%**.

### 이미지 — 여기서 갈린다 [확인]
- **Vibe Kanban: 파일 참조.** (`20250818150000_refactor_images_to_junction_tables.sql`, 직접 확인)
  ```sql
  CREATE TABLE images (
      id BLOB PRIMARY KEY,
      file_path TEXT NOT NULL,      -- cache/images/ 상대 경로
      original_name TEXT NOT NULL,
      mime_type TEXT, size_bytes INTEGER,
      hash TEXT NOT NULL UNIQUE,    -- SHA256, 내용 주소 기반 dedup
      created_at TEXT, updated_at TEXT);
  ```
- **Zed: 인라인 base64.** `LanguageModelToolResultContent::Image(_)` 가 경로가 아니라 이미지
  객체를 들고 zstd blob 에 들어간다. → **압축을 쓰는 유일한 도구조차 이미지 문제는 못 푼다.**
- Claude Code: 인라인 base64(자기 jsonl 에 378~532 KB 그대로).

### 상한은 저장이 아니라 런타임 메모리에 [확인]
Vibe Kanban `msg_store.rs` `HISTORY_BYTES = 100 MB`, 초과 시 **메시지 통째로 축출**.
**개별 메시지는 절대 안 자른다.** 파일 저장소에는 상한·로테이션·압축·삭제가 전부 없다.

### 본문을 DB·단일 JSON 에 몰아넣지 않는다 [확인]
Vibe Kanban 이 **두 번 옮겨서** 얻은 결론:
① `execution_processes` 의 stdout/stderr 컬럼 → 제거 →
② `execution_process_logs(logs TEXT, byte_size)` 테이블 → 또 제거 →
③ 현재는 SQLite 밖 **평문 JSONL 파일**(`{root}/sessions/{prefix}/{session_id}/processes/{id}.jsonl`)

### 계층 보관 — 공통 패턴 [확인]
**본문은 파일, 요약은 DB.** Codex `state_5.sqlite` 는 `rollout_path` 포인터 + `rollout_summary` 만.
Zed 는 `threads` 테이블에 `summary` 컬럼 분리.
Conductor·Orca 는 아예 **전문 사본을 안 만든다** — 하네스 원본(`~/.claude/projects/*.jsonl`)을
읽고 자기 저장소에는 파생 요약만 둔다(Conductor `.conductor-snapshot.md` 는 10분 롤링 발췌,
`decisions.json` 은 최근 100건 상한 / Orca `orca-claude-usage.json` 은 토큰 집계만).

### 이중 저장 — 따라 하지 말 것 [확인]
Claude Code 는 도구 결과를 **두 번** 저장한다 — `message.content[].tool_result` 와 형제
`toolUseResult`. 12.46 MB 파일에서 3.11 + 3.11 MB. **우리는 이미 안 한다.**

### eviction — 문서와 다르다 [확인, 문서 반증]
Claude Code 문서상 `cleanupPeriodDays` 기본 30일인데, **미설정 상태에서 85일 전 파일이 그대로 있다**
(833개 601 MB 누적). Codex 도 2025-12-28 것이 잔존. → **실효 eviction 없음.**

| | 압축 | 저장시 truncation | 계층 | 이미지 | eviction |
|---|---|---|---|---|---|
| Claude Code | ✗ | ✗ (도구 경계에서 이미 잘림) | ✗ | 인라인 base64 | 문서만 있고 실효 없음 |

## 결론

1. **압축을 하지 않는다.** 레퍼런스 6개 중 압축은 Zed 하나뿐이고, 우리 총량은 하네스 원본의
   1/9~1/25 다. 이미지에는 어차피 무효(PNG 94.4%)다.
2. **텍스트 truncation 을 하지 않는다.** 우리 텍스트 최대가 46 KB 로 하네스 임계값
   (Codex 40 KB, Claude Bash 30 KB) 대역에 이미 들어와 있다. 줄일 여지가 거의 없다.
3. **상한의 단위를 고친다.** ← **이 이슈의 본론.** 개수 상한이 대화를 먼저 지우고 있다.
4. **이미지를 `transcript.json` 밖으로 뺀다.** 선례는 Vibe Kanban(경로 + SHA256 dedup).
   **대상에 MCP 이미지 반환을 포함**한다(최대 유형이 UnityMCP 564 KB).
   이득은 디스크보다 **렌더러 JSON 파싱·메모리** 쪽이다(`App.tsx:395` 가 지적한 그 비용).

### 구현 지점
`src/main/partyRepository.ts:198` — `next.slice(-TRANSCRIPT_CAP)` 단순 꼬리 자르기.
뒤에서부터 훑되 **`kind !== "status"` 인 블록만 세어** 800에서 끊는 방식으로 바꾼다.

### 🔴 이 결정이 여는 구멍 — 반드시 같이 막을 것
status 를 예산에서 빼면 **status 만 쌓는 멤버는 상한이 영영 안 걸린다.**
실제 사례가 이미 있다: QA 임시 워크스페이스의 `main` 은 795 블록 중 **status 761 · tool 0 · assistant 4** 다.

→ **절대 상한(전체 블록 수)을 함께 둔다.** 측정상 status:비-status ≈ 1:1 이므로
비-status 800 + 여유를 감안해 **전체 4,000 블록**을 천장으로 잡는다. 둘 중 먼저 걸리는 쪽이 적용된다.

### ✅ 완료: 이미지 분리

바이트를 `<workspace>/.agent_party_app/images/<sha256>.<ext>` 에 쓰고 블록에는 참조만 남긴다.
`Read` 와 MCP 반환(UnityMCP 등) **양쪽 모두** 대상이다 — 최대 유형이 MCP 쪽이라 Read 만 하면
효과가 절반 이하다. 파일명이 곧 내용 해시라 **같은 스크린샷을 다시 읽어도 파일은 하나**다.

```json
{ "type": "image",
  "source": { "type": "agentparty-file", "file": "3f9a….png", "media_type": "image/png", "bytes": 576936 } }
```

**부수 발견 — 렌더러는 이 이미지들을 애초에 표시한 적이 없다.** `formatResult` 는 `type:"text"`
블록만 뽑기 때문에 이미지뿐인 결과는 `JSON.stringify` 로 떨어져 **base64 수십만 자가 텍스트로**
쏟아지고 있었다. 즉 사용자는 이미지가 아니라 잘린 base64 를 보고 있었다. 이제 실제 이미지를
그린다 — 저장된 참조든, 첫 저장 전 메모리에 남은 인라인 바이트든(둘 다 처리하지 않으면
**진행 중인 턴의 스크린샷만 안 보이는** 불일치가 생긴다).

이미지 쓰기가 실패하면 **바이트를 인라인으로 그대로 두고 로그를 남긴다.** 용량을 아끼려고
스크린샷을 조용히 버리지 않는다.

**새 엔드포인트** `GET /api/party/transcript-image/:file` (apiSpec + `docs/API.md` 등록 완료).
엔진 인터페이스에 올려서 **원격 엔진도 자기 디스크의 이미지를 서빙**한다.
