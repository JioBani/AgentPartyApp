# D-04. 파티 우클릭 메뉴에 검은 선이 보인다

**판정: 첫인상** · 출처: 사용자

---

## ✅ 완료 (2026-08-08, `beta-impl`) — 재현 캡처 없이 CDP 실측으로 원인 특정

### 원인
파티 우클릭 메뉴를 실제로 열어 계산된 스타일을 쟀다. **라이트 테마에서:**

```
menuBackground : rgb(243,244,246)   ← 페이지 배경과 완전히 동일
pageBackground : rgb(243,244,246)
menuBorder     : rgb(226,229,234)   ← 거의 안 보이는 실선
menuBoxShadow  : rgba(0,0,0,0.32)   ← 32% 순수 검정 (하드코딩)
```

> **메뉴 배경이 페이지 배경과 같은 색**이라, 메뉴를 그리는 것이 사실상
> **하드코딩된 32% 순수 검정 그림자 하나뿐**이었다.
> 밝은 배경 위의 순수 검정 그림자는 깊이가 아니라 **더러운 테두리 = "검은 선"** 으로 읽힌다.

다크에서는 검정 그림자가 배경에 묻혀 증상이 안 났다 — 문서가 예상한
*"한쪽 테마에서만 어긋난다"* 그대로다.

### 계열 전수 조사 결과 — `.wb-ctx-menu` 만의 문제가 아니었다

**① 레이어 규칙 이탈 3건**
이 앱의 관례는 `--bg-2` = 떠 있는 표면. `wb-header-menu`·`wb-mention-pop`·`usage-pop`·`mcp-modal` 은
지키는데 **`wb-ctx-menu`·`wb-cmd-palette`·`wb-tool-modal` 만 `--bg-1`(페이지 색)** 을 썼다 → 통일.

**② 그림자에 토큰이 아예 없었음**
팝오버·모달 **14곳 전부** `rgba(0,0,0,...)` 하드코딩.
→ `themes.ts` 에 **`shadow`·`shadow-strong` 토큰 신설** 후 전부 교체.

**③ 이미 있는 토큰을 두고 하드코딩**
`.wb-tool-modal-backdrop` 이 `--scrim` 토큰이 있는데도 `rgba(0,0,0,0.5)` 를 씀.

### 🔴 ④ 존재하지 않는 토큰을 가리키던 `var()` 9개 — 가장 조용한 결함

`var(--warning, #d9a441)` 처럼 **정의된 적 없는 토큰 + 하드코딩 폴백**이었다.
→ **테마를 바꿔도 영원히 그 리터럴이다. "테마 되는 척"만 했다.**

- **`--warning`/`--warning-dim` (5곳)** → `warning` 토큰군 신설.
  ⚠️ **마크업은 이미 `is-warning` 과 `is-error` 를 구분하는데 색만 못 바꾸고 있었다** —
  즉 **경고와 오류가 화면에서 구분되지 않았다.** 사용자에게 보이는 결함이다.
- `--ok` → 기존 `success`, `--accent-contrast` → 기존 `accent-fg` (중복 토큰이었음)
- **폴백조차 없던 4개**(`--mono`·`--border-1`·`--border-2`·`--surface-2`)
  → 선언 자체가 무효라 **의도한 테두리·배경이 그냥 적용이 안 되고 있었다.**
- `--radius-chip` → `radius-badge`

> **이건 `silent-noop` 계열이다** — 코드는 있는데 아무 일도 안 하고, 아무도 실패를 모른다.
> CSS 에서는 `var()` 폴백이 이 실패를 **정상으로 위장**한다.

### 수정 후 실측

| | 라이트 그림자 | 라이트 표면 vs 페이지 | 다크 그림자 |
|---|---|---|---|
| 전 | `rgba(0,0,0,.32)` 순수검정 | `#f3f4f6` = 페이지 (대비 0) | `rgba(0,0,0,.32)` |
| 후 | `rgba(20,23,29,.13)` | **`#ffffff`** vs `#f3f4f6` ✅ | `rgba(0,0,0,.4)` (유지) |

**다크는 의도적으로 기존 룩 유지** — 어두운 배경 위 중성 검정 그림자는 맞는 값이다. 바뀐 건 라이트뿐.

### 바꾼 파일
- `src/renderer/theme/themes.ts` — `shadow`·`shadow-strong`·`warning` 군 토큰 추가(두 테마 모두).
  `Record<ThemeColorToken,string>` 이라 **타입체커가 테마 누락을 잡아준다.**
- `src/renderer/styles.css` — 하드코딩 색 **54곳 → 19곳**, **팝오버 계열은 0곳.**
  남은 19곳은 액센트 위 `#fff`(스위치 노브·배지 글자)와 브랜드 그라데이션으로,
  테마 무관하게 흰색이어야 하는 것들.

### 검증
CDP 로 실제 메뉴를 열어 라이트/다크 계산 스타일 실측 ✅ ·
신규 토큰 9종이 양 테마에서 전부 실제 값으로 resolve 되는지 실측 ✅ ·
캡처 `shots/d04-ctxmenu-light.png`·`d04-ctxmenu-dark.png` ✅ ·
`typecheck` 통과 ✅ · `test:ui` 회귀 없음(선재 실패 1건 그대로) ✅

### 남은 것 — 시안 나오면 한 곳만 고치면 된다
1. **라이트 그림자 세기(`.13`/`.2`)는 구현자가 정한 값.** 순수 검정을 걷어내는 것은 규칙 준수지만
   **정확한 농도는 취향**이다.
2. **`warning` 라이트 값(`#b07816`)** 도 기존 다크 리터럴을 라이트 대비에 맞춰 잡은 것.
3. **사용자 재현 캡처를 받으면 "검은 선"이 이 그림자가 맞는지 최종 확인 필요.**
   아니면 다른 위치일 수 있다.

→ **이제 셋 다 `themes.ts` 한 곳만 고치면 전부 따라온다.** 그게 이 작업의 진짜 성과다.

## 무엇을

파티를 오른쪽 클릭했을 때 나오는 메뉴에 **검은색 선**이 비친다. 고친다.

## 성격

눈에 보이는 **마감 결함**이다. 기능은 되지만 **덜 만든 것처럼 보이는** 종류라
첫인상에 직접 걸린다.

이 문서의 다른 항목들과 달리 **작고 명확하다.** 착수 비용이 낮으므로
**첫인상 개선 중 회수율이 높은 편**이다.

## 볼 것

### ① 테마 토큰을 안 쓰고 색이 하드코딩됐을 가능성
색의 단일 소스는 `src/renderer/theme/themes.ts` 다.
거기서 벗어난 값이 있으면 **한쪽 테마에서만 어긋난다.**
→ **다크·라이트 양쪽에서 확인할 것.**

### ② 같은 계열에 같은 결함이 더 있는지 함께 훑을 것
드롭다운·팝오버·컨텍스트 메뉴는 대개 같은 컴포넌트 관례를 공유한다.
**한 군데만 고치면 옆 메뉴에서 또 나온다.**

관련 컴포넌트: `src/renderer/workbench/Dropdown.tsx`, `workbenchPopups.ts`,
그 밖의 모달·팝오버.

⚠️ 이 계열은 이미 두 번 문제가 있었다:
- **[#11]** — 목록이 넘쳐도 스크롤되지 않음(세로 오버플로)
- **[#18]** — 드롭다운이 창 오른쪽 밖으로 나가 잘림(가로 오버플로)

**→ 세 번째다. 이번엔 계열 전체를 한 번 훑는 것이 맞다.**

### ③ 무엇이 "검은 선"인지 특정
후보: 경계선(border) 색 토큰 누락 · 그림자(shadow)가 선처럼 보임 ·
투명 배경 뒤가 비침 · 구분선(divider) 색.

→ **재현 캡처 한 장이면 특정된다.** 사용자에게 받는 것이 가장 빠르다.
