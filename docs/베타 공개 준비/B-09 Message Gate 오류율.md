# B-09. Message Gate 오류율이 높다

**판정: 원인 분리 완료 (2026-08-08)** · 갈래: *조용히 실패한다* · 출처: 사용자

---

## 🔴 먼저 — `turns.jsonl` 로는 오류율을 낼 수 없다. **실패가 기록되지 않는다.**

원장에 `gate-review` 턴 **241개, 전부 verdict 있음**(allow 192 / reject 49), **verdict 없는 행 0개**.
"오류율 0%"가 아니라 **실패가 원장에 안 들어간다.**

`partyApplicationService.ts:1796~1820` — fail-open `catch` 블록은 배지·로그·전달까지 하고
**`return` 한다.** `recordGateReview()` 는 **성공 경로에만** 있다.
그리고 `tokenUsage.ts:91` 의 스키마 자체가 `gate?: { verdict: "allow" | "reject" }` 뿐이라
**실패를 표현할 자리가 없다.**

> **원장의 241행은 전부 "성공한 심사"다. 오류율의 분모도 분자도 원장에 없다.**

**자기 오류율을 못 세는 상태** — 이 저장소가 경계하는 *"측정할 수 없으면 고칠 수 없다"* 자리다.

## 층 분리 — 실패는 앱 NDJSON 로그에 있었다

사용자 실제 앱 로그(89파일 26MB)에서 `"message gate review failed (fail-open)"` **15건** 발견.

| 층 | 건수 | 비중 |
|---|---|---|
| **파싱 실패** | **10** | **67%** |
| 타임아웃 | 5 | 33% |
| **모델·전송로 실패** | **0** | 0% |

**전송로는 멀쩡하다.** 호출은 나가고 응답도 온다.

## 🔴 파싱 실패 10건의 원인 — 어휘 불일치 (스키마 위반이 아니다)

실패 원문이 전부 같은 모양이다. **JSON 은 멀쩡하고 `verdict` 값만 다르다:**
```json
{"verdict": "COMPLIANT", "rules_checked": [...]}
{"verdict": "compliant", "violations": [], "reasoning": "..."}
{"verdict": "complies",  ...}
```

`normalizeVerdict()`(`messageGateReviewer.ts:283-300`)를 보면:
- **verdict 값**으로 받는 어휘: `allow/approve/approved/pass/ok/accept/허용/승인/통과` …
- `complies`·`compliant`·`allowed` 는 **불리언 "키"로만** 인식한다(`{"compliant": true}` 형태)

> **`compliant`/`complies` 는 키로는 알아듣는데 값으로는 못 알아듣는다.** 그런데 모델은 값으로 쓴다.

프롬프트가 `"allow"|"reject"` 만 쓰라고 못박아도(`:82`) 모델이 안 지킨다 —
문서가 경고한 *"말이 많고 스키마를 바꿔 말한다"* 가 **바로 이것**이다.
관대한 파서를 만들어 뒀는데 **관대함이 한 칸 모자라다.**

## 타임아웃 5건
전부 `"This operation was aborted"`. 기본 타임아웃은 **60초**로 이미 넉넉하다
(sonnet+adaptive thinking 실측 17.7초라 20초 → 60초로 늘린 이력).
**60초 초과는 진짜 행에 가깝다.** 별도 조사 필요.

## 리뷰어 모델 — 문서 의심과 달랐다
```
claude-sonnet-4-6  n=12  {parsing:7, timeout:5}
sonnet             n=3   {parsing:3}
```
**전부 sonnet 계열.** 문서가 의심한 *"구독 프록시 경유 Haiku"* 는 이 표본에 없다.
→ **전역 기본값이 Haiku 로 적혀 있어도 실제로 돈 건 sonnet.**
문서의 *"리뷰어 상속 확인 필요"* 지적이 유효했다.

## fail-open 이 사용자에게 보이는가 — 조건부
`emitGateBadge(sender, {gate:"failed", errcode:"reviewer_error"})` 로 배지를 쏘고,
**코드 주석이 스스로 한계를 적어 뒀다**:
> *"The badge alone is not enough — it needs a LIVE sender session, and the reviewer
> being unreachable is exactly the case where nothing else says so."*

그래서 반환값 `message`/`partyMessage.error` 에도 문구를 덧붙인다.
**조사에서 지적된 "비동기 경로 배지 유실" 은 코드가 이미 인지하고 이중화해 둔 상태.**
다만 **보낸 멤버 세션이 죽어 있으면 배지는 못 뜬다**(실측 미확인).

## ⏸ ②는 대기 — 심층 조사가 먼저 (2026-08-08 사용자 결정)

**결정하기 전에 조사가 필요하다.** 지금 논의는 *"파서를 얼마나 관대하게 만들까"* 에 머물러 있는데,
[README 전제](README.md)의 원칙(**독창성은 목표가 아니다**)을 적용하면 질문이 바뀐다.

### 조사할 것 — "저쪽은 어떻게 하나"

**핵심 질문**: LLM 이 스키마를 안 지키는 문제를, 레퍼런스는 **관대한 파싱으로 푸나 스키마 강제로 푸나.**

1. **스키마 강제 수단** — Claude API 의 tool use / structured output, OpenAI structured outputs.
   도구 호출로 받으면 **스키마 위반 자체가 발생하지 않는다.**
   → 우리 리뷰어(`messageGateReviewer.ts`)가 지금 **평문 프롬프트로 부르는지, 도구 정의를 주는지** 확인.
2. **구독 프록시 경유에서 도구 강제가 가능한가** — 이게 안 되면 ⓑ 자체가 성립하지 않는다.
   ⚠️ 이력: 이 프로젝트는 **prefill 을 시도했다가 역효과**를 봤고 관대한 파서로 갔다.
   **도구 강제를 시도했는지는 기록에 없다.**
3. **LLM 을 심사자로 쓰는 레퍼런스** — 다른 도구들이 "모델이 판정을 뱉게 하고 그걸 신뢰"하는 문제를
   어떻게 다루나. 비스키마 응답이 왔을 때의 정책(재시도 / 강제 / fail-open).
4. **재시도** — 지금은 파싱 실패 즉시 fail-open 이다. **한 번 다시 묻는 것**만으로 67% 가 줄 수 있다.
   레퍼런스가 재시도를 두는지.

### 조사 후에 판단할 것
- ⓐ 파서 어휘 확장 (싸지만 **다음 모델이 새 단어를 만들면 반복**)
- ⓑ 도구 호출로 스키마 강제 (근본 해결, 전송로 확인 필요)
- ⓒ 재시도 1회 추가
- 그리고 `non-compliant`·`"N/A"` 처리 (아래)

### ⚠️ 2번이 왜 판단이 필요한가 — **생각보다 까다롭다**

지금은 `compliant` → 파싱 실패 → **fail-open → 전달됨.**
`compliant` → allow 로 매핑해도 **전달된다. 사용자 입장의 결과는 같다.**
바뀌는 것은 **정직해진다는 것**(가짜 "리뷰어 실패" 경고가 사라지고 진짜 판정이 기록된다).

**🔴 그런데 ① 작업 중 실패 원문을 다시 보니 어휘가 훨씬 다양했다:**

| 실제로 온 값 | 문제 |
|---|---|
| `COMPLIANT` · `compliant` · `complies` · `COMPLIES` | 대소문자·변형. 단순 추가로 커버 |
| **`non-compliant`** | 🔴 **`compliant` 를 부분일치로 잡으면 이걸 allow 로 읽는다.** 정반대다 |
| **`{"compliant": "N/A"}`** | 🔴 불리언 키 경로인데 값이 문자열 `"N/A"` — **판정 불가**다 |

→ **단순 어휘 추가가 아니다.** 최소한:
- `non-compliant`·`not compliant` 를 **reject 로** 먼저 걸러야 하고(순서가 중요하다)
- `"N/A"` 같은 **판정 불가**를 allow 로 흘리면 안 된다 — 그건 fail-open 이 맞다
- `{"verdict":"compliant","violations":[...]}` 같은 **모순 응답**을 어떻게 읽을지도 정해야 한다

**이건 게이트 판정 설계다. 사용자 판단으로 남긴다.**

## ✅ 1번 완료 (2026-08-08) — fail-open 이 원장에 남는다

**게이트 동작은 한 줄도 안 바꿨다.** 계측만 추가.

### 스키마 — 기존 소비자를 안 깨는 쪽
`verdict` 를 건드리지 않고 **상호배타적 형제 필드**를 뒀다:
```ts
gate?: {
  verdict?: "allow" | "reject";                          // 심사가 끝난 경우
  failure?: { layer: GateFailureLayer; detail?: string }; // fail-open 한 경우
};
```
**왜 union 확장이 아닌가**: `verdict` 에 `"failed"` 를 더하면
`verdict === "allow" ? … : reject` 식으로 읽는 코드가 **실패를 거부로 오해**한다.

### 집계 — 분모 오염을 막았다
실패를 `reviews` 에 넣으면 **분모만 늘어 `rejectRate` 가 조용히 낮아지고**
*"게이트가 더 통과시키네"* 로 읽힌다 — 실제로는 **돌지도 않은** 건데.

새 지표: **`failureRate = failures / (reviews + failures)`** ← *게이트가 실제로 얼마나 돌고 있나.*

### 층 분류 — 추측이 아니라 실데이터에서
`shared/messageGate.ts` 의 `classifyGateFailure()` (`parsing`/`timeout`/`transport`/`unknown`).
**실제 15건에서 규칙을 뽑았고**, 순서도 실측 기반이다(abort 메시지가 "operation" 을 포함해
timeout 을 transport 보다 먼저 본다).
⚠️ **`unknown` 을 억지로 셋 중 하나에 접지 않았다** — 억지 분류는 다음 조사를 엉뚱한 층으로 보낸다.

### 검증
실제로 실패를 만들어(없는 리뷰어 모델) 원장 기록 확인 ✅
```json
{"reviews":0,"rejects":0,"rejectRate":0,"failures":1,"failureRate":1,"failuresByLayer":{"unknown":1}}
```
빌드된 분류기를 **실로그 15건에 돌려** 손 분류와 일치 확인 ✅ `{"parsing":10,"timeout":5}`
기존 원장 893행 회귀 없음 ✅ `{"reviews":241,"rejects":49,"rejectRate":0.2033,"failures":0}`

⚠️ **정직하게**: 만든 실패가 preflight(카탈로그에 없는 모델)라 `unknown` 으로 분류됐다.
**`parsing`·`timeout` 층이 원장에 실제로 찍히는 것은 실측하지 못했다**
(모델이 `compliant` 를 뱉게 만드는 건 비결정적, 60초 타임아웃도 인위적으로 만들기 어려움).
분류기 자체는 실데이터로 검증했고 기록 경로는 같은 코드다.

## 무엇을

Message Gate 의 오류율이 높다. **원인을 찾는다.**

## ⚠️ 왜 가볍지 않은가 — fail-open 이기 때문이다

Gate 는 **리뷰어가 실패하면 차단하지 않고 통과시킨다**(기능정의서 1-16-2).
그 자체는 옳은 설계다 — 심사 도구가 고장 났다고 파티 통신이 멈추면 안 된다.

**하지만 오류율이 높다는 것은:**

> **심사가 실제로는 자주 안 걸리고 있는데, 사용자는 켜 놨으니 걸러지고 있다고 믿는다.**

기능이 **있는 척만 하는 상태**다. Message Gate 는 경쟁 조사에서 **이 제품의 유일한 미점유
차별점**으로 확인된 기능이라, 그게 실제로는 자주 통과된다면 **제품의 핵심 주장이 흔들린다.**

## 알려진 함정 — 원인 후보로 먼저 볼 것

**구독 프록시를 경유하는 리뷰어(Haiku 등)는 말이 많고 스키마를 그대로 안 지키고 바꿔 말한다.**
그래서 파서를 관대하게 만들어 뒀고, **프리필은 오히려 역효과**였다.

→ **실패가 어느 층인지부터 가른다:**

| 층 | 증상 | 확인법 |
|---|---|---|
| **모델·전송로** | 호출 자체가 실패 | 요청이 나가고 응답이 오는지 |
| **파싱** | 응답은 왔는데 판정을 못 읽음 | 원문을 남겨서 무엇이 왔는지 본다 |
| **타임아웃** | 오래 걸려 포기 | 리뷰어 모델별 소요 시간 |

**이 구분 없이 "오류율"만 보면 못 고친다.**

## 정해야 할 것

- **무엇을 "오류"로 세고 있는가** — 지금 집계 기준이 무엇인지부터.
- **리뷰어 모델별 실패율 차이** — 특정 모델·전송로에 몰려 있으면 원인이 좁혀진다.
  (전역·파티·멤버 순으로 리뷰어가 상속되므로 실제로 어느 모델이 돌았는지 확인 필요)
- **fail-open 이 일어났을 때 사용자에게 충분히 보이는가.**
  지금은 경고와 함께 전달한다고 돼 있는데, **그 경고가 실제로 눈에 띄는지**가 관건이다.
  ⚠️ 조사에서 *"비동기 전달 경로에서 배지가 유실될 수 있다"* 는 지적이 있었다 — 확인할 것.
