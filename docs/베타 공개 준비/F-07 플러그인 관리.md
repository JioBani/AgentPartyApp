# F-07. 플러그인 관리

**판정: 여유 — 후순위 가능 (사용자 명시)** · 출처: 사용자

## 무엇을

플러그인을 앱에서 관리할 수 있게 한다.

**사용자 단서**: *"너무 크면 후순위로 둘 수도 있어야겠다"*
→ **범위를 먼저 재고, 큰 쪽이면 베타에서 뺀다.**

## 지금은 — 읽기만 된다

커맨드 팔레트가 `Plugins` 를 **범주로 표시**하고 있다
(기능정의서 1-8-1, `src/renderer/workbench/paletteModel.ts`·`CommandPalette.tsx`).
하네스가 보고한 것을 그대로 보여준다.

**켜고 끄거나 설치하는 수단은 없다.**

→ 즉 **목록을 얻는 경로는 이미 있다.** 없는 것은 화면과 토글뿐이다.

## ⚠️ 범위를 두 개로 갈라야 한다 — 크기가 완전히 다르다

### ⓐ 보이기 + 켜고 끄기 ← **이것만**
지금 팔레트가 이미 읽고 있는 목록을 화면으로 세우고 토글을 붙인다.

**선례가 있다**: **MCP 서버 화면**(기능정의서 1-18)이 정확히 이 모양이다 —
현황 · 상태 구분 · 검색 · 필터 + 개별/일괄 제어.
**그 관례를 재사용하면 싸다.**

### ⓑ 설치·배포까지 ← **베타 범위 밖**
어디서 받고, 무엇을 믿고, 하네스별 설정 파일을 누가 쓰는가.
**신뢰·권한 설계가 통째로 따라붙는다.** 이게 "너무 큰" 쪽이다.

## 판단

**ⓑ 는 베타에서 뺀다.** ⓐ 만이라도 있으면
**"무엇이 켜져 있는지 모른다"** 는 가장 큰 불편이 사라진다.
ⓐ 조차 부담이면 통째로 후순위.

## ⚠️ 하네스별 제약

**Codex 는 설정 파일 기반이라 라이브 토글이 불가능하다.**
기능정의서 1-18-2 가 MCP 에 대해 **이미 같은 제약**을 적고 있다.

플러그인도 같은 벽에 부딪힐 가능성이 높으니 **하네스마다 되는 범위가 다를 것을 전제로**
설계할 것 — **안 되는 걸 되는 척하면 안 된다.**
