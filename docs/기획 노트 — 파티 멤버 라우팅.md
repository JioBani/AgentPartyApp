# 기획 노트 — 파티 멤버 라우팅

> 상태: 브레인스토밍 중
> 연결 항목: [IDEA-014 · 한 창구에 과업을 말하면 알맞은 멤버에게 직접 위임하기](../TODO/ideas/IDEA-014-task-routing.md)

## 기획 범위

이 문서는 **사용자가 파티를 사용하는 경험이 어떻게 달라져야 하는지**를 정의한다. 라우팅 모델,
프롬프트, 하네스 구성, 컨텍스트 요약 방식과 내부 메시지 전달 구조는 지금 결정하지 않는다.

## 1. 한 문장 정의

사용자는 여러 멤버 탭을 오가지 않고 하나의 창구에서 파티와 대화하며, 라우터는 적절한 담당
멤버에게 요청을 위임하고 담당 멤버는 라우터의 중계 없이 직접 답한다.

## 2. 문제

현재 사용자는 누구에게 말해야 하는지 알아야 한다. 잘못된 멤버에게 요청하면 그 멤버가 다시
전달하고 답을 받아 요약하거나, 사용자가 직접 올바른 탭을 찾아 이동해야 한다.

컨텍스트를 멤버별로 분리해도 **입력의 분류 책임이 사용자에게 남아 있으면 분리는 쉽게 깨진다.**
대화를 이어가다 보면 요청의 담당 영역이 모호하거나, 사용자가 어느 멤버에게 보내야 할지 헷갈리는
순간이 생긴다. 이때 잘못 선택한 멤버가 요청을 먼저 읽는 것만으로도 그 멤버의 컨텍스트에 불필요한
정보가 들어간다. 이후 올바른 멤버에게 다시 넘기려면 요청과 배경을 재설명하거나 복사해야 하므로,
컨텍스트 오염과 불필요한 컨텍스트 교환이 연쇄적으로 발생한다.

따라서 이 문제는 단순히 **메시지를 편리하게 전달하는 문제**가 아니다. 사용자가 확신하기 어려운
상황에서도 적절한 컨텍스트 경계를 유지하도록, **누가 먼저 이 요청을 읽어야 하는지 결정하는
부담을 제품이 맡는 문제**다.

동시에 사람에게 멤버별 대화창을 오가게 하는 것이 항상 좋은 경험은 아니다. 사용자는 작업의 전체
흐름을 한곳에서 읽고 이어서 말하고 싶을 수 있다. 여러 전문 멤버가 관여하더라도 하나의 채팅창에서
질문, 담당자 전환, 답변을 종합해서 보는 편이 더 자연스럽고 이해하기 쉬울 수 있다.

여기서 **사용자에게 보이는 대화 기록**과 **각 멤버가 모델 입력으로 받는 실행 컨텍스트**를 구분해야
한다. 화면은 하나로 통합하되, 각 멤버에게는 자신이 담당한 요청과 필요한 맥락만 전달할 수 있다.

중계 방식은 다음 문제를 만든다.

- 전문가의 답을 창구가 다시 쓰면서 정보가 손실될 수 있다.
- 같은 내용을 전문가와 창구가 각각 읽고 써 비용과 지연이 늘어난다.
- 모든 전문가의 대화가 창구 컨텍스트에 쌓여 창구가 가장 먼저 비대해진다.
- 실제 근거를 가진 전문가가 아니라 창구가 최종 답변의 책임자가 된다.

### 문제의 발생 흐름

```text
담당자 판단이 모호함
  -> 사용자가 임의의 멤버를 선택
  -> 잘못 선택된 멤버의 컨텍스트에 요청이 들어감
  -> 실제 담당자를 찾기 위한 재전달·재설명 발생
  -> 둘 이상의 컨텍스트에 같은 내용이 남음
```

### 2.1 현재 AgentParty의 사용자 경험

현재 AgentParty에서 사용자는 다음 방식으로 파티를 운영한다.

- 작업공간 안에 파티를 만들고 파티별 멤버를 구성한다.
- 각 멤버는 이름, 역할, 하네스, 모델, 추론 수준과 권한을 가진 독립된 대화 주체다.
- 사용자는 사이드바에서 멤버를 선택하고, 멤버별 탭과 패널을 열어 직접 대화한다.
- 여러 멤버를 분할 패널에 동시에 띄울 수 있고 파티별 배치가 저장된다.
- 멤버마다 대화 기록, 컨텍스트 사용량, 승인, 사용자 질문, 대기열과 실행 상태가 독립적이다.
- 멤버가 작업 중이면 새 메시지를 대기열에 두거나 현재 작업을 중단하고 먼저 전달할 수 있다.
- 멤버들은 서로 직접 메시지를 보내거나 전체 방송할 수 있고, Message Gate로 멤버 간 발신 규칙을
  적용할 수 있다.
- 사용자는 사이드바와 탭에서 작업 중, 유휴, 승인 대기, 오류, 읽지 않은 메시지와 대기 건수를 본다.
- 멤버가 만든 서브에이전트의 상태와 상세 작업도 해당 멤버 화면에서 확인한다.

즉 현재 워크벤치는 **독립된 AI 멤버 여러 명을 세밀하게 운영하는 도구**다. 강점은 각 멤버의
컨텍스트와 실행 구성을 분리하고 직접 들여다볼 수 있다는 점이다. 반면 사용자에게 파티 전체를 향한
단일 대화 표면은 없어서, 사용자가 직접 담당자를 고르고 탭을 이동하며 결과와 진행 상황을 종합한다.

실제 파티 사용 분석에서도 다음 사용자 문제가 확인됐다.

- 조정 역할인 `main`을 만들어도 사용자는 전문 멤버에게 직접 입력하는 경우가 많다.
- 한 멤버가 만능 창구가 되어 자기 역할 밖의 질문과 작업까지 받는다.
- 잘못 보낸 뒤 실제 담당자를 찾아 재질문하므로 최소 한 턴과 컨텍스트가 낭비된다.
- 만들어둔 전문 멤버를 거의 사용하지 않고 가까운 몇 명에게 입력이 몰린다.
- 진행 상황이 특정 멤버 컨텍스트에만 남아 사용자가 자기 지시의 행방을 놓친다.

이번 기능은 기존 멤버 탭과 독립 실행을 대체하지 않는다. 사용자의 기본 대화 동선을 **멤버 선택 →
멤버별 탭**에서 **파티에 질문 → 담당 멤버의 직접 답변**으로 바꾸고, 기존 탭은 개별 멤버의 역할,
전체 출력과 세부 작업을 확인하는 상세 보기로 유지한다.

### 2.2 사용자에게 전달할 가치

이 기능의 일차적 가치는 라우팅 기술 자체가 아니라 **여러 멤버와의 대화를 한곳에서 관리하는
것**이다. 현재 사용자는 멤버를 고르고, 탭을 이동하고, 맥락을 다시 설명하고, 여러 탭의 답을
머릿속에서 종합한다. 통합 채팅은 이 운영 부담을 줄인다.

고도화되면 사용자는 내부 팀 구조를 항상 의식하지 않고 **파티 전체를 하나의 에이전트처럼** 사용할
수 있다. 단, 내부 구조를 감추는 것과 없애는 것은 다르다. 필요할 때는 현황판에서 멤버 구성과 작업
과정을 확인하고 개입할 수 있어야 한다.

가치의 발전 단계는 다음과 같다.

1. **대화 통합**: 여러 탭을 오가지 않고 한곳에서 모든 멤버의 대화를 본다.
2. **입력 라우팅**: 사용자가 수신자를 판단하지 않아도 적절한 담당자에게 전달된다.
3. **직접 협업**: 멤버들이 오케스트레이터의 중계 없이 서로 소통하고 사용자에게 직접 답한다.
4. **파티 추상화**: 사용자는 파티를 하나의 에이전트처럼 사용한다.
5. **자율 팀 구성**: 오케스트레이터가 과업에 필요한 멤버와 하네스를 구성하고 운영한다.

### 2.3 파티 구성 방식

두 가지 파티 구성 방식을 장기적으로 지원한다.

| 구성 방식 | 사용자의 관계 | 멤버의 의미 |
|---|---|---|
| 사용자 구성 파티 | 사용자가 역할과 멤버를 직접 설계 | 사용자가 알고 협업하는 명시적 주체 |
| 자율 구성 파티 | 사용자는 과업을 주고 오케스트레이터가 팀 구성 | 문제 해결을 위한 내부 실행 구조 |

최소 기능은 **이미 사용자가 구성한 파티**를 대상으로 한다. 자율 구성은 그 위에 팀 설계와 멤버
생성을 추가하는 고도화 단계다.

자율 구성 단계에서도 오케스트레이터가 모든 소통을 중앙에서 중계하지 않는다. 오케스트레이터는
과업 분해, 팀 구성, 큰 방향과 라우팅을 담당하고, 세부 질문·보고·인계는 독립된 하네스 멤버들이
직접 수행한다. 이를 통해 오케스트레이터의 컨텍스트 부담을 줄이고 각 하네스의 도구, 지시, 작업
방식을 보존한다.

## 3. 사용자 경험 원칙

### 결정됨

1. **위임이지 중계가 아니다.** 창구는 담당자를 고르며, 전문가 답을 대신 작성하지 않는다.
2. **입력과 출력 경로는 비대칭이다.** 입력은 라우터를 거치고, 출력은 담당 멤버에서 사용자로 간다.
3. **사용자는 여러 탭을 관리하지 않는다.** 질문과 답변, 담당자 전환과 진행 상황을 하나의 흐름에서
   이해할 수 있어야 한다.
4. **라우팅은 대화를 방해하지 않는다.** 매번 확인을 요구하지 않고 바로 전달한다.
5. **사용자는 필요할 때 내부를 확인할 수 있다.** 평소에는 단순하게 쓰되 실제 답변자, 역할과 작업
   경로를 원할 때 확인할 수 있다.
6. **잘못된 담당을 바로잡을 수 있다.** 자동 선택이 틀렸을 때 사용자가 대화를 잃지 않고 수정할 수
   있어야 한다.
7. **파티를 단순화하되 블랙박스로 만들지 않는다.** 통합 채팅과 파티 현황판이 함께 제공되어야 한다.
8. **최소 기능에서는 사용자가 수신자를 직접 지정하지 않는다.** `@멤버` 같은 명시적 라우팅은
   구현하지 않고, 사용자가 담당자를 고르지 않아도 되는 통합 채팅 경험에 집중한다.
9. **통합 채팅에는 사용자와의 대화만 표시한다.** 멤버끼리 주고받는 질문, 보고와 조율 메시지는
   통합 채팅에 섞지 않는다. 사용자가 내부 과정을 확인하려 할 때는 파티 현황판에서 본다.
10. **여러 멤버가 사용자에게 답하면 모두 표시한다.** 하나의 사용자 질문에 복수의 멤버가 직접
    답한 경우, 하나만 선택하거나 자동으로 합치지 않고 각 답변을 작성자 이름과 함께 통합 채팅에
    그대로 보여준다.
11. **진행 중인 멤버에게 보내는 방식은 기존 선택을 유지한다.** 사용자는 현재 작업을 끊고 새 메시지를
    먼저 전달할지, 기존 작업 뒤에 큐로 쌓을지 선택할 수 있어야 한다. 통합 채팅이라고 해서 별도의
    전송 규칙을 만들지 않는다.
12. **사용자 개입 요청은 통합 채팅에서 처리한다.** 멤버가 작업 도중 실행 승인, 선택지 또는 추가
    입력을 요청하면 통합 채팅에 표시하고, 사용자는 멤버 탭으로 이동하지 않고 그 자리에서 응답할
    수 있어야 한다. 응답은 요청을 만든 멤버의 작업으로 돌아간다.
13. **사용자가 실제로 봐야 하는 정보만 통합 채팅에 표시한다.** 사용자의 판단이나 행동이 필요한
    답변·질문·승인은 한곳에 모으고, 도구 호출·명령 출력·파일 변경 과정과 멤버 간 내부 소통은
    기본 흐름에서 숨긴다. 세부 과정은 멤버 탭과 파티 현황판에서 확인한다.
14. **답변을 기다리는 동안 진행 상태를 보여준다.** 어떤 멤버가 요청을 처리하고 있는지, 작업 중인지,
    대기·승인 필요·차단·오류 상태인지 통합 채팅에서 알 수 있어야 한다. 세부 작업 로그가 아니라
    사용자가 기다리거나 개입할지 판단하는 데 필요한 수준의 상태를 표시한다.
15. **폴백은 담당 멤버가 실패한 경우에만 사용한다.** 작업 중이거나 응답이 늦는다는 이유로 다른
    멤버에게 같은 요청을 중복 전달하지 않는다. 담당 멤버가 명확히 실패했을 때만 다른 처리 경로를
    사용한다.
16. **폴백은 사용자 확인 없이 실행하고 담당 변경을 알린다.** 담당 멤버가 실패하면 다른 멤버에게
    바로 넘기고, 통합 채팅에 `A 실패 → B가 이어서 처리`처럼 실패와 새 담당자를 표시한다.
17. **폴백 대상이 없으면 실패 사유와 수동 확인 경로를 안내한다.** 별도의 재시도 기능을 제공하지
    않고, 사용자가 멤버별 탭으로 이동해 직접 질문하거나 상태를 확인하도록 안내한다.
18. **적합한 담당자를 찾지 못하면 억지로 전달하지 않는다.** 초기 라우팅에서 적합한 멤버가 없을
    때도 이유를 통합 채팅에 표시하고, 사용자가 멤버별 탭에서 직접 질문하도록 안내한다.
19. **통합 채팅 기록은 파티별로 독립적으로 유지한다.** 파티를 전환하면 해당 파티의 대화 기록으로
    바뀌고, 앱을 다시 열어도 이전 통합 대화를 그대로 이어갈 수 있어야 한다.
20. **파티 선택 시 통합 채팅을 기본 화면으로 연다.** 사용자는 파티에 들어오자마자 파티 전체와
    대화하고, 개별 멤버 탭은 역할·전체 출력·세부 작업 확인이나 직접 질문이 필요할 때 연다.
21. **멤버별 대화 기록은 통합 채팅에 합치지 않는다.** 기존 멤버 탭의 과거 대화나 사용자가 멤버
    탭에서 직접 주고받은 내용은 통합 채팅에 노출하지 않는다. 통합 채팅에는 그 창구를 통해 사용자와
    파티가 주고받은 내용만 기록한다.
22. **통합 채팅에서도 이미지와 파일을 첨부할 수 있다.** 사용자는 개별 멤버 탭으로 이동하지 않고
    현재 멤버 채팅과 동일하게 자료를 첨부해 파티에 질문할 수 있어야 한다.

### 가설

- 팀 자동 구성 없이, 사용자가 미리 만든 파티만으로도 독립적인 제품 가치가 있다.
- 기본 사용자 경험은 담당 멤버 탭으로 이동하는 방식보다, **하나의 통합 채팅창 안에서 발화별
  담당 멤버를 표시하는 방식**이 더 자연스러울 수 있다.
- 파티 현황판에서는 내부 라우팅 역할을 기본적으로 접힌 `시스템 멤버`로 표시할 수 있다. 이는 변경
  가능한 낮은 우선순위의 UX 가설이며 최소 기능의 핵심 요구사항은 아니다.

## 4. 개념적 사용자 흐름

1. 사용자가 단일 창구에 요청한다.
2. 앱이 후보 멤버의 역할과 상태를 바탕으로 담당자를 고른다.
3. 별도의 사용자 확인 없이 요청과 필요한 맥락이 담당 멤버에게 즉시 전달된다.
4. 사용자에게 실제 담당자와 라우팅 상태가 표시된다.
5. 담당 멤버가 작업하는 동안 이름과 진행 상태가 통합 채팅에 표시된다.
6. 담당 멤버가 자신의 이름이 표시된 답을 통합 채팅 흐름에 직접 게시한다.
7. 후속 질문은 같은 담당자에게 이어지되, 화제가 바뀌면 재라우팅 여부를 판단한다.

```text
사용자 ── 요청 ──> 라우터 ── 위임 ──> 담당 멤버
   ^                                      |
   └──────────── 직접 답변 ───────────────┘
```

## 5. 출력 모델

입력을 적절한 담당자에게 보내는 것과, 여러 멤버의 출력을 사용자에게 어떤 형태로 보여주는 것은
서로 다른 문제다. 두 가지 출력 모델을 지원하는 방향으로 본다.

### 5.1 단톡방형 직접 응답

라우터는 **입력만** 적절한 담당 멤버에게 전달한다. 담당 멤버가 생성한 답은 중계하거나 다시 쓰지
않고 통합 대화창에 그대로 표시한다. 여기서 단톡방은 여러 멤버의 내부 대화를 모두 공개한다는 뜻이
아니다. **사용자에게 직접 한 답변만** 한 대화 흐름에 모아 보여준다는 뜻이다.

사용자에게 직접 한 대화에는 최종 답변뿐 아니라 작업을 계속하기 위해 필요한 승인, 선택과 추가
질문도 포함한다.

최소 기능에서는 승인만 별도 화면으로 분리하지 않는다. 통합 채팅이 복잡해져 실제 사용성이 나빠질
경우, 사용자 개입 요청을 별도 UI로 분리하는 것을 후속 개선으로 검토한다.

```text
사용자: 이거 어떻게 됐어?
구현 담당: 구현은 완료했고 테스트에서 한 건이 실패했습니다.
테스트 담당: 실패 원인을 확인 중입니다.
```

장점:

- 중계로 인한 정보 손실이 없다.
- 한 번 생성한 답을 다시 요약하지 않아 비용과 지연이 작다.
- 실제 근거와 작업 컨텍스트를 가진 멤버가 직접 책임지고 답한다.
- 오케스트레이터나 라우터의 컨텍스트가 모든 보고로 비대해지지 않는다.
- 사용자는 여러 탭을 오가지 않으면서도 팀과 직접 대화하는 느낌을 얻는다.

단점:

- 여러 멤버의 답이 이어지면 대화가 산만해질 수 있다.
- 답변 사이의 중복이나 모순을 사용자가 직접 종합해야 할 수 있다.
- 진행 상황을 한 문장으로 알고 싶은 사용자에게는 정보가 과할 수 있다.

### 5.2 비서형 종합 응답

파티의 과업을 관리하는 별도 멤버가 각 담당자의 보고를 받아 정리한 뒤, 사용자에게 하나의 종합된
답을 제공한다. 이 멤버는 단순 라우터보다 **과업 관리자 또는 비서**에 가깝다.

```text
사용자: 이거 어떻게 됐어?
비서: 구현은 완료됐고 테스트 한 건이 실패해 원인을 확인 중입니다.
      현재 완료를 막는 항목은 그 테스트뿐입니다.
```

장점:

- 여러 작업의 상태를 짧고 일관된 보고로 받을 수 있다.
- 멤버별 표현 차이, 중복, 모순을 정리할 수 있다.
- 자율 생성 파티를 하나의 에이전트처럼 사용하는 경험과 잘 맞는다.
- 사용자가 내부 역할과 작업 구조를 몰라도 전체 상황을 파악하기 쉽다.

단점:

- 비서에게 여러 멤버의 보고가 쌓여 중앙 컨텍스트가 다시 비대해질 수 있다.
- 요약 과정에서 세부 정보가 손실되거나 왜곡될 수 있다.
- 같은 내용을 다시 읽고 쓰므로 비용과 지연이 늘어난다.
- 실제 담당자와 사용자 사이의 직접적인 책임 관계가 흐려질 수 있다.

### 5.3 단계적 구현 방향

1. **최소 기능: 단톡방형 직접 응답**
   - 하나의 통합 대화창
   - 사용자 입력만 담당 멤버에게 라우팅
   - 담당 멤버의 출력을 변경 없이 표시
   - 각 발화의 실제 작성자는 내부 기록에 항상 보존
2. **확장 기능: 비서형 종합 보고**
   - 과업 관리자/비서 역할의 멤버 추가
   - 필요할 때 여러 멤버의 상태와 결과를 모아 요약
   - 원본 보고와 실제 작성자를 펼쳐볼 수 있게 유지
3. **선택 가능한 운영 방식**
   - 파티 또는 대화 단위로 직접 응답과 종합 응답을 선택
   - 평소에는 직접 응답하되, 사용자가 전체 현황을 물을 때만 비서가 종합하는 혼합 방식 검토

비서형을 추가하더라도 모든 발화를 무조건 비서가 중계하게 만들지는 않는다. 직접 답변이라는 기본
경로를 유지하고, **여러 결과를 실제로 종합해야 할 때만 비서가 개입하는 방식**을 우선 검토한다.

### 5.4 답변자 표시

실제 작성자 귀속은 항상 기록하되, 사용자에게 드러내는 수준은 파티 구성 방식과 상황에 따라 달라질
수 있다.

| 상황 | 기본 표시 | 이유 |
|---|---|---|
| 사용자가 직접 구성한 파티 | 멤버 이름 표시 | 누가 답했는지 알 수 있되 통합 대화가 역할 정보로 복잡해지지 않음 |
| 자율 구성된 파티 | 파티를 기본 화자로 표시 | 임시 내부 구조를 몰라도 하나의 에이전트처럼 사용할 수 있음 |
| 오류·승인·검토·책임 확인 | 실제 작성자 표시 | 책임과 작업 경로를 추적해야 함 |

사람이 구성한 파티의 통합 채팅에서는 답변자의 **이름만 기본으로 표시하고 역할은 노출하지 않는다.**
이름 또는 프로필을 클릭하면 해당 멤버의 기존 탭을 연다. 사용자는 그곳에서 멤버의 역할과 해당
멤버가 생성한 전체 출력·작업 대화를 확인한다. 별도의 축약된 프로필 화면을 새로 만드는 것보다,
기존 멤버 탭을 상세 보기로 사용하는 경험에 가깝다.

화면의 화자 표현과 내부 귀속 데이터는 분리한다. 자율 구성 파티에서는 파티 하나의 답처럼 보여도,
필요하면 실제 작성자와 관련 멤버 탭을 확인할 수 있게 한다.

## 6. 파티 현황판

하나의 채팅창으로 대화를 통합하더라도 파티의 내부 구조를 블랙박스로 만들지 않는다. 사용자가
필요할 때 파티의 구성과 작동 방식을 보고 조정할 수 있는 **인터랙티브 현황판**을 함께 제공한다.

통합 채팅창과 현황판의 역할은 다르다.

| 표면 | 사용자가 해결하는 문제 |
|---|---|
| 통합 채팅창 | 어느 탭과 멤버를 선택할지 고민하지 않고 파티와 대화한다 |
| 파티 현황판 | 파티가 어떻게 구성되고 움직이는지 이해하고 필요할 때 개입한다 |

현황판은 현재 사용자가 워크벤치의 여러 멤버 탭을 돌아다니며 머릿속으로 종합하는 정보를 한곳에
모은다.

### 6.1 보여줘야 할 정보

- **파티 구성**: 현재 어떤 멤버들이 있으며, 고정 멤버인지 자율 생성된 임시 멤버인지
- **역할과 책임**: 각 멤버가 어떤 전문 영역과 과업을 맡았는지
- **실행 상태**: 작업 중, 유휴, 대기, 승인 필요, 오류, 종료 등 현재 상태
- **과업 진행 상황**: 전체 목표, 하위 과업, 담당자, 완료·진행·차단 상태
- **위계와 협업 구조**: 오케스트레이터, 과업 관리자, 담당자, 검토자 등의 관계
- **소통 경로와 규칙**: 누가 누구에게 직접 말할 수 있는지, 라우팅·보고·승인·Message Gate 규칙
- **최근 상호작용**: 어떤 멤버 사이에서 인계, 질문, 보고가 일어났는지

멤버끼리 주고받는 질문과 소통은 현황판에서 확인할 수 있어야 한다. 이를 타임라인, 관계 그래프,
이벤트 피드 또는 다른 방식 중 무엇으로 보여줄지는 아직 결정하지 않는다.

멤버 간 관계는 항상 단순한 상하 트리라고 가정하지 않는다. 지휘 관계, 과업 의존성, 메시지 흐름은
서로 다른 관계일 수 있으므로 시각적으로 구분해야 한다.

### 6.2 가능한 인터랙션

- 통합 채팅의 답변자 이름·프로필을 클릭해 해당 멤버 탭 열기
- 멤버 탭에서 역할, 현재 과업과 전체 출력·작업 대화 확인
- 과업 또는 대화를 다른 멤버에게 재배정
- 멤버 추가·종료·교체와 역할 수정
- 오케스트레이터 또는 비서 역할 지정
- 멤버 간 소통 허용 범위와 보고 규칙 확인·수정
- 차단되거나 승인이 필요한 작업에 개입
- 통합 채팅의 특정 답변에서 실제 담당 멤버와 관련 과업으로 이동

### 6.3 제품 원칙

1. **추상화는 불투명화가 아니다.** 평소에는 하나의 에이전트처럼 간단하게 쓰되, 원하면 내부 팀을
   이해하고 제어할 수 있어야 한다.
2. **관찰과 조작을 같은 화면에서 연결한다.** 상태를 보여주기만 하는 그림이 아니라, 문제를 발견한
   자리에서 담당 변경이나 규칙 수정 같은 행동으로 이어져야 한다.
3. **관측된 사실과 모델의 해석을 구분한다.** 멤버 상태와 메시지 흐름은 실제 이벤트로 표시하고,
   과업 요약이나 진행률 추정에는 추정임을 드러낸다.
4. **통합 채팅과 현황판은 같은 상태를 본다.** 채팅에서 일어난 라우팅과 담당자 전환이 현황판에 즉시
   반영되고, 현황판에서 한 변경이 이후 대화 라우팅에 적용되어야 한다.

이 현황판은 아이디어 백로그의 멤버 소통·작업 다이어그램과 공유 멤버 보드가 다루는 관측 정보를
재사용할 수 있다. 다만 이 기능에서는 단순 시각화보다 **파티를 하나의 에이전트처럼 쓰면서도 내부를
운영할 수 있게 하는 제어 표면**이라는 목적이 중심이다.

## 7. 서로 분리해서 설계할 기능

| 기능 | 담당자 결정 주체 | 예시 |
|---|---|---|
| 자동 라우팅 | 시스템 | 창구가 요청을 읽고 planner를 선택 |
| 수동 인계 | 현재 담당 멤버 | 작업 중 다른 전문 멤버에게 소유권 이전 |
| 멀티 멤버 작업 | 시스템 또는 담당 멤버 | 조사와 구현을 서로 다른 멤버에게 분담 |
| 동적 팀 구성 | 오케스트레이터 | 과업에 필요한 역할·모델·하네스의 멤버를 생성 |
| 멤버 간 직접 협업 | 각 멤버 | 구현 담당이 기획 담당에게 직접 질문하고 테스트 담당이 오류를 직접 전달 |

이들은 메시지 전달 기반을 공유할 수 있지만, 사용자 기대와 실패 처리 방식이 다르므로 하나의
기능으로 뭉뚱그리지 않는다.

## 8. 미결정 질문

### 사용자 경험

- 사용자가 담당자를 수정하거나 라우팅을 고정하는 인터랙션은 무엇인가?
- 담당 영역이 실제로 겹치거나 애매할 때, 제품은 한 명을 고를 것인가 아니면 사용자에게 선택지를
  설명할 것인가?
- 직접 응답과 비서형 종합 응답을 사용자가 명시적으로 고를 것인가, 질문의 성격에 따라 자동으로
  선택할 것인가?
- 비서가 종합한 답에서 원본 멤버 보고를 어떤 방식으로 펼쳐볼 수 있게 할 것인가?
- 통합 채팅과 파티 현황판을 한 화면에 나란히 둘 것인가, 필요할 때 전환하거나 펼칠 것인가?
- 현황판의 기본 시각화는 위계도, 과업 보드, 메시지 흐름 중 무엇을 중심으로 할 것인가?
- 멤버 간 질문과 소통을 현황판에서 어떤 표현 방식과 상세 수준으로 보여줄 것인가?
- 승인과 사용자 개입 요청이 통합 채팅을 복잡하게 만들 경우 별도 UI로 언제 분리할 것인가?

### 실패와 예외

- 담당 멤버가 종료됐거나 작업 중일 때 대기, 다른 후보 선택, 인터럽트 중 무엇을 택하는가?
- 한 요청에 여러 전문성이 필요할 때 대표 담당자를 둘 것인가, 작업을 분할할 것인가?
- 잘못 라우팅된 요청의 소유권과 대화 기록을 어떻게 바로잡는가?
- 어떤 상태를 담당 멤버의 `실패`로 보고 폴백을 시작할 것인가?

## 9. 후속 설계로 미룬 내용

- 라우팅 모델과 프롬프트
- 라우터 하네스와 내부 세션 구성
- 통합 대화 컨텍스트의 저장·요약 방식
- 담당 멤버에게 전달할 최소 컨텍스트
- Message Gate와 라우터의 기술적 책임 경계
- 내부 이벤트, 로그와 자동화 HTTP API의 구체적인 형태

이 항목들은 사용자 경험과 최소 기능 범위가 정해진 뒤 별도 설계에서 다룬다.

## 10. 브레인스토밍 정리 규칙

이 문서는 대화 중 나온 생각을 다음 기준으로 정리한다.

- 합의된 방향은 **결정됨**으로 이동한다.
- 검증이 필요한 생각은 **가설**로 남긴다.
- 선택이 필요한 것은 **미결정 질문**으로 적는다.
- 기존 원칙과 충돌하면 **충돌/리스크**를 명시한다.
- 말한 순서보다 제품 구조와 사용자 흐름에 맞춰 재배치한다.
