### #26 잘린 대화가 **잘렸다는 표시 없이** 끝난다 — "이전 대화 N개 더 보기"

- **상태**: OPEN (2026-08-03 `plaaner` 발견, **같은 날 심각도 하향**)
- **심각도**: 중간
- ⚠️ **최초 보고는 "진행 중인 데이터 손실 / 최우선"이었다. 과장이었고 정정한다.**
  - **앱 기록은 화면용 사본이고, 하네스가 자기 원본을 따로 남긴다.** 사라지는 게 아니라
    **스크롤백 한도**에 가깝다
  - **대화 연속성에 영향 없다** — 하네스 교체 시 인계는 **하네스 원본**을 쓰기로 결정됐다
  - 잘린 6명 중 **4명은 원본 파일이 실물로 확인**됐다
  - **왜 과장됐나**: 조사 시점의 전제가 "앱 기록을 인계에 쓴다"였다. **그 전제가 바뀐 뒤에도
    그때의 심각도가 그대로 따라왔다.** 그리고 발견자가 "사용자가 화면에서 손실을 목격했는지는
    **미검증**"이라고 명시했는데 **그 표시를 무시한 채 최우선으로 배정**됐다(main 판단 착오)

**측정된 사실 (그대로 유효)**
- 한도가 **"대화 개수"가 아니라 "기록 조각 개수"(800)** 이고, 조각의 **79~90%가 도구 실행·상태 표시**다
- 그래서 **도구를 많이 쓰는 멤버가 몇 배 빨리 찬다** — 한 멤버는 **15턴**, 다른 멤버는 57턴
- 저장 파일 15개 중 **6개가 정확히 800에서 멈춰 있고**, 그 6개의 **첫 기록이 전부 대화 도중 조각**이다
- 잘린 6명이 **전부 같은 파티**다(도구 사용이 몰린 파티). 다른 파티 3곳은 없음

**✅ 복구 불가 항목은 없다 (2026-08-03 2차 정정)**
1차 보고의 **"Cursor 멤버 2명은 원본을 못 이어 복구 불가"는 조사 누락이었다.**
Cursor 원본은 존재하고 **앱이 이미 연결하고 있다** — 앱이 저장하는 cursor 세션 번호가 곧 Cursor
쪽 폴더명이라 **6건 모두 일치**한다. 대화 본문이 평문으로 남아 있고 순서도 맞다.
(1차 조사가 Claude·Codex 저장 위치만 확인한 검색 범위 오류였다.)

**그래서 실제로 남는 것은 하나 — 표시 결함이다**
> **"이전 대화 N개 더 보기"는 데이터를 더 불러오는 것이 아니라 이미 가진 것을 더 그리는 기능**이다.
> 사용자는 "N개 숨김"을 **"남은 전부"로 읽는데**, 끝까지 누르면 **잘린 단면**이 나오고
> **거기에 아무 표시가 없다.** 원본이 남아 있어도, **사용자는 자기가 전부 봤다고 믿는다.**

즉 고칠 것은 **"여기서부터는 이 화면에 없다"를 드러내는 것**이다. 기록은 잃지 않았으므로
**"어디서 마저 볼 수 있는지"까지 알려줄 수 있으면 더 좋다.**

**완화**: 앱 기록을 **대화 위주로 줄이면**(도구 조각 비중을 낮추면) 같은 한도로 훨씬 오래 남는다 —
문제 자체가 크게 준다. [P-6] 기획 노트에 그 항목이 있다.

- **연관**: [P-6](대화 인계 — **인계는 하네스 원본을 쓴다**) · [#19](대화 소실 — 그쪽은 실제 손실이었다)

### #24 인터럽트로 메시지를 전달하면 멤버 쪽에 에러 메시지로 보임

- **상태**: OPEN
- **심각도**: 중간 — 정상 동작인데 실패처럼 보인다. 멤버(모델)가 이를 오류로 해석해 엉뚱한 복구를 시도할 수 있고, 사용자도 뭔가 잘못된 줄 안다
- **증상**: `interrupt: true` 로 메시지를 보내거나 턴을 중단시킬 때, 중단된 멤버 쪽에 **에러 메시지**가 나타남
- **기대 결과**: 인터럽트는 **의도된 정상 경로**이므로 그에 맞는 메시지여야 함 — 예: "사용자/다른 멤버의 요청으로 현재 턴이 중단되었고, 아래 메시지를 먼저 처리하라"는 식의 안내. 실패가 아니라 **무슨 일이 일어났고 다음에 뭘 해야 하는지**를 전달
- **주의**: 이건 "에러를 숨기자"가 아니다. AGENTS.md 의 "silent fallback 금지" 는 **진짜 실패를 감추지 말라**는 뜻이고, 여기는 반대로 **성공한 정상 동작을 실패로 표시**하고 있는 경우다. 실제 인터럽트 실패(대상 없음/중단 불가)는 지금처럼 에러로 남아야 함
- **확인 필요**: 어느 하네스에서 어떤 문구가 나오는지 원문. 하네스마다 중단 표현이 다름(Claude 는 `status: "interrupt"` 이벤트로 `no active query` / `requested` 를 구분해 보고함 — `claudeAdapter.ts` 273·279행)
- **연관**: [P-14] 인터럽트 기본값 설정 · [P-16] Esc 로 턴 중단 — **인터럽트를 더 쉽게 만들수록 이 메시지가 자주 보이므로 먼저 고치는 게 맞다**

- **고려 사항 / 방향 제안**:
  - (b) 방식이 데이터 정합성 측면에서 안전 — 한 프로세스/한 엔진이 작업공간 스토어를 소유하면서 창만 여러 개(detachable 워크벤치)로 여는 방식. 기존 다중 창 구조(`windowRegistry`) 확장.
  - (a) 방식(멀티 인스턴스)은 같은 작업공간 스토리지에 엔진이 2개 붙어 상태/파일 충돌 위험 → 허용하려면 스토어 동시성 설계 필요.
- **연관**: [#5]/[#7] 대화 상태 격리 이슈와 함께 고려 시, "작업공간 스토어 단일 소유 + 창 분리" 원칙이 더 명확해짐

1. **상태 칩을 왼쪽 사이드바에도** — 지금 사이드바에서는 멤버 상태가 그냥 텍스트로 나온다. 대화창 헤더와 동일한 **칩(chip) 형태**로 통일.
2. **멤버 이름 앞 동그라미는 상태색으로** — 현재 멤버 테마색을 따라가는데, **상태**(idle / working / 승인 대기 등)를 나타내도록 변경. 상태별 색 팔레트를 정의해 사이드바·헤더·칩이 같은 색 규칙을 공유(테마 토큰은 `themes.ts` 단일 소스).

**대화 출력**

3. **마크다운/코드 블록 원클릭 복사** — 블록 단위 복사 버튼 제공(코드 블록, 그리고 응답 전체).
4. **큐된 메시지는 대화창이 아니라 큐 목록으로** — 지금은 대기 중인 메시지가 대화 스트림에 그대로 섞인다. 별도 "대기열" UI(개수 표시 + 펼쳐서 확인/취소/편집)로 분리. → **별도 UI 설계 필요**.
5. **링크는 외부 기본 브라우저로** — Electron 내부 창이 아니라 OS 기본 브라우저에서 열리도록. 링크 옆에 **복사 아이콘**도 추가.
6. **전체보기 창 패딩 부족** — 전체보기(확대) 창이 콘텐츠에 딱 붙어 답답함. 여백 추가.
7. **`requesting` / `responding` 표시를 네이티브 그래픽으로** — 현재 텍스트 위주 표시를 적절한 인디케이터(스피너/펄스 등)로 교체.

**입력창**

8. **Enter vs Ctrl+Enter 전송 설정** — 어느 키로 전송할지 사용자 설정으로 선택 가능하게. (→ 이 설정이 생기면 [#15] 는 "설정값만 따른다"로 정리됨)
9. **업로드한 이미지 복사** — 첨부/업로드된 이미지를 클립보드로 복사하는 기능.
10. **파일 드래그 앤 드롭 → 경로 자동 입력** — 파일을 입력창에 끌어다 놓으면 해당 경로가 텍스트로 삽입되도록.

      [DESIGN_TODO.md](DESIGN_TODO.md) "파일 드래그앤드롭 디자인 수정" 참조. **완료로 치지 말 것.**

### P-4 파티/멤버 **보관(archive)** 기능 — 삭제 대신

- **상태**: OPEN (요청)
- **배경**: 지금은 정리 수단이 **삭제뿐**이라, 당장 안 쓰는 파티/멤버를 목록에서 치우려면 대화 이력까지 영구히 날려야 한다. 삭제는 되돌릴 수 없다.
- **요청 내용**: 파티와 멤버 모두 **보관** 상태를 지원.
  - 보관하면 기본 목록에서 사라지지만 **대화 이력·설정·세션 정보는 그대로 보존**
  - "보관함" 뷰에서 확인하고 **복구(unarchive)** 가능
  - 삭제는 별도로 남기되, 일상적인 정리는 보관이 기본 동선이 되도록
- **확인 필요 / 설계 포인트**:
  - 보관 시 실행 중인 세션은 어떻게 할지 — 종료 후 보관(멤버 close 와 유사)이 자연스러움
  - 보관된 멤버 이름을 새 멤버가 재사용할 수 있는지 (이름 충돌 정책)
  - 저장 형태: 삭제 표시만 하는 플래그(`archivedAt`) 방식이 복구가 단순함
  - AGENTS.md 원칙상 **HTTP 자동화 API로도 노출**되어야 함 (에이전트가 보관/복구/보관함 조회 가능)

### P-5 파티 **간** 소통 기능

- **상태**: OPEN (요청)
- **배경**: 지금 멤버 통신(`send`/`broadcast`)은 **같은 파티 안에서만** 가능하다. 파티가 여러 개로 나뉘면 서로 완전히 단절되어, 파티를 목적별로 쪼갤수록 협업이 끊긴다.
- **요청 내용**: 파티 경계를 넘는 메시지 전달. 예) 파티 A 의 멤버가 파티 B 의 멤버(또는 파티 B 전체)에게 메시지를 보낼 수 있어야 함.
- **확인 필요 / 설계 포인트**:
  - **주소 체계** — 이름은 파티 간 유일하지 않다(모든 파티에 `main` 이 있음). `파티/멤버` 형태의 정규화된 주소가 필요 (`send` 에 `party` 인자 추가 등). [#5]/[#7] 이 정확히 "이름만으로 키잉해서 섞인" 사고였음
  - **범위** — 같은 워크스페이스 내 파티끼리만인지, 다른 워크스페이스의 파티까지인지 (후자면 프로세스 간 전달 필요 → [#8] 멀티 인스턴스 구조와 연계)
  - **권한/격리** — 아무 파티나 무제한으로 찌를 수 있으면 격리 의미가 사라짐. 허용 대상 지정 또는 Message Gate 로 파티 간 발신 규칙 적용
  - **표시** — 받은 쪽에서 발신자가 외부 파티임을 명확히 (`<channel source="agentparty" from="파티/멤버">`)
  - UI 와 HTTP 자동화 API 양쪽에서 동일하게 동작해야 함

### P-6 하네스/프로바이더 교체 시 이전 트랜스크립트로 대화 이어가기

- **상태**: OPEN (요청)
- **배경**: 모델을 **다른 프로바이더나 다른 하네스**로 바꾸면 세션이 재시작되면서 대화 맥락이 끊긴다(하네스마다 세션/히스토리를 자기 형식으로 들고 있고, 백엔드가 바뀌면 그 세션을 이어받을 수 없음). 사용자는 UI 상 같은 멤버와 계속 대화하는 것처럼 보이는데 모델은 앞 내용을 모른다 — [#10] 의 무성 데이터 손실과 같은 종류의 체감.
- **요청 내용**: 하네스/프로바이더/모델을 교체해도, **앱이 보관 중인 트랜스크립트를 새 세션에 넘겨 자연스럽게 이어지도록** 할 것.
- **확인 필요 / 설계 포인트**:
  - 정본은 앱 트랜스크립트다(하네스 세션이 아님) → 교체 시 트랜스크립트를 **초기 컨텍스트로 재생**하는 방식이 자연스러움. [#10] 의 `<unsaved_history>` 재생(`src/core/cursorAdapter.ts`)이 이미 유사한 패턴 — 하네스 공통 계층으로 올릴 수 있는지 검토
  - **분량 처리** — 긴 대화는 그대로 다 넣을 수 없음. 요약/절단 정책이 필요하고, 무엇을 버렸는지 **조용히 숨기지 말고 표시**할 것 (AGENTS.md "silent fallback 금지")
  - **비텍스트 요소** — 도구 호출/결과, 첨부 이미지, 서브에이전트 활동은 하네스마다 표현이 달라 그대로 못 옮김. 텍스트 서술로 평탄화할지 범위를 정할 것
  - **교체 시점** — 턴 진행 중 교체와의 상호작용. [#4] 가 정확히 백엔드 교차 교체 시 재시작으로 큐가 데드락된 사고였으므로 회귀 주의
  - 교체 후 첫 응답에서 모델이 이전 내용을 실제로 기억하는지 **실모델 E2E 로 검증**([#10] 의 UNKNOWN → BANANA 방식)

### P-7 종량제(OpenRouter / API 키) 사용 비용 표시

- **상태**: OPEN (요청)
- **배경**: 현재 사용량 표시는 **구독 한도**(Claude/Codex 의 5시간/주간 rate limit) 중심이다. OpenRouter 나 직접 API 키처럼 **쓴 만큼 돈이 나가는** 경로는 한도 개념이 없어서, 얼마를 썼는지 앱 안에서 알 수 없다.
- **요청 내용**: 종량제 프로바이더에 대해 **누적 사용 비용**을 표시.
  - 멤버별 / 파티별 / 기간별(오늘·이번 달) 집계
  - 구독 한도 표시와 나란히, 다만 **성격이 다름을 구분**해서 (한도 잔량 vs 누적 금액)
- **확인 필요 / 설계 포인트**:
  - **금액 출처** — OpenRouter 는 응답에 실제 과금액(generation cost)이 실려오고 잔액 조회 API 도 있음 → **보고된 실제 값을 우선**하고, 없을 때만 토큰×단가로 추정하되 **추정임을 명시**할 것. 지어낸 숫자는 금지
  - **단가 정보** — 추정 경로를 쓴다면 모델별 단가가 필요. 단일 소스는 `src/shared/modelCatalog.json` 이며 단가는 변하므로 갱신일 표기 필요
  - 캐시 읽기/쓰기 토큰처럼 단가가 다른 항목을 따로 계산해야 정확함
  - 데이터는 이미 있는 사용량 원장(turns.jsonl)에 붙이는 게 자연스러움 → [#12] 수정과 같은 계층에서 다룰 것
  - HTTP 자동화 API(`/api/usage`)에도 동일하게 노출

### P-8 멤버에 **하네스** 표시 (지금은 모델만 보임)

- **상태**: OPEN (요청)
- **배경**: 멤버 정보에 모델만 나오고 **어느 하네스로 도는지**(Claude Code / Codex / Cursor)는 보이지 않는다. 같은 모델을 다른 하네스로 띄울 수 있고 하네스마다 도구·권한·동작이 다르므로, 모델만으로는 그 멤버가 무엇인지 알 수 없다.
- **요청 내용**: 멤버 목록/헤더 등 모델이 노출되는 곳에 하네스도 함께 표시.
- **확인 필요 / 설계 포인트**:
  - 표시 위치를 한 군데로 정하지 말고 **모델이 보이는 모든 곳**을 훑을 것 — 사이드바 멤버 항목, 대화창 헤더, 멤버 생성/편집 화면, 사용량 화면
  - 좁은 폭에서 `하네스 · 모델` 두 줄이 길어짐 → 아이콘/짧은 배지 + 툴팁 전체명 같은 축약 규칙 필요 ([P-3] 상태 칩과 같은 칩 체계로 통일)
  - 권한 모드도 하네스마다 다르므로(Claude `permissionMode` / Codex `codexPolicy` / Cursor `cursorPolicy`) 함께 보여줄지 결정
  - **연관**: [P-2] 모델 카탈로그 — 카탈로그에서도 어느 하네스로 쓸 수 있는 모델인지 구분되면 선택 실수가 줄어듦

### P-9 대화 검색

- **상태**: OPEN (요청)
- **배경**: 대화가 길어지면 이전에 나눈 내용을 다시 찾을 방법이 스크롤뿐이다.
- **요청 내용**: 대화 내용을 검색해 해당 지점으로 이동할 수 있어야 함.
- **확인 필요 / 설계 포인트**:
  - **범위** — ① 현재 열린 멤버 대화 안에서(브라우저 Ctrl+F 식, 매치 하이라이트 + 다음/이전 이동) ② 파티 전체 멤버 횡단 ③ 워크스페이스의 모든 파티 횡단. ①이 가장 흔하고 구현이 가벼우며, ②③은 결과 목록 UI 와 "어느 파티/멤버의 어느 시점" 표시가 필요함 → **먼저 어디까지 필요한지 확정할 것**
  - **대상** — 사용자·모델 메시지 텍스트만인지, 도구 호출/결과와 서브에이전트 활동까지인지
  - **데이터 소스** — 화면에 렌더된 것만 검색하면 가상 스크롤/미로드 구간을 놓친다. 정본 트랜스크립트(디스크)를 대상으로 하고 결과 클릭 시 해당 위치를 로드·스크롤하는 방식이 맞음
  - HTTP 자동화 API 로도 노출 (에이전트가 과거 대화를 조회할 수 있으면 활용도가 큼)

### P-10 스킬 카탈로그 UI 가 쓰기 어렵고 비직관적임

- **상태**: OPEN (요청 — **증상 특정 필요**)
- **배경**: 스킬 카탈로그 화면이 아직 손에 익지 않고, 무엇을 어떻게 하는 화면인지 바로 읽히지 않는다.
- **확인 필요 — 구체적으로 어디가 걸리는지**:
  - 스킬을 **찾는** 단계인지(목록이 길다/검색·필터 없다/분류가 없다)
  - **고르는** 단계인지(무슨 스킬인지 설명만으로 판단이 안 된다/어느 멤버에 붙는지 모르겠다)
  - **적용하는** 단계인지(켜고 끄는 방법이 안 보인다/적용됐는지 확인이 안 된다)
  - 화면 진입 자체가 어려운지(어디서 여는지 잘 안 보임)
- **개선 방향 후보** (특정 후 확정): 검색·필터, 출처(플러그인/사용자)별 그룹화 + 접기,
  현재 적용 상태를 목록에서 바로 보이게, 스킬 상세(무엇을 하는지·언제 쓰이는지)를 펼쳐 보기
- **연관**: [P-2] 모델 카탈로그와 **같은 계열의 "카탈로그 고르기" 화면** — 검색·그룹 접기·즐겨찾기라는
  해법이 겹치므로, 각각 다르게 만들지 말고 **공통 카탈로그 UI 패턴**으로 한 번에 정리하는 것을 권장

### P-11 입력창에서 스킬 자동완성

- **상태**: OPEN (요청)
- **배경**: 스킬을 쓰려면 이름을 정확히 기억해 직접 타이핑해야 한다. 카탈로그를 열어 확인하고
  돌아오는 왕복이 생긴다.
- **요청 내용**: 채팅 입력창에서 `/` 를 치면 **사용 가능한 스킬 목록이 뜨고 골라서 넣을 수 있게**.
  - 타이핑에 따라 실시간 필터, ↑↓ 로 이동, Enter/Tab 으로 확정
  - 항목에 스킬 이름 + 한 줄 설명 (무엇을 하는 스킬인지 목록에서 바로 판단 가능하게)
- **확인 필요 / 설계 포인트**:
  - **목록의 출처가 멤버마다 다르다** — 스킬은 하네스/플러그인/사용자 설치에 따라 갈리므로,
    **그 멤버가 실제로 쓸 수 있는 것만** 보여줘야 한다. 없는 스킬을 자동완성해 주면 오히려 함정
  - 하네스별 호출 표기가 같은지 확인 (Claude 의 `/skill` 관례를 Codex/Cursor 멤버에도 그대로 쓸 수 있는지)
  - 인자를 받는 스킬은 이름만 넣고 커서를 인자 위치에 둘지
  - **연관**: [P-10] 스킬 카탈로그 — 같은 "사용 가능한 스킬 목록" 데이터를 쓰므로 함께 설계할 것.
    [P-9] 대화 검색·[P-2] 검색과도 필터 UI 관례를 맞추면 좋음

### P-12 설정 화면 — 인증 / 런타임

- **상태**: OPEN (요청)
- **범위**: 설정의 **인증** 탭과 **런타임** 탭 (`src/renderer/app/secondaryViews.tsx`, 탭 정의는 `App.tsx`)

**1. 인증 탭 — 여백만 손보면 됨**

- 콘텐츠가 **오른쪽에 너무 붙어 있음** → 오른쪽 패딩 추가. 그 외 구조 변경은 불필요.

**2. 런타임 탭 — 여백 + 구조**

- 오른쪽 패딩 부족(인증 탭과 동일).
- **너무 많은 설정이 세로로 한 줄에 죽 나열**되어 있어 원하는 항목을 찾기 어려움 →
  성격별로 분류해 **탭(또는 하위 섹션)으로 분할**.
  - 분류 기준 예: 하네스별 생성 기본값 / 컨텍스트·자동 압축 / Message Gate·리뷰어 / 기타
  - 분류안은 실제 항목을 나열해 놓고 확정할 것 (지금 화면에 뭐가 있는지부터 정리)

**3. 하네스 기본값 — 추론 강도/모드 선택기를 없애고 카탈로그에서 한 번에 고르기**

- **현재(확인함)**: 하네스 기본값 편집기가 모델과 별개로 **"추론 강도"(effort)** 와
  **"추론 모드"(reasoning)** 선택기를 따로 두고 있다 (`secondaryViews.tsx` 의 `HarnessDefaults` 블록).
- **요청**: 이 별도 선택기들을 없애고 **모델 카탈로그에서 모델과 함께 선택**하게 할 것.
- **이미 되는 방식이다** — Message Gate 리뷰어 기본값이 정확히 그렇게 동작한다:
  `ModelCatalogModal` 을 `config={{ effort: true }}` 로 열어 모델 + effort 를 한 번에 고르고
  결과를 저장한다. 하네스 기본값도 같은 관례를 따르면 **선택기 3개가 1개로 줄고**, 모델별로
  어떤 추론 옵션이 유효한지도 카탈로그가 알고 있으므로 **잘못된 조합을 고를 여지가 사라진다**.
- ✅ **확인 완료 (2026-08-02) — 카탈로그는 이미 전부 다룬다. 추가 개발이 필요 없다.**
  `ModelCatalogModal` 컴포넌트는 **effort · serviceTier · thinking 모드 + 예산까지 이미 지원**한다.
  문제는 **런타임 화면이 `config={{}}` 로 그걸 전부 꺼놓고**, 대신 effort·reasoning 을
  **중복 셀렉터로 따로 갖고 있다**는 것이다. 즉 이 항목은 "카탈로그에 축을 추가하는 작업"이 아니라
  **"이미 있는 걸 켜고 중복을 지우는 작업"** 이다
- ⚠️ **함께 닫히는 죽은 설정 2개 (2026-08-02 발견)**: `HarnessDefaults` 의 **`reasoningBudget` 과
  `serviceTier` 는 저장 필드가 있는데 런타임 화면에 컨트롤이 아예 없어 설정할 방법이 없다**
  (카드 저장 패치가 `{model, effort, reasoning}` 뿐). **저장소만 있고 도달 경로가 없는 노브**다.
  카탈로그가 두 축을 이미 다루므로 이 항목을 하면 **같이 닫힌다**
- **연관**: [P-2] 모델 카탈로그 개선과 같은 컴포넌트를 건드림 → 함께 작업할 것

### P-14 메시지 전송 시 **인터럽트를 기본값으로 쓸지** 설정에 추가

- **상태**: OPEN (요청)
- **배경**: 멤버 간 메시지(`send`/`broadcast`)는 기본이 **큐잉**이라 상대가 턴 중이면 그 턴이 끝난 뒤에야
  읽힌다. 급한 지시를 넣어도 한참 뒤에 처리되는 경우가 있어, 매번 `interrupt: true` 를 명시해야 한다.
  반대로 항상 인터럽트하면 진행 중인 작업이 계속 끊긴다 — **어느 쪽이 기본이어야 하는지는 사용 방식에
  따라 갈리므로 설정으로 빼는 게 맞다.**
- **요청 내용**: 메시지 전송의 **인터럽트 기본값**을 설정에서 고를 수 있게 할 것.
  - 끄면 지금처럼 큐잉이 기본, 켜면 인터럽트가 기본
  - 개별 전송에서 명시한 값은 **항상 설정보다 우선**(설정은 어디까지나 기본값)
- **확인 필요 / 설계 포인트**:
  - **적용 범위** — 앱 전역 / 파티별 / 멤버별(수신자 기준) 중 어디까지. 수신자 기준이 자연스러울 수
    있음(중요한 멤버는 안 끊기게)
  - **사용자 전송과 멤버 간 전송을 구분할지** — 사용자가 UI 에서 보내는 메시지와 멤버가 `send` 도구로
    보내는 메시지는 성격이 다르다
  - UI 전송 지점에도 일회성 토글이 필요한지 (설정이 기본, 그때그때 뒤집기)
  - AGENTS.md 원칙상 **HTTP 자동화 API 로도 노출**되어야 하고 `src/shared/apiSpec.ts` · `docs/API.md`
    등록 필요
- **연관**: [P-3] 4 (대기열 UI) — 큐된 메시지가 눈에 보이면 "인터럽트할지"를 그 자리에서 판단할 수
  있으므로 같은 문제의 다른 해법. 함께 볼 것
- **추가 요청 — 사용자 전송에도 동일하게**: 사용자가 턴 진행 중에 메시지를 입력하면 지금은 무조건
  큐잉된다. **"턴을 끊고 바로 전달"** 을 선택할 수 있어야 함(설정으로 기본값 제공 + 그 자리에서
  뒤집기). 위 "사용자 전송과 멤버 간 전송을 구분할지" 항목이 바로 이 축이다.

### P-15 `@` 로 멤버 멘션 (자동완성)

- **상태**: OPEN (요청)
- **배경**: 지금은 특정 멤버에게 시키려면 *"planner 멤버에게 전달"* 처럼 문장으로 풀어 써야 하고,
  이름을 정확히 기억해 타이핑해야 한다.
- **요청 내용**: 입력창에서 **`@` 를 치면 파티 멤버 목록이 자동완성으로 뜨고**, 골라서 멘션.
  - 타이핑에 따라 필터, ↑↓ 이동, Enter/Tab 확정
  - 항목에 멤버 이름 + 역할(+ 하네스/상태)이 보이면 누구인지 바로 판단 가능
- **확인 필요 / 설계 포인트**:
  - **멘션의 의미를 확정할 것** — ① 단순 텍스트 삽입(모델이 알아서 해석) ② 실제 라우팅(그 멤버에게
    메시지를 전달) 중 무엇인가. ②면 "누가 보낸 것으로 기록되는지", 인터럽트 여부([P-14])까지 엮인다.
    ①로 시작해 ②로 확장하는 편이 안전
  - 후보 목록은 **같은 파티의 실행 중인 멤버** 기준. 죽은 멤버를 멘션하면 어떻게 되는지 정의 필요
    (`send` 는 수신자가 실행 중이 아니면 에러) → [#13] 상태 판정이 정확해야 목록도 정확해짐
  - [P-5] 파티 간 소통이 들어오면 `@파티/멤버` 형태로 확장 가능해야 함
  - **연관**: [P-11] 스킬 자동완성과 **같은 자동완성 UI**(트리거 문자만 `/` vs `@`) → 한 컴포넌트로
    만들어 두 곳에서 쓸 것. 따로 만들면 두 번 만든다

### P-16 `Esc` 로 턴 중단

- **상태**: OPEN (요청)
- **배경**: 진행 중인 턴을 멈추려면 마우스로 정지 버튼을 눌러야 한다. 키보드로 바로 멈출 수 있으면 빠르다.
- **요청 내용**: 입력창/대화 패널에 포커스가 있을 때 **`Esc` 로 현재 턴 중단**.
- **확인 필요 / 설계 포인트**:
  - **Esc 의 기존 용도와 충돌** — 모달 닫기·자동완성 팝업 닫기·검색 닫기에도 Esc 를 쓴다.
    우선순위를 정할 것(팝업이 열려 있으면 팝업 먼저, 없으면 턴 중단)
  - 오조작 방지가 필요한지(연타 시 두 번 눌러야 중단 등) — 다만 과하면 빠른 중단이라는 목적이 사라짐
  - **어느 멤버의 턴인지** 명확해야 함(포커스된 패널 기준)
  - [#16] 모달 정책과 함께 볼 것 — 모달은 바깥 클릭으로 닫지 않기로 했으므로 Esc 가 모달 닫기의
    주된 키보드 경로가 된다

### P-20 입력창에서 **하네스·모델을 빠르게 고르기** (`@` 멤버 멘션과 같은 방식)

- **상태**: OPEN (요청)
- **배경**: 하네스와 모델 이름을 **매번 하나하나 타이핑**하고 있다. 이름이 길고(`claude-opus-5[1m]`,
  `gpt-5.6-terra`), 정확히 써야 하며, 카탈로그를 열어 확인하고 돌아오는 왕복이 생긴다
- **요청 내용**: 입력창에서 **골라 넣을 수 있게** 할 것. 이미 만들어진 `@` 멤버 멘션과 같은 방식
- ⚠️ **먼저 정할 것 — 넣는 것인가, 실행하는 것인가**:
  - **(가) 이름을 글로 넣는다** — `@` 멘션과 같다. 고른 것이 **문장 안에 글자로** 들어가고,
    그걸 읽는 것은 모델이다. 예: *"이 작업은 `gpt-5.6-terra` 로 돌려줘"*
  - **(나) 그 자리에서 바꾼다** — 고르면 **그 멤버의 하네스·모델이 실제로 바뀐다.** 설정 화면에
    가지 않고 입력창에서 처리하는 것
  - **둘은 완전히 다른 기능이다.** (가)는 자동완성이고 (나)는 명령이다. **같은 트리거로 둘 다 하면
    사용자는 자기가 무엇을 했는지 모른다** — 이름을 넣으려 했는데 모델이 바뀌어 있을 수 있다
- **설계 포인트**:
  - **후보 목록의 출처** — 카탈로그가 단일 소스다. **그 멤버가 실제로 쓸 수 있는 것만** 보여야 한다.
    하네스마다 쓸 수 있는 모델이 다르고, 없는 조합을 자동완성해 주면 오히려 함정이다
  - **(나) 로 간다면 되돌리기** — 잘못 눌러 모델이 바뀌면 어떻게 되돌리는가. 모델 교체는 세션
    재시작을 부르므로 **실수의 값이 비싸다**
  - **트리거 문자** — `@` 는 멤버가 쓰고 `/` 는 스킬이 쓴다. 세 번째 것이 필요한지, 아니면
    **`@` 안에서 종류를 나눌지**([P-15]·[P-11] 과 한 컴포넌트로 묶으라는 기존 판단이 있다)
- **연관**: [P-15] `@` 멤버 멘션(구현됨 — 같은 컴포넌트 재사용) · [P-11] `/` 스킬 자동완성 ·
  [P-2] 모델 카탈로그(후보 출처)

### P-19 이미지를 여러 장 넣을 때 **"1번은 ~고 2번은 ~야"로 말해야 한다**

- **상태**: OPEN (요청)
- **배경**: 이미지를 여러 장 첨부하면 **어느 이미지에 대한 이야기인지 본문에서 번호로 가리켜야 한다.**
  *"1번은 이렇게 고쳐주고 2번은 저렇게 해줘"* 같은 식이다. 사람이 **머릿속으로 순서를 세어**
  글로 옮기는 일을 하고 있고, 순서가 어긋나면 모델이 반대로 이해한다
- **요청 내용**: 각 이미지에 대해 말하는 것이 **더 자연스러운 상호작용**이 되게 할 것
- **방향 후보** (확정 아님 — 설계 필요):
  - **이미지마다 설명을 붙인다** — 썸네일 옆/아래에 짧은 메모를 달고, 보낼 때 그 이미지와 함께 간다
  - **본문에서 이미지를 가리킨다** — 문장 안에서 특정 이미지를 지목하는 방법
  - **번호가 화면에도 보이게 한다** — 지금은 사용자가 세야 하는데, 썸네일에 번호가 붙어 있으면
    최소한 **세는 부담은 사라진다.** 가장 작은 변경이고 즉시 효과가 있다
- **설계 포인트**:
  - ⚠️ **보이는 것과 모델이 받는 것이 일치해야 한다.** 화면의 번호와 모델이 받는 순서가 어긋나면
    **지금보다 나쁘다** — 사용자는 맞다고 믿는데 모델이 다른 것을 본다
  - 첨부가 **취소·재정렬**되면 번호가 밀린다. 그때 본문에 이미 써둔 "2번은"이 어떻게 되는가
  - [R-62] 파일 칩과 **같은 표면**이다(첨부 띠). 함께 설계해야 화면이 따로 놀지 않는다
  - **인라인으로 문장 안에 넣는 방식**은 [R-62] 판단에서 한 번 보류됐다 — 입력 방식을 바꾸는 일이고,
    참조가 조용히 사라질 위험이 있다. 그 판단을 먼저 읽고 시작할 것
- **연관**: [R-62](파일 칩·같은 표면) · [P-13](첨부 저장·경로 전달) · [P-3]9→[P-18]

### P-18 **대화창에 보이는 이미지**의 복사 · 전체보기 — [P-3]9 가 잘못 구현됨

- **상태**: OPEN (요청 — **[P-3]9 재작업**)
- **⚠️ 무엇이 잘못됐나**: [P-3]9 "업로드한 이미지 복사"를 **입력창 첨부 썸네일**의 복사로 구현했다
  (2026-08-01, 커밋 `2ef5901`). 사용자가 말한 건 **대화창(트랜스크립트)에 보이는 이미지**였다.
  구현된 것은 "내가 방금 붙인 것을 도로 복사"라 쓸 일이 거의 없고, 정작 필요한
  **모델이 보낸/대화에 남아 있는 이미지**는 복사할 수 없다
- **요청 내용**:
  1. **대화창 이미지 복사** — 트랜스크립트에 렌더된 이미지를 클립보드로. 클립보드 배선
     (`clipboard.writeImage` + `POST /api/clipboard/image`)은 [P-3]9 에서 **이미 만들어졌으니 재사용**한다.
     바꿀 것은 **어디에 버튼을 다는가**뿐
  2. **전체보기** — 대화창 이미지는 지금 축소되어 보여 **원래 크기를 확인할 수 없다.**
     클릭하면 크게 볼 수 있어야 한다
- **설계 포인트**:
  - **전체보기 오버레이는 이미 있다** — 도구 결과의 `↗ 전체 보기`(`Transcript.tsx` 의 `DetailModal`,
    [P-3]6 에서 패딩까지 정리됨). 새로 만들지 말고 **이미지용으로 재사용**할 수 있는지 먼저 볼 것
  - 모달은 **Cancel/✕ 로만 닫힌다**([#16] 에서 바깥 클릭 차단이 이미 적용됨)
  - 큰 이미지가 화면을 넘칠 때의 처리(맞춤/실제 크기 토글, 스크롤) — 오버플로 안전 원칙
  - 기존 첨부 썸네일 복사 버튼을 **남길지 없앨지** 결정 필요. 남긴다면 두 위치가 같은 배선을 쓴다
- **연관**: [P-3]9(재사용할 배선) · [P-13](첨부 이미지 저장소) · 아이디어 [F-2](멤버가 대화창에
  이미지를 붙이는 기능 — 그게 생기면 **대화창 이미지가 훨씬 많아지므로 이 항목의 가치가 커진다**)

### P-17 QA 용 앱 띄우기를 **추론 없이 한 줄로** — 스크립트화

- **상태**: OPEN (요청)
- **배경**: 지금은 QA/확인용 인스턴스를 띄우는 절차가 **문서·메모리·각자의 e2e 스크립트에 흩어져 있고**,
  띄우는 사람이 매번 조합을 추론해야 한다. 실제로 2026-08-02 에 앱을 띄우려다 **워크스페이스 바인딩에
  실패**했다(앱은 떴는데 `.agent_party_app/instances/` 가 안 생기고 저장소가 비어 있었다). 조합을 아는
  사람에게 다시 맡겨야 했다.
- **매번 추론해야 하는 것들** (전부 이번 사이클에 실제로 문제가 됐던 항목):
  - 워크스페이스는 **격리 userData 의 `settings.json` `workspacePath` 로만** 정해진다
    (⚠️ `AGENTPARTY_WORKSPACE` env 는 앱이 읽지 않는다 — 죽은 노브)
  - `AGENTPARTY_ALLOW_MULTI_INSTANCE` 도 **죽은 플래그**다(단일 인스턴스 락 제거로 사문)
  - 포트는 고정하면 안 된다 — 인스턴스 파일 발견을 써야 하고, 고정 포트 드라이버가 **설치된 앱을
    가로챈 사고**가 있었다
  - **실행 중인 사용자 앱과 같은 파티를 열면 안 된다** (last-writer-wins 로 데이터가 깨진다)
  - 정리할 때 `taskkill /IM electron.exe /F` **전체 kill 금지** (사용자의 앱까지 죽는다)
- **요청 내용**: `npm run qa:app` 수준의 **단일 명령**으로 확인용 인스턴스를 띄울 것.
  - 격리 userData + 별도 워크스페이스를 **자동 생성**하고 바인딩까지 확인
  - **바인딩에 성공했는지 스스로 단언**하고, 실패면 조용히 빈 앱을 띄우지 말고 **실패로 끝낼 것**
    (AGENTS.md "silent fallback 금지" — 이번에 정확히 이 모양으로 실패했다)
  - 자동화 포트를 **표준출력으로 알려줄 것** (사람도 에이전트도 바로 쓸 수 있게)
  - 종료도 명령 하나로. **자기가 띄운 프로세스 트리만** 정리
- **선택**: 확인용 시드(하네스가 다른 멤버 몇 개, 목록이 넘칠 만큼의 파티/멤버, 코드 블록이 있는
  트랜스크립트, `disconnected` 상태 멤버 하나)를 옵션으로 얹으면 **빈 앱이 아니라 볼 것이 있는 앱**이
  뜬다. 매번 손으로 만드는 것이 실제 비용이었다
- **연관**: `docs/E2E_TESTING.md` §1b(빌드 동일성 단언), `scripts/lib/electron-e2e.mjs`(런치 헬퍼는
  이미 있다 — **없는 건 사람이 쓰는 진입점**이다). AGENTS.md "모든 사용자 기능은 로컬 자동화 HTTP API 로"
